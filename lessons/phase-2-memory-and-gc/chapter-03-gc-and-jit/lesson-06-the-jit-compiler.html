Lesson 06 — The JIT Compiler

How the JVM finds hot code and compiles it in tiers. How it pastes small methods into their callers, and makes objects that never leave a method disappear. And how it throws its own work away when a guess turns out wrong.

Position: Lesson 06 of 07  ·  Prerequisites: Lesson 01, Lesson 04  ·  Project files: jit/JitSubjects.java, jit/AllocationMeter.java, jit/JitStatus.java, jit/CompilationEvent.java, jit/CompilationLogParser.java, jit/CompilationReport.java, jit/CompilationLogTool.java, experiments/JitExperiment.java, JvmExplorer.java (modified), and five test classes

1 The pain

Lesson 01 timed the same method ten times. It dropped from about 28 ms to about 2 ms. Lesson 01 promised that Lesson 06 would explain why. Until that promise is kept, three costly mistakes stay easy to make.

The lying benchmark. A developer times a method once: long start = System.nanoTime(); ...; long end = .... They see 40 ms, decide it is slow, and spend a day rewriting it. The rewrite measures 35 ms, so it ships. But both numbers measured the interpreter, running code that had not been compiled yet. In production, after a few seconds, both versions run in under a millisecond. The rewrite may even be the slower one.

The myth about new. “Making objects is expensive, so reuse them.” Teams build object pools. They keep changeable “scratch” objects in fields. They make code harder to read and less thread-safe, just to avoid making an object. Often the JVM was already removing that object by itself. You have already seen this at work without being told. In Lesson 04, AllocationPatterns had to write every array into a volatile field. That was only so the JIT could not make the arrays disappear.

The mysterious slowdown. A service is slow for the first thirty seconds after every deploy, and the first users pay for it. Worse, it sometimes gets slower in the middle of a run for a few seconds, with no GC activity and no code change. Both are the JIT at work. It compiles code while it runs, and sometimes it un-compiles it. By the end of this lesson, your project will show you each of those events in the JVM's own words. It will also measure an object disappearing.

2 Real-world analogy

You hire an interpreter to translate a long speech live, into a language the audience understands. At first, they translate word by word. That is slow, but they can start the moment the speaker does.

After a few minutes, they notice the speaker repeats some phrases a lot. So, in the quiet moments, they write those phrases out fully translated. From then on, they just read them off. They notice the speaker always says “as my colleague said”, and always means Dana. So they start saying “as Dana said” straight away, without stopping to think. They stop writing notes they would throw away a second later. The translation gets faster and smoother, and the speech has not changed at all.

Then one day, “my colleague” means someone else. The interpreter must notice this. They throw away the shortcut and go back to translating that phrase carefully, until they learn the new pattern.

The interpreterThe JVM
Translating word by word at firstThe interpreter — tier 0
Noticing which phrases come up mostProfiling: counting calls, loops, branches and types
A quick prepared version, still taking notesC1 with profiling — tier 3
The polished prepared versionC2 — tier 4
Saying “Dana” instead of “my colleague”Inlining a call, based on a speculative guess
Not jotting down notes you'll throw away at onceEscape analysis — skipping objects that never leave a method
Switching to the prepared version mid-sentenceOn-stack replacement
“My colleague” turns out to be someone elseDeoptimization — compiled code “made not entrant”

The key detail: the prepared versions are better than any translation written in advance could be. They are based on how this speaker really talks today. That is the JIT's advantage over compiling everything before the program starts.

3 The concept explained

Lesson 01 covered the basics. The JVM interprets bytecode at once. It counts how often code runs. It compiles the hot methods to native code on background threads, first with C1, then with C2. This lesson opens up each of those steps. How is “hot” decided? What do the compilers actually do to your code? And how do they recover when they get it wrong?

3.1 Profiling: what the JVM learns before it compiles

The JVM's compilers can do something that no compiler running before the program can do. They can base their decisions on what the program actually did. While code runs, the JVM collects facts about it:

  • how many times each method was called,
  • how many times each loop went round,
  • which way each if went, and
  • which classes actually arrived at each method call made through an interface or a superclass.

Collecting facts about running code to guide later decisions is called profiling. The facts collected are the profile.

A profile answers questions like “this if has been false 2 million times and true never”. Or “every object that ever reached this shape.area() call was a Square”. As you will see, the best optimisations are bets placed on answers like these.

3.2 Finding hot code: counters, thresholds and tiers

Every method has two counters. One counts calls (also called invocations). The other counts loop iterations. A loop iteration is counted each time the code jumps back to the top of a loop. That backward jump is called a back-edge. (You saw it as the goto at the end of sumTo's bytecode in Lesson 01.) When the counters pass certain limits, the method moves up a level. HotSpot numbers the levels. Each level is called a tier:

TierWho runs the codeProfiling?When a method usually gets here
0the interpreteryes (basic counts)always, at first
1C1, full optimisationnovery simple methods (getters). C2 could not do better, so there is no point profiling them.
2C1lightwhen C2 is too busy to take the method yet
3C1fullthe usual first compile — roughly after a few hundred calls
4C2, using the profilenothe hot methods — roughly after a few thousand calls

The usual journey is 0 → 3 → 4. In HotSpot, the limits are about 200 calls for tier 3 and about 5,000 for tier 4, combined with loop counts. These are tuning details that change between versions. To see your JVM's real values, run java -XX:+PrintFlagsFinal -version and look for names starting with Tier3 and Tier4. Check them, but do not memorise them. This whole set of levels is called tiered compilation.

3.3 On-stack replacement: compiling a loop that is already running

What goes wrong without it. Picture a program whose main method holds one huge loop. It loads a file, processes 50 million records, and exits. main is called exactly once. Say the JVM only compiled methods that were called often. The call counter would never get past 1. The whole run would be interpreted, maybe fifty times slower than it needs to be. Compiling the method for its next call would not help either, because there is no next call.

The back-edge counter catches this case. When a loop has gone round enough times, the JVM compiles a special version of the method. This version starts in the middle of the loop. At the next back-edge, the interpreter moves the loop's current state into that compiled code. The state is the values in the local variable slots from Lesson 01. Then the code carries on in the compiled version, in the middle of the loop. Swapping a running interpreted frame on the stack for a compiled one is called on-stack replacement (OSR). In the compilation log, it is marked with %. The line also names the loop's position in the bytecode, such as @ 4.

3.4 Inlining: the optimisation that unlocks the others

What goes wrong without it. Good Java code is full of tiny methods: getters, isEmpty(), small helpers. Every call has a fixed cost. The JVM saves the caller's state, jumps, sets up a new frame, and jumps back. Worse, a call is a wall. When C2 compiles a method, it cannot see what a called method does. So it must assume the worst about it. That makes the caller much harder to optimise. Without a fix, small, readable methods would make code slower. People would merge methods by hand into unreadable ones. (Some still do, for no reason.)

The fix: the compiler copies the body of the called method straight into the caller, as if you had written it out by hand. The call disappears. This is called inlining. HotSpot happily inlines small methods, roughly up to 35 bytes of bytecode. For hot call sites, it inlines much larger ones, roughly up to 325 bytes. (Check these limits with -XX:+PrintFlagsFinal. Do not design your code around them.) So in Java, small methods cost nothing once the code is hot.

Removing the call is the small win. The big win is what inlining reveals. Once the called method's body sits inside the caller, C2 can see across the old wall. That allows more speed-ups:

  • A value worked out in one place and tested in the other can be worked out at compile time. This is called constant folding.
  • Code that can never run can be deleted.
  • Objects made in one place and used in the other can be checked by escape analysis (3.5).

This is why people often call inlining the mother of all optimisations.

Inlining through interfaces. A call like shape.area() could reach Square.area() or Circle.area(). So which body should be pasted in? This is where the profile pays off. HotSpot recorded which classes actually arrived at this exact call.

  • If only one class ever did, the call site is monomorphic. C2 inlines that class's method behind a cheap check (“is it still a Square?”).
  • With two classes, it is bimorphic. Both bodies are inlined behind checks.
  • With three or more, it is megamorphic. C2 gives up on inlining and makes a normal virtual call.

It gets even better. Say only one class that implements the interface has even been loaded. Then C2 can skip the check completely, because no other class exists yet. This decision, based on the classes loaded so far, is called class hierarchy analysis. It is a bet. Section 3.6 is about what happens when a new class is loaded and the bet is lost.

Is it worth manually copying a small helper method into its callers to “save the call”?
No. Once the code is hot, C2 inlines small methods by itself, so the call is already gone. The hand-made copy just makes the code harder to read and maintain. The only code where the call costs anything is cold code. Cold code does not run often enough to matter.

3.5 Escape analysis: objects that never need to exist

What goes wrong when you try to avoid making objects by hand. Look at this:

int distanceSquared(int x1, int y1, int x2, int y2) {
    Delta d = new Delta(x2 - x1, y2 - y1);   // a new object on every call...
    return d.dx() * d.dx() + d.dy() * d.dy();
}

The first idea is to “fix” this by keeping one reusable Delta in a field and overwriting it on each call. But that makes the method unsafe to call from two threads at once (Lesson 03: fields are shared, locals are not). It makes the code uglier. And, as you are about to measure, it is probably no faster at all.

Here is why. An object escapes a method if any code outside that method could ever get hold of it. That happens if the object is returned, stored in a field or a static, passed to a method that was not inlined, or thrown. d above does none of these. It is made, read, and dropped inside one call. C2 checks every object that the code it compiles makes. It works out whether each object can escape. It does this after inlining, which is why inlining matters so much here. This check is called escape analysis. When the answer is “no”, C2 can:

  • Not make the object at all. Its fields become ordinary local values, held in CPU registers or the frame. d.dx() becomes just “the value x2 - x1”. Breaking an object into its separate fields like this is called scalar replacement. No object means no garbage, and no work for the collector from Lessons 04 and 05.
  • Remove locks on it. A synchronized block on an object that no other thread can ever see protects nothing. So the lock is dropped. This is called lock elision.

Honest limits:

  • Only C2 does escape analysis, so it only helps hot code.
  • It is all-or-nothing for each object. If an object escapes even on a rare path, it is still made. The same goes for objects made in a method that was too big to inline.
  • The analysis is careful, so it can miss objects that a human can see do not escape.

So the rule is not “making objects is free”. It is: “making short-lived, local objects is much cheaper than you would guess. Measure before you make code more complicated to avoid it.” Lesson 03's footnote said objects might not reach the heap. This is that footnote, explained.

3.6 Speculation and deoptimization: betting, and losing

C2's best optimisations are bets based on the profile.

  • It bets that a branch that has never been taken never will be. So it leaves that path out of the compiled code.
  • It bets that a call site that has only ever seen Square will only ever see Square.
  • Through class hierarchy analysis, it bets that no other implementation will ever be loaded.

Optimising on the guess that the past will continue is called speculative optimisation. Without it, the compiled code would have to handle every possible case, and it would be much slower.

But a bet can be lost. Every guess is protected by a check, or written down as a dependency (“this code assumes Square is the only Shape”). A check may fail. Or loading a new class may break a recorded dependency. Then the JVM does something remarkable:

  1. It stops using the compiled code. New calls are no longer allowed to enter it. In the log, this version is made not entrant.
  2. Some threads may be running inside that compiled code right now. Each one has its frame turned back into a normal interpreter frame, values and all. It carries on in the interpreter from exactly the same point. Your program never notices, except for a short slowdown.
  3. The method climbs the tiers again. It gathers a fresh profile that now includes the new case, and it is compiled again.

Throwing away compiled code and going back to the interpreter like this is called deoptimization. It is the safety net that makes guessing affordable. It also explains the slowdown in the middle of a run from Section 1. A rare piece of code, or a newly loaded plugin class, can make a hot method fall back to the interpreter for a moment. A program that keeps switching between behaviours can deoptimize the same method again and again. That is worth knowing about, but it is rare in practice.

“Made not entrant” does not always mean deoptimization. When a method reaches tier 4, the JVM retires the old tier 3 version. The log uses the very same words for that. It is just a replacement, which is healthy and expected. A tier 4 version being made not entrant is the real deoptimization. That is exactly why the project's report counts the two separately.

A program runs for an hour with only Square objects, and C2 has compiled totalArea assuming every Shape is a Square. Then a plugin creates the first Circle. Can totalArea now compute the wrong answer?
No, never. Loading Circle breaks the recorded guess. So before any Circle can reach that code, the C2 version is made not entrant. Any thread inside it is moved back to the interpreter. The JIT's firm promise is that its optimisations never change what your program works out. Deoptimization is how it keeps that promise when its guesses go wrong.

3.7 Warm-up, shown — and measured honestly

Now we can explain all of Lesson 01's warm-up table, step by step. The first batch was slow for four reasons that overlapped:

  1. Classes were still being loaded and initialized (Lesson 02).
  2. The code ran in the interpreter (tier 0).
  3. Then, for a while, it ran in C1 code that was still collecting a profile (tier 3).
  4. C1 and C2 were compiling on background threads, which took CPU time.

The method only ran at full speed after C2 installed its version. If the loop had been running all along inside one call, OSR switched it over in the middle of the run. That settling-in time is warm-up.

What goes wrong with a stopwatch. A simple timing loop measures some unknown mix of all those stages. The JIT can fool it by deleting the work completely, if the result is never used. (That is why every experiment in this project writes its results to a sink.) And it gives different numbers on each run, depending on what was compiled when. The standard cure is JMH (the Java Microbenchmark Harness, part of OpenJDK, met in Lesson 01). JMH does three things:

  • It runs warm-up rounds before it measures.
  • It starts fresh JVMs, so earlier experiments cannot spoil the profile.
  • It gives you a “blackhole” that takes in results, so the JIT cannot delete the work.

This project does not use JMH, because it needs a separate build setup. But the rule it teaches applies to every timing you ever take.

One last memory area from Lesson 03 belongs here. Compiled machine code lives in the code cache. If it ever fills up, HotSpot prints CodeCache is full. Compiler has been disabled. It stops compiling. Anything not yet compiled keeps running in the interpreter: correctly, but slowly. That is rare with modern default settings. It is the answer when a long-running application slowly gets slower with no GC problem in sight.

4 Applied to jvm-explorer

The project gets a jit package. It holds:

  • methods built to be compiled,
  • an allocation meter that can see escape analysis at work,
  • a reader for -XX:+PrintCompilation output that tells one method's story, and
  • the JIT's own status.

An experiment runs five phases. Each phase is built to make one JIT behaviour appear in the log.

4.1 What happens, step by step

  1. You run JitExperiment with -XX:+PrintCompilation, and send everything to jit.log. The JVM's compilation lines and the program's own === PHASE === markers land in the same file, in time order.
  2. Phase 1 calls sumOfSquares(10) 100 times. That is too few calls and loop rounds to compile it. So no line for it appears.
  3. Phase 2 calls it 20,000 times. Its counters pass the tier 3 limit, so C1 compiles it. Later they pass the tier 4 limit, so C2 compiles it using the profile. Then the tier 3 version is made not entrant. That is a replacement.
  4. Phase 3 calls longRunningLoop once, with a loop of 50 million rounds. The back-edge counter starts an OSR compilation. You get a line with % and @ position.
  5. Phase 4 measures the bytes allocated per distanceSquared call, in eight batches of 200,000. It uses HotSpot's per-thread allocation counter. Early batches run in the interpreter or in C1, so each call really makes its roughly 24-byte Delta. Then C2 compiles the loop, with distanceSquared inlined into it. Escape analysis proves Delta never escapes, and stops making it.
  6. Phase 5 calls totalArea with only Squares, until C2 compiles it on the guess that every Shape is a Square. Phase 5b makes the first Circle. That loads the Circle class and breaks the guess. So the tier 4 version of totalArea is made not entrant (a real deoptimization), and the method is compiled again.
  7. CompilationLogTool jit.log JitSubjects reads the file, even if Windows PowerShell wrote it as UTF-16. It parses every compilation line and prints a report. Then it tells the story of every JitSubjects method, with the phase markers kept in place.

4.3 Measuring an object that disappears

public static OptionalLong currentThreadAllocatedBytes() {
    // HotSpot's extended ThreadMXBean keeps a running total of bytes each thread allocated.
    if (ManagementFactory.getThreadMXBean() instanceof com.sun.management.ThreadMXBean sunBean
            && sunBean.isThreadAllocatedMemorySupported()) {
        return OptionalLong.of(sunBean.getCurrentThreadAllocatedBytes());
    }
    return OptionalLong.empty();   // not part of the Java spec - say so honestly
}

// Bytes per call = (total after - total before) / calls. The loop's result goes into
// a volatile sink, so a "0 bytes" reading cannot be caused by the JIT deleting the loop.
public static OptionalDouble bytesPerCall(int calls, IntToLongFunction loop) { /* … */ }

The syntax x instanceof SomeType name checks the type. If it matches, it also gives you the converted variable under that name, in one step. This is called pattern matching for instanceof (Java 16 and later). Notice that the meter guards against the one thing that could fake the result. If the JIT deleted the whole loop, the meter would also read 0 bytes, but for the wrong reason. Writing the result to a volatile field stops that.

4.4 Telling replacement from deoptimization

if (e.madeNotEntrant()) {
    retired++;
    if (e.tier() == 4) {
        retiredFromTier4++;   // C2 code thrown away: a real deoptimization
    }                         // otherwise: a C1 version replaced by C2 - healthy
}

4.5 The Windows trap the tool survives

What goes wrong without care. In Windows PowerShell 5.1, the > redirection writes text as UTF-16. In UTF-16, every character takes two bytes, and the file starts with two marker bytes, FF FE. Almost every other shell writes plain UTF-8. If you read that UTF-16 file as UTF-8, every line is garbage and nothing parses. The tool would happily report “0 compilations”. A marker at the start of a file that says which text encoding it uses is called a byte order mark (BOM). The tool checks the first bytes and decodes the file to match. It uses Lesson 01's & 0xFF, because Java bytes are signed. A test writes a real UTF-16 file and checks that it reads back line for line.

4.6 The tests

Parsing and reporting are pure text work. So they are tested exactly, against a sample worked out by hand. The JIT itself is tested only where it makes a firm promise. JitSubjectsTest checks every answer exactly. That is because the JIT's one firm promise is that compiled code works out exactly what interpreted code does. AllocationMeterTest checks that a 1 MB array that escapes is counted in full. No test checks that escape analysis removes an object. Nothing promises that C2 will compile something during a test run. That is something to watch in your terminal.

// A tier 3 retirement is replacement; a tier 4 retirement is deoptimization.
@Test
void separatesReplacementFromDeoptimization() {
    CompilationReport r = CompilationReport.of(CompilationLogParser.parse(JitLogSamples.LOG));
    assertEquals(1, r.retired());
    assertEquals(0, r.retiredFromTier4(), "It was a tier 3 version - replaced, not deoptimized.");
}

Read it as a story:

Most of the thousand or so compilations in the summary are the JDK's own methods. Every Java program compiles a lot of the standard library as it warms up.

The only difference between those runs is one switch. But the second run gives the collector tens of megabytes more garbage in phase 4. Eight batches of 200,000 calls at about 24 bytes each is about 38 MB. With escape analysis on, it is only a few megabytes. The roughly 24 bytes is one small object on a 64-bit HotSpot JVM: a 12-byte header plus two 4-byte ints, rounded up to a multiple of 8. Exact sizes depend on the JDK and its settings.

Run all of it and compare the shapes. If your phase 4 never reaches 0, try more batches. Also check that no -XX:TieredStopAtLevel flag is set. If PowerShell's > wrote the file, the tool can still read it. Project state: compiles, 105 tests green (predicted). Only your machine can give these numbers. Where the shape is different, the machine wins. Tell me what you saw.

5 In the wild

For a few JDK methods, HotSpot does not compile the Java source at all. Instead, it uses hand-written machine code that is built into it, tuned for the processor it is running on. A method replaced like this is called an intrinsic. On common platforms, these are intrinsics: System.arraycopy, many Math methods, String.equals, and parts of Arrays and of the cryptography code. That is why calling System.arraycopy beats any loop you could write, however hot. (The exact list changes by JDK and processor. -XX:+PrintInlining marks them with (intrinsic). Check this yourself.) It is the strongest reason to use standard library methods instead of writing your own. The JVM has a faster version of them than your source could ever compile to.

Warm-up is a deployment problem, not just a benchmarking one. A freshly started service runs in the interpreter, at a fraction of its final speed. The first users after a deploy pay for it. Real teams plan for this:

  • They send fake “warm-up” traffic before putting a new instance behind the load balancer.
  • They delay readiness checks until the hot code paths have run.
  • They roll out slowly, so only a few cold instances serve traffic at once.

The JDK also keeps adding features to save or reuse warm-up work across runs, such as class-data sharing and newer ahead-of-time caches. (These depend on the version and are outside this course.) In interviews, “why is the first request slow?” now has an exact answer: class loading, the interpreter, and compilation still in progress.

6 Gotchas and common mistakes

  • Timing cold code. A single nanoTime measurement mostly times the interpreter, class loading, and compilation in progress. People do it because it looks like measuring. Avoid it: use JMH for anything you will base a decision on. For quick checks, at least warm up first, repeat, and use the result so it cannot be deleted.
  • Hand-optimising for the interpreter. Merging small methods, pooling short-lived objects and reusing scratch fields all make code worse. They save costs that C2 already removes from hot code. Pooling can also make objects live longer, so they get promoted and cost the collector more (Lesson 04). Avoid it: write clear code, measure, and optimise only what a profiler shows is hot.
  • Megamorphic call sites in hot loops. Say a call through an interface sees three or more implementations in one hot place. It cannot be inlined. So it blocks escape analysis and the other optimisations that depend on inlining. People hit this by pushing many unrelated types through one generic loop. Avoid it: only worry about it if a profiler points at it. Then make sure each hot call site sees only a few types.
  • Huge methods are never compiled. By default, HotSpot will not JIT-compile a method bigger than 8,000 bytes of bytecode. It leaves it in the interpreter forever. You can hit this by accident with a generated parser or a giant switch. (The flag names are DontCompileHugeMethods / HugeMethodLimit. Check them.) Avoid it: keep methods reasonably small. The JIT's inlining makes that free anyway.
  • Treating every “made not entrant” as a problem. Most are tier 3 versions being replaced by tier 4. Avoid it: look at the tier, as the project's report does. The pattern worth looking into is the same method being retired from tier 4 again and again.

7 Key takeaways

  • HotSpot profiles running code and moves hot methods up the tiers, usually from the interpreter (0) to C1 with profiling (3) to C2 (4). On-stack replacement compiles a long-running loop while it is still running.
  • Inlining copies small and hot methods into their callers. That removes the call and, more importantly, lets C2 optimise across what used to be method walls. So small methods cost nothing once code is hot.
  • Escape analysis lets C2 skip making objects that never leave a method, and use plain local values instead. That is why short-lived local objects are much cheaper than you would guess.
  • C2's best optimisations are guesses based on the profile. When a guess is wrong, the compiled code is made not entrant, running frames fall back to the interpreter, and the method is compiled again. The program's results never change.
  • The first run is slow because of class loading, the interpreter, and compilation in progress, so any timing taken without warm-up is meaningless. -XX:+PrintCompilation shows every step, and JMH is the tool for real measurement.

Part A (1). Price::amount is 5 bytes of bytecode, so it is almost certainly a getter. C2 could not make anything better for it than C1 does. So profiling it would be wasted effort. It goes straight to tier 1: C1 without profiling. (In practice, it will also be inlined into its hot callers, where the call disappears completely.)

But it has a loop that ran long enough for the back-edge counter to start compilation in the middle of the run. That is what a “process every record” method looks like.

Part A (3). At 291 ms, compilation 88 (tier 3) is retired, one millisecond after tier 4 compilation 101 arrived. That is a replacement, and it is healthy. At 9400 ms, compilation 101 (tier 4) is retired. That is a deoptimization. The method then climbs again: tier 3 at 9460 ms, tier 4 at 9900 ms.

Part A (4). Something broke a guess C2 had made about convert. For example, a new Currency implementation was loaded for the first time. So an interface call inside convert stopped being monomorphic. Or a branch that had never been taken in nine seconds finally was, such as the first price with a rare rounding rule. The usual causes are a plugin loading, a new kind of input arriving, or a rarely used feature being used.

Part B.

  • (a) About 0 once hot. The object never escapes, so it is replaced by plain values (scalar replacement).
  • (b) About 24 (one object per call). Storing it in a static field makes it reachable from anywhere. So it escapes, and it must really exist.
  • (c) About 24, usually. Returning an object makes it escape c itself. But say c is inlined into a hot caller that only reads the fields and then drops the object.
