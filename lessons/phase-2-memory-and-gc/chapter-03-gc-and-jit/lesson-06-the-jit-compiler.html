Lesson 06 — The JIT Compiler

How the JVM finds hot code, compiles it in tiers, pastes small methods into their callers, makes objects that never escape disappear — and throws its own work away when a guess turns out wrong.

Position: Lesson 06 of 07  ·  Prerequisites: Lesson 01, Lesson 04  ·  Project files: jit/JitSubjects.java, jit/AllocationMeter.java, jit/JitStatus.java, jit/CompilationEvent.java, jit/CompilationLogParser.java, jit/CompilationReport.java, jit/CompilationLogTool.java, experiments/JitExperiment.java, JvmExplorer.java (modified), and five test classes

1 The pain

Lesson 01 timed the same method ten times and watched it drop from about 28 ms to about 2 ms, with a promise that Lesson 06 would explain it properly. Until that promise is kept, three expensive mistakes stay easy to make.

The lying benchmark. A developer times a method once — long start = System.nanoTime(); ...; long end = ... — sees 40 ms, decides it is slow, and spends a day rewriting it. The rewrite measures 35 ms, so it ships. Both numbers measured the interpreter, running code that had not been compiled yet. In production, after a few seconds, both versions run in under a millisecond, and the rewrite may well be the slower of the two.

The superstition about new. “Creating objects is expensive, so reuse them.” Teams build object pools, keep mutable “scratch” objects in fields, and make code harder to read and less thread-safe to avoid an allocation — often an allocation the JVM was already deleting by itself. You have seen this optimisation at work without being told: in Lesson 04, AllocationPatterns had to write every array into a volatile field purely so the JIT could not make the allocations vanish.

The mysterious slowdown. A service is sluggish for the first thirty seconds after every deploy, and the first users pay for it. Worse, it occasionally gets slower mid-run for a few seconds, with no GC activity and no code change. Both are the JIT at work: compiling code while it runs, and sometimes un-compiling it. By the end of this lesson your project will show you each of those events in the JVM's own words, and measure an object disappearing.

2 Real-world analogy

You hire an interpreter to translate a long speech live, into a language the audience understands. At first they translate word by word — slow, but they can start the instant the speaker does.

After a few minutes they notice the speaker repeats certain phrases constantly. So, during the quieter moments, they write those phrases out fully translated, and from then on simply read them off. They notice the speaker always says “as my colleague said” and always means Dana, so they start saying “as Dana said” directly, without stopping to think. They stop jotting down notes that they will throw away a second later. The translation gets faster and smoother — without the speech changing at all.

Then, one day, “my colleague” means someone else. The interpreter must notice, throw away the shortcut, and go back to translating that phrase carefully, until they have learned the new pattern.

The interpreterThe JVM

The key detail: the prepared versions are better than any translation written in advance could be, because they are based on how this speaker actually talks today. That is the JIT's advantage over compiling everything before the program starts.

3 The concept explained

Lesson 01 established the basics: the JVM interprets bytecode immediately, counts how often code runs, and compiles the hot methods to native code on background threads — first with C1, then with C2. This lesson opens each of those steps up: how “hot” is decided, what the compilers actually do to your code, and how they recover when they get it wrong.

3.1 Profiling: what the JVM learns before it compiles

The JVM's compilers can do something no compiler that runs before the program can: base their decisions on what the program actually did. While code runs, the JVM collects facts about it — how many times each method was called, how many times each loop went round, which way each if went, and which classes actually arrived at each method call made through an interface or a superclass. Collecting facts about running code to guide later decisions is called profiling, and the facts collected are the profile.

A profile answers questions like “this if has been false 2 million times and true never” or “every object that ever reached this shape.area() call was a Square”. As you will see, the best optimisations are bets placed on answers like these.

3.2 Finding hot code: counters, thresholds and tiers

Every method has two counters: one for calls (invocations) and one for loop iterations. A loop iteration is counted each time execution jumps back to the top of a loop, and that backward jump is called a back-edge (you saw it as the goto at the end of sumTo's bytecode in Lesson 01). When the counters cross thresholds, the method moves up a level. HotSpot names the levels by number, and each level is called a tier:

TierWho runs the codeProfiling?When a method usually gets here
0the interpreteryes (basic counts)always, at first
1C1, full optimisationnotrivial methods (getters) — C2 could not do better, so there is no point profiling them
2C1lightwhen C2 is too busy to take the method yet
3C1fullthe usual first compile — roughly after a few hundred calls
4C2, using the profilenothe hot methods — roughly after a few thousand calls

The typical journey is 0 → 3 → 4. The exact thresholds (in HotSpot, about 200 calls for tier 3 and about 5,000 for tier 4, combined with loop counts) are tuning details that differ by version. To see your JVM's real values, run java -XX:+PrintFlagsFinal -version and look for names starting with Tier3 and Tier4 — to verify, not to memorise. The whole multi-level arrangement is called tiered compilation.

3.3 On-stack replacement: compiling a loop that is already running

What goes wrong without it. Picture a program whose main method contains one enormous loop — load a file, process 50 million records, exit. main is called exactly once. If the JVM only compiled methods that were called often, the call counter would never move past 1, and the whole run would be interpreted, perhaps fifty times slower than necessary. Compiling the method for its next call would not help either, because there is no next call.

The back-edge counter catches it. When a loop has gone round enough times, the JVM compiles a special version of the method that starts in the middle of the loop. At the next back-edge, the interpreter transfers the loop's current state — the values in the local variable slots from Lesson 01 — into that compiled code, and execution continues there, mid-loop. Replacing a running interpreted frame on the stack with a compiled one is called on-stack replacement (OSR). In the compilation log it is marked with %, and the line names the loop's position in the bytecode, such as @ 4.

3.4 Inlining: the optimisation that unlocks the others

What goes wrong without it. Good Java code is full of tiny methods: getters, isEmpty(), small helpers. Every call has a fixed cost — save the caller's state, jump, set up a new frame, jump back. Worse, a call is a wall: when C2 compiles a method, it cannot see what a called method does, so it must assume the worst about it. That makes the caller far harder to optimise. Without a fix, writing small, readable methods would carry a real speed penalty, and people would hand-merge methods into unreadable ones (some still do, needlessly).

The fix: the compiler copies the body of the called method directly into the caller, as if you had written it out by hand. The call disappears. This is called inlining. HotSpot readily inlines small methods (roughly up to 35 bytes of bytecode) and, for hot call sites, much larger ones (roughly up to 325 bytes) — thresholds to verify with -XX:+PrintFlagsFinal, not to design around. So in Java, writing small methods is free once the code is hot.

Removing the call is the small win. The big win is what inlining exposes. Once the callee's body sits inside the caller, C2 can see across the old boundary: a value computed in one place and tested in the other can be worked out at compile time (constant folding), code that can never run can be deleted, and objects created in one place and used in the other become candidates for escape analysis (3.5). This is why inlining is often called the mother of all optimisations.

Inlining through interfaces. A call like shape.area() could reach Square.area() or Circle.area(), so which body should be pasted in? This is where the profile pays off. HotSpot recorded which classes actually arrived at this exact call. If only one ever did, the call site is monomorphic, and C2 inlines that class's method behind a cheap check (“is it still a Square?”). With two it is bimorphic, and both bodies are inlined behind checks. With three or more it is megamorphic: C2 gives up inlining and makes an ordinary virtual call. Better still, if only one class implementing the interface has even been loaded, C2 can skip the check entirely, because no other class exists yet. That decision, based on the classes loaded so far, is called class hierarchy analysis. It is a bet — and Section 3.6 is about what happens when a new class is loaded and the bet is lost.

Is it worth manually copying a small helper method into its callers to “save the call”?
No. Once the code is hot, C2 inlines small methods by itself, so the call is already gone — and the manual copy just makes the code harder to read and maintain. The only code where the call costs anything is cold code, which by definition does not run often enough to matter.

3.5 Escape analysis: objects that never need to exist

What goes wrong when you optimise allocation by hand. Consider:

int distanceSquared(int x1, int y1, int x2, int y2) {
    Delta d = new Delta(x2 - x1, y2 - y1);   // a new object on every call...
    return d.dx() * d.dx() + d.dy() * d.dy();
}

The instinct is to “fix” this by keeping one reusable Delta in a field and overwriting it each call. That makes the method unsafe to call from two threads at once (Lesson 03: fields are shared, locals are not), uglier, and — as you are about to measure — probably no faster at all.

Here is why. An object escapes a method if some code outside that method could ever get hold of it. That happens if the object is returned, stored in a field or a static, passed to a method that was not inlined, or thrown. d above does none of these: it is born, read, and abandoned inside one call. C2 checks every allocation in the code it compiles — after inlining, which is why inlining matters so much here — and works out whether the object can escape. This check is called escape analysis. When the answer is “no”, C2 can:

  • Not create the object at all. Its fields become ordinary local values, held in CPU registers or the frame. d.dx() becomes simply “the value x2 - x1”. Breaking an object into its separate fields like this is called scalar replacement. No allocation means no garbage, and no work for the collector of Lessons 04 and 05.
  • Remove locks on it. A synchronized block on an object no other thread can ever see protects nothing, so the lock is dropped. This is called lock elision.

Honest limits. Only C2 does escape analysis, so it only helps hot code. It is all-or-nothing per allocation, and anything that escapes even on a rare path, or whose method was too big to inline, keeps its allocation. The analysis is also conservative: it can miss objects that a human can see do not escape. So the rule is not “allocation is free”, it is “short-lived, local allocation is far cheaper than intuition says — measure before you complicate code to avoid it.” Lesson 03's footnote said objects might not reach the heap; this is that footnote, paid off.

3.6 Speculation and deoptimization: betting, and losing

C2's best optimisations are bets based on the profile. It bets that a branch that has never been taken never will be, and leaves that path out of the compiled code. It bets that a call site that has only ever seen Square will only ever see Square. It bets, through class hierarchy analysis, that no other implementation will ever be loaded. Optimising on the assumption that past behaviour continues is called speculative optimisation. Without it, the compiled code would have to handle every theoretical possibility and would be much slower.

But a bet can be lost. Every speculation is protected by a check, or recorded as a dependency (“this code assumes Square is the only Shape”). When a check fails, or when loading a new class breaks a recorded dependency, the JVM does something remarkable:

  1. It stops using the compiled code. New calls are no longer allowed to enter it — in the log, the version is made not entrant.
  2. Any thread currently running inside that compiled code has its frame converted back into an ordinary interpreter frame, values and all, and carries on in the interpreter from exactly the same point. Your program never notices, apart from a temporary slowdown.
  3. The method climbs the tiers again, gathers a fresh profile that now includes the new case, and is recompiled.

Throwing away compiled code and returning to the interpreter like this is called deoptimization. It is the safety net that makes speculation affordable. It also explains the mid-run slowdown from Section 1: a rare code path or a newly loaded plugin class can make a hot method fall back to the interpreter for a moment. A program that keeps flipping between behaviours can deoptimize the same method over and over, which is worth knowing exists and rare in practice.

“Made not entrant” does not always mean deoptimization. When a method reaches tier 4, the JVM retires the old tier 3 version, which is logged with the very same words. That is simple replacement — healthy and expected. A tier 4 version being made not entrant is the real deoptimization. The project's report counts the two separately for exactly this reason.

A program runs for an hour with only Square objects, and C2 has compiled totalArea assuming every Shape is a Square. Then a plugin creates the first Circle. Can totalArea now compute the wrong answer?
No — never. Loading Circle breaks the recorded assumption, so before any Circle can reach that code, the C2 version is made not entrant, and any thread inside it is moved back to the interpreter. The JIT's absolute promise is that optimisations never change what your program computes; deoptimization is how it keeps that promise when its guesses go wrong.

3.7 Warm-up, demonstrated — and measured honestly

Now the whole of Lesson 01's warm-up table can be explained, step by step. The first batch was slow for four overlapping reasons: classes were still being loaded and initialized (Lesson 02); the code ran in the interpreter (tier 0); then, for a while, in C1 code that was still collecting a profile (tier 3); and C1 and C2 were compiling on background threads, taking CPU time. Only after C2 installed its version did the method run at full speed — and if the loop had been running all along inside one call, OSR switched it over mid-run. That settling-in period is warm-up.

What goes wrong with a stopwatch. A naive timing loop measures some unknown mix of all those phases. It can be fooled by the JIT deleting the work entirely, because the result is never used (that is why every experiment in this project writes its results to a sink). And it differs from run to run depending on what was compiled when. The standard cure is JMH (the Java Microbenchmark Harness, part of OpenJDK, met in Lesson 01). It runs warm-up iterations before measuring, starts fresh JVMs so earlier experiments cannot pollute the profile, and provides a “blackhole” that consumes results so the JIT cannot delete the work. This project does not use JMH, because it is a separate build setup; the rule it teaches still applies to every timing you ever take.

Compiler has been disabled, stops compiling, and keeps running whatever is not yet compiled in the interpreter — correctly, but slowly. That is rare with modern defaults, and it is the explanation when a long-running application gradually gets slower with no GC problem in sight.

4 Applied to jvm-explorer

The project gains a jit package. It holds methods built to be compiled, an allocation meter that can see escape analysis at work, a reader for -XX:+PrintCompilation output that tells one method's story, and the JIT's own status. An experiment runs five phases designed to make each behaviour appear in the log.

4.1 What happens, step by step

  1. You run JitExperiment with -XX:+PrintCompilation, sending everything to jit.log. The JVM's compilation lines and the program's own === PHASE === markers land in the same file, in time order.
  2. Phase 1 calls sumOfSquares(10) 100 times: too few calls and loop iterations to compile it, so no line for it appears.
  3. Phase 2 calls it 20,000 times. Its counters cross the tier 3 threshold, so C1 compiles it, and later the tier 4 threshold, so C2 compiles it using the profile. Then the tier 3 version is made not entrant: a replacement.
  4. Phase 3 calls longRunningLoop once with a 50-million-iteration loop. The back-edge counter triggers an OSR compilation: a line with % and @ position.
  5. Phase 4 measures the bytes allocated per distanceSquared call, in eight batches of 200,000, using HotSpot's per-thread allocation counter. Early batches run interpreted or in C1, so each call really allocates its roughly 24-byte Delta. Once C2 has compiled the loop, with distanceSquared inlined into it, escape analysis proves Delta never escapes and stops creating it.
  6. Phase 5 calls totalArea with only Squares until C2 compiles it on the assumption that every Shape is a Square. Phase 5b creates the first Circle, which loads the Circle class and breaks that assumption, so the tier 4 version of totalArea is made not entrant (a real deoptimization), and the method is compiled again.
  7. CompilationLogTool jit.log JitSubjects reads the file — even if Windows PowerShell wrote it as UTF-16 — parses every compilation line, prints a report, and then tells the story of every JitSubjects method with the phase markers kept in place.

4.3 Measuring an object that disappears

public static OptionalLong currentThreadAllocatedBytes() {
    // HotSpot's extended ThreadMXBean keeps a running total of bytes each thread allocated.
    if (ManagementFactory.getThreadMXBean() instanceof com.sun.management.ThreadMXBean sunBean
            && sunBean.isThreadAllocatedMemorySupported()) {
        return OptionalLong.of(sunBean.getCurrentThreadAllocatedBytes());
    }
    return OptionalLong.empty();   // not part of the Java spec - say so honestly
}

// Bytes per call = (total after - total before) / calls. The loop's result goes into
// a volatile sink, so a "0 bytes" reading cannot be caused by the JIT deleting the loop.
public static OptionalDouble bytesPerCall(int calls, IntToLongFunction loop) { /* … */ }

The syntax x instanceof SomeType name checks the type and, if it matches, gives you the converted variable under that name in one step. It is called pattern matching for instanceof (Java 16 and later). Notice the meter is careful about the one thing that could fake the result: if the JIT deleted the whole loop, the meter would also read 0 bytes — for the wrong reason. Writing the result to a volatile field prevents that.

4.4 Telling replacement from deoptimization

if (e.madeNotEntrant()) {
    retired++;
    if (e.tier() == 4) {
        retiredFromTier4++;   // C2 code thrown away: a real deoptimization
    }                         // otherwise: a C1 version replaced by C2 - healthy
}

4.5 The Windows trap the tool survives

What goes wrong without care. In Windows PowerShell 5.1, the > redirection writes text as UTF-16, where every character takes two bytes, starting with two marker bytes, FF FE. Almost every other shell writes plain UTF-8. Read that UTF-16 file as UTF-8 and every line is garbage, nothing parses, and the tool would cheerfully report “0 compilations”. A marker at the start of a file announcing its text encoding is called a byte order mark (BOM). The tool checks the first bytes — with Lesson 01's & 0xFF, because Java bytes are signed — and decodes accordingly. A test writes a real UTF-16 file and checks it reads back line for line.

4.6 The tests

Parsing and reporting are pure string work, so they are tested exactly against a hand-worked sample. The JIT itself is tested only where a guarantee exists. JitSubjectsTest pins every answer, because the JIT's one absolute promise is that compiled code computes exactly what interpreted code does. AllocationMeterTest checks that a 1 MB array that escapes is counted in full. No test asserts that escape analysis removes an allocation, because whether C2 compiles something during a test run is not guaranteed. That is an observation for your terminal.

// A tier 3 retirement is replacement; a tier 4 retirement is deoptimization.
@Test
void separatesReplacementFromDeoptimization() {
    CompilationReport r = CompilationReport.of(CompilationLogParser.parse(JitLogSamples.LOG));
    assertEquals(1, r.retired());
    assertEquals(0, r.retiredFromTier4(), "It was a tier 3 version - replaced, not deoptimized.");
}

5 In the wild

For a handful of JDK methods, HotSpot does not compile the Java source at all. It substitutes hand-written machine code it carries built in, tuned for the processor it is running on. A method replaced like this is called an intrinsic. System.arraycopy, many Math methods, String.equals and parts of Arrays and of the cryptography code are intrinsified on common platforms — which is why calling System.arraycopy beats any loop you could write, however hot. (The exact list varies by JDK and processor; -XX:+PrintInlining marks them with (intrinsic) — to verify.) It is the strongest argument for using standard library methods instead of reimplementing them: the JVM has a faster version of them than your source could ever compile to.

Warm-up is a deployment problem, not just a benchmarking one. A freshly started service runs interpreted, at a fraction of its eventual speed, and the first users after a deploy pay for it. Real teams handle this deliberately. They send synthetic “warm-up” traffic before putting an instance behind the load balancer. They delay readiness checks until hot paths have run. They roll out gradually, so only a few cold instances serve traffic at once. And the JDK keeps adding features to save or reuse warm-up work across runs — class-data sharing, and newer ahead-of-time caches (version-specific; outside this course). In interviews, “why is the first request slow?” has a precise answer now: class loading, interpretation, and compilation still in progress.

6 Gotchas and common mistakes

  • Timing cold code. A single nanoTime measurement mostly times the interpreter, class loading and compilation in progress. People do it because it looks like measurement. Avoid it: use JMH for anything you will base a decision on, and for quick checks at least warm up first, repeat, and use the result so it cannot be deleted.
  • Hand-optimising for the interpreter. Merging small methods, pooling short-lived objects and reusing scratch fields all make code worse to save costs that C2 already removes from hot code — and pooling can make objects live longer, so they get promoted and cost the collector more (Lesson 04). Avoid it: write clear code, measure, and optimise only what a profiler shows is hot.
  • Megamorphic call sites in hot loops. A call through an interface that sees three or more implementations in one hot place cannot be inlined, so it blocks escape analysis and the other optimisations that depend on inlining. People hit this by funnelling many unrelated types through one generic loop. Avoid it: only worry about it if a profiler points at it — and then keep each hot call site seeing few types.
  • Huge methods are never compiled. By default HotSpot refuses to JIT-compile a method larger than 8,000 bytes of bytecode, and leaves it in the interpreter forever. That is easy to hit by accident with a generated parser or a giant switch (flag names DontCompileHugeMethods / HugeMethodLimit, to verify). Avoid it: keep methods reasonably small — which the JIT's inlining makes free anyway.
  • Reading every “made not entrant” as a problem. Most are tier 3 versions being replaced by tier 4. Avoid it: look at the tier, as the project's report does. Repeated tier 4 retirements of the same method are the pattern worth investigating.

7 Key takeaways

  • HotSpot profiles running code and moves hot methods up the tiers — usually from the interpreter (0) to C1 with profiling (3) to C2 (4) — and on-stack replacement compiles a long-running loop while it is still running.
  • Inlining copies small and hot methods into their callers, which removes the call and, more importantly, lets C2 optimise across what used to be method boundaries — so small methods cost nothing once code is hot.
  • Escape analysis lets C2 skip creating objects that never leave a method, replacing them with plain local values, which is why short-lived local allocation is far cheaper than intuition suggests.
  • C2's best optimisations are speculative bets on the profile, and when a bet is lost the compiled code is made not entrant, running frames fall back to the interpreter, and the method is recompiled — the program's results never change.
  • The first run is slow because of class loading, interpretation and compilation in progress, so any timing taken without warm-up is meaningless; -XX:+PrintCompilation shows every step, and JMH is the tool for real measurement.

Part B. (a) About 0 once hot: the object never escapes, so it is scalar-replaced. (b) About 24 (one object per call): storing it in a static field makes it reachable from anywhere, so it escapes and must really exist. (c) About 24 — usually. Returning an object makes it escape c itself.
