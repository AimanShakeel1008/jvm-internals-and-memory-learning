Lesson 05 — GC Algorithms & Reading GC Logs

Serial, Parallel, G1 and ZGC make four different choices about the same trade-off. Learn what each one gives up. Read a GC log line by line. Then give jvm-explorer a tool that sums up its own log.

Position: Lesson 05 of 07  ·  Prerequisites: Lesson 04 — Object Lifecycle & GC Fundamentals  ·  Project files: gclog/GcEvent.java, gclog/ParsedGcLog.java, gclog/GcLogParser.java, gclog/GcSummary.java, gclog/GcLogSummaryTool.java, experiments/GcWorkload.java, JvmExplorer.java (modified), .gitignore (modified), and four test classes

You will meet HotSpot's four main garbage collectors — Serial, Parallel, G1 and ZGC — and learn what each one gives up to be good at something else.

You will also learn to switch on GC logging, read a log line piece by piece, and run a project tool that sums up a whole log in ten lines.

1 The pain

Pain 1: flags that silently do nothing

A team copies a block of JVM flags from a well-known blog post into their startup script. It was good advice in 2015. On Java 21, the JVM prints one line as it starts: Ignoring option UseConcMarkSweepGC; support was removed in 14.0. Then it carries on.

Nobody reads startup warnings. The collector that flag chose was removed from Java years ago. The flags that tune it do nothing. Nobody on the team can say which collector is really running, or why it was chosen.

Pain 2: an average that hides the worst case

Their dashboard (a screen of live charts about the running system) says “average GC pause: 6 ms”, and everyone relaxes. Meanwhile, about one request in a few hundred takes almost a second.

Here is why. Every few minutes, one full collection freezes the whole application for 900 ms. An average spreads that one terrible pause across thousands of tiny ones, until you cannot see it. Users feel the worst case. Dashboards show the average.

Pain 3: a log nobody can read

When someone finally turns on GC logging, the file is full of lines like GC(14) Pause Young (Concurrent Start) (G1 Humongous Allocation) 48M->45M(64M) 3.112ms. Every number in that line answers a question the team has argued about for weeks. And nobody can read it.

By the end of this lesson, you will know what each collector gives up. You will read that line piece by piece. And you will run your own tool that turns a whole log into ten readable lines.

2 Real-world analogy

A restaurant must be cleaned while it is open for business. There are four ways to organise the cleaning:

  • One cleaner, restaurant closed. Close the doors. One person cleans everything. Reopen. Simple and cheap. Fine for a tiny café, painful for a big one.
  • A whole team, restaurant closed. Close the doors. Everyone available cleans at once. Reopen quickly. This serves the most meals per day. But every diner still waits through each closure, and a bigger restaurant means longer closures.
  • Section by section, dirtiest first. The cleaners walk the floor first and note which tables are dirtiest. Then they close one section at a time, starting with the worst. They only take as many tables as they can finish in a promised time. Closures are short and fairly predictable.
  • Cleaning while diners eat. Cleaners work around the diners, and the restaurant almost never closes. But the cleaners use up staff and floor space that could have served more meals.

No way of cleaning is best at everything. A banquet hall that serves set meals cares about meals per day. A café whose customers walk out after a 30-second wait cares about closures. Choosing a collector means deciding which kind of restaurant you are.

3 The concept explained

We build this in order. First, the three goals every collector must balance. Then the four collectors, one by one. Then a side-by-side comparison. Finally, how to turn on GC logging and read every part of a log line.

3.1 Three goals that fight each other

Lesson 04 described what every collector must do. It must find the live objects by tracing from the roots, free the rest, and use generations to keep that cheap. Collectors differ in how they organise that work.

One word first. Work done concurrently runs at the same time as your code, on other threads, instead of stopping your code. You will see this word all through the lesson.

We judge collectors on three measures:

  • Throughput. Out of all the time the program runs, this is the share spent running your code instead of collecting. For example, say an hour-long batch job (a program that works through a big pile of data and then stops) spends 3 minutes in GC. Then its throughput is 57 ÷ 60 = 95%. Throughput matters most for batch work, where only the total time counts.
  • Pause time (also called latency). This is how long the application stands still during a stop-the-world pause. Both the usual pause and, much more importantly, the worst one. It matters most for anything a person or another service is waiting on.
  • Footprint. This is how much extra memory and CPU the collector needs on top of your program. That includes spare heap to copy into, record-keeping tables, and threads doing GC work.

Why can't one collector win at all three? Look at what each improvement costs.

  • Shorter pauses mean doing more of the work while your code runs. That needs extra record-keeping on every reference your code touches (more on that in 3.5). That record-keeping lowers throughput.
  • Doing everything in one stop-the-world burst, using every CPU, is the most efficient way to do the work. But it means long pauses.
  • A bigger heap means fewer collections. But each full collection has more to walk.

Every collector picks a point between these three goals. The best collector is the one whose choice matches what your program cares about.

3.2 Serial: one thread, everything stopped

The Serial collector (-XX:+UseSerialGC) is the textbook picture from Lesson 04, run by a single thread:

  • Minor GCs copy live young objects between Eden and the survivor spaces.
  • When the old generation needs collecting, Serial pauses everything and runs mark-compact over the whole heap. That means marking from the roots, then sliding every live object together.

Every step is stop-the-world, and only one CPU does the work.

That sounds basic, and for a big server it is. But with a small heap and one CPU, Serial has the lowest extra cost of any collector. GC threads do not need to coordinate, and there is no background record-keeping.

It is the right choice for small command-line tools and for containers limited to one CPU. In fact, the JVM picks it for you automatically on a machine it thinks is too small for anything else. Roughly, that means fewer than two processors, or less than about 1792 MB of memory. (That cut-off is HotSpot's own rule. Check it for your JDK.)

3.3 Parallel: the same algorithm, every CPU at once

The Parallel collector (-XX:+UseParallelGC) runs exactly the same stop-the-world algorithms as Serial. But it splits the work across many GC threads. By default, there is about one thread per CPU core.

  • A pause that takes Serial 400 ms might take Parallel 60 ms on eight cores.
  • Nothing runs at the same time as your code. So there is no record-keeping on each reference at all.

That is why Parallel usually gives the highest throughput of any HotSpot collector.

Its weakness: every pause still stops everything. And full-collection pauses grow with the size of the old generation. A 32 GB heap can mean full pauses that last several seconds.

Parallel was the default collector up to Java 8. It is still the right choice for batch jobs, data processing, and anything where the total run time matters and nobody waits on a single response.

3.4 G1: regions, garbage first, and a pause goal

What goes wrong with one big old generation

With Serial and Parallel, collecting the old generation means marking and compacting all of it in one pause. A bigger heap means a longer pause, whatever the program needs. You cannot ask for “at most 200 ms, please”, because the work cannot be split into smaller pieces.

G1's answer: regions

G1 (“Garbage First”, -XX:+UseG1GC) has been the default since Java 9. It fixes this by changing the shape of the heap:

  • It does not use a few big solid areas. It divides the heap into many blocks of equal size, usually between 1 and 32 MB each (chosen from the heap size). Each block is called a region.
  • At any moment, each region has one role: Eden, survivor, old, or free.
  • The young and old generations of Lesson 04 still exist. But now each generation is a group of regions, spread across the heap.
  • A region can change role after it is emptied.

One more word helps with the diagram. To evacuate a region means to copy its live objects out to free regions, so the whole region becomes free.

Regions make three things possible:

  1. Concurrent marking. When the old generation gets full enough, G1 starts marking it while your code keeps running, using background threads. Your code may change references during the walk. To stay correct, every reference write gets a small extra step that records the old value. This is a write barrier, like the card-table barrier from Lesson 04. Marking ends with two short stop-the-world pauses to finish up: Remark and Cleanup. You will see all of these in the log.
  2. Garbage first. Marking tells G1 how much garbage each old region holds. Then, during normal young collections, it also adds a few of the old regions with the most garbage. Copying the few live objects out of a mostly dead region frees almost the whole region, for very little work.
    • A young collection that also includes old regions is called a mixed collection.
    • The regions picked for one pause are its collection set.
  3. A pause goal. The work comes in region-sized pieces. So G1 can choose how many pieces to take on in one pause. You set a goal with -XX:MaxGCPauseMillis (default 200 ms). G1 sizes the young generation and the collection set to try to meet it. It is a goal, not a promise.

Two more terms appear in G1 logs:

  • Humongous objects. An object that is at least half a region in size gets regions of its own, straight in the old generation. Copying it around would cost too much. Such an object is called humongous (“huge”). Making one can itself start a collection. The log shows this as G1 Humongous Allocation.
  • Falling back to a full GC. Sometimes G1 falls behind: your code makes objects faster than concurrent marking and mixed collections can free space. Then G1 runs out of free regions to copy into. It falls back to a full GC: the whole heap, compacted, with everything stopped. In a healthy G1 application, full GCs should be rare or never happen. In the log, they are the first line to look for.

3.5 ZGC: moving objects while your code runs

The problem ZGC solves

G1 still copies objects inside stop-the-world pauses. That is where its remaining pause time goes. ZGC (-XX:+UseZGC, ready for real-world use since Java 15) does even the copying while your code runs.

That causes a hard problem. If the collector moves an object while your code is using it, your code may follow an old reference to where the object used to be. That would be like following an old address to a house whose owner has moved.

How ZGC solves it: the load barrier

ZGC solves this by checking every read:

  1. Every time your code loads a reference from a field, a tiny check runs. The JIT adds this check.
  2. The check looks at a few spare bits inside the reference. They record whether the reference is up to date.
  3. If the object has moved, the check fixes the reference on the spot, before your code uses it.

That small check on every reference read is called a load barrier. (A write barrier runs on stores. A load barrier runs on reads.)

Nearly all the work happens while your code runs. So ZGC's pauses are usually well under a millisecond. And unlike every collector above, its pauses do not grow with the heap size. A 4 GB heap and a 4 TB heap pause for about the same time.

The cost is real:

  • The load barrier runs on every reference read.
  • ZGC's background threads take CPU your code could have used.
  • It needs spare heap to keep working while your code keeps making objects.

So it usually gives lower throughput than Parallel or G1, and it wants more spare memory.

A version detail to check on your JDK: Java 21 added a generational mode for ZGC (JEP 439). You switch it on with -XX:+UseZGC -XX:+ZGenerational. Later releases made generational the default. Another low-pause collector, Shenandoah, works in a similar way. It ships in OpenJDK builds such as Temurin.

An overnight report job runs for two hours and nobody waits on it until it finishes. Which collector, and why?
Parallel. Only the total run time matters. Parallel has the highest throughput, because nothing runs alongside your code. There are no barriers and no background threads taking CPU. Its long pauses do no harm, because nobody is waiting on a single response. ZGC would make the job slower, in return for short pauses nobody would notice.
What is the difference between a write barrier and a load barrier?
Both are tiny pieces of code the JIT adds to your program. A write barrier runs every time your code stores a reference; G1 uses one to keep its marking and card table correct. A load barrier runs every time your code reads a reference; ZGC uses one to fix references to objects it has moved.

3.7 Switching on GC logging

Since Java 9, all of the JVM's logging goes through one system with one flag, -Xlog. This system is called unified logging (“unified” means everything is joined into one). Its general shape is four parts, separated by colons:

-Xlog:WHAT:WHERE:DECORATIONS:OUTPUT-OPTIONS

-Xlog:gc                                    one line per pause, to the console
-Xlog:gc*                                   every GC-related tag - phases, sizes, much more detail
-Xlog:gc:file=gc.log                        the same as -Xlog:gc, written to a file instead
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=10m
                                            full detail, wall-clock time added, rotating over 5 files of 10 MB
  • WHAT is a list of tags. Tags are labels on log messages, such as gc, gc+age and class+load (Lesson 02). A * means “this tag and every tag joined with it”. You can add =level (info, debug, trace) to ask for more detail.
  • WHERE is stdout (the program's normal output), stderr (its error output), or file=name. A file keeps the log out of your program's own output. It also keeps it out of the way of anything that reads that output.
  • DECORATIONS are the fields in brackets at the start of each line. The default is uptime,level,tags, which gives [0.215s][info][gc].
  • OUTPUT-OPTIONS control file rotation (starting a new file when the old one is big enough). So a long-running service never fills its disk with one giant log.

The GC logging flags from before Java 9 are deprecated or gone. These include -XX:+PrintGCDetails, -XX:+PrintGCTimeStamps and -Xloggc:file. Some are turned into the matching -Xlog setting, with a startup warning. Others stop the JVM from starting at all. (Check the exact behaviour of each flag on your JDK.) Old scripts that use them should be rewritten. Old log-reading tools that expect the old format will not understand the new one.

3.8 Reading a log line, piece by piece

Here is one line from the default collector, taken apart:

[0.215s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 25M->3M(256M) 2.512ms
 ^^^^^^  ^^^^  ^^  ^^^^^ ^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^  ^^ ^^^^^ ^^^^^^^
   |      |    |     |        |                    |                 |   |    |      |
   |      |    |     |        |                    |                 |   |    |      +-- how long ALL your threads stood still
   |      |    |     |        |                    |                 |   |    +--------- heap committed (its current size)
   |      |    |     |        |                    |                 |   +-------------- heap in use AFTER the pause
   |      |    |     |        |                    |                 +------------------ heap in use BEFORE the pause
   |      |    |     |        |                    +------------------------------------ why it happened (one or more causes)
   |      |    |     |        +--------------------------------------------------------- what kind of pause: Young = minor GC
   |      |    |     +---------------------------------------------------------------- collection number, counting from 0
   |      |    +---------------------------------------------------------------------- the tag the message was logged under
   |      +--------------------------------------------------------------------------- the level: info, debug, trace
   +---------------------------------------------------------------------------------- seconds since the JVM started

These are the kinds of pause you will meet:

  • Young: a minor GC.
  • Full: the whole heap. This is the one to worry about.
  • Remark and Cleanup: G1's two short pauses that finish a concurrent marking cycle.

Lines that say Concurrent describe work running alongside your code. They are not pauses, even when they show a duration. The causes in brackets tell you what started the collection:

A short G1 log, as it might look for a program whose old generation is filling:

[0.004s][info][gc] Using G1
[0.215s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 25M->3M(256M) 2.512ms
[0.640s][info][gc] GC(1) Pause Young (Concurrent Start) (G1 Humongous Allocation) 40M->38M(64M) 3.100ms
[0.641s][info][gc] GC(2) Concurrent Mark Cycle
[0.660s][info][gc] GC(2) Pause Remark 41M->41M(64M) 1.200ms
[0.680s][info][gc] GC(2) Pause Cleanup 41M->41M(64M) 0.100ms
[0.690s][info][gc] GC(2) Concurrent Mark Cycle 49.012ms
[1.000s][info][gc] GC(3) Pause Full (System.gc()) 30M->2M(64M) 15.300ms

Read it as a story.

  • GC(0) is a normal young collection. It frees 22 MB in 2.5 ms.
  • GC(1) is started by a humongous allocation. It also starts concurrent marking. Look at 40M->38M: almost nothing was freed. So most of what was in the heap is alive.
  • GC(2) is the concurrent marking cycle. It ran for 49 ms alongside the program, with only 1.3 ms of real pauses (Remark and Cleanup).
  • GC(3) is a full GC that the code asked for. It gives the most important number in the whole log. After a full collection, only 2 MB is in use. So the program's live data is about 2 MB (Lesson 04).

What goes wrong when you only look at averages

This log's five pauses add up to 22.2 ms, so they average 4.4 ms. That is what a dashboard would show. But the full GC took 15.3 ms, three and a half times the average. In a real service, the same shape looks like “average 6 ms” hiding a 900 ms pause every few minutes. The cure is to always read three numbers together:

  • the count of each kind of pause (are full GCs happening at all?),
  • the maximum pause (what the unluckiest user felt), and
  • the heap after full GCs, over time (if it rises, that is a leak, Lesson 04).

That is exactly what the project's summary tool prints.

A log line reads Pause Young (Allocation Failure) 120M->118M(128M) 40.1ms, and the next few look similar. What is happening?
Each minor GC frees almost nothing (120 → 118 MB), in a heap that is almost full (128 MB committed). The pauses are long for young collections, because so much is being copied. The live data nearly fills the heap. Either the heap is too small for what the program really needs, or something is holding on to objects it should not (a leak). The next step is to look at the heap after the next full GC. If even that stays near 118 MB, the live data really is that big.

4 Applied to jvm-explorer

The project gets a gclog package. It reads a GC log that the project itself made, and prints a summary of the numbers that matter. A small workload experiment (a program whose only job is to give the collector work to do) makes the log.

4.1 What happens, step by step

  1. You run GcWorkload with -Xlog:gc:file=gc.log. The JVM opens gc.log and writes its Using G1 line.
  2. The workload makes 512 MB of garbage in 4 MB steps, using AllocationPatterns.churn from Lesson 04. Eden keeps filling. So the JVM writes a Pause Young line for every minor GC.
  3. After each step, it keeps one more 64 KB array, up to 400 (about 25 MB). In a 64 MB heap, those arrays age, get promoted, and fill the old generation. That usually makes G1 start a concurrent marking cycle. So Concurrent Mark Cycle, Pause Remark and Pause Cleanup lines appear.
  4. Finally, it calls System.gc() once, just so the log has a full GC to read. The JVM exits and the log is complete.
  5. You run GcLogSummaryTool gc.log. It reads every line into a list.
  6. GcLogParser.parse walks the lines. The first Using ... line gives the collector's name. Every other line is checked against the pause-line pattern. Lines that match become GcEvent records. Everything else (concurrent phases, other messages) is skipped.
  7. GcSummary.of goes through the events once. It counts each kind and adds up the pauses. It also tracks the longest pause, the total freed, the latest uptime, and the heap after the last full GC.
  8. describe() prints ten lines. JvmExplorer does the same thing automatically if it finds gc.log in its working folder.

4.3 The parser: one pattern, read piece by piece

A parser is code that reads text and turns it into structured data. You could pull numbers out of the text by hand: split on spaces, strip brackets, guess positions. But that breaks the moment a cause has two words.

Java has a small language for describing the shape of text and pulling named pieces out of it. It is called a regular expression (“regex” for short). For example, the regex \d+ means “one or more digits”, so it finds 25 in 25M. In Java, you use the Pattern and Matcher classes. The parser's whole job is done by one pattern:

private static final Pattern PAUSE_LINE = Pattern.compile(
        "\\[(?<uptime>\\d+\\.\\d+)s\\]"                      // [0.215s]
        + ".*?GC\\((?<id>\\d+)\\) "                           // ...GC(0)
        + "Pause (?<kind>[A-Z][a-z]+(?: [A-Z][a-z]+)?)"      // Pause Young / Pause Init Mark
        + "(?<causes>(?: \\((?:[^()]|\\(\\))*\\))*) "          // (Normal) (G1 Evacuation Pause)
        + "(?<before>\\d+)(?<beforeUnit>[BKMG])->"             // 25M->
        + "(?<after>\\d+)(?<afterUnit>[BKMG])"                 // 3M
        + "\\((?<committed>\\d+)(?<committedUnit>[BKMG])\\) "   // (256M)
        + "(?<millis>\\d+(?:\\.\\d+)?)ms");                   // 2.512ms

A short key to the symbols:

  • \\d+ means one or more digits.
  • (?<name>...) captures a piece under a name. Later the code can ask for it with m.group("before").
  • \\[ and \\( mean a real bracket character. Without the backslash, brackets have a special meaning in the pattern language.
  • [BKMG] means exactly one of those letters.
  • ? after something makes it optional.
  • * means zero or more times.

(Each backslash is written twice, because Java strings themselves use the backslash as a special character.)

What goes wrong with the obvious pattern

The natural way to say “a cause in brackets” is: “an open bracket, then anything except a close bracket, then a close bracket”. Try that on Pause Full (System.gc()) 30M->2M(64M):

  1. It stops at the first ), the one inside gc().
  2. That leaves a stray ) behind, so the whole line fails to match.
  3. Every full GC caused by System.gc() quietly disappears from the summary.

The cure is the piece (?:[^()]|\\(\\))*. It means: inside a cause, accept any normal character or the exact pair (). A test checks this case, so it can never quietly break again.

4.4 The summary

for (GcEvent event : log.pauses()) {
    if (event.isYoung()) {
        young++;
    } else if (event.isFull()) {
        full++;
        // Overwritten each time, so it ends up holding the LAST full collection:
        // the most recent measurement of how much is still reachable.
        afterLastFull = OptionalLong.of(event.heapAfterBytes());
    } else {
        other++;                                   // Remark, Cleanup, ...
    }
    total += event.pauseMillis();
    max = Math.max(max, event.pauseMillis());       // the number averages hide
    reclaimed += event.reclaimedBytes();         // never negative - see GcEvent
    span = Math.max(span, event.uptimeSeconds());
}

Honest limits of the summary:

  • “Throughput” here counts only stop-the-world pauses. It is measured up to the last pause, not up to when the JVM exits. So it is only roughly right.
  • It cannot see the CPU that concurrent collectors take from your code on background threads. That is exactly ZGC's main cost.
  • Java 21 logs ZGC's pauses under a more detailed tag, not gc. So for ZGC, the parser will report few or no pauses. That is because the format is different, not because ZGC did nothing.

4.5 The tests

Parsing is pure text work. So, unlike Lesson 04's collector tests, every check can be exact. The tests share a sample log. A comment in it shows every expected number, worked out by hand:

// The trap: "(System.gc())" has brackets inside brackets.
@Test
void parsesAFullPauseWhoseCauseContainsBrackets() {
    GcEvent e = GcLogParser.parsePause(
            "[1.000s][info][gc] GC(3) Pause Full (System.gc()) 30M->2M(64M) 15.300ms").orElseThrow();
    assertEquals(List.of("System.gc()"), e.causes(), "The cause keeps its inner brackets.");
    assertTrue(e.isFull());
}

// The average hides the worst pause - the reason the summary prints both.
@Test
void theAverageHidesTheWorstPause() {
    GcSummary s = GcSummary.of(GcLogParser.parse(GcLogSamples.G1_LOG));
    assertTrue(s.maxPauseMillis() > 3 * s.averagePauseMillis(), /* … */);
}

The tool's test writes the sample to a temporary folder (@TempDir). JUnit creates that folder and deletes it afterwards. So the test reads a real file without ever touching the project folder.

5 In the wild

You can turn on unified logging in a JVM that is already running, without a restart. You use the JDK's jcmd tool (Lesson 07 covers it). Every running program has a PID (process id), a number the operating system gives it. The command jcmd <pid> VM.log output=gc.log what=gc starts writing exactly the log this lesson reads, from that moment on.

That is how engineers look into a live service that is misbehaving. They do not restart it, because a restart would lose the very state they want to see. (Check the exact option spelling with jcmd <pid> help VM.log on your JDK.)

The most common collector surprise on live systems is one nobody chose:

  1. A service runs happily with G1 on developers' laptops.
  2. Then it is deployed into a container limited to one CPU and 1 GB of memory.
  3. The JVM reads the container's limits. It decides the machine is too small for G1, and quietly picks Serial.
  4. Pauses get longer and responses get slower, but nothing in the code changed.

The first line of the GC log (Using Serial) answers it in a second. So does the first line of jvm-explorer's collector report. Teams that have been hurt by this choose the collector on purpose in the container's settings.

In job interviews, “how would you choose a collector?” really asks two things. Do you know it is a choice between throughput and short pauses? And would you check the log before guessing?

6 Gotchas and common mistakes

  • Copying GC flags from old articles. The CMS collector (-XX:+UseConcMarkSweepGC) was removed in Java 14. Old logging flags are deprecated. Many tuning flags no longer exist or no longer matter. On a modern JVM, most of them are ignored with a warning nobody reads. Avoid it: on Java 21, start with no GC flags at all. Measure with a log. Add a flag only for a reason you can name.
  • Judging GC by its average pause. An average spreads one long full GC across thousands of short pauses until you cannot see it. But users feel the worst case. Avoid it: always read the count of full GCs and the maximum pause. The summary tool prints both.
  • Treating -XX:MaxGCPauseMillis as a promise. It is a goal that G1 tries to meet by sizing its work. Set it too low, and G1 shrinks the young generation until it collects all the time. That costs throughput. And it still misses the goal when the live data is too big. Avoid it: keep the default unless a log shows you need something else. Change it in small steps, while watching the log.
  • Not knowing which collector is really running. If you do not choose one, the JVM picks one by itself. Its choice depends on the machine or container it runs on. Avoid it: before you reason about any GC behaviour, read the Using ... line at the top of the log, or GcStats' collector names.
  • Logging GC to the console on a live system. GC lines then get mixed into your application's own output, and into anything that reads it. Nothing rotates them either. Avoid it: log to a file with rotation (file=gc.log plus filecount and filesize). GC logging at the gc level is cheap enough to leave on all the time. It is the first thing you will want after a problem on a live system.

Part A — read a log. A service's GC log contains these lines:

[0.005s][info][gc] Using Parallel
[12.10s][info][gc] GC(0) Pause Young (Allocation Failure) 512M->60M(1963M) 18.204ms
[31.47s][info][gc] GC(1) Pause Young (Allocation Failure) 572M->121M(1963M) 21.551ms
[52.88s][info][gc] GC(2) Pause Young (Allocation Failure) 633M->190M(1963M) 25.010ms
[71.03s][info][gc] GC(3) Pause Full (Ergonomics) 1700M->640M(1963M) 1840.733ms
[95.62s][info][gc] GC(4) Pause Young (Allocation Failure) 1152M->702M(1963M) 31.380ms
[140.2s][info][gc] GC(5) Pause Full (Ergonomics) 1890M->910M(1963M) 2304.118ms
  1. Which collector is running?
  2. What is the average pause, and what is the maximum?
  3. What is the best estimate of live data after each full GC? What does the trend suggest?
  4. This service answers web requests. Name two changes you would consider, in order.

Part B — choose a collector for each of these, with one reason:

  1. a nightly ETL batch job on a 16-core machine (ETL = Extract, Transform, Load: copying data from one system into another),
  2. a trading service whose contract says every response must come within 10 ms, with a 40 GB heap,
  3. a command-line tool that runs for half a second in a container with one CPU.

Part C — check yourself on the machine. Run GcWorkload under G1 with -Xmx64m, then with -Xmx32m. Sum up both logs. Before you look, predict: which summary has more pauses? Does the live-data estimate change?

Click to reveal the answer

Part A (1). Parallel. The Using Parallel line says so. Also, Allocation Failure and Ergonomics are Parallel's causes.

Part A (2). The six pauses add up to 18.204 + 21.551 + 25.010 + 1840.733 + 31.380 + 2304.118 = 4240.996 ms. So the average is about 707 ms. The maximum is 2304 ms: a 2.3-second freeze. Notice that even here the average misleads in both directions. It makes the full GCs look smaller than they are, and the young ones look far bigger.

Part A (3). The heap after the full GCs is 640 MB, then 910 MB. The live data grew by 270 MB in about 70 seconds. Live data that rises after full collections is the sign of a leak (Lesson 04). Or, to be generous, it could be a cache that is still filling up and has not reached its steady size. The heap is committed at 1963 MB. If the trend continues, this service will hit OutOfMemoryError within a few minutes.

Part A (4). In order:

  1. First, find out why live data keeps growing. Take a heap dump (a snapshot of everything in memory, Lesson 07) and see what is holding the extra 270 MB. No collector setting fixes a leak.
  2. Second, once the live data is stable: Parallel is the wrong collector for a web service. Its full-GC pauses grow with the old generation, and multi-second freezes are exactly what users feel. Switch to G1 (the default, so just remove the flag). Or, if short responses are critical, switch to ZGC. Both give up a little throughput for short pauses.

Changing the collector while leaving the leak in place only changes how the service dies.

Part B.

  • (a) Parallel. Only the total run time matters, and it has the highest throughput on many cores.
  • (b) ZGC. A 10 ms limit on every response, with a 40 GB heap, rules out any collector whose pauses grow with the heap. ZGC's pauses stay under a millisecond. Accept the throughput cost, and give it spare memory.
  • (c) Serial. The JVM will very likely pick it by itself here: one CPU, a tiny heap, a short run. A concurrent collector's background threads would fight the program for its only CPU.

Part C. Predicted: the 32 MB run has more pauses. Eden is smaller, so it fills more often for the same 512 MB of garbage. The old generation is also under more pressure. So expect more concurrent cycles, and maybe extra full GCs.

The live-data estimate should barely change (around 25 MB in both). Live data belongs to the program, not to the heap size. That is exactly why it is the number to read before choosing -Xmx.

25 MB of live data hardly fits in 32 MB. So you may even see the workload fail with OutOfMemoryError. If so, that perfectly shows what happens when a heap is smaller than its live data. Whatever your machine shows, it wins. Tell me what you saw.

9 Key words

Every new term from this lesson, with a one-line meaning.

Dashboard
A screen of live charts about a running system.
Concurrent
Running at the same time as your code, on other threads, instead of stopping it.
Batch job
A program that works through a big pile of data and then stops.
Throughput
The share of run time spent running your own code, not collecting. 3 min of GC in 1 hour = 95%.
Pause time (latency)
How long your code stands still during a pause — especially the worst one.
Footprint
The extra memory and CPU a collector needs on top of your program.
Serial collector
-XX:+UseSerialGC: one GC thread, everything stopped. Lowest overhead on small machines.
Mark-compact
Marking live objects from the roots, then sliding them together.
Parallel collector
-XX:+UseParallelGC: Serial's method on many threads. Highest throughput; pauses grow with the heap.
G1 (Garbage First)
-XX:+UseG1GC, the default since Java 9. Regions, concurrent marking, garbage-first collection, a pause goal.
Region
One of G1's many equal-sized heap blocks (1–32 MB), each with a role: Eden, survivor, old, humongous or free.
Evacuate
Copy a region's live objects out, so the whole region becomes free.
Concurrent marking
Marking live objects on background threads while your code runs.
Remark / Cleanup
G1's two short pauses that finish a concurrent marking cycle.
Mixed collection
A G1 collection of all young regions plus a few of the old regions with the most garbage.
Collection set
The regions G1 picks to evacuate in one pause.
-XX:MaxGCPauseMillis
G1's pause-time goal (default 200 ms). A goal, not a promise.
Humongous object
In G1, an object at least half a region in size. It gets whole regions of its own.
ZGC
-XX:+UseZGC: marks and moves objects concurrently, so pauses stay under a millisecond.
Load barrier
A tiny check on every reference read. ZGC uses it to fix references to moved objects.
Shenandoah
Another low-pause collector that moves objects concurrently.
CMS
An old collector, removed in Java 14. Its flags are now ignored with a warning.
Unified logging (-Xlog)
The JVM's single logging system since Java 9, e.g. -Xlog:gc:file=gc.log.
Log tag / level / decoration
A tag labels a message's subject (gc); the level is its detail (info, debug, trace); decorations are the bracketed fields at the start.
stdout / stderr
A program's normal output and its error output.
Log rotation
Starting a new log file when the current one is big enough, so logs never fill the disk.
Pause line
One GC log line for one pause: uptime, GC(n), pause kind, causes, heap before → after (committed), duration.
GC cause
The bracketed reason a collection started, e.g. Allocation Failure or System.gc().
Live data
How much the heap holds right after a full GC — what the program really still uses.
Workload
A program whose only job is to give the system work to do.
Parser
Code that reads text and turns it into structured data.
Regular expression (regex)
A small language for describing the shape of text, used with Java's Pattern and Matcher.
@TempDir
A JUnit feature that gives a test a fresh empty folder, deleted afterwards.
PID
The number the operating system gives each running program.
ETL
Extract, Transform, Load: copying data from one system into another.

10 Quick recap

  • Every collector trades throughput, pause time and footprint against each other. Shorter pauses mean doing work concurrently, and that background work costs CPU and throughput.
  • Serial (one thread) and Parallel (many threads) stop everything to collect. Serial has the lowest overhead, Parallel the highest throughput, and both have pauses that grow with the heap.
  • G1, the default since Java 9, splits the heap into regions, marks concurrently, and collects the regions with the most garbage first, sized to a pause goal. It falls back to a full GC only when it falls behind.
  • ZGC moves objects while your code runs, using a load barrier on every reference read. Its pauses stay under a millisecond at any heap size, at a cost in throughput and spare memory.
  • Turn on logging with -Xlog:gc:file=gc.log. Read three numbers first: how many full GCs, the longest pause, and the heap after full GCs over time.
