Lesson 04 — Object Lifecycle & GC Fundamentals

When does an object become garbage? Who decides? Why does the heap split itself into young and old? Meet the rule of reachability, and the bet that most objects die young.

Position: Lesson 04 of 07  ·  Prerequisites: Lesson 03 — Runtime Memory Areas  ·  Project files: gc/Generation.java, gc/CollectorReading.java, gc/GcStats.java, gc/AllocationPatterns.java, gc/ReachabilityProbe.java, experiments/GenerationsExperiment.java, JvmExplorer.java (modified), and four test classes

You will learn the exact rule that decides when an object becomes garbage, and why Java programs can still leak memory.

You will also learn how the JVM splits the heap into a young area and an old area, because most objects die young. Then you will watch real objects grow older and move from one area to the other.

1 The pain

Pain 1: letting go “didn't work”

In Lesson 03 the project held 8 MB, let go of it, and printed the heap again. The used number may not have moved at all.

People meet this small mystery all the time. Someone sets a big list to null. They watch the memory graph stay flat. They decide that letting go “didn't work”. They start adding System.gc() (a request to clean up memory now) all over the code. The program gets slower, and the graph still does not do what they expect.

Pain 2: “Java can't leak”

The second pain is a belief: “Java has garbage collection, so Java programs can't leak memory.” Then a service dies with OutOfMemoryError: Java heap space after six hours of perfectly normal traffic.

The cause is one line. A static map is used as a cache (a store of saved results, kept to avoid redoing work). It gains one entry per request and never loses any. The garbage collector did nothing wrong. It was not allowed to touch those objects, because something could still reach them. That sentence makes no sense until you know the exact rule the collector follows.

Pain 3: the freeze

The third pain is a freeze. Every few minutes, the application stops answering for a fraction of a second. Then it carries on as if nothing happened.

That is the collector at work. Some of its work happens while your code stands still. How often that happens, and how long it lasts, depends on how the collector divides up the heap. That is the second half of this lesson.

By the end, your project will prove the reachability rule in four different ways. You will also watch real objects survive collections, grow older, and move to a new area.

2 Real-world analogy

Picture a busy office desk. Papers land on it all day: memos, drafts, printouts. Most are read once and are useless within minutes.

A paper is worth keeping only if you can reach it from something you are working on right now. That could be a task in your hands, a folder pinned to the wall, or a paper clipped to one of those. A paper clipped only to another useless paper is useless too, however tightly the two are clipped together.

Clearing the desk is quick, because you do not sort the rubbish:

  1. You rescue only the few papers still linked to live work.
  2. You put them in a small tray beside the desk.
  3. You sweep everything else into the bin in one go.

A paper that survives several clearings is clearly long-term. So it gets filed in the big archive cabinet, and you stop checking it every time. Deep-cleaning the archive is a big job, so you do it rarely.

Notice that the bin is never sorted. That is the most important idea in the second half of this lesson. A well-designed collector does work in proportion to what it keeps, not to what it throws away.

3 The concept explained

We build this in the order the ideas depend on each other:

  1. what “garbage” means exactly,
  2. why Java programs can still leak,
  3. how a collector finds garbage,
  4. the pattern that makes generations worth having,
  5. how the young and old generations work, and
  6. how to watch all of it from inside Java.

3.1 What “garbage” actually means

Lesson 03 showed that every object lives on the heap. It also showed that a variable holds a reference: an arrow to the object, not the object itself.

Nothing in your code ever frees an object. So something has to work out which objects are no longer needed. That something is the garbage collector (GC). It is the part of the JVM that finds objects the program can no longer use, and frees their memory.

But what exactly does “can no longer use” mean? Before the real answer, here is the obvious one, and why it fails.

What goes wrong with the obvious answer

The natural first idea is to count arrows:

  1. Each object gets a counter of how many references point at it.
  2. Add one when a reference is made. Subtract one when a reference goes away.
  3. Free the object when its counter reaches zero.

This is called reference counting, and some languages really use it. Now try it on this code:

Node a = new Node();
Node b = new Node();
a.next = b;          // b's counter: 2 (from the variable b, and from a.next)
b.next = a;          // a's counter: 2 (from the variable a, and from b.next)
a = null;            // a's counter: 1 (b.next still points at it)
b = null;            // b's counter: 1 (a.next still points at it)
// Nothing in the program can reach either node ever again -
// but both counters are stuck at 1. Under counting, they are never freed.

Two objects that point at each other form a cycle. They keep each other's counters above zero forever. Real data is full of cycles:

  • A parent lists its children, and each child points back at its parent.
  • In a list where each item points to both its next and previous neighbour, every neighbour pair points at each other.
  • A listener (an object that waits to be told when something happens) often holds the object it listens to, and that object holds the listener.

Counting would leak every one of them.

The real rule: reachability

Java asks a different question. It does not ask “does anything point at this object?”. It asks: “can the running program reach this object by following arrows from somewhere it is surely using?”

Those starting points, the places the program is surely using right now, are called GC roots. The main ones are:

  • Local variables in every live frame, on every thread's stack (Lesson 03's frames). A method that is still running is still using its variables.
  • Static fields of every loaded class. A static field lives as long as its class. For a normal application, that is the whole run.
  • The running threads themselves, plus a few things the JVM holds inside itself, such as references held by native code. You will rarely need to think about those.

An object is reachable if a chain of references leads to it from at least one root. Everything else is garbage, no matter how many arrows point at it from other garbage.

In the example above, once a and b are both null, no root leads to either node. So both are garbage. The cycle makes no difference at all.

A collector that works by following arrows from the roots is called a tracing collector (to trace means to follow a path). Every collector in HotSpot is one.

An object is referenced by ten other objects. Can it be garbage?
Yes. If no root can reach any of those ten objects, then no root can reach it either. All eleven are garbage together. The number of arrows pointing at an object tells you nothing. Only one thing matters: is there a path from a root?

3.2 How objects become unreachable — and how Java programs still leak

An object stops being reachable when the last path to it from a root is cut. In everyday code, that happens in four ways:

  • A method returns. Its frame is popped, so its local variables stop being roots. This is by far the most common way. Every temporary object made inside a method becomes garbage the moment the method finishes, unless it was returned or stored somewhere. (The list made inside replace in Lesson 03's challenge died exactly this way.)
  • A variable is overwritten. It is set to null, or pointed at a different object.
  • An object is removed from a collection, so the list or map no longer points at it.
  • The object that pointed at it becomes unreachable itself. Everything hanging off a garbage object is garbage too.

What goes wrong when you expect the collector to read your mind

Now back to Pain 2 from Section 1:

public final class PriceService {
    // A static field is a GC root. Everything this map reaches stays alive
    // for as long as the class is loaded - which is the whole run.
    private static final Map<String, Quote> CACHE = new HashMap<>();

    Quote quote(String requestId) {
        Quote q = calculate(requestId);
        CACHE.put(requestId, q);   // one entry per request, never removed
        return q;
    }
}
// PREDICTED symptom, hours later:
java.lang.OutOfMemoryError: Java heap space

Every request ID is unique, so the cache never helps anyone. But every Quote stays reachable through this path: root → static field → map → entry → Quote. So the collector must keep it.

That is what a memory leak is in Java. It is not an object the collector forgot. It is an object the program no longer needs that is still reachable. The collector cannot know you will never ask for request #41,207 again. It only knows that you still could.

The cure is always the same: cut the path. Remove entries you no longer need, limit the cache's size, or use a structure built to forget (Section 5).

“Can be collected” is not “collected”. Cutting the last path makes an object eligible (able) to be collected. It does not collect it. It does not give memory back to the operating system either. The collector runs when it decides, usually when the area for new objects fills up (Section 3.5).

That fully explains Lesson 03's 8 MB mystery. The chunks became garbage the moment the list was cleared. But they sat in the heap, still counted in used, until the next collection happened to run.

System.gc() only asks for a collection. The JVM is allowed to ignore the request. The flag -XX:+DisableExplicitGC makes HotSpot ignore it on purpose.

A method creates a 10 MB array in a local variable, uses it, and returns. When does the array become garbage, and when is it collected?
It becomes garbage when the method returns. The frame is popped, the local variable stops being a root, and no other path leads to the array. It is collected whenever the collector next runs. That might be milliseconds later, or much later. Between those two moments, it still takes up heap and still shows in the used number.

3.3 How a collector actually finds the garbage

Every HotSpot collector does two jobs. First it finds the live objects. Then it frees the rest.

Finding: marking

Here is how the collector finds every live object:

  1. It starts at every root.
  2. It follows every reference from there. It sets a flag on each object it reaches, meaning “this one is alive”.
  3. It follows the references inside those objects, and so on.
  4. It stops when there is nothing new to reach.

This walk is called marking. Anything left unmarked at the end is garbage.

Notice what marking costs. Its work grows with the number of live objects, because those are the only ones it visits. It never looks at the garbage.

The catch: your code keeps changing the arrows

Say your program kept running while the collector walked. It could move a reference from an object the collector has not visited yet into one it already visited. Then the collector would never see that reference, and would wrongly decide a live object was garbage.

The simplest fix is to pause every application thread during the walk. A pause where all your code stops so the collector can work is called a stop-the-world pause. That is the freeze from Section 1.

Modern collectors do much of their work while your code runs. They use careful record-keeping to stay correct, and keep the stop-the-world parts short. Lesson 05 compares how each collector does that.

Freeing memory: three ways

Once the collector knows which objects are live, it has three basic ways to free the rest:

  • Sweep: walk the heap and add every dead object's space to a list of free gaps. This is simple. But the free memory ends up spread out in small holes between live objects. When free memory is split into pieces too small to use, that is called fragmentation. It can mean a large array does not fit, even though there is plenty of free memory in total.
  • Compact: slide all the live objects together at one end, so the free space becomes one solid block. There is no fragmentation. But every reference to a moved object must be updated.
  • Copy: copy every live object into a separate, empty area. Then treat the whole old area as free, in one step. This is called copying collection. It needs spare space to copy into. But it has a great property: its cost depends only on how much is alive. If almost everything is dead, there is almost nothing to copy, and wiping the old area costs nothing.

Keep that last property in mind. The next idea depends on it.

3.4 The generational hypothesis: most objects die young

What goes wrong without generations

Imagine a collector that marks the whole heap every time:

  • Your application holds 3 GB of long-lived data, such as caches, settings and lookup tables.
  • It also makes temporary objects very fast.
  • Every collection walks all 3 GB of live data, just to find out again that it is still alive.
  • All that work, just to clear away a few hundred megabytes of temporary objects.

The bigger your heap, the longer every collection takes, even though the long-lived data never changes.

The pattern: most objects die very young

Engineers who measured real programs saw a pattern that holds almost everywhere: most objects die very young. Think of what a typical method makes:

  • a StringBuilder to build a message;
  • an iterator (a small helper object that steps through a list);
  • boxed Integers (an int wrapped in an object so it can go into a list);
  • a request object that lives for one web request.

Almost all of it is garbage within microseconds (millionths of a second) or milliseconds. The few objects that survive a while tend to survive a long time.

This pattern is called the generational hypothesis. (Its usual form is called the weak generational hypothesis.) A hypothesis is an idea you test rather than a proven law. This one is a bet about how programs behave. But the bet pays off for almost all real Java code.

The cure: separate areas by age

The cure follows directly:

  1. Keep new objects in their own small area, and collect that area often.
  2. Almost everything in it is dead. So a copying collection there is very cheap. It never needs to walk the long-lived data at all.
  3. Move the rare survivors to another area, and collect that area rarely.

An area that holds objects of roughly the same age is called a generation. HotSpot uses two: the young generation and the old generation.

3.5 The young generation: Eden, two survivor spaces, and growing old

The young generation is itself split into three parts.

Eden: where new objects are born

Eden is where (almost) every new object is made. Making an object there is very cheap. Here is why:

  1. Eden is one block of empty memory, with a marker (a pointer) that shows where the free part begins.
  2. To make a new object of N bytes, the JVM hands out the next N bytes.
  3. It moves the marker forward by N. That is all.

That is called bump-the-pointer allocation.

But many threads make objects at once, and they should not have to wait in line for that one marker. So each thread gets its own private slice of Eden to bump through. This slice is called a TLAB (thread-local allocation buffer). Because of it, most allocations need no coordination with other threads at all. That is why new in Java is much cheaper than many people think.

Two survivor spaces

Two survivor spaces sit beside Eden. They are usually called S0 and S1 (or “from” and “to”). They are small and the same size. At any moment, one of them holds objects that survived earlier collections, and the other is empty, waiting.

A minor GC, step by step

When Eden fills up, the JVM runs a collection of the young generation only. That is called a minor GC, and it goes like this:

  1. All application threads pause. This stop-the-world pause is short, because the young generation is small and mostly dead.
  2. Starting from the roots, the collector finds every live object in Eden and in the survivor space that is in use.
  3. It copies each of those live objects into the empty survivor space. It adds one to each copied object's age. The age is the number of collections the object has survived. It is kept in a few bits of the object's header (a small block of bookkeeping data at the start of every object).
  4. Eden and the old survivor space now hold nothing but garbage. So both are marked empty in one step. Nothing is swept, and the garbage is never looked at.
  5. The two survivor spaces swap roles. The one just filled becomes “from”. The one just emptied becomes “to” for next time.

Growing old: promotion

An object that keeps surviving keeps getting copied back and forth, one “year” older each time. When its age reaches a limit, the next collection copies it into the old generation instead.

Moving an object from the young generation to the old one is called promotion (or tenuring, like a teacher who has earned a permanent job). The age limit is called the tenuring threshold.

  • Its maximum in HotSpot is 15, because the age is stored in four bits. (Four bits can count from 0 to 15.)
  • You set it with -XX:MaxTenuringThreshold.
  • The JVM may also lower the threshold by itself if the survivor space is getting too full.

Two more ways into the old generation

Both matter in real programs:

  • Premature promotion. The empty survivor space may be too small for everything that survived. Then the extra objects go straight to the old generation, however young they are. (“Premature” means “too early”.) This is bad news. Short-lived objects end up in the area that is collected rarely and at high cost.
  • Very large objects. These may be made directly in the old generation, skipping the young one. Copying them back and forth would cost too much. (The G1 collector calls these humongous objects. See Lesson 05.)

One gap left to close: references that point backwards

A minor GC is meant to look only at the young generation. But an old object can hold a reference to a young one. For example, an old cache gets a brand-new entry.

If the minor GC ignored the old generation, it would miss that path and wrongly free the young object. Scanning the whole old generation every time would throw away the whole benefit. So HotSpot keeps a record instead:

  • It divides the old generation into small, fixed-size slices called cards.
  • Every time your code stores a reference into an old object, a tiny extra piece of code marks that slice as “dirty”. The JIT adds this code to every such store. It is called a write barrier.
  • The table of dirty marks is the card table.
  • During a minor GC, only the dirty cards are scanned, as extra roots.

A small cost on every reference store buys the ability to collect the young generation on its own.

Why is a minor GC usually fast even when the heap is several gigabytes?
Because it only deals with the young generation. And inside it, it only touches the live objects, copying them to a survivor space. The garbage is never visited. Eden is just marked empty afterwards. If most young objects are dead (the generational hypothesis), there is very little to copy. The old generation's size hardly matters, except for the dirty cards in the card table.

3.6 The old generation, and minor versus major versus full

The old generation (also called the tenured generation) holds promoted objects. It fills slowly, because only survivors arrive there.

When it gets full enough, it must be collected too. It is large and mostly alive, so collecting it is expensive. This is where long pauses have usually come from.

People use these words loosely. Here are the three terms as most people mean them:

TermWhat it collectsHow oftenCost
Minor GCthe young generation onlyoften — whenever Eden fillssmall: proportional to young survivors
Major GCthe old generationrarelylarge: the old generation is big and mostly alive
Full GCthe whole heap (young and old), often Metaspace tooideally almost neverthe largest; usually a long stop-the-world pause

Everything above describes the generations as ideas. It matches the heap layout of HotSpot's simplest collector, called Serial, exactly: one solid Eden, two survivor spaces, one old generation.

Since Java 9, the default collector is G1. G1 keeps the same young and old roles. But it builds them from many equal-sized blocks called regions, and a region can change role. It also collects the old generation a piece at a time, together with young collections. These are called “mixed” collections. Another collector, ZGC, can also work with generations in Java 21.

Lesson 05 covers how each collector really works and how to choose one. The rules of this lesson hold for all of them: reachability, most objects die young, copy the survivors, promote the old ones.

3.8 Watching an object without keeping it alive

To prove the reachability rule from inside a Java program, we need to check on an object after a collection. But a normal reference to it would make it reachable. Just watching it would keep it alive. We need a reference that does not count.

Java has exactly that. It is a small wrapper object that points at another object, without counting toward its reachability:

  • Say the only paths left to an object go through wrappers like this. Then the collector may free it.
  • Once it does, asking the wrapper for its object returns null.

This is called a weak reference. An ordinary reference is called a strong reference, because it keeps its object alive. The class is java.lang.ref.WeakReference:

Object strong = new Object();                         // an ordinary reference: keeps it alive
WeakReference<Object> watcher = new WeakReference<>(strong);  // watches, does not keep alive

watcher.get();     // the object - while something strong still reaches it
// ... after the last strong path is cut AND a collection has run ...
watcher.get();     // null

A surprise: a variable can “die” before its block ends

One detail shows up the moment you use this, and it surprises nearly everyone. You might think strong keeps its object alive until the end of the block it was declared in. Not always.

Scope means where a variable's name can be used in the source code. It is a compile-time idea. Reachability is decided while the program runs. The JIT may notice that strong is never used again after some line. It is then allowed to treat it as dead from that point, even though it is still in scope.

For almost all code, this changes nothing you could notice. But when you are watching an object on purpose, it can make the object disappear early. The fix is Reference.reachabilityFence(strong) (Java 9 and later). This call does nothing except promise the JVM that the object stays reachable up to that line. The project uses it everywhere it watches an object.

4 Applied to jvm-explorer

The project gets a new package, gc. It does three things:

  • It proves the reachability rule by watching it happen.
  • It reads the collector's own counters.
  • It makes real objects age and get promoted.

One Java word in the code below may be new. A volatile field is one whose every read and write really goes to memory, so all threads see the latest value. Here it also stops the JIT from deciding the writes are pointless and skipping them.

4.1 What happens, step by step, when the new code runs

  1. JvmExplorer.main runs its Lesson 00–03 sections as before. Then it calls ReachabilityProbe.describe().
  2. Reachable: the probe makes an object and holds it in a local variable (a root). It watches the object through a WeakReference. It asks for two collections. The object must survive. reachabilityFence makes sure the local variable really counts until the check.
  3. Unreachable: it makes an object that only a weak reference points at. That object is garbage from the start. It asks for collections until get() returns null.
  4. A cycle: it builds two Nodes that point at each other and watches both. Then it sets both local variables to null. The pair still point at each other, but no root reaches them. So both are freed. A reference-counting collector would keep them forever.
  5. A leak: it puts an object in a static list, drops its own local reference, and asks for collections. The static field is a root, so the object must survive. Then it clears the list.
  6. AllocationPatterns.churnUntilCollection reads the total collection count for all collectors. Then it makes 64 KB arrays, one after another:
    • Each new array replaces the last one in a volatile static field. That turns the previous array into garbage. It also forces the JVM to really make each array.
    • After each one, it reads the total again.
    • Eden fills, a minor GC runs, and the total goes up.
    The loop stops and reports how much garbage that took.
  7. GcStats.describe() prints each collector's name, count and total time. It also prints how many kilobytes Eden, the survivor space and the old generation hold right now.

4.3 Proving the rule: the cycle

public static boolean unreachableCycleIsCollected() {
    Node first = new Node();
    Node second = new Node();

    // The cycle: a collector that counted incoming arrows would see 1 for each, forever.
    first.next = second;
    second.next = first;

    WeakReference<Node> watchFirst = new WeakReference<>(first);
    WeakReference<Node> watchSecond = new WeakReference<>(second);

    // Cut the only paths from a root. The nodes still point at each other.
    first = null;
    second = null;

    // Tracing starts at the roots, never reaches the pair, and reclaims both.
    return requestGcUntilCleared(watchFirst, DEFAULT_GC_ATTEMPTS)
            && requestGcUntilCleared(watchSecond, DEFAULT_GC_ATTEMPTS);
}

4.4 Forcing a collection without System.gc()

// Every short-lived object is written here, then overwritten by the next one.
// Escaping into a field stops the JIT optimising the allocation away (Lesson 06).
private static volatile Object sink;

public static long churnUntilCollection(int objectBytes, long capBytes) {
    long before = GcStats.totalCollectionCount();
    long allocated = 0;
    while (allocated < capBytes) {
        sink = new byte[objectBytes];              // the previous array is garbage now
        allocated += objectBytes;
        if (GcStats.totalCollectionCount() > before) {
            sink = null;
            return allocated;                     // Eden filled; a collection ran
        }
    }
    sink = null;
    return -1;                                    // no collection within the cap
}

Why must a collection happen before the cap? The cap is four times the heap's ceiling. Garbage beyond the ceiling has nowhere to go, so the JVM must collect to make room. In practice, the first minor GC comes as soon as Eden fills, long before that.

4.5 The tests

The probe's test file says clearly that its claims are not all equally strong:

  • “A reachable object is never collected” is a promise of the Java specification. So those tests cannot fail on a correct JVM.
  • “An unreachable object is collected” is not promised, because System.gc() is only a request. Those tests rely on HotSpot doing what it is asked. By default, it does.
// GUARANTEED: a static field is a root, so whatever it reaches stays alive.
@Test
void anObjectHeldByAStaticFieldIsNeverCollected() {
    assertTrue(ReachabilityProbe.objectHeldByStaticFieldSurvives(), /* … */);
}

// RELIES ON System.gc() being honoured: a cycle reachable from no root is garbage.
// This is the test a reference-counting collector would fail.
@Test
void anUnreachableCycleIsCollected() {
    assertTrue(ReachabilityProbe.unreachableCycleIsCollected(),
            "... If this fails, check that -XX:+DisableExplicitGC is not set.");
}

// GUARANTEED by logic: garbage beyond the heap ceiling must force a collection.
@Test
void enoughGarbageAlwaysForcesACollection() {
    long before = GcStats.totalCollectionCount();
    long garbage = AllocationPatterns.churnUntilCollection(
            AllocationPatterns.DEFAULT_OBJECT_BYTES, AllocationPatterns.safeCapBytes());
    assertTrue(garbage > 0, /* … */);
    assertTrue(GcStats.totalCollectionCount() > before, /* … */);
}

No test checks when promotion happens, how many collections have run, or how big any generation is. Those depend on the collector, the machine, and everything that ran earlier in the same test JVM. They are things to watch in your terminal, not facts a test can rely on.

  2. Collection 1 copies it into a survivor space at age 1.
  3. Collections 2 and 3 copy it across again, at ages 2 and 3.
  4. At collection 4, the objects have reached the threshold. So they are copied into the old generation instead. Survivor drops and old jumps by about 1 MB, in one step.
  5. After that, the old generation stays flat, because minor GCs never touch it.

5 In the wild

The JDK comes with a map built on weak references: java.util.WeakHashMap. Here is how it works:

  1. Its keys are held weakly.
  2. When nothing else in the program references a key any more, the collector may free it.
  3. Then the map quietly drops that entry.

It is a cache that forgets by itself. In the right situations, that is exactly the cure for Section 3.2's leak. A classic use is attaching extra data to objects you do not own, without keeping those objects alive.

It also has a famous trap, and the trap is pure reachability. Say a value holds a reference back to its own key. Then the entry never disappears:

  • The map holds the value strongly.
  • The value holds the key strongly.
  • So the key can always be reached, through the map itself.
Map<Customer, Report> reports = new WeakHashMap<>();
reports.put(customer, new Report(customer));  // the Report points back at its key...
// ...so this entry is never removed, however unused customer becomes. A leak.

On live systems, GC tuning (adjusting the collector's settings so pauses are short and rare) starts with two questions that come straight from this lesson.

  • How fast is the program making objects? That decides how often Eden fills, and so how often minor GCs run.
  • How much survives? That decides how much each minor GC costs, and how fast the old generation fills.

Now compare two services:

  • Service A's old generation climbs steadily and never comes back down after full GCs. It has a leak: something is reachable that should not be.
  • Service B's old generation fills fast, but drops back after each full GC. It is suffering from premature promotion. It needs a bigger young generation, not a bigger heap.

If you can tell those two apart in a job interview, just from a description of a memory graph, it shows real understanding.

6 Gotchas and common mistakes

  • Calling System.gc() to “free memory”. People reach for it because a memory graph did not drop after they let go of something. It is a request the JVM may ignore. On HotSpot's default settings, it starts a full GC: the most expensive kind, with a long pause, right in the middle of your traffic. Avoid it: never call it in application code. If memory is not freed, the question is “what still reaches it?”, not “how do I force the collector?”
  • Believing Java cannot leak. The collector only frees what is unreachable. So anything still reachable stays, however useless it is. The usual causes are static collections, caches with no size limit, listeners that are added and never removed, and values left in a ThreadLocal (a per-thread storage box) on threads that are reused forever. Avoid it: for every long-lived collection, know what removes entries from it.
  • Keeping an outer object alive by accident with an inner class or lambda. Some code carries a hidden reference to the outer object's this:
    • a non-static inner class (a class written inside another class);
    • an anonymous class (an inner class with no name, written right where it is used);
    • a lambda that uses any instance field or method.
    Register one as a long-lived listener, and the whole outer object stays reachable for as long as the listener does. So does everything the outer object references. Avoid it: make nested classes static unless they really need the outer object. Unregister listeners when their owner is done.
  • Relying on finalize() to clean up. A finalize() method was meant to run when an object became garbage. But it runs at a time you cannot predict, or not at all. It slows the collector. It can even bring a dead object back to life. It was deprecated for removal in Java 18 (by JEP 421; a JEP is a numbered, official proposal for changing Java). Avoid it: release files, network connections (sockets) and locks with try-with-resources (Lesson 01). Use java.lang.ref.Cleaner only as a last-resort safety net.
  • Assuming an object lives until the end of its variable's scope. Scope is a compile-time idea. The JIT may treat a variable as dead after its last use. So the object can become collectable before the closing brace. This only matters when you are watching objects (weak references), or when an object guards something outside the heap. Avoid it: use Reference.reachabilityFence(obj) to keep an object reachable up to an exact line.

7 Challenge

Part A — which objects are garbage? At the line marked // HERE, look at each object from A to F. Decide whether it is reachable or garbage, and say why.

public class Puzzle {
    static List<Object> registry = new ArrayList<>();

    static class Box { Object item; }

    public static void main(String[] args) {
        Box a = new Box();          // object A
        a.item = new Object();       // object B

        Box c = new Box();          // object C
        Box d = new Box();          // object D
        c.item = d;
        d.item = c;
        c = null;
        d = null;

        registry.add(new Object());  // object E

        helper();                    // creates object F inside, and returns nothing

        a.item = null;
        // HERE
        System.out.println(a);
    }

    static void helper() {
        Object f = new Object();    // object F
    }
}

Part B — read two memory graphs. Two services each have an old generation that keeps climbing. In service 1, every full GC brings the old generation back down to about 400 MB. Then it climbs again. In service 2, every full GC brings it down a little less than the time before: 400 MB, then 550, then 700. Which one is leaking? What is the other one's problem? What would you change for each?

Part C — check yourself on the machine. Run the generations experiment with -XX:MaxTenuringThreshold=1. Predict the round of the jump before you look. Then shrink the young generation so the survivor space is smaller than 1 MB, with -Xmn8m. (Each survivor space is then about 0.8 MB.) Predict what happens. Run it and see.

Click to reveal the answer

Part A.

  • A — reachable. The local variable a is in main's live frame, so it is a root, and it points at A. (It is also used on the next line, so even the JIT cannot treat it as dead.)
  • B — garbage. Its only path was a.item, and a.item = null cut it.
  • C and D — garbage. They point at each other. But both local variables were set to null, so no root reaches either one. The cycle does not matter. This is exactly the case reference counting gets wrong.
  • E — reachable. registry is a static field, so it is a root. The list it points at holds E. This is what a leak looks like: E will stay for the whole run unless something removes it.
  • F — garbage. Its only reference was the local variable f in helper's frame. That frame was popped when helper returned.

Remember the difference between garbage and collected. B, C, D and F can be collected at // HERE. But they will only be freed when a collection next runs. They were all made in Eden, so the next minor GC frees them without looking at them.

Part B. Service 2 is leaking. The level a full GC drops back to is the amount of live data. In service 2, it keeps rising, so something reachable keeps growing. More heap only delays the OutOfMemoryError. The fix is to find what still reaches the growing objects (with a heap dump, Lesson 07) and cut the path.

Service 1 is not leaking. Its live data stays at 400 MB. But its old generation keeps filling with objects that die soon after they arrive. That is the sign of premature promotion. Short-lived objects get pushed out of a young generation that is too small, or out of survivor spaces that overflow. The fix is a bigger young generation (or bigger survivor spaces). Then those objects die young, where they are cheap to collect.

Part C. With MaxTenuringThreshold=1, the kept objects go into a survivor space at age 1 on the first collection. They are promoted on the second. So the predicted jump is at round 2. With -Xmn8m, 1 MB of survivors cannot fit in a survivor space of about 0.8 MB. So the extra is promoted too early, at round 1, whatever the threshold. Survivor stays low and old jumps at once. That is premature promotion, caused on purpose. (The JVM may also lower the threshold by itself when the survivor space gets crowded. That pushes in the same direction.) If your machine shows something else, that is the interesting result. Tell me what you saw.

9 Key words

Every new term from this lesson, with a one-line meaning.

Cache
A store of saved results, kept so work does not have to be redone.
Garbage collector (GC)
The part of the JVM that finds objects nobody can use any more and frees their memory.
Reference counting
Freeing an object when nothing points at it. Java does NOT use it, because cycles would leak.
Cycle
Objects that point at each other in a loop.
Listener
An object that waits to be told when something happens.
GC roots
The starting points the program is surely using: live local variables, static fields, running threads.
Reachable
Some chain of references leads to the object from a root.
Garbage
An object no root can reach. It can be collected, but may not be yet.
Tracing collector
A collector that finds live objects by following references from the roots. All of HotSpot's are.
Memory leak (Java)
An object the program no longer needs that is still reachable.
Eligible for collection
No longer reachable, so it may be freed — but it still uses memory until a collection runs.
System.gc()
A request for a collection. The JVM may ignore it.
Marking
The collector's walk from the roots, flagging every object it reaches as alive.
Stop-the-world pause
A moment when all your code is paused so the collector can work safely.
Sweep
Adding every dead object's space to a list of free gaps.
Fragmentation
Free memory split into holes too small to use.
Compaction
Sliding live objects together so free space is one solid block.
Copying collection
Copying live objects to an empty area, then treating the old area as free. Cost depends only on what is alive.
Iterator
A small helper object that steps through a list.
Boxed Integer
An int wrapped in an object, for example so it can go into a list.
Microsecond
One millionth of a second.
Generational hypothesis
The observed bet that most objects die young, and survivors tend to live long.
Generation
An area of the heap holding objects of roughly the same age.
Young generation
Where new objects live: Eden plus two survivor spaces. Collected often and cheaply.
Eden
The part of the young generation where (almost) every new object is made.
Bump-the-pointer allocation
Making an object by handing out the next N free bytes and moving a marker forward.
TLAB
A thread's private slice of Eden, so it can make objects without waiting for other threads.
Survivor spaces (S0 / S1)
Two small areas next to Eden. One holds survivors; the other waits empty. They swap each minor GC.
Minor GC
A collection of the young generation only, run when Eden fills.
Object header
A small block of bookkeeping data at the start of every object. It holds the object's age.
Object age
How many collections an object has survived (at most 15 in HotSpot).
Promotion (tenuring)
Moving an object from the young generation to the old one.
Tenuring threshold
The age at which an object is promoted. Set with -XX:MaxTenuringThreshold.
Premature promotion
Short-lived objects pushed into the old generation too early, often because a survivor space overflowed.
Old (tenured) generation
Where long-lived, promoted objects live. Collected rarely and at high cost.
Card table / write barrier
A write barrier is tiny code on every reference store that marks a slice of old memory “dirty” in the card table, so minor GCs scan only those slices.
Major GC / full GC
A major GC collects the old generation; a full GC collects the whole heap. Usually the longest pauses.
Serial / G1
Two HotSpot collectors: Serial is the simplest; G1 is the default since Java 9. Lesson 05.
Weak reference
A reference that does not keep its object alive. get() returns null once the object is collected.
Strong reference
An ordinary reference, which keeps its object alive.
Scope
Where a variable's name can be used in the source code.
Reference.reachabilityFence
A call that keeps an object reachable up to that exact line.
volatile
A field modifier: every read and write really goes to memory, so all threads see the latest value.
Enum
A type with a fixed list of named values.
Unified logging
The JVM's built-in reporting system, switched on with -Xlog. Lesson 05.
WeakHashMap
A map whose keys are held weakly, so entries disappear once nothing else uses the key.
GC tuning
Adjusting collector settings so pauses are short and rare.
Inner / anonymous class
A class written inside another class; an anonymous one has no name. Both secretly hold the outer object.
finalize() / Cleaner
An old, unreliable clean-up hook, now deprecated. Cleaner is the last-resort replacement.
JEP
A numbered, official proposal for changing Java.
Socket
One open network connection.

10 Quick recap

  • An object is garbage when no chain of references leads to it from a GC root. So unreachable cycles are garbage too — that is why Java traces from the roots instead of counting references.
  • A Java memory leak is an object you no longer need that is still reachable, usually through a static collection, an unlimited cache or a forgotten listener. The cure is to cut the path.
  • Cutting the last path makes an object able to be collected, not collected. The collector runs when it decides, and System.gc() is only a request.
  • Most objects die young, so new objects start in Eden and the young generation is collected often by copying. The cost depends only on what survives — garbage is never even looked at.
  • Each survival raises an object's age. At the tenuring threshold it is promoted to the old generation, which is collected rarely and expensively. Minor GCs never free anything there.
