Lesson 04 — Object Lifecycle & GC Fundamentals

When does an object become garbage, who decides, and why does the heap split itself into young and old? The rule of reachability, and the bet that most objects die young.

Position: Lesson 04 of 07  ·  Prerequisites: Lesson 03 — Runtime Memory Areas  ·  Project files: gc/Generation.java, gc/CollectorReading.java, gc/GcStats.java, gc/AllocationPatterns.java, gc/ReachabilityProbe.java, experiments/GenerationsExperiment.java, JvmExplorer.java (modified), and four test classes

1 The pain

In Lesson 03 the project held 8 MB, let go of it, and printed the heap again — and the used figure may not have moved at all. That small mystery is the first pain of this lesson, and people meet it constantly. Someone sets a big list to null, watches the memory graph stay flat, decides the release “didn't work,” and starts sprinkling System.gc() through the code. The program gets slower and the graph still doesn't do what they expect.

The second pain is a belief: “Java has garbage collection, so Java programs can't leak memory.” Then a service dies with OutOfMemoryError: Java heap space after six hours of perfectly normal traffic. The cause is one line — a static map used as a cache, gaining one entry per request, never losing any. The garbage collector did nothing wrong. It was forbidden to touch those objects, because something could still reach them. Until you know the exact rule the collector follows, that sentence is impossible to understand.

The third pain is a freeze. Every few minutes the application stops answering for a fraction of a second, then carries on as if nothing happened. That is the collector at work, and some of its work happens while your code stands still. How often that happens, and how long it lasts, depends entirely on how the collector divides up the heap — which is the second half of this lesson. By the end, your project will prove the reachability rule four different ways, and you will watch real objects survive collections, grow older, and move house.

2 Real-world analogy

Picture a busy office desk. Papers land on it all day — memos, drafts, printouts. Most of them are read once and are useless within minutes.

A paper is worth keeping only if you can reach it from something you are actively working on: a task in your hands, a folder pinned to the wall, or a paper clipped to one of those. A paper clipped only to another useless paper is useless too, however tightly the two are clipped together.

Clearing the desk is quick, because you do not sort the rubbish — you only rescue the few papers still connected to live work, put them in a small tray beside the desk, and sweep everything else into the bin in one motion. A paper that survives several clearings is clearly long-term, so it gets filed in the big archive cabinet and you stop checking it every time. Deep-cleaning the archive is a big job, so you do it rarely.

Notice that the bin is never sorted. That is the single most important idea in the second half of this lesson: a well-designed collector does work in proportion to what it keeps, not to what it throws away.

3 The concept explained

We build this in dependency order: what “garbage” means exactly, why Java programs can still leak, how a collector finds garbage, the observation that makes generations worth having, how the young and old generations work, and how to watch all of it from inside Java.

3.1 What “garbage” actually means

Lesson 03 established that every object lives on the heap, and that a variable holds a reference — an arrow to the object, not the object itself. Nothing in your code ever frees an object. So somebody has to work out which objects are finished with. That somebody is the garbage collector (GC): the part of the JVM that finds objects the program can no longer use and reclaims their memory.

But what does “can no longer use” mean, precisely? Before the real answer, here is the obvious one — and why it fails.

What goes wrong with the obvious answer. The natural first idea is to count arrows: give each object a counter of how many references point at it, add one whenever a reference is created, subtract one whenever a reference goes away, and free the object when its counter reaches zero. This is called reference counting, and some languages really use it. Now run this through it:

Node a = new Node();
Node b = new Node();
a.next = b;          // b's counter: 2 (from the variable b, and from a.next)
b.next = a;          // a's counter: 2 (from the variable a, and from b.next)
a = null;            // a's counter: 1 (b.next still points at it)
b = null;            // b's counter: 1 (a.next still points at it)
// Nothing in the program can reach either node ever again -
// but both counters are stuck at 1. Under counting, they are never freed.

Two objects pointing at each other — a cycle — keep each other's counters above zero forever. Real data is full of cycles: a parent that lists its children while each child points back at its parent; a doubly linked list; a listener that holds the object it listens to. Counting leaks every one of them.

The real rule: reachability. Java asks a different question. Instead of “does anything point at this object?” it asks: “can the running program reach this object by following arrows from somewhere it is certainly using?” Those starting points — the places the program is certainly using right now — are called GC roots. The main ones are:

  • Local variables in every live frame, on every thread's stack (Lesson 03's frames). A method that is still running is still using its variables.
  • Static fields of every loaded class. A static field lives as long as its class, which for a normal application is the whole run.
  • The running threads themselves, plus a few things the JVM holds internally — for example references held by native code. You will rarely need to think about those.

An object is reachable if there is a chain of references leading to it from at least one root. Everything else is garbage, however many arrows point at it from other garbage. In the example above, once a and b are both null, no root leads to either node, so both are garbage — the cycle makes no difference at all. A collector that works by following arrows from the roots is called a tracing collector, and every collector in HotSpot is one.

An object is referenced by ten other objects. Can it be garbage?
Yes. If none of those ten objects can be reached from a root, then neither can it, and all eleven are garbage together. The number of arrows pointing at an object says nothing; only whether a path from a root exists matters.

3.2 How objects become unreachable — and how Java programs still leak

An object stops being reachable when the last path to it from a root is cut. In everyday code that happens in four ways:

  • A method returns. Its frame is popped, so its local variables stop being roots. This is the most common way by far — every temporary object made inside a method becomes garbage the moment the method finishes, unless it was returned or stored somewhere. (The list made inside replace in Lesson 03's challenge died exactly this way.)
  • A variable is overwritten — set to null, or pointed at a different object.
  • An object is removed from a collection, so the list or map no longer points at it.
  • The object that pointed at it becomes unreachable itself — everything hanging off a garbage object is garbage too.

Now the pain from Section 1. What goes wrong when you trust the collector to read your mind:

public final class PriceService {
    // A static field is a GC root. Everything this map reaches stays alive
    // for as long as the class is loaded - which is the whole run.
    private static final Map<String, Quote> CACHE = new HashMap<>();

    Quote quote(String requestId) {
        Quote q = calculate(requestId);
        CACHE.put(requestId, q);   // one entry per request, never removed
        return q;
    }
}
// PREDICTED symptom, hours later:
java.lang.OutOfMemoryError: Java heap space

Every request ID is unique, so the cache never helps anyone — but every Quote stays reachable through root → static field → map → entry → Quote, and the collector must keep it. That is what a memory leak is in Java: not an object the collector forgot, but an object the program no longer needs that is still reachable. The collector cannot know you will never ask for request #41,207 again; it only knows you still can. The cure is always the same — cut the path: remove entries you no longer need, bound the cache's size, or use a structure designed to forget (Section 5).

Eligible is not collected. Cutting the last path makes an object eligible for collection. It does not collect it, and it does not hand memory back to the operating system. The collector runs when it decides — usually when the area new objects are made in fills up (Section 3.5). That is the whole answer to Lesson 03's 8 MB mystery: the chunks became garbage the moment the list was cleared, but they sat in the heap, still counted in used, until the next collection happened to run. System.gc() asks for a collection; the JVM is allowed to ignore the request, and the flag -XX:+DisableExplicitGC makes HotSpot ignore it on purpose.

A method creates a 10 MB array in a local variable, uses it, and returns. When does the array become garbage, and when is it collected?
It becomes garbage when the method returns: the frame is popped, the local variable stops being a root, and no other path leads to the array. It is collected whenever the collector next runs — possibly milliseconds later, possibly much later. Between those two moments it still occupies heap and still shows in the used figure.

3.3 How a collector actually finds the garbage

Every HotSpot collector does two jobs. First it finds the live objects, then it reclaims the rest.

Finding: marking. The collector starts at every root and follows every reference, setting a flag on each object it reaches (“this one is alive”). It follows the references inside those objects in turn, and keeps going until there is nothing new to reach. This walk is called marking. Anything left unmarked at the end is garbage. Notice what marking costs: its work is proportional to the number of live objects, because those are the only ones it visits. The garbage is never looked at.

There is a catch. If your program kept running while the collector walked, it could move a reference from an unvisited object into an already-visited one, and the collector would wrongly decide a live object was garbage. The simplest fix is to pause every application thread while the walk happens. A pause in which all your code stops so the collector can work is called a stop-the-world pause — the freeze from Section 1. Modern collectors do much of their work while your code runs, using clever bookkeeping to stay correct, and keep the stop-the-world parts short. Lesson 05 compares how each collector does that.

Reclaiming: three strategies. Once the live objects are known, the collector has three basic ways to recover the rest:

  • Sweep: walk the heap and add every dead object's space to a list of free gaps. Simple, but the free memory ends up scattered in small holes between live objects. Splitting free memory into pieces too small to use is called fragmentation, and it can mean a large array fails to fit even though plenty of memory is free in total.
  • Compact: slide all the live objects together at one end, so the free space becomes one solid block. No fragmentation, but every moved object's references must be updated.
  • Copy: copy every live object into a separate, empty area, then treat the entire old area as free in one step. Called copying collection. It needs spare space to copy into, but it has a wonderful property: its cost depends only on how much is alive. If almost everything is dead, there is almost nothing to copy, and wiping the old area costs nothing.

Keep that last property in mind. It is exactly what the next idea exploits.

3.4 The generational hypothesis: most objects die young

What goes wrong without generations. Imagine a collector that marks the entire heap every time. Your application holds 3 GB of long-lived data — caches, configuration, loaded reference tables — and creates temporary objects at a furious rate. Every collection walks all 3 GB of live data just to rediscover that it is still alive, in order to clear away a few hundred megabytes of temporaries. The bigger your heap, the longer every single collection takes, even though the long-lived data never changes.

Engineers who measured real programs noticed a pattern that holds almost everywhere: most objects die very young. Think of what a typical method creates — a StringBuilder to build a message, an iterator to walk a list, boxed Integers, a request object that lives for one web request. Almost all of it is garbage within microseconds or milliseconds. The few objects that survive a while tend to survive a long time. This observation is called the generational hypothesis (in its usual form, the weak generational hypothesis). It is called a hypothesis because it is a bet about how programs behave, not a law — but it is a bet that pays off for the overwhelming majority of real Java code.

The cure follows directly. Keep new objects in their own small area and collect that area often. Because almost everything in it is dead, a copying collection there is very cheap, and it never needs to walk the long-lived data at all. Move the rare survivors somewhere else, and collect that somewhere-else rarely. An area holding objects of roughly the same age is called a generation. HotSpot uses two: the young generation and the old generation.

3.5 The young generation: Eden, two survivor spaces, and growing old

The young generation is itself split into three parts.

Eden is where (almost) every new object is created. Creating an object there is remarkably cheap. Eden is one block of empty memory with a pointer marking where the free part begins; making a new object means handing out the next N bytes and moving the pointer forward by N. That is called bump-the-pointer allocation. To stop threads queueing for that one pointer, each thread is handed its own private slice of Eden to bump through, called a TLAB (thread-local allocation buffer), so most allocations need no coordination with other threads at all. This is why new in Java is far cheaper than many people assume.

Two survivor spaces, usually called S0 and S1 (or “from” and “to”), are small, equal areas beside Eden. At any moment one of them holds objects that survived earlier collections and the other is empty, waiting.

When Eden fills up, the JVM runs a collection of the young generation only. That is called a minor GC, and it goes like this:

  1. All application threads pause (a short stop-the-world pause — short because the young generation is small and mostly dead).
  2. Starting from the roots, the collector finds every live object in Eden and in the occupied survivor space.
  3. It copies each of those live objects into the empty survivor space, and adds one to each copied object's age — the number of collections it has survived, kept in a few bits of the object's header.
  4. Eden and the old survivor space now contain nothing but garbage, so both are declared empty in one step. Nothing is swept, and the garbage is never looked at.
  5. The two survivor spaces swap roles: the one just filled becomes “from”, and the one just emptied becomes “to” for next time.

An object that keeps surviving keeps getting copied back and forth, one year older each time. When its age reaches a limit, the next collection copies it into the old generation instead. Moving an object from the young generation to the old one is called promotion (or tenuring), and the age limit is called the tenuring threshold. Its maximum in HotSpot is 15, because the age is stored in four bits, and it is set with -XX:MaxTenuringThreshold. The JVM may also lower the threshold on its own if the survivor space is getting too full.

Two more ways into the old generation exist, and both matter in practice. If the empty survivor space is too small for everything that survived, the overflow goes straight to the old generation, however young it is. That is called premature promotion, and it is bad news: short-lived objects end up in the area that is collected rarely and expensively. And very large objects may be created directly in the old generation, skipping the young one entirely, because copying them back and forth would be costly (G1 calls these humongous objects — Lesson 05).

One gap left to close: references that point backwards. A minor GC is supposed to look only at the young generation. But an old object can hold a reference to a young one — an old cache gets a brand-new entry, for example. If the minor GC ignored the old generation, it would miss that path and wrongly free the young object. Scanning the whole old generation every time would throw away the entire benefit. So HotSpot keeps a record instead. It divides the old generation into small fixed-size slices called cards, and every time your code stores a reference into an old object, a tiny piece of extra code the JIT adds to that store marks the slice as “dirty”. That extra code is called a write barrier, and the table of dirty marks is the card table. During a minor GC, only the dirty cards are scanned as extra roots. A small cost on every reference store buys the ability to collect the young generation alone.

Why is a minor GC usually fast even when the heap is several gigabytes?
Because it only deals with the young generation, and within it, it only touches the live objects — copying them to a survivor space. The garbage is never visited; Eden is simply declared empty afterwards. If most young objects are dead (the generational hypothesis), there is very little to copy. The old generation's size barely matters, apart from the dirty cards in the card table.

3.6 The old generation, and minor versus major versus full

The old generation (also called the tenured generation) holds promoted objects. It fills slowly, because only survivors arrive there, and when it gets full enough it must be collected too. Because it is large and mostly alive, collecting it is expensive — this is where the long pauses traditionally come from.

The vocabulary here is loose in everyday use, so here are the three terms as most people mean them:

TermWhat it collectsHow oftenCost
Minor GCthe young generation onlyoften — whenever Eden fillssmall: proportional to young survivors
Major GCthe old generationrarelylarge: the old generation is big and mostly alive
Full GCthe whole heap (young and old), often Metaspace tooideally almost neverthe largest; usually a long stop-the-world pause

Everything above describes the generations logically, and it matches the Serial collector's heap layout exactly: one contiguous Eden, two survivor spaces, one old generation. The default collector since Java 9, G1, keeps the same young and old roles but builds them from many equal-sized regions that can change role, and it collects the old generation a piece at a time alongside young collections (“mixed” collections). ZGC in Java 21 can also run generationally. How each collector really works, and how to choose between them, is Lesson 05. The rules of this lesson — reachability, die young, copy survivors, promote the old — hold for all of them.

3.8 Watching an object without keeping it alive

To prove the reachability rule from inside a Java program, we need to check on an object after a collection. But holding an ordinary reference to it would make it reachable — the act of watching would keep it alive. We need a reference that does not count.

Java provides exactly that. It is a small wrapper object that points at another object without counting toward its reachability. If the only remaining paths to an object go through wrappers like this, the collector may reclaim it, and once it does, asking the wrapper for its object returns null. This is called a weak reference, and the class is java.lang.ref.WeakReference:

Object strong = new Object();                         // an ordinary reference: keeps it alive
WeakReference<Object> watcher = new WeakReference<>(strong);  // watches, does not keep alive

watcher.get();     // the object - while something strong still reaches it
// ... after the last strong path is cut AND a collection has run ...
watcher.get();     // null

One subtlety turns up the moment you use this, and it surprises nearly everyone. You might think strong keeps its object alive until the end of the block it was declared in. Not necessarily. Scope — where a variable's name is valid in the source — is a compile-time idea. Reachability is decided while the program runs, and the JIT is allowed to notice that strong is never used again after a certain line, and to treat it as dead from that point on, even though it is still in scope. For almost all code this changes nothing you could observe. When you are deliberately watching an object, it can make the object vanish early. The fix is Reference.reachabilityFence(strong) (Java 9 and later): a call that does nothing except promise the JVM that the object stays reachable up to that line. The project uses it everywhere it watches an object.

4 Applied to jvm-explorer

The project gains a new package, gc, that proves the reachability rule by observation, reads the collector's own counters, and makes real objects age and get promoted.

4.1 What happens, step by step, when the new code runs

  1. JvmExplorer.main runs its Lesson 00–03 sections as before, then calls ReachabilityProbe.describe().
  2. Reachable: the probe makes an object, holds it in a local variable (a root) and watches it through a WeakReference. It requests two collections. The object must survive, and reachabilityFence guarantees the local really counts until the check.
  3. Unreachable: it makes an object that only a weak reference points at — garbage from birth — and requests collections until get() returns null.
  4. A cycle: it builds two Nodes pointing at each other, watches both, then sets both local variables to null. The pair still point at each other, but no root reaches them, so both are reclaimed. A reference-counting collector would keep them forever.
  5. A leak: it puts an object in a static list, drops its own local reference, and requests collections. The static field is a root, so the object must survive. Then it clears the list.
  6. AllocationPatterns.churnUntilCollection reads the collectors' combined total, then makes 64 KB arrays, each one replacing the last in a volatile static field. That turns the previous array into garbage, and also forces the allocation to really happen. After each allocation it re-reads the total. Eden fills, a minor GC runs, the total goes up, and the loop stops and reports how much garbage that took.
  7. GcStats.describe() prints each collector's name, count and total time, and how many kilobytes Eden, the survivor space and the old generation currently hold.

4.3 Proving the rule: the cycle

public static boolean unreachableCycleIsCollected() {
    Node first = new Node();
    Node second = new Node();

    // The cycle: a collector that counted incoming arrows would see 1 for each, forever.
    first.next = second;
    second.next = first;

    WeakReference<Node> watchFirst = new WeakReference<>(first);
    WeakReference<Node> watchSecond = new WeakReference<>(second);

    // Cut the only paths from a root. The nodes still point at each other.
    first = null;
    second = null;

    // Tracing starts at the roots, never reaches the pair, and reclaims both.
    return requestGcUntilCleared(watchFirst, DEFAULT_GC_ATTEMPTS)
            && requestGcUntilCleared(watchSecond, DEFAULT_GC_ATTEMPTS);
}

4.4 Forcing a collection without System.gc()

// Every short-lived object is written here, then overwritten by the next one.
// Escaping into a field stops the JIT optimising the allocation away (Lesson 06).
private static volatile Object sink;

public static long churnUntilCollection(int objectBytes, long capBytes) {
    long before = GcStats.totalCollectionCount();
    long allocated = 0;
    while (allocated < capBytes) {
        sink = new byte[objectBytes];              // the previous array is garbage now
        allocated += objectBytes;
        if (GcStats.totalCollectionCount() > before) {
            sink = null;
            return allocated;                     // Eden filled; a collection ran
        }
    }
    sink = null;
    return -1;                                    // no collection within the cap
}

Why is a collection guaranteed before the cap? The cap is four times the heap's ceiling, and garbage beyond the ceiling has nowhere to go — the JVM must collect to make room. In practice the first minor GC arrives as soon as Eden fills, long before that.

4.5 The tests

The test file for the probe states plainly that its claims are not all equally strong. “A reachable object is never collected” is a guarantee of the Java specification, so those tests cannot fail on a correct JVM. “An unreachable object is collected” is not guaranteed, because System.gc() is only a request. Those tests rely on HotSpot honouring it, which it does by default.

// GUARANTEED: a static field is a root, so whatever it reaches stays alive.
@Test
void anObjectHeldByAStaticFieldIsNeverCollected() {
    assertTrue(ReachabilityProbe.objectHeldByStaticFieldSurvives(), /* … */);
}

// RELIES ON System.gc() being honoured: a cycle reachable from no root is garbage.
// This is the test a reference-counting collector would fail.
@Test
void anUnreachableCycleIsCollected() {
    assertTrue(ReachabilityProbe.unreachableCycleIsCollected(),
            "... If this fails, check that -XX:+DisableExplicitGC is not set.");
}

// GUARANTEED by logic: garbage beyond the heap ceiling must force a collection.
@Test
void enoughGarbageAlwaysForcesACollection() {
    long before = GcStats.totalCollectionCount();
    long garbage = AllocationPatterns.churnUntilCollection(
            AllocationPatterns.DEFAULT_OBJECT_BYTES, AllocationPatterns.safeCapBytes());
    assertTrue(garbage > 0, /* … */);
    assertTrue(GcStats.totalCollectionCount() > before, /* … */);
}

No test asserts when promotion happens, how many collections have run, or how big any generation is. Those depend on the collector, the machine and everything that ran earlier in the same test JVM — they are observations for your terminal, not facts for a test.

Read it as a story. Our 1 MB of kept objects was created in Eden. Collection 1 copies it into a survivor space at age 1; collections 2 and 3 copy it across again at ages 2 and 3. At collection 4 the objects have reached the threshold, so they are copied into the old generation instead — survivor drops, old jumps by about 1 MB, in one step. After that the old generation stays flat, because minor GCs never touch it. The small amounts left in survivor are the last garbage array that happened to be reachable when each collection ran, plus a few JDK objects.

To see the JVM's own account of the same events, add two logging switches (unified logging, Java 9 and later). gc prints one line per collection, and gc+age=trace prints the age table each time:

5 In the wild

The JDK ships a map built on weak references: java.util.WeakHashMap. Its keys are held weakly. When nothing else in the program references a key any more, the collector may reclaim it, and the map quietly drops that entry. It is a cache that forgets on its own — exactly the cure for Section 3.2's leak, in the right situations. A classic use is attaching extra data to objects you do not own, without keeping those objects alive.

It also has a famous trap, and the trap is pure reachability. If a value holds a reference back to its own key, the entry never disappears: the map holds the value strongly, the value holds the key strongly, so the key is always reachable — through the map itself.

Map<Customer, Report> reports = new WeakHashMap<>();
reports.put(customer, new Report(customer));  // the Report points back at its key...
// ...so this entry is never removed, however unused customer becomes. A leak.

In production, GC tuning starts with two questions that come straight from this lesson. How fast is the program allocating? That decides how often Eden fills, and so how often minor GCs run. How much survives? That decides how much each minor GC costs, and how fast the old generation fills. A service whose old generation climbs steadily and never comes back down after full GCs has a leak — something reachable that should not be. A service whose old generation fills fast but drops back after each full GC is suffering from premature promotion, and needs a bigger young generation, not a bigger heap. Telling those two apart in an interview, from a description of a memory graph, is a strong signal.

6 Gotchas and common mistakes

  • Calling System.gc() to “free memory”. People reach for it because a memory graph did not drop after a release. It is a request the JVM may ignore, and on HotSpot's default settings it triggers a full GC — the most expensive kind, with a long pause — in the middle of your traffic. Avoid it: never call it in application code. If memory is not reclaimed, the question is “what still reaches it?”, not “how do I force the collector?”
  • Believing Java cannot leak. The collector only frees what is unreachable, so anything still reachable stays — however useless. The usual culprits are static collections, caches with no size limit, listeners that are registered and never removed, and ThreadLocal values on pooled threads that live forever. Avoid it: for every long-lived collection, know what removes entries from it.
  • Keeping an outer object alive by accident with an inner class or lambda. A non-static inner class, an anonymous class, and a lambda that uses any instance field or method all carry a hidden reference to the enclosing this. Register one as a long-lived listener, and the entire outer object — with everything it references — stays reachable for as long as the listener does. Avoid it: make nested classes static unless they truly need the outer object, and unregister listeners when their owner is done.
  • Relying on finalize() to clean up. A finalize() method was meant to run when an object became garbage, but it runs at an unpredictable time or not at all, slows the collector, and can even bring a dead object back to life. It was deprecated for removal in Java 18 (JEP 421). Avoid it: release files, sockets and locks with try-with-resources (Lesson 01), and use java.lang.ref.Cleaner only as a last-resort safety net.
  • Assuming an object lives until the end of its variable's scope. Scope is a compile-time idea. The JIT may treat a variable as dead after its last use, so the object can become collectable earlier than the closing brace. This only matters when you are watching objects (weak references) or when an object guards something outside the heap. Avoid it: use Reference.reachabilityFence(obj) to keep an object reachable up to an exact line.

7 Key takeaways

  • An object is garbage when no chain of references leads to it from a GC root — a local variable in a live frame, a static field, or a running thread — so unreachable cycles are garbage too, which is why Java traces from the roots instead of counting references.
  • A Java memory leak is an object the program no longer needs that is still reachable, usually through a static collection, an unbounded cache or a forgotten listener, and the cure is always to cut the path.
  • Cutting the last path makes an object eligible for collection, not collected; the collector runs when it decides, and System.gc() is only a request.
  • Because most objects die young, HotSpot allocates new objects in Eden and collects the young generation often with a copying collection, whose cost depends only on how much survives — the garbage is never even looked at.
  • Each survival raises an object's age, and at the tenuring threshold it is promoted to the old generation, which is collected rarely and expensively; minor GCs never reclaim anything in the old generation.

Part A — which objects are garbage? At the line marked // HERE, decide for each of the objects A to F whether it is reachable or garbage, and say why.

public class Puzzle {
    static List<Object> registry = new ArrayList<>();

    static class Box { Object item; }

    public static void main(String[] args) {
        Box a = new Box();          // object A
        a.item = new Object();       // object B

        Box c = new Box();          // object C
        Box d = new Box();          // object D
        c.item = d;
        d.item = c;
        c = null;
        d = null;

        registry.add(new Object());  // object E

        helper();                    // creates object F inside, and returns nothing

        a.item = null;
        // HERE
        System.out.println(a);
    }

    static void helper() {
        Object f = new Object();    // object F
    }
}

Part B — read two memory graphs. Two services each have a steadily climbing old generation. In service 1, every full GC brings the old generation back down to about 400 MB, then it climbs again. In service 2, every full GC brings it down a little less than the time before — 400 MB, then 550, then 700. Which one is leaking, what is the other one's problem, and what would you change for each?

Part C — check yourself on the machine. Run the generations experiment with -XX:MaxTenuringThreshold=1 and predict the round of the jump before you look. Then predict what happens if you shrink the young generation until the survivor space is smaller than 1 MB, with -Xmn8m (each survivor space then about 0.8 MB). Run it and see.

Part A.

  • A — reachable. The local variable a is in main's live frame, so it is a root, and it points at A. (It is also used on the next line, so even the JIT cannot treat it as dead.)
  • B — garbage. Its only path was a.item, and a.item = null cut it.
  • C and D — garbage. They point at each other, but both local variables were set to null, so no root reaches either one. The cycle is irrelevant — this is exactly the case reference counting gets wrong.
  • E — reachable. registry is a static field, so it is a root; the list it points at holds E. This is the shape of a leak: E will stay for the whole run unless something removes it.
  • F — garbage. Its only reference was the local variable f in helper's frame, and that frame was popped when helper returned.

Remember the difference between garbage and collected: B, C, D and F are eligible at // HERE, but they will only be reclaimed when a collection next runs. They were all created in Eden, so the next minor GC reclaims them without looking at them.

Part B. Service 2 is leaking. The level a full GC returns to is the amount of live data, and it keeps rising — something reachable keeps growing. More heap only delays the OutOfMemoryError; the fix is to find what still reaches the growing objects (a heap dump, Lesson 07) and cut the path. Service 1 is not leaking: its live data is a stable 400 MB. Its old generation keeps filling with objects that die soon after arriving — the signature of premature promotion, where short-lived objects get pushed out of a young generation that is too small, or survivor spaces that overflow. The fix is a larger young generation (or survivor spaces), so those objects die young where they are cheap to collect.

Part C. With MaxTenuringThreshold=1, the kept objects go into a survivor space at age 1 on the first collection and are promoted on the second, so the predicted jump is at round 2. With -Xmn8m, 1 MB of survivors cannot fit in a survivor space of about 0.8 MB, so the overflow is promoted prematurely at round 1, whatever the threshold — survivor stays low and old jumps immediately. That is premature promotion, caused on purpose. (The JVM may also lower the threshold on its own when survivors crowd the space, which pushes in the same direction.)
