Lesson 03 — Runtime Memory Areas

Where a running program actually puts things: the per-thread stack of frames, the one shared heap of objects, and the Metaspace full of class descriptions — plus the two walls the JVM hits when either runs out.

Position: Lesson 03 of 07  ·  Prerequisites: Lesson 01, Lesson 02  ·  Project files: memory/HeapSnapshot.java, memory/MemoryRegions.java, memory/StackDepthProbe.java, memory/HeapFiller.java, memory/ReferenceDemo.java, experiments/MemoryLimitsExperiment.java, JvmExplorer.java (modified), and five test classes

1 The pain

Here is a bug that has cost more hours than it has any right to. A method is supposed to fill in a customer's address, and half of it silently vanishes.

void enrich(Customer c) {
    c.setCity("Berlin");       // the caller DOES see this
    c = new Customer();        // from here on, the caller sees NOTHING
    c.setCountry("Germany");   // lost, silently, every time
}

The city arrives. The country does not. No exception, no warning, no log line — just a field that is stubbornly null in production. People explain it to each other with half-remembered phrases: “Java is pass-by-reference, except sometimes.” It is not, and there is no sometimes. There is one rule, it is simple, and it is a rule about where things live — which is exactly what this lesson is about.

The second pain arrives at 3 a.m. as a one-line email: java.lang.OutOfMemoryError: Java heap space. Somebody suggests adding RAM to the server. Somebody else suggests -Xmx8g. Nobody can say what the heap is, so nobody can say whether either suggestion is a fix or just a way to make the same crash take longer to arrive. Worse, next week's reads OutOfMemoryError: Metaspace — a different region, with a different cause, that more heap cannot help at all. Those words are not interchangeable, and treating them as “the memory error” is how teams end up restarting a server nightly for two years.

The third pain is a stack trace a thousand lines long, all the same line. StackOverflowError, then at com.acme.Node.total(Node.java:41) repeated until the console gives up. It is not an OutOfMemoryError, even though something clearly ran out of space. It does not involve the heap, even though everyone's first instinct is to raise -Xmx. The dial that actually moves it is a flag most developers have never typed. By the end of this lesson your project will report every region the JVM is using, walk up to both walls on purpose, and read the sign on each one.

2 Real-world analogy

Picture a furniture workshop. Three places hold things, and each has its own rules.

The workbench is where one carpenter does the job in front of them: the measurements for this cut, a pencil, the piece in progress. When a job needs a sub-job — “first make the drawer” — a fresh tray of notes and tools is stacked on the bench, used, and lifted off the instant the drawer is done. Everything on that tray goes with it. The bench is narrow: stack too many trays and the pile topples.

The warehouse out the back holds the finished pieces: tables, chairs, drawers. It is large, it is shared by every carpenter in the shop, and nothing is thrown out just because one carpenter finished a job. What a carpenter keeps on the bench is not the table — it is a docket with a shelf number written on it. Two carpenters can hold dockets bearing the same shelf number, and then they are both talking about one table.

The blueprint cabinet in the office holds one drawing per kind of furniture: what a “chair” is, how many legs it has, how to assemble one. There is exactly one chair blueprint no matter how many chairs exist. Nobody sits on a blueprint; you build from it.

Now re-read the bug from Section 1 with dockets in mind. enrich was handed a photocopy of the docket. Writing on the table that the docket names — setCity — changes the real table in the warehouse, and everybody sees it. Throwing the photocopy away and writing a different shelf number on it — c = new Customer() — changes nothing about the caller's docket, which is still in the caller's hand with the original number on it. One rule, two outcomes, no exceptions.

3 The concept explained

We build the map in dependency order: what a running program must keep somewhere, the per-thread stack, the shared heap, the one rule that connects them, where the classes from Lesson 02 ended up, the smaller regions nobody mentions, and finally what happens when each region fills.

3.1 Two kinds of memory, because there are two kinds of question

A running program constantly answers two different questions, and they want opposite things from memory.

The first is “where am I in the work?” — which method is running, what were its arguments, what is the value of its loop counter right now, and where do I return to when I finish. This information has a perfectly predictable lifetime: it is born when a method is called and dies when that method returns, in exactly reverse order. Nothing needs to be searched for and nothing needs to be cleaned up later. That question is answered by the stack.

The second is “what data exists?” — the customer object, the list of orders, the string you built. This has an unpredictable lifetime: an object created inside a method may be returned, stored in a field, handed to another thread, and still be in use an hour later. Nothing about the method's return tells you whether the object is finished with. That question is answered by the heap.

Because the lifetimes differ, the management differs. Stack memory is reclaimed for free and instantly, by arithmetic. Heap memory needs someone to work out what is still wanted — which is garbage collection, the subject of Lessons 04 and 05. Every memory decision in Java flows from this split.

Here is the whole map before we take it apart. Notice what is per-thread and what is shared, because that single distinction explains most of the rules that follow.

3.2 The stack: one pile of frames per thread

A thread is one independent line of execution — one worker carrying out instructions in order. A plain Java program starts with one, called main, and may create more. Every thread gets its own stack: a region of memory it alone can touch, used as a pile.

Each time the thread calls a method, the JVM pushes a new frame onto that pile. A frame is a small block of working space belonging to exactly one in-progress method call, and it holds three things:

  • the local variable table — the numbered slots holding the method's parameters and local variables. You met these in Lesson 01: your variable names became slot numbers at compile time, with slot 0 being this in an instance method;
  • the operand stack — the scratch space where bytecode instructions push and pop the values they are working on, also from Lesson 01;
  • the return address — where to carry on in the calling method once this one finishes.

When the method returns, the frame is popped: the pointer marking the top of the stack simply moves back down, and every local variable in that frame is gone. No search, no bookkeeping, no collector. That is why stack memory costs essentially nothing to reclaim — it is one subtraction.

Two consequences follow immediately and are worth saying out loud.

Local variables are automatically thread-safe. Not by luck and not by a rule someone enforces: a local variable lives in a frame, a frame lives on one thread's stack, and no other thread can reach that stack. Two threads running the same method at the same time each have their own frame, their own slots, their own values.

The pile has a fixed size. It is chosen when the thread is created, and it does not grow on demand. So a chain of calls that never returns must eventually run out of room — which is the StackOverflowError of Section 3.7.

Two threads run the same method, which declares int total = 0;. How many total variables exist?
Two — one per frame, one frame per thread, each on its own stack. Neither thread can see or corrupt the other's copy. This is why local variables never need synchronized, and it is the reason the standard advice “keep state local” actually works rather than merely sounding tidy.

3.3 The heap: one shared pool of objects

The heap is a single region shared by every thread in the JVM, and it holds exactly one kind of thing: objects. Every object created with new goes there. So does every array, because in Java an array is an object. So does every string literal, and every object the JDK creates on your behalf.

Why the name? “Heap” here is an old programming word for a pool of memory you can take pieces from in any order and give back in any order — a heap of material to cut from, as opposed to a neat pile. (It has nothing to do with the heap data structure used in priority queues, which is an unrelated use of the same word. Two meanings, one word, permanent confusion.)

Three properties of the heap decide almost everything in the rest of this course:

  • It is shared. Any thread holding a reference to an object can read and write it, which is why object state — unlike local variables — needs thinking about when threads are involved.
  • It has a ceiling. The JVM may grow the heap up to a maximum, set by -Xmx or chosen for you from the machine's RAM. Hitting that ceiling with nothing reclaimable left is OutOfMemoryError: Java heap space.
  • It is cleaned by the garbage collector. Nothing on the heap is freed by your code. An object survives exactly as long as some chain of references can reach it, and the collector reclaims the rest at times of its own choosing. That is Lesson 04.

“Every object lives on the heap” is the right model to hold, and there is one honest footnote: if the JIT compiler can prove that an object never escapes the method that created it, it may skip the heap allocation entirely and keep the object's fields in registers or in the frame. This is called escape analysis, it is an optimisation you cannot observe from Java, and it never changes program behaviour. Lesson 06 covers it. Until then: heap.

3.4 The one rule: a variable is an arrow, not an object

This is the section that pays for the whole lesson, so we start with the pain rather than the rule.

What goes wrong without this. Here is the naive model almost everyone starts with — that a variable contains its object, the way a box contains a thing:

StringBuilder a = new StringBuilder("hello");
StringBuilder b = a;                // naive model: "b is a copy of a"
b.append(" world");                // naive model: "only b changes"
System.out.println(a);            // naive model predicts: hello

It prints hello world. The naive model is not slightly off; it predicts the opposite. And the same wrong model produces the Section 1 bug, the “why did my list change when I only changed the other list” bug, and the “I passed a copy, didn't I?” bug. One correction fixes all three.

The rule. A variable whose type is a class, an interface or an array does not hold the object. It holds a reference: a value that identifies where the object lives on the heap. Think of it as an arrow, or the docket from Section 2. Assignment copies the arrow, never the object. Two arrows can point at one object.

Primitive types work differently and that difference is the whole contrast: there are exactly eight of them — byte, short, int, long, float, double, char, boolean — and a variable of a primitive type holds the value itself, right there in the frame's slot. No arrow, no heap, nothing shared.

Now the method-argument rule, which is just the same fact applied once more. Java is always pass-by-value: the callee gets a copy of what the caller had. For an int, that is a copy of the number. For an object type, that is a copy of the arrow — pointing at the very same object.

void mutate(StringBuilder text) {
    text.append("!");                       // follows the arrow → the caller's object changes
}

void reassign(StringBuilder text) {
    text = new StringBuilder("other");      // overwrites THIS frame's slot only
    text.append("!");                       // changes an object nobody else can reach
}

Both methods look like they modify the argument. mutate modifies the object; reassign modifies the variable. Only the first survives the return, because the object is on the shared heap and the variable is in a frame that is about to be destroyed. That is the entire explanation of the Section 1 bug, and there is nothing else to it.

The phrase to retire for good: “Java passes objects by reference.” It is wrong, and it is wrong in a way that predicts the Section 1 bug incorrectly. Java passes references by value. Every argument, always, is copied — it is just that copying an arrow gives you a second arrow to the same thing.

After int[] a = {1,2,3}; int[] b = a; b[0] = 99; — what is a[0]?
99. An array is an object, so b = a copied the arrow, not the array. There is one array on the heap with two names. To get a genuinely separate array you must make one: int[] b = a.clone(); or Arrays.copyOf(a, a.length).

3.5 Metaspace, and what happened to PermGen

Lesson 02 watched hundreds of classes load. Each one left something behind: a description of the class — its name, its superclass, its field layout, its method table, its constant pool, and the bytecode of each method. That description is not an object on the heap. It is the blueprint from Section 2, and since Java 8 it lives in a region called Metaspace.

One description per class, however many instances exist. A million Customer objects sit on the heap; the single description of what a Customer is sits in Metaspace.

What goes wrong without this distinction. Before Java 8, class descriptions lived in a heap region called the permanent generation (“PermGen”), and it had a fixed maximum size set by -XX:MaxPermSize, defaulting to something small like 64 MB. Redeploy a web application a few times without restarting the server, and each redeploy created a new class loader defining a new copy of every class — the class loader leak from Lesson 02. PermGen filled up and the server died with:

java.lang.OutOfMemoryError: PermGen space

Java 8 removed PermGen entirely. Metaspace replaced it and is allocated from native memory — the memory the JVM requests directly from the operating system, outside the Java heap — and by default it is unbounded: it grows as long as the OS will supply memory. That trades a common, baffling crash for a rarer one: a genuine class-loader leak now consumes machine memory instead of hitting a small ceiling. You can restore a ceiling deliberately with -XX:MaxMetaspaceSize, and many teams do exactly that so a leak announces itself as OutOfMemoryError: Metaspace rather than as a server that slowly eats the machine.

Two related moves often get mixed up with this one. Interned strings — the pool behind string literals — moved out of PermGen and onto the ordinary heap in Java 7, one release before PermGen itself was removed. And -XX:MaxPermSize on Java 8 or later is not an error you will notice: the JVM ignores it with a warning, which is why a startup script can carry it for years unquestioned.

For learning only: a detail worth knowing but not worth relying on. In HotSpot, a class's static fields are not stored in Metaspace with the rest of the description — they live in the java.lang.Class object for that class, which is on the heap. So “class metadata is in Metaspace, static data is on the heap” is the accurate split for HotSpot today. This is an implementation choice, not a specification requirement; treat it as a fact about the JVM you are running, marked to verify against your JDK's documentation if it ever matters.

3.6 The regions nobody mentions

Three more areas exist, and knowing their names turns three otherwise baffling error messages into readable ones.

The PC register. One per thread. “PC” stands for program counter, and it holds the address of the bytecode instruction that thread is executing right now. It is tiny and you will never interact with it — but it is what makes “each thread has its own place in the program” true.

The native method stack. One per thread, alongside the Java stack. When Java code calls into code written in C or C++ — which the JDK does constantly, for file access, networking and timing — those calls need their own frames, in the form the C compiler expects. That is what this is.

The code cache. Shared. When the JIT compiler turns a hot method into native machine code (Lesson 01, in depth in Lesson 06), the machine code has to live somewhere. It lives here. If this region fills, the JVM prints CodeCache is full. Compiler has been disabled and the application keeps running — correctly, but interpreted and therefore slow. An application that mysteriously loses performance hours into a run, with no code change and no GC problem, is the classic sighting.

And one non-region worth naming because it accounts for memory that no heap tool will show you: direct (off-heap) buffers, created by ByteBuffer.allocateDirect and used heavily by networking and I/O libraries. The bytes live in native memory; only a small Java object on the heap points at them. A process whose memory use far exceeds its heap, with a healthy-looking heap graph, is usually holding direct buffers — and exhausting them gives a third distinct message, OutOfMemoryError: Direct buffer memory.

3.7 The two walls

Each region has a limit, and the JVM says something different at each one. Confusing them is the single most expensive mistake in this lesson.

Wall one: the stack runs out of frames. A thread's stack has a fixed size — typically around 512 KB to 1 MB on a 64-bit JVM, set by -Xss, and genuinely machine-dependent. Every call pushes a frame; nothing pops until a method returns. Recursion without a working base case therefore has exactly one possible ending:

int total(Node n) {
    return n.value + total(n.next);   // no base case: never returns, always pushes
}
Exception in thread "main" java.lang.StackOverflowError
        at com.acme.Node.total(Node.java:41)
        at com.acme.Node.total(Node.java:41)
        at com.acme.Node.total(Node.java:41)
        ... the same line, roughly a thousand more times

Reading it: the repeated line is the diagnosis. If one method repeats, you have runaway recursion — find the missing base case. If a short group of methods repeats in a cycle (a → b → c → a), you have mutual recursion, often through a framework: two objects whose toString methods call each other, or a JPA entity graph with a cycle in it. If the trace shows a thousand different frames, the recursion is legitimate and too deep for the stack, and your options are a bigger -Xss or rewriting the algorithm with an explicit list instead of the call stack.

-Xss is per thread, not global. Doubling it on a server with 500 threads asks the OS for an extra 500 × the increase. Raising it is a real fix for genuinely deep recursion and a terrible fix for a missing base case — that one just takes longer to crash.

Wall two: the heap has no reclaimable space left. Note the careful wording. Running out of heap does not mean “you allocated a lot”; a program can allocate a terabyte in a 32 MB heap quite happily, as long as it stops using each piece. The error arrives only when the collector cannot find anything to reclaim and the ceiling has been reached — which means something is still holding on:

Exception in thread "main" java.lang.OutOfMemoryError: Java heap space

The words after the colon are the whole message. They name the region, and the region names the investigation:

The two errors are not both “memory errors” in any useful sense. StackOverflowError is about one thread's fixed working space and is usually a logic bug; OutOfMemoryError: Java heap space is about shared object storage and is usually a retention bug. They are also both Error, not Exception — the JVM's way of saying “do not plan to recover from this.” The project's probes catch them anyway, deliberately and in a controlled way, which Section 4 explains carefully.

4.2 Reading the regions

Two different doors lead to the same house. Runtime has answered heap questions since Java 1.0 and needs nothing extra. The management API — a set of objects the JVM keeps about itself, reachable through ManagementFactory — answers finer questions, including which named memory pools exist. We use both.

public static HeapSnapshot heapSnapshot() {
    Runtime runtime = Runtime.getRuntime();

    // The ceiling -Xmx sets, or a default derived from the machine's RAM.
    long max = runtime.maxMemory();

    // What the JVM has actually taken from the OS so far. Read BEFORE freeMemory()
    // so the two readings are as close together in time as we can make them.
    long committed = runtime.totalMemory();
    long free = runtime.freeMemory();

    // used = committed - free, clamped: a garbage collection landing between the
    // two calls could otherwise produce a negative number. A reporting method
    // should never be the thing that throws.
    long used = Math.min(committed, Math.max(0L, committed - free));

    return new HeapSnapshot(max, committed, used);
}

Metaspace needs the other door, and needs care: “Metaspace” is a HotSpot pool name, not something the Java specification promises. So the method searches the pools by name and returns OptionalLong — “a number, or nothing” — rather than inventing -1 as a secret code for absent:

public static OptionalLong metaspaceUsedBytes() {
    // The pool list differs by JVM, by collector and by version, which is exactly
    // why we search it by name instead of indexing into it.
    for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans()) {
        if (METASPACE_POOL_NAME.equals(pool.getName())) {
            MemoryUsage usage = pool.getUsage();
            if (usage != null) {
                return OptionalLong.of(usage.getUsed());
            }
        }
    }
    // Empty means "this JVM did not offer that pool" - a different statement
    // from "zero bytes are in use".
    return OptionalLong.empty();
}

4.3 Walking to wall one, on purpose

There is no API that answers “how many frames fit on my stack”. The only honest way to find out is to fall off the end and count on the way down. The probe does exactly that:

// Lives OUTSIDE the recursion, because every local variable inside it dies with
// its frame as the stack unwinds - by the time we catch the error, they are gone.
private static int deepestReached;

public static int measureMaxDepth() {
    deepestReached = 0;
    try {
        descend(1);                  // can only end by overflowing
    } catch (StackOverflowError expected) {
        lastErrorType = expected.getClass().getName();
    }
    return deepestReached;
}

private static void descend(int depth) {
    deepestReached = depth;          // record on the way DOWN - there is no way back up
    descend(depth + 1);
}

Catching an Error is normally wrong, and this is the exception that proves the rule. An Error signals a condition you are not expected to recover from, so code that swallows one usually hides a disaster. Here the overflow is the measurement, it is provoked deliberately, and by the time the catch block runs the entire recursion has unwound — so the stack is empty again and there is plenty of room to do the counting. Copying this pattern into ordinary application code is a bug; the file says so in its own comments.

4.4 Walking to wall two — carefully

Allocating is not enough to exhaust a heap. A loop that creates a million arrays and forgets each one immediately runs forever in a tiny heap, because the collector reclaims each one as fast as it appears. To fill a heap you must keep what you allocate — which is also the exact definition of a memory leak: not allocating too much, but holding on to things you no longer need.

// The list is what keeps every chunk REACHABLE, and therefore uncollectable.
// Remove this list and the method allocates nothing that survives.
List<byte[]> retained = new ArrayList<>();
long held = 0;

// Stop when one MORE chunk would exceed the budget, so we never overshoot -
// which is what makes the chunk count exactly predictable in a test.
while (held + chunkBytes <= budgetBytes) {
    retained.add(new byte[chunkBytes]);
    held += chunkBytes;
}

The fatal version has one subtlety that matters enormously in real code. When the OutOfMemoryError arrives, the very first thing the catch block does is let go of everything — before formatting any message:

} catch (OutOfMemoryError expected) {
    // Reporting an out-of-memory condition needs memory. If we still held the
    // heap hostage, the report itself would fail with a SECOND OutOfMemoryError.
    retained.clear();
    retained = null;

    String message = expected.getMessage();   // "Java heap space"
    return new ExhaustionReport(held, count, expected.getClass().getName(),
            message == null ? "(no message)" : message);
}

fillUntilExhausted is deliberately never called from a test. A JVM that has just run out of memory is in no state to run the tests that come after it, and a suite that sometimes dies halfway through teaches a team to ignore red builds. The tests check the safe method's arithmetic and the report's formatting; the exhaustion itself you run by hand, with a small -Xmx, where it is the entire point.

4.5 What happens when it runs

A numbered trace of MemoryLimitsExperiment, run with --oom and -Xmx32m:

  1. The JVM starts, loads the classes it needs (Lesson 02's machinery, unchanged), and calls main. A frame for main is pushed onto the main thread's stack.
  2. MemoryRegions.describe() asks Runtime for three numbers and the management API for two more, and prints one line per region. Used heap will be small — a few megabytes of JDK and project objects.
  3. StackDepthProbe.measureMaxDepth() resets its counter and calls descend(1). Each call pushes a frame and writes its depth to the static field.
  4. Somewhere in the tens of thousands of frames, the next push has nowhere to go. The JVM throws StackOverflowError, which unwinds every frame back to measureMaxDepth, where it is caught.
  5. The method returns the last depth recorded before the fall. The stack is now empty again and the thread is perfectly healthy.
  6. The fat-frame probe repeats the whole thing with four extra longs per frame. Prediction: a smaller number, because bigger frames mean fewer of them fit — but the JIT is free to lay out compiled frames differently, so your machine decides.
  7. HeapFiller.fillUpTo allocates eight 1 MB arrays and holds them in a list. Used heap climbs by roughly 8 MB.
  8. The list is cleared, so all eight are now unreachable, and the snapshot printed afterwards may show used memory back down — or not, if no collection has happened yet. Both are correct; the collector runs when it decides, not when you stop using something.
  9. Because --oom was passed, fillUntilExhausted starts allocating 1 MB chunks and keeping every one. In a 32 MB heap this takes well under a second.
  10. The collector runs, finds nothing reclaimable (every chunk is in the list), the heap is at its ceiling, and the JVM throws OutOfMemoryError: Java heap space.
  11. The catch block drops the list first, then builds the report, then prints it — and the program exits normally, having survived the thing that kills most programs.

5 In the wild

Open the JDK's own java.lang.StringBuilder and you find a class whose entire public contract depends on the rule in Section 3.4. Every mutating method — append, insert, reverse, delete — ends with return this;. Not a copy: this, the very same object, so that chained calls all operate on one object on the heap:

StringBuilder sb = new StringBuilder();
sb.append("a").append("b").append("c");   // one object, three visits

Contrast it with String, whose methods return new objects and leave the original untouched — which is why text.trim(); on a line by itself does nothing at all, a mistake every Java developer makes exactly once. Same language, same heap; opposite design, and the difference is entirely about whether the returned reference points at the old object or a new one.

In the real world, this is the interview question that separates recited answers from understood ones. “Is Java pass-by-value or pass-by-reference?” has a one-word correct answer — by value, always — but the follow-up is the real question: then why did my object change? Being able to answer with the stack slot, the copied arrow and the shared heap object, in that order, is the difference between having memorised a phrase and having a model. The same model is what lets you read a heap dump in Lesson 07 without it being a wall of noise.

6 Gotchas and common mistakes

  • Treating StackOverflowError as a memory shortage and raising -Xmx. People do this because both errors feel like “out of memory”, and the heap flag is the one they know. The heap is not involved. The flag that moves the stack is -Xss, and it is per thread — but before reaching for it, check the repeated line in the trace, because nine times out of ten the real bug is a missing base case and a bigger stack just delays the crash.
  • Believing that dropping a reference frees memory immediately. Setting x = null makes an object eligible for collection; it does not collect it, and it does not return memory to the operating system. The used-heap figure may not move at all until the collector next runs. This is why the project's snapshot after releasing 8 MB may look identical to the one before — and why System.gc() is a request the JVM is free to ignore, not a command.
  • Reading “used heap” as “memory my program needs”. Used heap includes garbage that has not been collected yet, so it routinely reads far higher than the live data. The number that matters for sizing is how much survives a full collection, which you will learn to read from GC logs in Lesson 05. Sizing a heap from a single used reading is guessing with extra steps.
  • Assuming the same numbers on another machine. The default heap ceiling comes from the machine's RAM (roughly a quarter of it, though that is a default to verify, not a law); the default stack size differs by platform and JDK build; and inside a container the JVM reads the container's limits, not the host's — which is why a service that is fine on a laptop dies immediately in Kubernetes. Every number this lesson prints is an observation about one machine at one moment.
  • Catching OutOfMemoryError in application code to “keep going”. The project catches it deliberately, in a tool whose whole purpose is to provoke it, after dropping every reference it held. Application code that catches it has almost always kept holding everything, so the very next allocation fails again — and the log line explaining it needs memory to build. The correct response to OutOfMemoryError in production is to let the JVM die and read the heap dump (Lesson 07), which is why -XX:+HeapDumpOnOutOfMemoryError exists.

7 Key takeaways

  • Each thread has its own stack of frames holding one method call's locals and working space, reclaimed instantly when the method returns — which is why local variables cost nothing and are automatically thread-safe.
  • Every object and array lives on the one shared heap, and a variable of an object type never holds the object itself: it holds a reference, an arrow to where the object lives.
  • Java passes every argument by value, including references — so a method can permanently change the object it was handed and can never change which object the caller's variable points at.
  • Class descriptions live in Metaspace, which replaced PermGen in Java 8, is taken from native memory, and is unbounded by default unless you set -XX:MaxMetaspaceSize.
  • StackOverflowError and OutOfMemoryError name different regions with different causes and different fixes, and the words after the colon in an OutOfMemoryError are the most important part of the message.

Line by line:

  • 1 and 2 are identical, and both show two elements. b = a copied the arrow, so there is one ArrayList object on the heap with two names. addOne followed its copy of the arrow and added to that one object. replace pointed its own parameter slot at a brand-new list, added "replaced" to it, and then that frame died — taking the only arrow to that new list with it, which means the list became garbage before main even resumed. Nothing in the output mentions it. Finally b.add("via b") added to the same single list as always.
  • 3: true. == on references compares the arrows, and both point at the same object. It was never going to be anything else: no line in main assigned to a or b after the first two.
  • 4: 1. grow received a copy of the number in its own frame's slot and multiplied that copy. main's slot was never touched. There is no arrow involved at all — this is the contrast case.
  • 5: true. equals on lists compares contents, and the copy's contents are equal.
  • 6: false. == compares arrows, and new made a genuinely separate object at a different address. Lines 5 and 6 are the same two objects judged by two different questions, which is exactly why mixing up == and equals produces bugs that look like magic.

The bonus insight: the most interesting object in this program never appears in the output at all. The list created inside replace was alive for two lines, became unreachable the instant that frame was popped, and is now waiting for a collector that has not been mentioned yet. That is Lesson 04.

Part B (1) — GC overhead limit exceeded, the heap. This is the heap saying “I am nearly full and collecting is achieving almost nothing”, which the JVM reports early rather than crawling for hours. A sawtooth whose floor rises over the run is the signature of retention: each cycle leaves more behind than the last. First investigation: what is still reachable at the bottom of each cycle? A static collection, a cache with no eviction, or a listener list that is only ever added to. A heap dump (Lesson 07) answers it in minutes; more -Xmx only moves the crash to hour six.

Part B (2) — Metaspace, class metadata. Six redeploys, six sets of class loaders, and something is keeping the old ones alive — the class-loader leak from Lesson 02. Every class defined by a leaked loader keeps its description in Metaspace forever. The heap looking normal is the clue that points away from the heap. First investigation: which loaders are still reachable, and from what — typically a ThreadLocal, a static registry, or a thread the application started and never stopped. The operational workaround is to restart between deploys; the fix is to release the reference.

Part B (3) — neither the heap nor Metaspace: operating-system memory. “Unable to create native thread” means the JVM asked the OS for a thread and was refused, because of an OS limit on threads per process or because there was not enough native memory left to allocate another stack. On a 64 GB machine with a 20% full heap, the usual cause is a thread leak — an executor created per request, a connection pool that never closes. Note the trap: raising -Xmx makes this worse, because the heap takes memory the thread stacks needed. First investigation: count the threads (jstack, Lesson 07) and see what they all have in common.

Part C — what you should see. Roughly proportional: -Xss2m should give several times the depth of -Xss256k, though not exactly eight times, because the stack also holds fixed overhead and the JIT may compile the recursive method partway through and change the frame size. For the heap, -Xmx16m should produce roughly half the chunk count of -Xmx32m, landing a little under the ceiling in both cases — the JVM needs some of its own heap for the list holding the chunks and for everything else that was already alive. If your numbers behave differently, that is the interesting result and worth telling me about.
