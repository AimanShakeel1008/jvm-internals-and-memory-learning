Lesson 03 — Runtime Memory Areas

Where a running program actually puts things. Each thread has its own stack of frames. There is one shared heap of objects, and a Metaspace full of class descriptions. You will also meet the two walls the JVM hits when they run out.

Position: Lesson 03 of 07  ·  Prerequisites: Lesson 01, Lesson 02  ·  Project files: memory/HeapSnapshot.java, memory/MemoryRegions.java, memory/StackDepthProbe.java, memory/HeapFiller.java, memory/ReferenceDemo.java, experiments/MemoryLimitsExperiment.java, JvmExplorer.java (modified), and five test classes

1 The pain

Here is a small bug that has wasted a huge number of hours. A method is supposed to fill in a customer's address. Half of it quietly disappears.

void enrich(Customer c) {
    c.setCity("Berlin");       // the caller DOES see this
    c = new Customer();        // from here on, the caller sees NOTHING
    c.setCountry("Germany");   // lost, silently, every time
}

The city arrives. The country does not. There is no exception, no warning, no log line. There is just a field that stays null in production. People explain it to each other with half-remembered phrases like “Java is pass-by-reference, except sometimes.” It is not, and there is no “sometimes”. There is one simple rule. It is a rule about where things live, and that is exactly what this lesson is about.

The second pain arrives at 3 a.m. as a one-line email: java.lang.OutOfMemoryError: Java heap space. Somebody suggests adding RAM to the server. Somebody else suggests -Xmx8g. Nobody can say what the heap is. So nobody can say if either idea is a fix, or just a way to make the same crash take longer to arrive. Next week it gets worse: the error says OutOfMemoryError: Metaspace. That is a different area of memory, with a different cause, and more heap cannot help at all. These messages mean different things. Teams that treat them all as “the memory error” end up restarting a server every night for two years.

The third pain is a stack trace a thousand lines long, all the same line. It says StackOverflowError, then at com.acme.Node.total(Node.java:41), over and over until the console gives up. It is not an OutOfMemoryError, even though something clearly ran out of space. It has nothing to do with the heap, even though everyone's first idea is to raise -Xmx. The setting that really changes it is a flag most developers have never typed. By the end of this lesson, your project will report every memory area the JVM is using. It will also walk up to both walls on purpose, and read what each one says.

2 Real-world analogy

Picture a furniture workshop. Three places hold things, and each one has its own rules.

The workbench is where one carpenter does the job in front of them. It holds the measurements for this cut, a pencil, and the piece being made. Sometimes a job needs a smaller job first, like “first make the drawer”. Then a fresh tray of notes and tools is stacked on the bench. It is used, and lifted off the moment the drawer is done. Everything on that tray goes with it. The bench is narrow. Stack too many trays and the pile falls over.

The warehouse out the back holds the finished pieces: tables, chairs, drawers. It is large, and every carpenter in the shop shares it. Nothing is thrown out just because one carpenter finished a job. A carpenter does not keep the table on the bench. They keep a ticket with a shelf number written on it. Two carpenters can hold tickets with the same shelf number. Then they are both talking about one table.

The blueprint cabinet in the office holds one drawing for each kind of furniture. It says what a “chair” is, how many legs it has, and how to build one. There is exactly one chair blueprint, no matter how many chairs exist. Nobody sits on a blueprint. You build from it.

Now read the bug from Section 1 again, with tickets in mind. enrich was handed a photocopy of the ticket. setCity writes on the table that the ticket points to. That changes the real table in the warehouse, and everybody sees it. c = new Customer() throws the photocopy away and writes a different shelf number on a new one. That changes nothing about the caller's ticket. It is still in the caller's hand, with the original number on it. One rule, two results, no exceptions.

3 The concept explained

We build the map in the order the ideas depend on each other:

  1. what a running program must keep somewhere,
  2. the stack (one per thread),
  3. the shared heap,
  4. the one rule that connects them,
  5. where the classes from Lesson 02 ended up,
  6. the smaller areas nobody mentions, and
  7. what happens when each area fills up.

3.1 Two kinds of memory, because there are two kinds of question

A running program keeps answering two different questions. They need opposite things from memory.

The first question is “where am I in the work?” Which method is running? What were its arguments? What is its loop counter right now? Where do I go back to when I finish? This information has a lifetime you can predict exactly. It starts when a method is called and ends when that method returns, in exactly reverse order. Nothing needs to be searched for, and nothing needs cleaning up later. The stack answers this question.

The second question is “what data exists?” The customer object, the list of orders, the string you built. Their lifetime is hard to predict. An object made inside a method may be returned, stored in a field, or handed to another thread. It may still be in use an hour later. When a method returns, that tells you nothing about whether the object is still needed. The heap answers this question.

Because the lifetimes are different, the memory is managed differently. Stack memory is freed instantly and for free, with simple arithmetic. Heap memory needs something to work out what is still wanted. That is garbage collection, the topic of Lessons 04 and 05. Every memory decision in Java comes from this split.

Here is the whole map before we take it apart. Notice what belongs to each thread and what is shared. That one difference explains most of the rules that follow.

3.2 The stack: one pile of frames per thread

A thread is one separate line of work. Think of it as one worker carrying out instructions in order. A plain Java program starts with one thread, called main, and may create more. Every thread gets its own stack. It is an area of memory that only that thread can touch, and it is used as a pile.

Each time the thread calls a method, the JVM pushes a new frame onto that pile. A frame is a small block of working space for exactly one method call that is still running. It holds three things:

  • the local variable table: the numbered slots that hold the method's parameters and local variables. You met these in Lesson 01. Your variable names became slot numbers at compile time. In an instance method, slot 0 is this.
  • the operand stack: the scratch space where bytecode instructions push and pop the values they are working on. This is also from Lesson 01.
  • the return address: where to carry on in the calling method once this one finishes.

When the method returns, the frame is popped. The pointer that marks the top of the stack just moves back down. Every local variable in that frame is gone. There is no search, no record-keeping, no collector. That is why freeing stack memory costs almost nothing. It is one subtraction.

Two results follow right away. They are worth saying out loud.

Local variables are automatically thread-safe. This is not luck, and nobody has to enforce it. A local variable lives in a frame. A frame lives on one thread's stack. No other thread can reach that stack. Two threads running the same method at the same time each have their own frame, their own slots, and their own values.

The pile has a fixed size. The size is chosen when the thread is created. It does not grow when needed. So a chain of calls that never returns must run out of room in the end. That is the StackOverflowError of Section 3.7.

Two threads run the same method, which declares int total = 0;. How many total variables exist?
Two. There is one per frame, and one frame per thread, each on its own stack. Neither thread can see or damage the other's copy. This is why local variables never need synchronized. It is also why the standard advice “keep state local” really works, and is not just a tidy habit.

3.3 The heap: one shared pool of objects

The heap is one area of memory shared by every thread in the JVM. It holds exactly one kind of thing: objects. Every object made with new goes there. So does every array, because in Java an array is an object. So does every string literal (text in quotes in your code), and every object the JDK makes for you.

Why the name? Here, “heap” is an old programming word for a pool of memory. You can take pieces from it in any order, and give them back in any order. Think of a heap of material to cut from, not a neat pile. (It has nothing to do with the heap data structure used in priority queues. That is a different use of the same word. Two meanings, one word, endless confusion.)

Three facts about the heap decide almost everything in the rest of this course:

  • It is shared. Any thread that holds a reference to an object can read and change it. So, unlike local variables, object state needs care when several threads are involved.
  • It has a ceiling. The JVM may grow the heap up to a maximum size. You set it with -Xmx, or the JVM picks it from the machine's RAM. If the heap hits that ceiling and nothing can be freed, you get OutOfMemoryError: Java heap space.
  • The garbage collector cleans it. Your code never frees anything on the heap. An object stays alive exactly as long as some chain of references can reach it. The collector frees the rest, at times it chooses. That is Lesson 04.

“Every object lives on the heap” is the right picture to hold. There is one honest footnote. Sometimes the JIT compiler can prove that an object never leaves the method that made it. Then it may skip putting it on the heap at all. It keeps the object's fields in CPU registers or in the frame instead. This is called escape analysis. You cannot see it from Java code, and it never changes what your program does. Lesson 06 covers it. Until then: heap.

3.4 The one rule: a variable is an arrow, not an object

This section is the most important part of the lesson. So we start with the pain, not the rule.

What goes wrong without this. Almost everyone starts with a simple but wrong picture. They think a variable contains its object, the way a box contains a thing:

StringBuilder a = new StringBuilder("hello");
StringBuilder b = a;                // naive model: "b is a copy of a"
b.append(" world");                // naive model: "only b changes"
System.out.println(a);            // naive model predicts: hello

It prints hello world. The wrong picture is not slightly off. It predicts the opposite. The same wrong picture causes three common bugs: the Section 1 bug, the “why did my list change when I only changed the other list?” bug, and the “I passed a copy, didn't I?” bug. One fix solves all three.

The rule. Take a variable whose type is a class, an interface or an array. It does not hold the object. It holds a reference: a value that says where the object lives on the heap. Think of it as an arrow, or the ticket from Section 2. Assigning one variable to another copies the arrow, never the object. Two arrows can point at one object.

Primitive types work differently, and that difference is the whole point. There are exactly eight of them: byte, short, int, long, float, double, char and boolean. A variable of a primitive type holds the value itself, right there in the frame's slot. No arrow, no heap, nothing shared.

Now the rule for method arguments. It is just the same fact used once more. Java is always pass-by-value. The called method gets a copy of what the caller had. For an int, that is a copy of the number. For an object type, that is a copy of the arrow, and it points at the very same object.

void mutate(StringBuilder text) {
    text.append("!");                       // follows the arrow → the caller's object changes
}

void reassign(StringBuilder text) {
    text = new StringBuilder("other");      // overwrites THIS frame's slot only
    text.append("!");                       // changes an object nobody else can reach
}

Both methods look like they change the argument. mutate changes the object. reassign changes the variable. Only the first change is still there after the method returns. The object is on the shared heap. The variable is in a frame that is about to be thrown away. That is the whole explanation of the Section 1 bug. There is nothing more to it.

Stop using this phrase for good: “Java passes objects by reference.” It is wrong, and it would make you predict the Section 1 bug wrongly. Java passes references by value. Every argument is always copied. It is just that copying an arrow gives you a second arrow to the same thing.

After int[] a = {1,2,3}; int[] b = a; b[0] = 99; — what is a[0]?
99. An array is an object, so b = a copied the arrow, not the array. There is one array on the heap with two names. To get a really separate array, you must make one: int[] b = a.clone(); or Arrays.copyOf(a, a.length).

3.5 Metaspace, and what happened to PermGen

In Lesson 02 we watched hundreds of classes load. Each one left something behind: a description of the class. It holds the class's name, its superclass, the layout of its fields, its table of methods, its constant pool, and the bytecode of each method. That description is not an object on the heap. It is the blueprint from Section 2. Since Java 8, it lives in an area called Metaspace.

There is one description per class, no matter how many objects of it exist. A million Customer objects sit on the heap. The one description of what a Customer is sits in Metaspace.

What goes wrong without this split. Before Java 8, class descriptions lived in a heap area called the permanent generation (“PermGen”). It had a fixed maximum size, set by -XX:MaxPermSize. The default was small, something like 64 MB. Say you redeployed a web application a few times without restarting the server. Each redeploy made a new class loader, which defined a new copy of every class. That is the class loader leak from Lesson 02. PermGen filled up, and the server died with:

java.lang.OutOfMemoryError: PermGen space

Java 8 removed PermGen completely. Metaspace replaced it. Metaspace uses native memory: memory the JVM asks for straight from the operating system, outside the Java heap. By default it has no limit. It grows as long as the operating system gives it memory. This swaps a common, confusing crash for a rarer one. Now a real class-loader leak eats the machine's memory, instead of hitting a small ceiling. You can set a ceiling again on purpose with -XX:MaxMetaspaceSize. Many teams do exactly that. Then a leak shows up as a clear OutOfMemoryError: Metaspace, not as a server that slowly eats all the machine's memory.

Two related changes often get mixed up with this one. First, interned strings (the pool behind string literals) moved out of PermGen and onto the normal heap in Java 7. That was one release before PermGen itself was removed. Second, -XX:MaxPermSize on Java 8 or later does not cause an error you would notice. The JVM just ignores it and prints a warning. That is why a startup script can carry it for years without anyone asking why.

For learning only: a detail worth knowing, but not worth relying on. In HotSpot, a class's static fields are not stored in Metaspace with the rest of the description. They live in the java.lang.Class object for that class, and that object is on the heap. So for HotSpot today the accurate split is: “class information is in Metaspace, static data is on the heap”. This is a choice HotSpot made, not something the specification requires. Treat it as a fact about the JVM you are running. If it ever matters, check your JDK's documentation.

3.6 The areas nobody mentions

Three more areas exist. Knowing their names turns three confusing error messages into readable ones.

The PC register. There is one per thread. “PC” stands for program counter. It holds the address of the bytecode instruction that thread is running right now. It is tiny, and you will never touch it. But it is what lets each thread keep its own place in the program.

The native method stack. There is one per thread, next to the Java stack. Sometimes Java code calls code written in C or C++. The JDK does this all the time, for file access, networking and timing. Those calls need their own frames, in the shape the C compiler expects. That is what this stack holds.

The code cache. This one is shared. The JIT compiler turns hot methods into native machine code (Lesson 01, and in depth in Lesson 06). That machine code has to live somewhere. It lives here. If this area fills up, the JVM prints CodeCache is full. Compiler has been disabled. The application keeps running correctly, but now it is interpreted, so it is slow. The classic sign is an application that suddenly gets slower hours into a run, with no code change and no GC problem.

One more thing is worth naming, even though it is not a separate area. No heap tool will show you this memory. It is direct (off-heap) buffers. They are made by ByteBuffer.allocateDirect, and networking and I/O libraries use them a lot. The bytes live in native memory. Only a small Java object on the heap points at them. Say a process uses far more memory than its heap, but its heap graph looks healthy. It is usually holding direct buffers. Running out of them gives a third, separate message: OutOfMemoryError: Direct buffer memory.

3.7 The two walls

Each area has a limit, and the JVM says something different at each one. Mixing them up is the most expensive mistake in this lesson.

Wall one: the stack runs out of room for frames. A thread's stack has a fixed size. On a 64-bit JVM it is usually around 512 KB to 1 MB. You set it with -Xss, and it really does change from machine to machine. Every call pushes a frame. Nothing is popped until a method returns. So recursion without a working base case (a stopping condition) can only end one way:

int total(Node n) {
    return n.value + total(n.next);   // no base case: never returns, always pushes
}
Exception in thread "main" java.lang.StackOverflowError
        at com.acme.Node.total(Node.java:41)
        at com.acme.Node.total(Node.java:41)
        at com.acme.Node.total(Node.java:41)
        ... the same line, roughly a thousand more times

How to read it: the repeated line is the answer.

  • If one method repeats, you have runaway recursion. Find the missing base case.
  • If a short group of methods repeats in a loop (a → b → c → a), you have methods calling each other in a circle. This often happens through a framework. Examples: two objects whose toString methods call each other, or a JPA entity graph with a loop in it.
  • If the trace shows a thousand different frames, the recursion is correct but too deep for the stack. You can use a bigger -Xss, or rewrite the algorithm to use your own list instead of the call stack.

-Xss is per thread, not one setting for the whole JVM. Doubling it on a server with 500 threads asks the operating system for 500 times the extra amount. Raising it is a real fix for recursion that truly needs to go deep. It is a terrible fix for a missing base case. That just takes longer to crash.

Wall two: the heap has no space left that can be freed. Notice the careful wording. Running out of heap does not mean “you made a lot of objects”. A program can make a terabyte of objects in a 32 MB heap without trouble, as long as it stops using each one. The error only comes when the heap is at its ceiling and the collector cannot find anything to free. That means something is still holding on to objects:

Exception in thread "main" java.lang.OutOfMemoryError: Java heap space

The words after the colon matter most. They name the area that filled up, and the area tells you where to look:

OutOfMemoryError: Java heap space is about the shared object storage. It is usually a bug where something holds on to objects too long. Both are Error, not Exception. That is the JVM's way of saying “do not plan to recover from this.” The project's probes catch them anyway, on purpose and in a controlled way. Section 4 explains how, carefully.

4.2 Reading the regions

There are two ways to ask. Runtime has answered heap questions since Java 1.0, and needs nothing extra. The management API is a set of objects the JVM keeps about itself. You reach them through ManagementFactory. It answers more detailed questions, such as which named memory pools exist. We use both.

public static HeapSnapshot heapSnapshot() {
    Runtime runtime = Runtime.getRuntime();

    // The ceiling -Xmx sets, or a default derived from the machine's RAM.
    long max = runtime.maxMemory();

    // What the JVM has actually taken from the OS so far. Read BEFORE freeMemory()
    // so the two readings are as close together in time as we can make them.
    long committed = runtime.totalMemory();
    long free = runtime.freeMemory();

    // used = committed - free, clamped: a garbage collection landing between the
    // two calls could otherwise produce a negative number. A reporting method
    // should never be the thing that throws.
    long used = Math.min(committed, Math.max(0L, committed - free));

    return new HeapSnapshot(max, committed, used);
}

For Metaspace we need the management API, and we need to be careful. “Metaspace” is a name HotSpot gives to one of its pools. The Java specification does not promise it exists. So the method searches the pools by name. It returns OptionalLong, which means “a number, or nothing”. It does not make up -1 as a secret code for “not there”:

public static OptionalLong metaspaceUsedBytes() {
    // The pool list differs by JVM, by collector and by version, which is exactly
    // why we search it by name instead of indexing into it.
    for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans()) {
        if (METASPACE_POOL_NAME.equals(pool.getName())) {
            MemoryUsage usage = pool.getUsage();
            if (usage != null) {
                return OptionalLong.of(usage.getUsed());
            }
        }
    }
    // Empty means "this JVM did not offer that pool" - a different statement
    // from "zero bytes are in use".
    return OptionalLong.empty();
}

4.3 Walking to wall one, on purpose

No API answers “how many frames fit on my stack?”. The only honest way to find out is to go until you fall off the end, counting as you go. The probe does exactly that:

// Lives OUTSIDE the recursion, because every local variable inside it dies with
// its frame as the stack unwinds - by the time we catch the error, they are gone.
private static int deepestReached;

public static int measureMaxDepth() {
    deepestReached = 0;
    try {
        descend(1);                  // can only end by overflowing
    } catch (StackOverflowError expected) {
        lastErrorType = expected.getClass().getName();
    }
    return deepestReached;
}

private static void descend(int depth) {
    deepestReached = depth;          // record on the way DOWN - there is no way back up
    descend(depth + 1);
}

Catching an Error is normally wrong. This is the rare case where it is right. An Error means something you are not expected to recover from. So code that silently catches one usually hides a disaster. Here, things are different:

  • The overflow is the measurement.
  • We cause it on purpose.
  • By the time the catch block runs, the whole recursion has unwound. The stack is empty again, so there is plenty of room to do the counting.

Copying this pattern into normal application code is a bug. The file says so in its own comments.

4.4 Walking to wall two — carefully

Making lots of objects is not enough to fill a heap. Say a loop makes a million arrays and forgets each one at once. It runs forever, even in a tiny heap, because the collector frees each one as fast as it appears. To fill a heap, you must keep what you make. That is also the exact meaning of a memory leak. A leak is not making too much. It is holding on to things you no longer need.

// The list is what keeps every chunk REACHABLE, and therefore uncollectable.
// Remove this list and the method allocates nothing that survives.
List<byte[]> retained = new ArrayList<>();
long held = 0;

// Stop when one MORE chunk would exceed the budget, so we never overshoot -
// which is what makes the chunk count exactly predictable in a test.
while (held + chunkBytes <= budgetBytes) {
    retained.add(new byte[chunkBytes]);
    held += chunkBytes;
}

The version that fills the heap all the way has one small detail that matters a lot in real code. When the OutOfMemoryError arrives, the very first thing the catch block does is let go of everything. It does this before building any message:

} catch (OutOfMemoryError expected) {
    // Reporting an out-of-memory condition needs memory. If we still held the
    // heap hostage, the report itself would fail with a SECOND OutOfMemoryError.
    retained.clear();
    retained = null;

    String message = expected.getMessage();   // "Java heap space"
    return new ExhaustionReport(held, count, expected.getClass().getName(),
            message == null ? "(no message)" : message);
}

fillUntilExhausted is never called from a test, on purpose. A JVM that has just run out of memory cannot be trusted to run the tests that come after it. A test suite that sometimes dies halfway through teaches a team to ignore red builds. The tests check the safe method's arithmetic and the report's formatting. You run the full fill yourself, by hand, with a small -Xmx. There, it is the whole point.

4.5 What happens when it runs

Here is a numbered trace of MemoryLimitsExperiment, run with --oom and -Xmx32m:

  1. The JVM starts. It loads the classes it needs (Lesson 02's machinery, unchanged) and calls main. A frame for main is pushed onto the main thread's stack.
  2. MemoryRegions.describe() asks Runtime for three numbers and the management API for two more. It prints one line per area. Used heap will be small: a few megabytes of JDK and project objects.
  3. StackDepthProbe.measureMaxDepth() resets its counter and calls descend(1). Each call pushes a frame and writes its depth to the static field.
  4. Somewhere in the tens of thousands of frames, there is no room for the next one. The JVM throws StackOverflowError. The error unwinds every frame back to measureMaxDepth, where it is caught.
  5. The method returns the last depth recorded before the fall. The stack is empty again, and the thread is perfectly healthy.
  6. The bigger-frame probe does the whole thing again, with four extra longs in each frame. Prediction: a smaller number, because bigger frames mean fewer fit. But the JIT is free to lay out compiled frames differently, so your machine decides.
  7. HeapFiller.fillUpTo makes eight 1 MB arrays and holds them in a list. Used heap goes up by about 8 MB.
  8. The list is cleared, so nothing can reach the eight arrays now. The snapshot printed next may show used memory back down. Or it may not, if no collection has happened yet. Both are correct. The collector runs when it decides, not when you stop using something.
  9. Because --oom was passed, fillUntilExhausted starts making 1 MB chunks and keeping every one. In a 32 MB heap this takes well under a second.
  10. The collector runs and finds nothing it can free, because every chunk is in the list. The heap is at its ceiling. The JVM throws OutOfMemoryError: Java heap space.
  11. The catch block drops the list first. Then it builds the report and prints it. The program ends normally. It survived the thing that kills most programs.

5 In the wild

Open the JDK's own java.lang.StringBuilder. Its whole public design depends on the rule in Section 3.4. Every method that changes it (append, insert, reverse, delete) ends with return this;. Not a copy. This, the very same object. So chained calls all work on one object on the heap:

StringBuilder sb = new StringBuilder();
sb.append("a").append("b").append("c");   // one object, three visits

Compare it with String. Its methods return new objects and leave the original untouched. That is why text.trim(); on a line by itself does nothing at all. Every Java developer makes this mistake exactly once. Same language, same heap, opposite design. The whole difference is whether the returned reference points at the old object or a new one.

In the real world, this interview question shows who has memorised an answer and who really understands it. “Is Java pass-by-value or pass-by-reference?” has a one-word correct answer: by value, always. But the follow-up is the real question: then why did my object change? A strong answer explains three things in order: the stack slot, the copied arrow, and the shared heap object. That shows you have a real picture of how it works, not just a phrase. The same picture lets you read a heap dump in Lesson 07 without it looking like a wall of noise.

6 Gotchas and common mistakes

  • Treating StackOverflowError as a lack of memory and raising -Xmx. People do this because both errors feel like “out of memory”, and the heap flag is the one they know. The heap is not involved. The flag that changes the stack is -Xss, and it is per thread. But before you reach for it, check the repeated line in the trace. Nine times out of ten, the real bug is a missing base case. A bigger stack just delays the crash.
  • Believing that dropping a reference frees memory at once. Setting x = null makes an object able to be collected. It does not collect it. It does not give memory back to the operating system either. The used-heap number may not change at all until the collector next runs. This is why the project's snapshot after releasing 8 MB may look the same as the one before. It is also why System.gc() is a request the JVM may ignore, not a command.
  • Reading “used heap” as “memory my program needs”. Used heap includes garbage that has not been collected yet. So it is often much higher than the data you actually still use. The number that matters for sizing is how much is left after a full collection. You will learn to read that from GC logs in Lesson 05. Choosing a heap size from one used reading is just guessing.
  • Expecting the same numbers on another machine. The default heap ceiling comes from the machine's RAM. It is roughly a quarter of it, but check that default rather than trusting it. The default stack size is different on each platform and JDK build. Inside a container, the JVM reads the container's limits, not the host machine's. That is why a service that is fine on a laptop can die at once in Kubernetes. Every number this lesson prints is about one machine at one moment.
  • Catching OutOfMemoryError in application code to “keep going”. The project catches it on purpose, in a tool whose whole job is to cause it, after dropping every reference it held. Application code that catches it has almost always kept holding everything. So the very next allocation fails again. Even the log line that explains the problem needs memory to build. The right response to OutOfMemoryError in production is to let the JVM die and read the heap dump (Lesson 07). That is why -XX:+HeapDumpOnOutOfMemoryError exists.

7 Key takeaways

  • Each thread has its own stack of frames. A frame holds one method call's local variables and working space, and it is freed instantly when the method returns. That is why local variables cost almost nothing and are automatically thread-safe.
  • Every object and array lives on the one shared heap. A variable of an object type never holds the object itself. It holds a reference: an arrow to where the object lives.
  • Java passes every argument by value, including references. So a method can change the object it was given, for good, but it can never change which object the caller's variable points at.
  • Class descriptions live in Metaspace, which replaced PermGen in Java 8. Metaspace uses native memory and has no limit by default, unless you set -XX:MaxMetaspaceSize.
  • StackOverflowError and OutOfMemoryError are about different memory areas, with different causes and different fixes. In an OutOfMemoryError, the words after the colon are the most important part of the message.

Part B — explain three production failures. For each one, name the memory area involved and the first thing you would look into:

  1. A batch job dies with OutOfMemoryError: GC overhead limit exceeded after four hours. Heap graphs show a sawtooth (a zig-zag line) that climbs steadily over the whole run.
  2. A web application was redeployed six times without a restart. It dies with OutOfMemoryError: Metaspace. Heap use is normal.
  3. A service on a 64 GB machine dies with OutOfMemoryError: unable to create native thread. The heap is only 20% full.

Part A — the predicted output.

1: [added, via b]
2: [added, via b]
3: true
4: 1
5: true
6: false

Line by line:

  • 1 and 2 are the same, and both show two elements. b = a copied the arrow. So there is one ArrayList object on the heap with two names. addOne followed its copy of the arrow and added to that one object. replace pointed its own parameter slot at a brand-new list and added "replaced" to it. Then that frame ended, and the only arrow to the new list went with it. So the new list became garbage before main even carried on. Nothing in the output mentions it. Finally, b.add("via b") added to the same single list as always.
  • 3: true. == on references compares the arrows, and both point at the same object. It could never be anything else. No line in main changed a or b after the first two lines.
  • 4: 1. grow got a copy of the number in its own frame's slot, and multiplied that copy. main's slot was never touched. No arrow is involved at all. This is the case to compare against.
  • 5: true. equals on lists compares contents, and the copy has the same contents.
  • 6: false. == compares arrows. new made a really separate object at a different address. Lines 5 and 6 judge the same two objects with two different questions. That is exactly why mixing up == and equals causes bugs that seem like magic.

The bonus lesson: the most interesting object in this program never appears in the output at all. The list made inside replace was alive for two lines. It became unreachable the moment that frame was popped. Now it is waiting for a collector we have not talked about yet. That is Lesson 04.

Part B (1) — GC overhead limit exceeded: the heap. The heap is saying “I am nearly full, and collecting frees almost nothing”. The JVM reports this early, instead of crawling along for hours. Look at the zig-zag graph. If its lowest points rise over the run, something is holding on to objects. Each cycle leaves more behind than the last. First thing to look into: what can still be reached at the bottom of each cycle? Often it is a static collection, a cache that never removes old entries, or a listener list that only ever grows. A heap dump (Lesson 07) answers this in minutes. More -Xmx only moves the crash to hour six.

Part B (2) — Metaspace: class information. Six redeploys made six sets of class loaders, and something is keeping the old ones alive. This is the class-loader leak from Lesson 02. Every class defined by a leaked loader keeps its description in Metaspace forever. The normal-looking heap is a clue: the problem is not in the heap. First thing to look into: which loaders can still be reached, and from what? It is usually a ThreadLocal, a static registry, or a thread the application started and never stopped. A short-term workaround is to restart between deploys. The real fix is to release the reference.

Part B (3) — not the heap, not Metaspace: operating-system memory. “Unable to create native thread” means the JVM asked the operating system for a new thread, and was refused. Either the operating system has a limit on threads per process, or there was not enough native memory left for another stack. On a 64 GB machine with a 20% full heap, the usual cause is a thread leak. For example: a new thread pool made for every request, or a connection pool that never closes. Watch out for the trap here: raising -Xmx makes this worse, because the heap takes memory the thread stacks needed. First thing to look into: count the threads (jstack, Lesson 07) and see what they all have in common.

Part C — what you should see. The depth should grow roughly in line with the stack size. -Xss2m should give several times the depth of -Xss256k, but not exactly eight times. The stack also holds some fixed overhead. The JIT may also compile the recursive method partway through, which changes the frame size. For the heap, -Xmx16m should give roughly half the chunk count of -Xmx32m. Both should land a little under the ceiling. The JVM needs some heap for the list that holds the chunks, and for everything else that was already alive. If your numbers behave differently, that is the interesting result. Tell me about it.
