2 Cheatsheet by topic

2.1 Setup and the toolchain (Lesson 00)

  • JDK = build + run (JRE + javac, javap, jcmd…). JRE = run only. JVM = the engine inside both (HotSpot). Developers install a JDK.
  • PATH picks your terminal's java; JAVA_HOME picks Maven's. They can disagree. Check mvn -version, in a fresh terminal.
  • Pin versions in committed files (maven.compiler.release, dependency and plugin versions) and make the build check them. Never write RELEASE as a version.
  • Java 21 is LTS, which is why it is pinned. The default collector since Java 9 is G1.

2.5 Object lifecycle and GC fundamentals (Lesson 04)

  • Garbage = unreachable from every GC root. Roots: locals in live frames, static fields, running threads, JVM-internal references. Unreachable cycles are garbage too, because Java traces; it does not count references.
  • A Java leak = no longer needed but still reachable (static collections, unbounded caches, unremoved listeners, ThreadLocal on pooled threads, inner classes or lambdas capturing this).
  • Eligible is not collected. x = null makes an object eligible; the collector decides when. System.gc() is a request (and a full GC on HotSpot defaults).
  • Generational hypothesis: most objects die young. Young generation = Eden + S0 + S1. A minor GC copies the live objects to the empty survivor (age +1) and wipes Eden. At the tenuring threshold, an object is promoted to old.
  • Copying cost ∝ survivors: garbage is never looked at. Card table + write barrier let a minor GC find old→young references without scanning old.
  • Premature promotion (survivor overflow) fills old with short-lived objects. Fix with a bigger young generation, not a bigger heap.

2.7 The JIT compiler (Lesson 06)

TierMeaning
0interpreter (profiles basic counts)
1C1, no profiling — trivial methods
2C1, light profiling — C2 busy
3C1, full profiling — the usual first compile

  • OSR: a long loop in a method called once is compiled via the back-edge counter and switched over mid-loop (% in -XX:+PrintCompilation).
  • Inlining copies small or hot callees into callers, which unlocks every other optimisation. Small methods are free once hot. A megamorphic call site (3+ classes seen) blocks it.
  • Escape analysis (C2, after inlining): a non-escaping object is scalar-replaced (never allocated) and its locks elided. Measured in the course: ≈24 bytes/call cold → ≈0 hot.
  • Speculation + deoptimization: C2 bets on the profile; a lost bet makes the code “made not entrant” and falls back to the interpreter. Results never change. A tier 3 retirement is a replacement; a tier 4 retirement is a deoptimization.
  • The first run is slow because of class loading, interpretation, profiling, and compilation in progress. Measure with JMH, never a cold stopwatch.

2.8 Seeing inside a live JVM (Lesson 07)

  • Find it: jps -l or jcmd → PID. Attach only on the same machine, as the same OS user (inside the container for containers).
  • Thread states: RUNNABLE, BLOCKED (waiting for a monitor), WAITING, TIMED_WAITING. Frozen with the CPU idle → look for deadlocks (“Found one Java-level deadlock”). Take three dumps a few seconds apart.
  • Class histogram = instances + shallow bytes per class. Two histograms minutes apart → the class that keeps growing is the suspect.
  • Heap dump = every object and reference. Retained size points at the holder; path to GC roots names the field. It pauses the JVM, is about the size of the live heap, and contains secrets.
  • Order: GC log → two histograms → one heap dump at a quiet moment → fix the removal rule → confirm with flat histograms.

5 Myths vs facts

MythFact
“Java passes objects by reference.”Java passes everything by value; for objects the value is a reference. A callee can change the object, never the caller's variable.
“Java compiles to machine code.”javac compiles to bytecode; the JIT compiles hot bytecode to machine code at run time.
“Write once, run anywhere means any Java version.”It means any machine. An older JVM always refuses a newer class file.
“Java can't leak memory — it has GC.”Anything still reachable is kept. Unbounded static collections leak.
“Setting a variable to null frees memory.”It makes an object eligible; the collector reclaims it later, on its own schedule.
“Call System.gc() to clean up.”A request, usually a full GC — an expensive pause. Never in application code.
“Two objects pointing at each other are never collected.”Java traces from roots; unreachable cycles are garbage.
“Creating objects is expensive — pool them.”Allocation is a pointer bump; non-escaping objects may never exist. Pooling often makes things worse.
“Small methods are slow — merge them.”Hot small methods are inlined; the call disappears.
“Average GC pause is what matters.”Users feel the maximum. Read the max and the full-GC count.
“More heap fixes any OutOfMemoryError.”Not for Metaspace, native threads or leaks — for a leak, more heap only delays the crash.
“StackOverflowError needs more -Xmx.”The stack is not the heap. Usually a missing base case; the stack flag is -Xss.
“Changing a public static final constant updates all callers.”Compile-time constants are inlined into callers; recompile them.
“An import loads a class.”Imports vanish at compile time; nothing loads until first real use.
“A heap dump is just a debug file.”It contains every value in memory, passwords included. Treat it as sensitive data.
“Every 'made not entrant' is a deoptimization.”At tier 3 it is usually replacement by tier 4; tier 4 retirements are deoptimizations.

6 Interview questions

Answer each one out loud first, then open it. A good answer names the mechanism, then the consequence.

6.1 Bytecode and the class file

What is the difference between the JDK, the JRE and the JVM?
The JVM is the engine that runs bytecode and manages memory. The JRE is the JVM plus the standard library — enough to run programs. The JDK is the JRE plus developer tools such as javac, javap and jcmd. Developers install a JDK; modern Java no longer ships a separate JRE. (L00)
What does “write once, run anywhere” really mean, and where does it break?
The compiled class file — bytecode for an imaginary machine — runs unchanged on any machine with a JVM. It breaks across Java versions (an older JVM refuses newer class files), and around the edges: native libraries, hard-coded file paths, platform encodings, and timing-dependent concurrency bugs. (L01)
Decode: UnsupportedClassVersionError … class file version 65.0, this runtime only recognizes 61.0.
Subtract 44: the file was compiled for Java 21, the JVM running it is Java 17. Older JVMs always refuse newer files. The usual fix is to run on Java 21 or later; the alternative is to build with --release 17 and actually test on 17. You can check a jar without running it: javap -v and read major version. (L01)
Why use --release instead of -source/-target?
-source/-target set the language level and class file version but still compile against the current JDK's library, so code can call a method that does not exist on the target release and fail at run time with NoSuchMethodError. --release also swaps in that release's API definitions, so the compiler catches it. (L01)
What does new Foo() compile to, and why is there a dup?
new allocates a blank object and pushes a reference; dup copies the reference; invokespecial Foo.<init> runs the constructor, consuming one copy. The dup leaves a reference on the operand stack to assign or return, because the constructor call consumes the original. (L01)
Why does string concatenation compile to invokedynamic, and what else uses it?
Since Java 9, javac emits one invokedynamic that asks a JDK helper (makeConcatWithConstants) to build an optimised routine the first time the line runs. The JDK can then improve concatenation without anyone recompiling. Lambdas use the same mechanism via LambdaMetafactory. (L01)
Why is the JVM a stack machine rather than a register machine?
Stack instructions need no register operands (iadd takes its inputs from the top of the operand stack), so bytecode is compact and makes no assumptions about how many registers the real chip has. Mapping the stack onto real registers is the JIT's job. (L01)

6.2 Class loading

Name the built-in class loaders. Why does String.class.getClassLoader() return null?
Bootstrap (loads java.base), platform (the rest of the JDK) and application (your class path), in a parent chain. The bootstrap loader is implemented inside the JVM and has no Java object, so null is how it is represented — not an error. Calling a method on that result is a guaranteed NullPointerException. (L02)
What is parent delegation and why does it exist?
A loader asks its parent before searching its own sources, so classes are found as high in the chain as possible. Three benefits follow. Core classes cannot be replaced: a fake java.lang.String on your class path is never reached. Each JDK class exists exactly once, so there is one String type. And “not found” means genuinely nowhere. It is a convention in loadClass; servlet containers and plugin systems deliberately invert it. (L02)
ClassNotFoundException versus NoClassDefFoundError?
ClassNotFoundException (checked) comes from a lookup by name as text — Class.forName, a framework reading config — that found nothing: a name or class-path problem. NoClassDefFoundError (an Error) means compiled code refers to a class that is missing at run time: a packaging problem. NoClassDefFoundError: Could not initialize class X is different again: X is present, but its static initializer failed earlier. (L02)
Exactly when is a class initialized?
On first new, first call of a static method it declares, first use of a non-constant static field it declares, Class.forName(name), when a subclass is initialized (parent first), or when it is the main class. Not by an import, Foo.class, new Foo[n], reading a compile-time constant, loadClass, or reading a superclass's static field through a subclass name. (L02)
A library changed public static final String VERSION from “1.0” to “2.0”, but the application still prints 1.0. Why?
A static final primitive or String assigned a constant expression is a compile-time constant. javac copies its value into every caller's class file. The application holds its own copy and never reads the library's field. Recompile the callers — and in a public API, expose changeable values through a method. (L02)
How can you get ClassCastException: com.acme.Config cannot be cast to com.acme.Config?
A class's runtime identity is its name plus its defining loader. Two loaders — say the application loader and a plugin loader — each defined their own Config, giving two incompatible types. The message lists both loaders. Usually a shared jar is present in two places; fix it so only one loader can define the class. (L02)
Is static initialization thread-safe? How is that used in practice?
Yes. The JVM runs <clinit> exactly once per loader, under its own lock, and other threads block until it finishes. The initialization-on-demand holder idiom exploits this: a private nested Holder class holds a static instance, which is created lazily and thread-safely on first access with no synchronized. The flip side: if <clinit> throws, the class is unusable for the rest of the run. (L02)

6.3 Memory

Stack versus heap?
Each thread has its own fixed-size stack of frames, holding the locals, operand stack and return address of each in-progress call. It is reclaimed instantly when a method returns. The heap is shared by all threads and holds every object. It is reclaimed by the garbage collector, based on reachability. A local of object type sits on the stack and holds a reference to a heap object. (L03)
Is Java pass-by-value or pass-by-reference? Then why did my object change?
Always pass-by-value. For object types the value copied is the reference, so caller and callee point at the same heap object. Mutating that object through the copy is visible to the caller. Reassigning the parameter only changes the callee's own frame slot, so the caller never sees it. (L03)
What replaced PermGen, and why?
In Java 8, Metaspace replaced PermGen for class metadata. Metaspace lives in native memory and is unbounded by default, so the old small fixed limit (OOM: PermGen space after a few redeploys) went away. A class-loader leak now consumes machine memory instead; set -XX:MaxMetaspaceSize if you want it to fail visibly. (Interned strings had already moved to the heap in Java 7.) (L03)
StackOverflowError versus OutOfMemoryError — causes and fixes?
StackOverflowError: one thread's fixed stack ran out of frames. It is usually runaway recursion — a missing base case, or two toStrings calling each other — and the repeated lines in the trace are the diagnosis. Only legitimately deep recursion justifies raising -Xss (which applies per thread). OutOfMemoryError: a shared region is full. The words after the colon name the region, and so the investigation. (L03)
Why can a JVM process use far more memory than -Xmx?
-Xmx caps only the heap. On top of it come Metaspace, the code cache, one stack per thread, direct (off-heap) buffers, GC bookkeeping, and the JVM's own native memory. A process with many threads, or heavy NIO use, can exceed its heap by gigabytes. Size containers for all of it. (L03)
Are local variables thread-safe? Are the objects they point to?
The variables, yes: each lives in a frame on one thread's stack that no other thread can reach. The objects they reference, no: those are on the shared heap, and any thread holding a reference can modify them. “Keep state local” works only for primitives and objects that never escape the thread. (L03)

6.4 Garbage collection fundamentals

How does the JVM decide an object is garbage? What are GC roots?
An object is garbage when no chain of references from any GC root reaches it. The roots are the local variables in every live frame, static fields of loaded classes, running threads, and some JVM-internal references. Collectors mark everything reachable by tracing from the roots and reclaim the rest. (L04)
Why doesn't Java use reference counting?
Counting can never free cycles. Two objects pointing at each other keep each other's counts above zero forever, even when nothing else can reach them, and real data structures are full of cycles. Tracing from the roots ignores cycles entirely: an unreachable cycle is simply never reached. (L04)
Can a Java program leak memory? Give examples.
Yes. A Java leak is an object that is no longer needed but still reachable. Examples: a static map used as a cache without eviction; listeners registered and never removed; ThreadLocal values on pooled threads; a non-static inner class or lambda capturing this and registered long-term; class loaders kept alive across redeploys. (L04)
Explain the generational hypothesis and how a minor GC works.
Most objects die young, so new objects go into a small young generation (Eden plus two survivor spaces) that is collected often. When Eden fills, a minor GC pauses briefly and copies live objects from Eden and the occupied survivor space into the empty survivor space, adding one to each object's age. It then declares Eden and the old survivor empty. The cost is proportional to survivors; garbage is never visited. At the tenuring threshold, objects are promoted to the old generation instead. (L04)
Minor, major and full GC — what is the difference?
A minor GC collects only the young generation: frequent and cheap. A major GC collects the old generation: rare and expensive. A full GC collects the whole heap, often Metaspace too, and is usually the longest stop-the-world pause. People use the terms loosely, so say what you mean. (L04)
What is premature promotion, and how do you fix it?
Short-lived objects get pushed into the old generation too early, usually because the survivor space overflowed. The old generation then fills with garbage that only expensive collections reclaim. The tell-tale sign is an old generation that fills fast but drops back to the same level after full GCs. The fix is a larger young generation or survivor spaces — not a larger heap. (L04)
If a minor GC only scans the young generation, how does it find old objects that point to young ones?
Through the card table. The old generation is divided into small cards, and a write barrier — a little code the JIT adds to every reference store — marks a card dirty when an old object gets a reference. A minor GC scans only the dirty cards as extra roots. (L04)
What is a weak reference, and what is the classic WeakHashMap trap?
A WeakReference points at an object without keeping it alive. Once only weak references remain, the collector may reclaim the object and get() returns null. WeakHashMap holds its keys weakly, so entries vanish when keys become unreachable. The trap: if a value refers back to its own key, the map's strong reference to the value keeps the key reachable, and the entry never goes. (L04)
Why shouldn't you use finalize()?
It runs at an unpredictable time or never, slows the collector, can resurrect objects, and was deprecated for removal in Java 18 (JEP 421). Release resources with try-with-resources; java.lang.ref.Cleaner is a last-resort safety net. (L04)

6.5 Collectors and GC logs

Throughput versus latency: which collector for a nightly batch job, and which for a low-latency API?
Batch: Parallel. Only total run time matters, and with no concurrent work it has the highest throughput; long pauses hurt nobody. Low-latency API: ZGC for strict, sub-millisecond-scale pause needs or huge heaps; otherwise G1, the default, with its pause goal. Shorter pauses are always paid for with background CPU and barriers — that is, throughput. (L05)
How does G1 work?
The heap is split into equal regions, each with a role: Eden, survivor, old, humongous or free. When the old generation reaches a threshold, G1 marks it concurrently, finishing with short Remark and Cleanup pauses. It then runs mixed collections that evacuate the young regions plus the old regions with the most garbage (“garbage first”), sizing each collection set to the pause goal -XX:MaxGCPauseMillis (default 200 ms). Objects of at least half a region are humongous. If G1 falls behind, it falls back to a full GC. (L05)
How does ZGC keep pauses under a millisecond, and what does it cost?
It marks and moves objects concurrently. A load barrier on every reference read checks whether the referenced object has moved and fixes the reference before use, so the stop-the-world parts stay tiny and do not grow with heap size. The costs: the barrier on every read, background CPU, and the heap headroom it needs — so usually lower throughput than Parallel or G1. Java 21 added a generational mode (-XX:+ZGenerational). (L05)
Read this line: GC(14) Pause Young (Concurrent Start) (G1 Humongous Allocation) 48M->45M(64M) 3.112ms.
The 15th collection was a G1 young pause, triggered by allocating a humongous object, that also starts a concurrent marking cycle. Heap use went from 48 MB to 45 MB in a 64 MB committed heap: it freed almost nothing, so live data is close to filling the heap. The pause lasted 3.1 ms. Worth watching: a nearly full heap and frequent humongous allocations. (L05)
Which numbers in a GC log matter most, and why not the average pause?
The count of full GCs (ideally zero); the maximum pause (what the unluckiest request felt); and the heap after full GCs over time (live data — rising means a leak). An average spreads one long full GC across thousands of short pauses until it disappears. (L05)
Which collector runs if you set none? Can it surprise you?
G1 since Java 9 — unless the JVM judges the machine small (roughly fewer than 2 CPUs or less than about 1792 MB; verify), in which case it silently picks Serial. In a container it reads the container's limits, so a 1-CPU pod may run Serial while laptops run G1. Check the Using … line in the GC log, or set the collector explicitly. (L05)
How do you enable GC logging on Java 21? On an already-running JVM?
Start-up: -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=10m, using unified logging (the old -XX:+PrintGCDetails/-Xloggc are pre-Java-9). Running JVM: jcmd <pid> VM.log output=gc.log what=gc. GC-level logging is cheap enough to leave on permanently. (L05)

6.6 The JIT

Why is the first run of code slow and the tenth fast?
At first, classes are being loaded and initialized, the code runs in the interpreter, then in C1 code that is still profiling, while C1 and C2 compile on background threads. Once C2 installs optimised code (and OSR switches running loops over), it runs at full speed. That settling-in period is warm-up, and it is why a cold timing measures the wrong thing. (L01, L06)
Explain tiered compilation.
Methods climb tiers as their call and loop counters cross thresholds: 0 (interpreter), then usually 3 (C1 with full profiling), then 4 (C2, optimised using that profile). Trivial methods go to tier 1 (C1, no profiling). Tier 2 is used when C2 is busy. C1 gives fast start-up and gathers the profile; C2 gives peak speed. (L06)
What is on-stack replacement?
Compiling a method while one of its loops is running, then transferring the loop's live state into the compiled code mid-loop. It is triggered by the back-edge counter, so a long loop in a method called only once — such as main — still gets compiled. Marked % in -XX:+PrintCompilation. (L06)
Why is inlining called the mother of all optimisations? What blocks it?
Copying a callee into its caller removes the call and lets the compiler see across the boundary, enabling constant folding, dead-code removal and escape analysis. It is blocked by megamorphic call sites (three or more receiver classes seen), very large methods, and cold call sites. Monomorphic and bimorphic sites are inlined behind cheap type checks. (L06)
What is escape analysis? Does it mean allocation is free?
After inlining, C2 checks whether each object can escape — be returned, stored in a field, passed to non-inlined code, or thrown. If not, it can scalar-replace the object (its fields become locals; no allocation) and elide locks on it. It is not universal: only C2 does it, only in hot code, and anything that escapes on any path keeps its allocation. So: short-lived local allocation is far cheaper than intuition says — measure before you pool. (L06)
What is deoptimization? Is it safe?
C2 compiles using speculative assumptions — a branch is never taken, a call site sees one class, only one implementation is loaded. When one breaks, the compiled code is made not entrant, running frames are converted back to interpreter frames, and the method later recompiles. It is completely safe: results never change, only speed dips briefly. (L06)
How do you benchmark Java code properly?
With JMH. It runs warm-up iterations before measuring, forks fresh JVMs so profiles do not leak between benchmarks, and provides a Blackhole that consumes results so the JIT cannot delete the work. A one-off nanoTime measurement mostly times the interpreter and the compiler. (L01, L06)
Should I hand-inline small methods or pool short-lived objects for speed?
Almost never. The JIT inlines hot small methods and may remove non-escaping allocations, so the “optimisation” only helps cold code that does not matter. Pooling can even hurt: pooled objects live long, get promoted, and cost the collector more. Write clear code and optimise what a profiler shows is hot. (L06)

6.7 Diagnosing a live JVM

A service's memory grows steadily for days. How do you investigate, step by step?
First, confirm it is the heap: does the GC log show the heap-after-full-GC level rising? Next, take two class histograms (jcmd <pid> GC.class_histogram) minutes apart and look for your own classes growing in step with load. Then take one heap dump at a quiet moment and open it in MAT or VisualVM: retained size points at the holder, and the path to GC roots names the field. Fix the removal rule, and confirm with flat histograms. Make sure -XX:+HeapDumpOnOutOfMemoryError is set for next time. (L05, L07)
An application is frozen, the CPU is idle, nothing logs. What do you do?
Take thread dumps (jcmd <pid> Thread.print or jstack), three of them a few seconds apart. Look for threads BLOCKED on each other's monitors; HotSpot prints “Found one Java-level deadlock” for simple cases. Also look for threads all waiting on one exhausted resource, such as a connection pool. A thread in the same frame in all three dumps is stuck. The usual deadlock fix is a consistent lock order. (L07)
Shallow size versus retained size?
Shallow size is the object itself — header and fields. Retained size is everything that would be freed if the object were collected: the object plus all objects reachable only through it. A leaking HashMap may be 48 bytes shallow and hundreds of megabytes retained. Histograms show shallow sizes; heap-dump tools compute retained sizes via the dominator tree. (L07)
What are the risks of taking a heap dump in production?
It pauses the JVM, for seconds on a large heap. It needs disk roughly equal to the live heap and can fill the disk. And it contains every value in memory — passwords, tokens, personal data — so it must be stored securely and deleted afterwards. Prefer histograms first, and dump during low traffic or from an instance removed from the load balancer. (L07)
jcmd cannot attach to the JVM. Why might that be?
Attaching works only on the same machine, as the same operating-system user that started the JVM, and inside a container only from within that container (docker exec/kubectl exec). The process may also have exited, or been started with attaching disabled. (L07)
Which jcmd commands would you reach for first?
VM.version and VM.flags (what is running and how); GC.heap_info (generation sizes); Thread.print (threads); GC.class_histogram (what fills the heap); GC.heap_dump (full evidence, carefully); VM.log (switch on GC logging live); JFR.start (low-overhead recording). jcmd <pid> help lists everything. (L07)

7 Predict-the-output puzzles

Interviewers love these, because they test the model rather than the vocabulary. Predict before you open.

Puzzle 1 — references

static void a(List<String> l) { l.add("x"); }
static void b(List<String> l) { l = new ArrayList<>(); l.add("y"); }
static void c(int n) { n++; }

List<String> list = new ArrayList<>();
int n = 1;
a(list); b(list); c(n);
System.out.println(list + " " + n);
Click to reveal the answer

[x] 1. a mutates the shared object through a copied reference. b repoints only its own parameter slot; the new list becomes garbage when b returns. c increments a copy of the number. (L03)

Puzzle 2 — class initialization

class P { static { System.out.println("P"); } static final int K = 1; static int v = 2; }
class C extends P { static { System.out.println("C"); } }

System.out.println(C.K);
C[] arr = new C[2];
System.out.println(C.v);
System.out.println(new C() != null);
Click to reveal the answer

1, then P, 2, then C, true. K is a compile-time constant, inlined, so nothing initializes. An array of C initializes nothing. C.v is declared in P, so only P initializes. new C() finally initializes C (P is already done). (L02)

Puzzle 3 — reachability

static List<Object> cache = new ArrayList<>();

Object a = new Object();            // A
Object[] pair = { new Object() };   // B (inside an array)
Node x = new Node(), y = new Node(); // C, D
x.next = y; y.next = x;
cache.add(new Object());           // E
x = null; y = null; pair = null;
// which of A-E are garbage here (a is still used below)?
System.out.println(a);
Click to reveal the answer

Garbage: B (its array is unreachable), C and D (a cycle no root reaches). Reachable: A (a live local, used afterwards) and E (held by a static field — the shape of a leak). “Garbage” means eligible; collection happens at the next GC. (L04)

Puzzle 4 — the stack

class Team   { Player captain; public String toString() { return "Team(" + captain + ")"; } }
class Player { Team team;      public String toString() { return "Player(" + team + ")"; } }

Team t = new Team(); Player p = new Player();
t.captain = p; p.team = t;
System.out.println(t);
Click to reveal the answer

StackOverflowError. The two toStrings call each other forever, each call pushing a frame, until the thread's stack runs out. The trace repeats a two-method cycle — the diagnosis is in the pattern. Raising -Xmx does nothing; the fix is to break the cycle in toString. (L03)

Puzzle 5 — the JIT

static int len(int x, int y) { Point p = new Point(x, y); return p.x() * p.x() + p.y() * p.y(); }
// called 10 million times in a hot loop - how many Point objects end up on the heap?
Click to reveal the answer

Typically: some during warm-up (interpreter and C1 really allocate), then roughly none. Once C2 compiles the hot loop with len inlined, escape analysis proves p never escapes and scalar-replaces it. With -XX:-DoEscapeAnalysis, all ten million are allocated. The result is identical either way. (L06)

9 How to answer well

Strong answers to JVM questions follow the same four-step shape. Practise it on any question in Section 6:

  1. Mechanism. Say what actually happens: “the reference is copied into the callee's frame”, “C2 proves the object never escapes”.
  2. Consequence. Say what that means for the code: “so the caller sees mutations but not reassignment”.
  3. Evidence. Say how you would check it on a real JVM: javap -c, a GC log line, -XX:+PrintCompilation, two histograms. This is what separates practitioners from people who have read about it.
  4. Trade-off. Say what it costs or where it stops being true: “ZGC's short pauses cost throughput”, “escape analysis only helps hot code”.

Phrases to retire: “Java is pass-by-reference for objects” · “GC means no memory leaks” · “System.gc() frees memory” · “Java is slow because it's interpreted” · “object creation is expensive” · “just give it more heap”. Phrases that signal depth: “reachable from a GC root” · “the heap after full GCs” · “the max pause, not the average” · “it depends on whether the object escapes” · “I'd take two histograms before a heap dump” · “let me check which collector is actually running”.

When you are unsure of a default or a flag name — and HotSpot defaults do change — say so, and say how you would verify it (-XX:+PrintFlagsFinal, jcmd <pid> VM.flags). Interviewers trust “I'd verify that on the JDK we run” far more than a confidently wrong number.

10 Night-before checklist

If you can say each of these in one breath, with the reason, you are ready.

  1. JDK = build + run, JRE = run, JVM = the engine.
  2. Bytecode is portable; Java release = major version − 44; old JVMs refuse new class files.
  3. new = new / dup / invokespecial; string + and lambdas = invokedynamic.
  4. Three loaders, parent delegation, identity = name + loader.
  5. What triggers class initialization — and that constants are inlined.
  6. ClassNotFoundException = by name; NoClassDefFoundError = missing at run time; “Could not initialize” = earlier <clinit> failure.
  7. Stack per thread, heap shared, Metaspace for classes, code cache for compiled code.
  8. Java is pass-by-value; references are copied.
  9. The words after the colon in an OutOfMemoryError decide the investigation.
  10. Garbage = unreachable from GC roots; cycles do not matter.
  11. Leak = reachable but unwanted; eligible ≠ collected; System.gc() is a request.
  12. Most objects die young; minor GC copies survivors and wipes Eden; promotion at the threshold.
  13. Minor / major / full; card table for old → young references.
  14. Serial, Parallel, G1, ZGC — the throughput-versus-pause trade-off for each.
  15. G1: regions, concurrent marking, mixed collections, pause goal, humongous, full-GC fallback.
  16. Read a GC line; watch full-GC count, max pause, heap after full GCs.
  17. Tiers 0 → 3 → 4, OSR, inlining, escape analysis, deoptimization.
  18. Never trust a cold timing; JMH.
  19. jcmd: threads, histograms, heap dumps; three thread dumps; two histograms.
  20. Retained size and path to GC roots; heap dumps are sensitive and pause the JVM.
