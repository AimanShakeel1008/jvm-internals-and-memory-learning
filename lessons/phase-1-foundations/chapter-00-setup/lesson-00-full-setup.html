Core Java · Course 01 · JVM Internals & Memory

Lesson 00 — Full Setup

Choose every version once. Write it into files that live with the code. Make the machine prove what it is before anything else runs.

Position: Lesson 00 of 07 (the setup lesson)  ·  Prerequisites: none  ·  Project files: pom.xml, JvmExplorer.java, JvmExplorerTest.java

You will install every tool this course uses: Java 21, Maven, Git and an editor. You will learn what each tool is for and why we fix its version.

You will also build the first small program. It asks Java about itself. A test then checks that your machine runs the right Java.

1 The pain

Same code, two machines, two results

Picture two people working on the same small Java program. Their names are Priya and Sam. On Priya's laptop the program compiles. (To compile means to turn the code you typed into a form the computer can run.) Every test passes.

Priya sends the exact same code to Sam. On Sam's laptop, things go wrong:

  • The compiler rejects one of her lines.
  • A test fails with a strange message.
  • The build quietly downloads a different version of a helper library.

The code did not change. The machines are different. Sam has an older Java and a different build tool. Nobody wrote down which library versions the project needs.

This problem is so common it has a joke name: “works on my machine.” The hours it costs are wasted. Nobody is fixing a real bug. They are fixing a disagreement between two computers.

The same trap, with just you

Now picture just one person: you, three weeks from now. In those weeks you installed some other tool. Without telling you, it put a different Java first on your computer. Lesson code that worked before now acts a little differently.

That matters a lot in this course. This course is about watching exactly what Java does inside. Suppose Java's memory clean-up report suddenly looks different. Is that a fact about Java? Or a fact about the upgrade you did by accident? You cannot tell.

The cure

The cure is boring, but it works every time. It has three parts:

  1. Choose every version once.
  2. Write that choice into files that live with the code.
  3. Make the machine prove what it is before anything else runs.

That is all this lesson does. It looks like installing tools. But it is really the first lesson about Java's inner workings. Our first program asks Java about itself: its version, its maker, and its memory limit. We also build a test. The test fails loudly if the machine stops matching what we agreed.

3 The concept explained

We meet each tool in the order they depend on each other:

  1. The thing that runs Java at all.
  2. The thing that builds projects.
  3. The thing that tests them.
  4. The thing that keeps their history.

Take it slowly. Everything later in the course stands on these.

3.1 What actually runs your Java code

A puzzle

Start with a puzzle. A program compiled on Windows normally cannot run on Linux. Why not?

Every computer has an operating system. That is the main program that runs the computer, such as Windows, macOS or Linux. A compiled program is a list of instructions for one kind of machine and one operating system. Different machines follow different rules. So a program built for one usually means nothing to another.

Yet compiled Java runs on Windows, macOS and Linux, unchanged. How?

The answer: an imaginary machine

The trick is that Java is not compiled for any real machine. It is compiled for an imaginary machine. The rules of this machine are written down exactly on paper. But nobody has ever built it as real hardware.

On every real computer, you install a program whose whole job is to pretend to be that imaginary machine. Here is how it works:

  1. Your Java code is compiled into instructions for the imaginary machine.
  2. The pretender program reads those instructions one by one.
  3. It carries out each one on the real computer underneath.

Your compiled program only ever talks to this pretender. So it never notices which real computer it is on.

Think of an interpreter at a meeting. You speak only English. The interpreter repeats your words in French, Japanese or Arabic, depending on the room. You never need to learn those languages. The interpreter handles each room.

A program that plays the part of a machine like this is called a virtual machine. (“Virtual” means “not physically real, but acting as if it were.”) The one that plays Java's imaginary machine is the Java Virtual Machine — the JVM.

Why the JVM matters so much

The JVM is the main character of this whole course. It does four big jobs:

  • It runs your compiled code.
  • It holds your objects in its memory.
  • It cleans up objects you no longer use.
  • It speeds up your code while it runs.

Each of these jobs gets its own lesson later. (How your source code becomes instructions for the imaginary machine is the topic of Lesson 01.)

JDK, JRE and JVM — three names people mix up

People mix up three names all the time. Let us make them clear, smallest first:

  • The JVM runs code that is already compiled. It cannot compile anything itself.
  • Every program uses a huge set of ready-made classes, like String and ArrayList. This set is called the standard library. The JVM plus the standard library is the least you need to run Java programs. This run-only bundle is called the JRE — Java Runtime Environment. Modern Java no longer offers the JRE as a separate download. But the name still appears in error messages and old articles, so you need to know it.
  • The compiler is the tool that compiles. Java's compiler is called javac. It turns your .java files into instructions the JVM understands. The JRE plus developer tools like javac is called the JDK — Java Development Kit. As a developer, you always install a JDK.

Who makes the JDK?

“The JDK” is not one product from one company. Java's source code is open for anyone to read and use. It lives in a public project called OpenJDK.

Several groups take that shared source and turn it into packages you can install. They include Eclipse Adoptium, Oracle, Amazon, Microsoft and others. Think of the same novel printed by different publishers. The story inside is the same. Only the cover differs.

This course uses Eclipse Adoptium's package, which is called Temurin. It is free for any use, and most people pick it.

The JVM inside all these packages has a name too: HotSpot. Remember that name. When this course says “the JVM does X,” it means HotSpot. Our first program will print that name, so you can see it is really there.

Why does compiled Java run unchanged on Windows and Linux?
Because javac does not compile for any real machine. It compiles for an imaginary one. Each real computer runs a JVM. The JVM pretends to be that imaginary machine on top of the real hardware. Your program only ever talks to the JVM. So it never notices the real operating system or chip underneath.

3.2 Why version 21, and what “pinned” means

Why Java 21

Java releases a new version every six months. Most versions get fixes for only six months. That is fine for quick experiments. It is bad for a long series of 19 courses.

Every couple of years, one version gets a special promise: fixes and security updates for years. A version with that long promise is called an LTS — Long-Term Support release. Java 21 is an LTS release. Many companies use it. It has every feature this series needs. So the whole series uses Java 21.

What pinning means

Pinning a version means three things together:

  1. The version is written into saved project files. (pom.xml says 21, and the almanac records it.)
  2. The build checks it automatically, every time.
  3. Nobody changes it without a good reason.

Why bother? When code acts strangely, you can rule out “wrong version somewhere” in seconds. You run one test, and you know.

This course watches exact JVM behaviour, so that certainty really matters. Many things we will study change between versions. Examples are memory clean-up settings, report formats and speed-up behaviour.

Pinning is a promise to manage versions, not to freeze them forever. Small updates such as 21.0.1 and 21.0.2 are called patch releases. They fix bugs and security holes (weak spots attackers could use). They add no new features. If you stay on one exact build for years, those holes stay open.

Real teams upgrade on purpose, on a schedule, and re-check everything when they do. That is why our test checks only the major version. The major version is the first number: 21 in 21.0.7. The test accepts any patch release of 21.

3.3 Maven — the build tool

Life without a build tool

Imagine there were no build tool. To build even our small project, you would have to do all of this yourself:

  • Download the JUnit testing library from the internet. Then find and download, by hand, every other library JUnit needs.
  • Run javac with a correctly spelled list of every source file and where every library lives.
  • Keep compiled test code out of the finished program.
  • Run the tests.
  • Package the result.

You would retype every step, in the right order, every time. Your teammate would need your exact downloads to get the same result. People really worked this way, and it was miserable.

What Maven does

A build tool is a program that does all of those steps for you, from one written description. The standard one for Java is Maven. (Another popular one is called Gradle.)

Here is the deal. In one file, you write down what the project is: its name, its Java version, and which libraries it uses. Maven then works out how to build it.

That file is called pom.xml. POM stands for Project Object Model. That just means “the project, written down in a fixed format.” The file always sits in the project's top folder.

Words you will see in a POM

  • Library and dependency. A library is ready-made code that someone else wrote for others to use. A dependency is a library your project needs. You name it in the POM. Maven downloads it for you, plus everything that library needs. Our only dependency is JUnit.
  • Coordinates. Every library (and your own project) is named by three parts, like a postal address:
    • groupId says who made it. It is written like a web address turned backwards, e.g. org.junit.jupiter.
    • artifactId says which product, e.g. junit-jupiter.
    • version says which edition, e.g. 5.13.4.
    We need three parts because names clash. Dozens of libraries are simply called “core”.
  • Maven Central. This is a public online store of libraries. Maven downloads from it. It keeps a copy of each download in a folder on your machine (C:\Users\<you>\.m2\repository on Windows). So each library downloads only once. The first build is slow and prints many Downloading… lines. Later builds are quick and quiet.
  • Plugins. Maven itself only organises the work. The real work is done by plugins. A plugin is an add-on that does one job. One calls the compiler. One runs tests. One runs your main class. Plugins have versions too, and our POM pins each one.
  • SNAPSHOT. Our own version is 1.0-SNAPSHOT. The ending SNAPSHOT is Maven's way of saying “still changing, not finished yet”. That fits a project that grows every lesson.

What goes wrong without pinning

Here is a POM that looks fine and builds fine today. But it is broken in a way you will not notice for weeks:

<!-- WRONG: builds today, drifts tomorrow -->
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>RELEASE</version>   <!-- "whatever is newest when you build" -->
</dependency>
<!-- ...and no <maven.compiler.release> at all, and no plugin versions. -->

Three separate problems hide in there. Each one lets the build change without anyone noticing:

  1. RELEASE means “the newest version on the day you build.” Two builds of the same code, a month apart, can use different JUnit versions. Then they can give different results.
  2. There is no maven.compiler.release line. So each machine decides which Java version to compile for. Priya's says 21. Sam's says 17. Code that needs Java 21 builds for her but not for him.
  3. There are no plugin versions. So each Maven install picks its own compiler plugin and test runner.

The cure is simple: write every one of those numbers down. That is exactly what our POM does (Section 4).

Where files go

Maven also decides where files go. Every Maven project uses the same folder layout. A shared habit like this is called a convention. Because everyone follows it, you can open any Maven project and find your way around.

jvm-explorer/
    pom.xml                                   <- the recipe card (committed)
    src/main/java/com/corejava/jvm/           <- the real program code (committed)
    src/test/java/com/corejava/jvm/           <- the test code (committed)
    target/                                   <- Maven's generated output (NEVER committed)

target/ is where Maven writes everything it makes. You can throw it away at any time. You never edit it, and you never save it into history. Deleting it costs nothing. In fact, that is exactly what mvn clean does.

The four Maven commands you need

You run Maven from a terminal. A terminal is a window where you type commands instead of clicking. Always run Maven inside the folder that holds pom.xml:

CommandWhat it does
mvn compileCompiles the main source code into target/
mvn testCompiles everything, then runs all tests and reports pass or fail
mvn cleanDeletes target/, so the next build starts completely fresh
mvn exec:javaRuns the project's main class (our POM says which one)

Honest limit: for a tiny 30-line program you will throw away, Maven plus tests plus Git is far more than you need. The command java One.java (Java 11 and later) compiles and runs a single file in one step. That is the right tool there. In this course, small throwaway programs go into a clearly labelled experiments/ package inside the project. They do not get projects of their own.

3.4 JUnit — tests that check themselves

Without tests, how do you know the project still works? You run the program and read the output by eye. As the project grows, you must re-read everything after every change. In real life, people stop checking. Then they break things without noticing.

A unit test fixes this. It is a small piece of code that checks a piece of real code for you. It works in three steps:

  1. It calls the real code.
  2. It states what must be true about the result.
  3. A testing tool runs all such checks and prints pass or fail.

The standard testing tool for Java is JUnit. It is a framework: ready-made code that does the common work (finding tests, running them, reporting), while you write only your part (the checks). We pin version 5.13.4 of JUnit 5.

Inside a test, each “this must be true” line is called an assertion. For example, assertEquals(21, actualVersion) passes quietly if the value is 21. If the value is anything else, it fails the test loudly.

This course builds one habit: every new thing jvm-explorer can do comes with a test. So mvn test answers “did I break anything?” with one command. Run it any time, and always before saving your work into history.

3.5 Git and GitHub — the project's memory

Life without version control

Without version control, a project's history is a pile of folders with names like project-final-v2-REALLY-FINAL/. One bad edit, with no copy left, loses work for good.

A version control system is a program that saves snapshots of your files over time. With it you can see what changed, when, and why. You can also go back to any earlier state. The standard one is Git.

Git's words, in plain language

  • Repository (“repo”). A folder whose history Git is tracking. It holds your normal files plus a hidden .git folder. That hidden folder stores every saved snapshot. This course folder is a repo. That is why it contains .git/.
  • Commit. One saved snapshot, with a message saying what changed. Making one takes two steps:
    1. git add <files> picks which changes to include. (git add . means “every change in this folder”.)
    2. git commit -m "message" saves them into history.
  • GitHub and remote. History on one disk is lost if that disk breaks. GitHub is a website that keeps copies of Git repos online. It is a backup that you can also share. The online copy linked to your local repo is called the remote. git push uploads your new commits to it.
  • .gitignore. A file that lists names Git must pretend not to see. So git add . can never include them by accident. Ours lists two kinds of thing:
    • Generated output, such as target/, *.class and editor settings folders. Saving these makes history huge. It also causes pointless clashes when two people's machines generate slightly different copies.
    • This course's three private control files: CLAUDE.md, curriculum.md and progress-tracker.md.

The order rule that cannot be undone: .gitignore must exist before the first git add .. Git only ignores files that are not already in history.

If you commit first, thousands of files from target/, plus private files, are saved forever. Adding .gitignore later does not remove them. Your repo was set up in the right order.

The one-time setup

For a brand-new project, the one-time setup is below. Your repo has already done this. It is shown so you know what created it:

git init                                    # turn this folder into a repository
# ...write .gitignore FIRST...
git add .
git commit -m "chore: initial course setup"
git branch -M main                          # name the main line of history "main"
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main                     # first upload; -u remembers where to push

The pattern for the rest of the course is one lesson → one commit → one push. Messages look like lesson: 01/lesson-XX - <title>. Every lesson ends by giving you the exact commands.

3.6 The IDE

You could write Java in Notepad. But you would be typing blind. You would get no red line under a typo and no auto-complete. You could not rename a thing everywhere with one key, or click on a test result.

An IDE — Integrated Development Environment fixes this. It is one program that combines an editor, live error-checking, code navigation and test running.

We recommend IntelliJ IDEA Community Edition. It is free and has the best Java support. (VS Code with the “Extension Pack for Java” is a fine, lighter choice.)

One honest warning. IntelliJ keeps its own list of JDKs and its own test runner. So it can disagree with the pinned setup. In this course, the terminal command mvn test has the final say. The IDE is just a comfortable place to read and write code.

3.7 How your computer chooses a Java — and the classic trap

PATH: how the terminal finds java

When you type a command like java, the operating system searches a list of folders, in order. It runs the first match it finds. That list is called the PATH.

When an installer offers to “add to PATH”, it means it will put its folder on that list. If several Javas are installed, the winner is simply the one that comes first in the list.

JAVA_HOME: how Maven finds Java

Many Java tools also read a setting you create, usually named JAVA_HOME. It holds the folder where your JDK is installed.

A named setting like this is called an environment variable. The operating system keeps it, and any program can read it. PATH is an environment variable too.

Maven uses JAVA_HOME to choose which Java to run with. So if JAVA_HOME is missing, or points at an old JDK, Maven goes wrong. This can happen even when java -version looks perfect.

See the trap for yourself

This is the most common first-day trap. It helps to see it before you read the fix. Remember the two rules:

  • java -version follows PATH.
  • mvn test follows JAVA_HOME.

In the model below, pick which JDK comes first on PATH and where JAVA_HOME points. Then read what each command reports. Watch them disagree. That disagreement is the whole bug.

3.8 The installation checklist

Do these steps in order. Each step ends with a check. If a tool is already installed, just run its check. You do not need to install it again. Fixes for every likely failure are in troubleshooting.md.

  1. JDK 21 (Temurin).
    • Go to adoptium.net. Download Temurin 21 (LTS) for Windows x64 (the .msi file).
    • In the installer, turn on both “Add to PATH” and “Set JAVA_HOME”.
    • Check in a fresh terminal. java -version must say 21.x and name Temurin.
    • Also run javac -version. It must say javac 21.x. This proves you have the full JDK, not just the run-only part.
  2. Maven.
    • Go to maven.apache.org. Download the binary zip of the current 3.9.x release. (“Binary” here means the ready-to-use program, not its source code.)
    • Unzip it somewhere it can stay, e.g. C:\tools\apache-maven-3.9.x.
    • Add its bin folder to PATH.
    • Open a fresh terminal and check. mvn -version must print the Maven version and Java version: 21.
  3. Git.
    • Go to git-scm.com and install with the default options.
    • Check with git --version.
    • Tell Git who you are, once: git config --global user.name "Your Name" and git config --global user.email "you@example.com".
  4. GitHub. Create an account at github.com. Then create an empty repository (with no auto-generated README). This is already done for this repo. The remote is connected.
  5. IDE.
    • Install IntelliJ IDEA Community Edition from jetbrains.com/idea.
    • Open the jvm-explorer folder.
    • Go to File → Project Structure → SDK. (SDK is IntelliJ's word for the JDK a project uses.) Check that it is the Temurin 21 you installed.

4 Applied to jvm-explorer

This lesson creates the project. It has three files, all saved to disk:

  • jvm-explorer/pom.xml — the pinned build recipe.
  • jvm-explorer/src/main/java/com/corejava/jvm/JvmExplorer.java — the program's starting point.
  • jvm-explorer/src/test/java/com/corejava/jvm/JvmExplorerTest.java — the tests that check your machine.

4.1 The pins, in pom.xml

Every line of the POM has a comment in the file itself. These are the lines that fix the three problems from Section 3.3:

<!-- Compile for Java 21 and ONLY Java 21, on every machine. -->
<maven.compiler.release>21</maven.compiler.release>

<!-- One exact JUnit version, named once and reused below. -->
<junit.version>5.13.4</junit.version>

<!-- Every plugin pinned, so the compiler and test runner never differ. -->
<artifactId>maven-compiler-plugin</artifactId>   <version>3.13.0</version>
<artifactId>maven-surefire-plugin</artifactId>   <version>3.5.2</version>
<artifactId>exec-maven-plugin</artifactId>       <version>3.5.0</version>

The Surefire plugin is the part of Maven that finds and runs your tests. Its version matters more than it looks. Old versions cannot see JUnit 5 tests at all. They do not show an error. They just report Tests run: 0, which is easy to miss.

4.2 The program

The first program asks the running JVM to describe itself. Every line has a comment saying why it is there:

// Every Java file declares which package it belongs to. A package is a named
// folder for classes; Maven REQUIRES the folder path on disk to match this line.
package com.corejava.jvm;

// The front door of jvm-explorer. For Lesson 00 its only job is to prove the
// toolchain works end to end by asking the running JVM to describe itself.
// "final" because nothing should ever extend this entry point.
public final class JvmExplorer {

    // The method the JVM looks for, by this exact signature, when told to run this
    // class. No object is created first, which is why it must be static; it must be
    // public so the JVM (outside our package) is allowed to call it.
    public static void main(String[] args) {

        // A banner, so our output is easy to spot among Maven's own lines.
        System.out.println("=== jvm-explorer: hello from inside the JVM ===");

        // "java.version": the exact version of the Java running RIGHT NOW - which
        // can differ from what is installed elsewhere, so we ask the JVM, not the OS.
        System.out.println("Java version : " + System.getProperty("java.version"));

        // "java.vm.name": which JVM implementation this is (expected: HotSpot).
        System.out.println("JVM name     : " + System.getProperty("java.vm.name"));

        // "java.vm.vendor": who built this JVM (Eclipse Adoptium, Oracle, ...).
        System.out.println("JVM vendor   : " + System.getProperty("java.vm.vendor"));

        // Runtime is the JVM's description of itself. maxMemory() answers "how big
        // may the heap grow?" in bytes. A long, because byte counts overflow an int
        // past about 2 GB.
        long maxHeapBytes = Runtime.getRuntime().maxMemory();

        // Bytes to megabytes, purely so the number is readable.
        System.out.println("Max heap     : " + (maxHeapBytes / (1024 * 1024)) + " MB");

        // How many CPU cores the JVM believes it may use; it sizes its own
        // clean-up threads from this number (Lessons 04 and 05).
        System.out.println("CPU cores    : " + Runtime.getRuntime().availableProcessors());
    }
}

Three ideas in there need a proper introduction.

System properties

The JVM keeps a small table of facts about itself and the machine. Each fact is a pair: a name and a value. For example, the name "java.version" has the value "21.0.7". Each entry is called a system property. System.getProperty reads one by its name.

The heap

The JVM sets aside one big pool of memory. Every object your program makes with new is stored there. That pool is called the heap.

The number we print is the largest size the heap may grow to. By default, the JVM picks it based on your machine's memory. It is often about a quarter of it. But that default changes with version and setup. So check it on your machine rather than trusting a rule. The heap is the main stage of Lessons 03–05. Today we only read its size.

CPU cores

The CPU (processor) is the chip that does the actual work in a computer. Modern CPUs contain several cores. Each core can work on one task at a time, so more cores means more work at once. The JVM uses this count to decide how many helpers to start for its own jobs.

Why does maxHeapBytes have to be a long, not an int?
An int can only go up to about 2.1 billion. Counted in bytes, that is about 2 GB. Heaps are often bigger than that. (4 GB is about 4.29 billion bytes.) An int would overflow: it would run past its limit, wrap around, and give a wrong number, often a negative one. A long can safely hold much larger numbers.

4.3 The tests

This lesson's tests are unusual. They check the machine, not our code. The first one guards against the trap from Section 3.7.

// Fails loudly if the JVM running the build is not Java 21.
@Test
void runsOnPinnedJavaVersion() {
    // Runtime.version().feature() is the major number: 21 for any 21.x.y build.
    // Major only, because patch releases (21.0.1, 21.0.2...) are all "Java 21".
    assertEquals(21, Runtime.version().feature(),
            // The failure message says what to FIX, not just what broke.
            "Expected Java 21 (the pinned course version). "
                    + "Run 'java -version' and check troubleshooting.md.");
}

// A working JVM must report a heap limit above zero.
@Test
void jvmReportsAPositiveMaxHeap() {
    assertTrue(Runtime.getRuntime().maxMemory() > 0, /* … */);
}

// And at least one CPU core - never legally fewer.
@Test
void jvmSeesAtLeastOneCpuCore() {
    assertTrue(Runtime.getRuntime().availableProcessors() >= 1, /* … */);
}

Notice what the first test checks. It checks the JVM that is actually running the tests. It does not check what java -version says in your terminal. Section 3.7 showed those can be two different Javas. This test measures the one that matters.

4.4 What happens when you run mvn test

  1. Maven starts on the Java that JAVA_HOME names. It reads pom.xml. It learns the Java 21 pin, the JUnit 5.13.4 dependency, and the three pinned plugins.
  2. For each item it needs, it looks in the local copy folder (C:\Users\<you>\.m2\repository). It downloads anything missing from Maven Central. On the first run, you see a minute or more of Downloading… lines. That is normal, and it only happens once.
  3. The compiler plugin calls javac on JvmExplorer.java for Java 21. The compiled file lands in target/classes/.
  4. It compiles the test file into target/test-classes/. JUnit is now available for this step.
  5. Surefire finds JvmExplorerTest and runs each @Test method.
  6. runsOnPinnedJavaVersion asks the running JVM for its major version and checks that it is 21. The other two tests check for a heap limit above zero and at least one core.
  7. Surefire prints the count. Maven prints BUILD SUCCESS. Or it prints BUILD FAILURE and names exactly which check broke and why.

[INFO] -------------------------------------------------------
[INFO]  T E S T S

4.5 What happens when you run the program

  1. mvn compile exec:java compiles anything out of date into target/classes/.
  2. The exec plugin reads the main class named in the POM: com.corejava.jvm.JvmExplorer.
  3. JvmExplorer.main runs inside the same Java that Maven itself is running on.
  4. The banner prints. Then the program asks the running JVM five questions. Three go to its system properties (version, name, maker). Two go to Runtime (heap limit, core count).
  5. Each answer prints as one labelled line. main ends. Maven reports success.

Predicted output of mvn compile exec:java (Maven's [INFO] lines removed). Your numbers will be different. Patch version, heap size and core count are facts about your machine. That is exactly the point:

=== jvm-explorer: hello from inside the JVM ===
Java version : 21.0.7
JVM name     : OpenJDK 64-Bit Server VM
JVM vendor   : Eclipse Adoptium
Max heap     : 4096 MB
CPU cores    : 8
[INFO] BUILD SUCCESS

From inside jvm-explorer/, run mvn clean test. Then run mvn compile exec:java. Compare both with the predictions above.

Two lines matter most. Java version should start with 21. JVM vendor should name the maker you actually installed. Project state: compiles, 3 tests green (predicted).

If what you see is different, the machine is right. troubleshooting.md covers the likely failures. The difference is itself the lesson.

5 In the wild

Real software asks the JVM the same questions we just asked. Then it adjusts itself to fit the machine.

The clearest example is our last line, Runtime.getRuntime().availableProcessors(). To understand it, you need one new word. A thread is one worker inside a running program. It carries out instructions one after another. A program can have many threads working at the same time. (Lesson 03 explains threads fully.)

Now the example. The JDK has a shared group of worker threads called ForkJoinPool.commonPool(). It does the work when you split a job across workers, for example with list.parallelStream(). Here is how it decides how many workers to create:

  1. It calls availableProcessors(), exactly like our program.
  2. It creates about one worker per core.

That is why the same program uses 4 workers on your laptop and 32 on a big server, with no setup anywhere. The JVM does the same thing when it decides how many clean-up threads to run. We will see those threads in its reports in Lesson 05.

You can see this habit in Maven too. Look at the top of your own mvn -version output. It shows the Java version, maker and operating system. Maven is doing exactly what JvmExplorer.main does, for the same reason.

Companies run their software on production machines: the real systems that real customers use. When something breaks there, the first question is not “what's the bug?”. It is “what machine, what JVM, what version?”

The automatic steps that put software live, and the checklists teams follow when something breaks, all start by printing what JvmExplorer prints. In job interviews, explaining why java -version and mvn -version can disagree shows you have real Java experience.

6 Gotchas and common mistakes

  • Checking in an old terminal. Installers change PATH and JAVA_HOME. But a terminal that was already open keeps the old values. So java -version can look broken when it is fine, or fine when it is broken. Avoid it: always open a fresh terminal after installing anything. If in doubt, restart the IDE too.
  • java -version right, Maven wrong. The terminal finds java through PATH. Maven picks its Java through JAVA_HOME. So the two can disagree. Avoid it: read the Java version: line inside mvn -version. It must say 21. (The simulation in Section 3.7 shows this.)
  • Running mvn from the wrong folder. Maven needs pom.xml in the current folder. From the repo's top folder, you get there is no POM in this directory. Avoid it: run every mvn command in this course from inside jvm-explorer/.
  • Following old tutorials. Much Java setup advice online was written for very old Java. It talks about separate JRE downloads, a CLASSPATH setting, and old POM snippets that do not work with JUnit 5. The classic sign is Tests run: 0: the tests are quietly skipped instead of failing. Avoid it: trust the pinned setup here, and treat Tests run: 0 as a failure.
  • Trusting the IDE's green tick over Maven's. IntelliJ may run tests with its own JDK and its own runner. So it can show green while mvn test shows red, or the other way round. Avoid it: the terminal has the final say. If they disagree, believe mvn test and fix the IDE's SDK setting.

7 Challenge

Your friend copies the repo and runs mvn test inside jvm-explorer/. They get BUILD FAILURE.

  • The failing test is runsOnPinnedJavaVersion.
  • The message is Expected Java 21 ... but was: 17.
  • Yet java -version in their terminal prints openjdk version "21.0.7".

Answer three questions:

  1. How can both outputs be true at the same time?
  2. Which one command from this lesson shows which Java Maven is really using?
  3. What should they fix?

Bonus: why is it good that this failure happened on day one?

Tip: try it in the simulation. Set PATH to “JDK 21 first” and JAVA_HOME to “JDK 17”.

Click to reveal the answer

(1) How both can be true. Two different lookups choose the Java in the two cases:

  • The terminal finds java by going down the PATH list. On this machine, it reaches Java 21 first.
  • Maven does not use that list. It starts the Java named by JAVA_HOME. Here, JAVA_HOME points at an installed JDK 17.

So the terminal's Java really is 21, and the Java running the tests really is 17. They are two different JVMs on the same computer. The test checked the Java actually running it (Runtime.version().feature()). That is why it caught what java -version could not.

(2) The command that shows it. mvn -version. Its output has a Java version: line that names the Java Maven runs on. It also has a runtime: line that shows where that Java is installed.

(3) The fix.

  1. Point JAVA_HOME at the JDK 21 folder. On Windows: Edit environment variables for your account → set JAVA_HOME to e.g. C:\Program Files\Eclipse Adoptium\jdk-21….
  2. Open a fresh terminal, because an old one keeps the old value.
  3. Check that mvn -version now says Java version: 21.
  4. Run mvn test again.
# PREDICTED output after the fix (trimmed):
[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS

Bonus. The mismatch showed up on day one, as one loud failure with a clear message. Without the test, it would show up weeks later. The JVM would quietly behave differently from the lesson text, with no error at all. The test turns a hidden problem into an instant, labelled failure. That is the whole reason runsOnPinnedJavaVersion exists. It is also the whole point of pinning.

8 Almanac update

The almanac is this course's cheat-sheet file, almanac.md. These rules were added to it:

  • The pinned-version table for the series.
  • JDK = build + run, JRE = run only, JVM = the engine.
  • Never use RELEASE or leave versions out. Write every number down.
  • .gitignore comes before the first git add ..
  • PATH picks your terminal's java. JAVA_HOME picks Maven's. Check mvn -version, always in a fresh terminal.

  • Never commit target/.
  • The terminal beats the IDE.
  • The machine's real output always beats a prediction.

9 Key words

Every new term from this lesson, with a one-line meaning. Come back here whenever a word feels fuzzy.

Compile
Turn the code you typed into a form a computer (or the JVM) can run.
Operating system
The main program that runs a computer, such as Windows, macOS or Linux.
Virtual machine
A program that pretends to be a computer. It carries out instructions meant for an imaginary machine.
JVM (Java Virtual Machine)
The program that runs compiled Java. It holds your objects, cleans up unused ones, and speeds up busy code.
Standard library
The big set of ready-made classes that comes with Java, like String and ArrayList.
JRE (Java Runtime Environment)
The JVM plus the standard library. Enough to run Java, not to compile it.
Compiler / javac
The tool that turns .java files into .class files the JVM can run.
JDK (Java Development Kit)
The JRE plus developer tools like javac. This is what you install.
OpenJDK
The public, open project that holds Java's shared source code.
Temurin
Eclipse Adoptium's free JDK package. The one this course uses.
HotSpot
The name of the JVM inside standard JDK packages.
LTS (Long-Term Support)
A Java version that gets fixes for years, not months. Java 21 is one.
Patch release
A small update (like 21.0.2) that fixes bugs and security holes but adds no features.
Major version
The first number of a version: 21 in 21.0.7.
Pinning
Choosing a version once, writing it into project files, and having the build check it.
Build tool
A program that fetches libraries, compiles, tests and packages a project from one description.
Maven
The standard Java build tool. It reads pom.xml.
POM / pom.xml
The one file that describes a Maven project: name, Java version, libraries, plugins.
Library
Ready-made code someone wrote for others to use.
Dependency
A library your project needs. Maven downloads it, plus everything it needs.
Coordinates
The three-part name of a library: groupId (who), artifactId (what), version (which edition).
Maven Central
The public online store Maven downloads libraries from.
Plugin (Maven)
An add-on that does one build job, such as compiling or running tests.
Surefire
The Maven plugin that finds and runs your tests.
SNAPSHOT
A version ending that means “still changing, not finished”.
Convention
A shared habit everyone follows, like Maven's fixed folder layout.
target/
The folder where Maven puts everything it makes. Safe to delete. Never committed.
Terminal
A window where you type commands instead of clicking.
Unit test
A small piece of code that checks a piece of real code and reports pass or fail.
Framework
Ready-made code that does the common work, so you only write your own part.
JUnit
The standard Java testing framework. We use version 5.13.4.
Assertion
One “this must be true” line in a test, like assertEquals(21, version).
Version control system
A program that saves snapshots of your files so you can see and undo changes.
Git
The standard version control system.
Repository (repo)
A folder whose history Git is tracking.
Commit
One saved snapshot with a message. Made with git add then git commit.
GitHub
A website that keeps online copies of Git repos.
Remote
The online copy of your repo that git push uploads to.
.gitignore
A file listing names Git must ignore. Must exist before the first git add ..
IDE
One program that combines an editor, error-checking and test running, like IntelliJ IDEA.
PATH
The ordered list of folders the system searches when you type a command like java.
Environment variable
A named setting the operating system keeps for programs to read, like PATH.
JAVA_HOME
An environment variable naming your JDK folder. Maven uses it to pick its Java.
System property
One name/value fact the JVM keeps about itself, read with System.getProperty.
Heap
The JVM's big memory pool where every object made with new lives.
CPU / core
The CPU is the chip that does the work. A core is one part of it that can run one task at a time.
Overflow
When a number runs past the largest value its type can hold and wraps around to a wrong value.
Thread
One worker inside a program, carrying out instructions in order. Explained fully in Lesson 03.
Production
The real system that real customers use, as opposed to your own laptop.

10 Quick recap

  • The JVM pretends to be one imaginary machine, so compiled Java runs unchanged on any computer. The JDK is the JVM plus developer tools, and it is what you install.
  • This series pins Java 21 (LTS), Maven 3.9.x and JUnit 5.13.4 in saved project files. Versions that are not pinned change quietly and spoil every observation.
  • Maven reads pom.xml and builds the same way on any machine. Everything it makes goes into target/, which is never committed.
  • mvn test answers “did I break anything?” in one command. Our first tests fail loudly if the Java running the build is not 21.
  • PATH picks the terminal's Java and JAVA_HOME picks Maven's, so they can disagree. And .gitignore must exist before the first git add ..
