Core Java · Course 01 · JVM Internals & Memory

Lesson 00 — Full Setup

Choose every version once. Write it into committed files. Make the machine prove what it is before anything else runs.

Position: Lesson 00 of 07 (the setup lesson)  ·  Prerequisites: none  ·  Project files: pom.xml, JvmExplorer.java, JvmExplorerTest.java

1 The pain

Picture two people working on the same small Java program. On Priya's laptop it compiles and every test passes. She sends the exact same code to Sam. On Sam's laptop, the compiler rejects one of her lines. A test fails with a strange message. The build also downloads a different version of a library without telling anyone. The code did not change. The machines are different. Sam has an older Java and a different build tool. Nobody wrote down which library versions the project needs. This problem is so common it has a joke name: “works on my machine.” The hours it costs are wasted. Nobody is fixing a real bug. They are fixing a disagreement between two computers.

Now make the story about one person: you, three weeks from now. In those weeks you installed some other tool. Without telling you, it put a different Java first on your system. Lesson code that worked before now acts a little differently. That matters a lot in this course, because this course is about watching exactly what the JVM does. A garbage-collection log line looks different. A default setting has changed. Now you cannot tell if you are learning a fact about Java or a fact about the upgrade you did by accident.

The cure is boring, but it works every time: choose every version once, write that choice into files that live with the code, and make the machine prove what it is before anything else runs. That is all this lesson does. It looks like installing tools, but it is really the first JVM lesson. The first thing we build is a program that asks the JVM about itself: its version, its maker, and its memory limit. We also build a test that fails loudly if the machine stops matching what we agreed.

3 The concept explained

We meet each tool in the order they depend on each other. First comes the thing that runs Java at all. Then the thing that builds projects. Then testing. Then keeping history. Take it slowly. Everything later in the course stands on these.

3.1 What actually runs your Java code

Start with a puzzle. A program compiled on Windows normally cannot run on Linux. A compiled program is a list of instructions for one kind of machine. Different machines and operating systems follow different rules. Yet compiled Java runs on both, unchanged. How?

The trick is that Java is not compiled for any real machine. It is compiled for an imaginary machine. This machine is described exactly on paper, but nobody has ever built it as hardware. On every real computer, you install a program whose whole job is to pretend to be that imaginary machine. It reads the imaginary machine's instructions and carries them out on the real computer underneath. Your compiled program only ever talks to this pretender. So it never notices which real computer it is on. A program that plays the part of a machine like this is called a virtual machine. The one that plays Java's imaginary machine is the Java Virtual Machine — the JVM. The JVM is the main character of this whole course. Your objects live inside it. It manages memory. It cleans up objects you no longer use. It makes code faster as it runs. (How your source code becomes instructions for that imaginary machine is the topic of Lesson 01.)

People mix up three names all the time. Let us make them clear, smallest first:

  • The JVM can run code that is already compiled. It cannot compile anything itself.
  • Every program uses a huge set of ready-made classes, like String and ArrayList. This set is the standard library. The JVM plus the standard library is the least you need to run Java programs. This run-only bundle is called the JRE — Java Runtime Environment. Modern Java no longer offers it as a separate download. But the name still shows up in error messages and old articles, so you need to know it.
  • The compiler, javac, turns your .java source files into instructions the JVM understands. Everything in the JRE plus developer tools like javac is called the JDK — Java Development Kit. As a developer, you always install a JDK.

One more detail: “the JDK” is not one product from one company. Java's source code is open to everyone. It lives in a public project called OpenJDK. Several groups take that shared source and turn it into packages you can install. They include Eclipse Adoptium (its builds are named Temurin), Oracle, Amazon, Microsoft and others. It is the same engine in a different wrapper, like the same novel printed by different publishers. This course uses Eclipse Temurin. It is free for any use, and most people choose it by default. The engine inside all of them is called HotSpot. Remember that name. When this course says “the JVM does X,” it means HotSpot. Our first program will print that name, so you can see it is really there.

Why does compiled Java run unchanged on Windows and Linux?
Because javac does not compile for any real machine. It compiles for an imaginary one. Each real computer runs a JVM, and the JVM pretends to be that imaginary machine on top of the real hardware. Your program only ever talks to the JVM. So it never notices the real operating system or chip underneath.

3.2 Why version 21, and what “pinned” means

Java puts out a new version every six months. Most versions get fixes for only six months. That is fine for experiments, but bad for a 19-course journey. Every couple of years, one version is chosen to get fixes and security patches for years. A version with that long promise is called an LTS — Long-Term Support release. Java 21 is an LTS release. Many companies use it, and it has every feature this series needs. So the whole series uses Java 21.

Pinning means three things together. First, the version is written into committed files (pom.xml says 21, and the almanac records it). Second, the build checks it automatically. Third, nobody changes it on a whim. The reward: when code acts strangely, you can rule out “wrong version somewhere” in seconds. You run one test and you know. This course watches exact JVM behavior, so that certainty really matters. Garbage-collection defaults, log formats and speed-up behavior all change between versions.

Pinning is a promise to manage versions, not to freeze them forever. New patch releases (21.0.1, 21.0.2, …) carry security fixes. If you stay on one exact build for years, you stay open to known security holes. Real teams upgrade on purpose, on a schedule, and re-check everything when they do. That is why our test pins only the major version (21). It accepts any patch release of 21.

3.3 Maven — the build tool

Imagine there were no build tool. To build even our small project, you would have to do all of this yourself:

  • Download the JUnit testing library from the internet. Then find and download, by hand, every other library JUnit needs.
  • Run javac with a correctly spelled list of every source file and where every library lives.
  • Keep compiled test code out of the finished program.
  • Run the tests.
  • Package the result.

You would retype every step, in the right order, every time. Your teammate would need your exact downloads to get the same result. People really worked this way, and it was miserable.

A program that does all of that from one written description is called a build tool. The standard one for Java is Maven. (A popular other choice is called Gradle.) In one file, you write down what the project is: its name, its Java version, and which libraries it uses. Maven works out how to build it. That file is pom.xml. POM stands for Project Object Model, which just means “the project, written down as structured data”. It always sits in the project's top folder.

You will see these POM words all the time:

  • A dependency is a library your code needs. It is someone else's code that you use instead of writing it yourself. You name it in the POM. Maven downloads it for you, plus everything that library needs. Our only dependency is JUnit.
  • Every library (and your own project) is named by three coordinates, like a postal address. groupId says who made it. It is written like a web address turned backwards, e.g. org.junit.jupiter. artifactId says which product, e.g. junit-jupiter. version says which edition, e.g. 5.13.4. We need three parts because names clash. Dozens of libraries are called “core”.
  • Maven downloads libraries from a public online store called Maven Central. It keeps a copy of each download in a folder on your machine (C:\Users\<you>\.m2\repository on Windows). So each library downloads only once. The first build is slow and prints many Downloading… lines. Later builds are quick and quiet.
  • Maven itself only organises the work. The real work is done by plugins. A plugin is an add-on piece that does one job. One calls the compiler, one runs tests, one runs your main class. Plugins have versions too, and our POM pins each one.
  • Our own version is 1.0-SNAPSHOT. The ending SNAPSHOT is Maven's way of saying “still changing, not finished yet”. That fits a project that grows every lesson.

What goes wrong without pinning. Here is a POM that looks fine and builds fine today. But it is broken in a way you will not notice for weeks:

<!-- WRONG: builds today, drifts tomorrow -->
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>RELEASE</version>   <!-- "whatever is newest when you build" -->
</dependency>
<!-- ...and no <maven.compiler.release> at all, and no plugin versions. -->

Three separate problems hide in there. Each one lets the build change without anyone noticing:

  • RELEASE means two builds of the same code, a month apart, can use different JUnit versions. Then they can give different results.
  • There is no maven.compiler.release. So each machine decides which Java level to compile for. Priya's says 21. Sam's says 17. Code that needs Java 21 builds for her but not for him.
  • There are no plugin versions. So each Maven install picks its own compiler plugin and test runner.

The cure is simple: write every one of those numbers down. That is exactly what our POM does (Section 4).

Maven also answers “where do files go?” with a fixed layout that every Maven project shares. A shared habit like this is called a convention:

jvm-explorer/
    pom.xml                                   <- the recipe card (committed)
    src/main/java/com/corejava/jvm/           <- the real program code (committed)
    src/test/java/com/corejava/jvm/           <- the test code (committed)
    target/                                   <- Maven's generated output (NEVER committed)

target/ is where Maven writes everything it makes. You can throw it away at any time. You never edit it and never commit it. Deleting it costs nothing. In fact, that is exactly what mvn clean does. You run Maven from a terminal, inside the folder that holds pom.xml:

CommandWhat it does
mvn compileCompile the main source code into target/
mvn testCompile everything, then run all tests and report pass or fail
mvn cleanDelete target/, so the next build starts completely fresh
mvn exec:javaRun the project's main class (our POM says which one)

Honest limit: for a 30-line throwaway program, Maven plus tests plus Git is far more than you need. java One.java (Java 11 and later) compiles and runs a single file in one step. That is the right tool there. In this course, small throwaway programs go into a clearly labelled experiments/ package inside the project. They do not get projects of their own.

3.4 JUnit — tests that check themselves

Without tests, “does the project still work?” means running the program and reading the output by eye. As the project grows, you would have to re-read everything after every change. In real life, people stop checking and break things without noticing. A unit test is a small piece of code that checks a piece of real code for you. It calls the real code. It states what must be true about the result. A framework then runs all these checks and prints the result: pass or fail. The standard framework for this in Java is JUnit. We pin version 5.13.4 of JUnit 5.

Inside a test, each “this must be true” line is called an assertion. For example, assertEquals(21, actualVersion) passes quietly if the value is 21. If the value is anything else, it fails the test loudly. This course builds one habit: every new thing jvm-explorer can do comes with a test. So mvn test is a one-command answer to “did I break anything?” Run it any time, and always before committing.

3.5 Git and GitHub — the project's memory

Without version control, a project's history is a pile of folders with names like project-final-v2-REALLY-FINAL/. One bad edit, with no copy left, loses work for good. A version control system is a program that saves snapshots of your files over time. You can see what changed, when, and why. You can also go back to any earlier state. The standard one is Git. Here are its words, each in plain language first:

  • A repository (“repo”) is a folder whose history Git is tracking. It holds your normal files plus a hidden .git folder with every saved snapshot. This course folder is a repo. That is why it contains .git/.
  • A commit is one saved snapshot, with a message saying what changed. It takes two steps. First, git add <files> picks which changes to include. (git add . means “everything that changed in this folder”.) Then git commit -m "message" saves them into history.
  • History on one disk is lost if that disk dies. GitHub is a website that keeps copies of Git repos online. It is a backup that you can also share. The online copy linked to your local repo is called the remote. git push uploads your new commits to it.
  • A .gitignore file lists names that Git must pretend not to see. So git add . can never include them by accident. Ours lists two kinds of thing. The first is generated output (target/, *.class, IDE settings folders). Committing it makes history huge and causes pointless conflicts. The second is this course's three private control files (CLAUDE.md, curriculum.md, progress-tracker.md).

The order rule that cannot be undone: .gitignore must exist before the first git add .. Git only ignores files that are not already in history. If you commit first, thousands of files from target/, plus private files, are saved forever. Adding .gitignore later does not remove them. Your repo was set up in the right order.

For a brand-new project, the one-time setup is below. Your repo has already done this. It is shown so you know what created it:

git init                                    # turn this folder into a repository
# ...write .gitignore FIRST...
git add .
git commit -m "chore: initial course setup"
git branch -M main                          # name the main line of history "main"
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main                     # first upload; -u remembers where to push

The pattern for the rest of the course is one lesson → one commit → one push. Messages look like lesson: 01/lesson-XX - <title>. Every lesson ends by giving you the exact commands.

3.6 The IDE

You could write Java in Notepad, but you would be typing blind. There would be no red line under a typo, no auto-complete, no one-key rename, and no clickable test results. A program that puts an editor, live error-checking, code navigation and test running in one place is called an IDE — Integrated Development Environment. We recommend IntelliJ IDEA Community Edition. It is free and has the best Java support. (VS Code with the “Extension Pack for Java” is a fine, lighter choice.) One honest warning: IntelliJ keeps its own list of JDKs and its own test runner. So it can disagree with the pinned setup. In this course, the command line (mvn test) has the final say. The IDE is just a comfortable place to read and write code.

3.7 How your computer chooses a Java — and the classic trap

Two terms first. When you type a command like java, the operating system looks through a list of folders, in order. It runs the first match it finds. That list is called the PATH. When an installer offers to “add to PATH”, it means it will put its folder on that list. If several Javas are installed, the one that wins is simply the one that comes first in the list.

Many Java tools also read a setting you create, usually named JAVA_HOME. It holds the folder where your JDK is installed. (A named setting like this, kept by the operating system for programs to read, is called an environment variable. PATH is one too.) Maven uses JAVA_HOME to choose which Java to run with. So if JAVA_HOME is missing, or points at an old JDK, Maven goes wrong. This can happen even when java -version looks perfect.

This is the most common day-one trap. It helps to see it before you read the fix. Pick which JDK comes first on PATH and where JAVA_HOME points. Then read what each command reports. java -version follows PATH. mvn test follows JAVA_HOME. Watch them disagree. That disagreement is the whole bug.

3.8 The installation checklist

Do these in order. Each step ends with a check. If a tool is already installed, just run its check. You do not need to install it again. Fixes for every likely failure are in troubleshooting.md.

  1. JDK 21 (Temurin). Go to adoptium.net. Download Temurin 21 (LTS) for Windows x64 (the .msi file). In the installer, turn on both “Add to PATH” and “Set JAVA_HOME”. Then check in a fresh terminal. java -version must say 21.x and name Temurin. javac -version must say javac 21.x. This proves you have the full JDK, not just the run-only part.
  2. Maven. Go to maven.apache.org. Download the binary zip of the current 3.9.x release. Unzip it somewhere it can stay (e.g. C:\tools\apache-maven-3.9.x). Add its bin folder to PATH. Open a fresh terminal and check: mvn -version must print the Maven version and Java version: 21.
  3. Git. Go to git-scm.com and install with the default options. Check with git --version. Then tell Git who you are, once: git config --global user.name "Your Name" and git config --global user.email "you@example.com".
  4. GitHub. Create an account at github.com. Then create an empty repository (no auto-generated README). This is already done for this repo. The remote is connected.
  5. IDE. Install IntelliJ IDEA Community Edition from jetbrains.com/idea. Open the jvm-explorer folder. In File → Project Structure → SDK, check that the SDK is the Temurin 21 you installed.

4 Applied to jvm-explorer

This lesson creates the project. Three files, all saved to disk:

  • jvm-explorer/pom.xml — the pinned build recipe.
  • jvm-explorer/src/main/java/com/corejava/jvm/JvmExplorer.java — the program's entry point.
  • jvm-explorer/src/test/java/com/corejava/jvm/JvmExplorerTest.java — the environment tests.

4.1 The pins, in pom.xml

Every line of the POM has a comment in the file itself. These are the lines that fix the three problems from Section 3.3:

<!-- Compile for Java 21 and ONLY Java 21, on every machine. -->
<maven.compiler.release>21</maven.compiler.release>

<!-- One exact JUnit version, named once and reused below. -->
<junit.version>5.13.4</junit.version>

<!-- Every plugin pinned, so the compiler and test runner never differ. -->
<artifactId>maven-compiler-plugin</artifactId>   <version>3.13.0</version>
<artifactId>maven-surefire-plugin</artifactId>   <version>3.5.2</version>
<artifactId>exec-maven-plugin</artifactId>       <version>3.5.0</version>

The Surefire plugin is the part of Maven that finds and runs your tests. Its version matters more than it looks. Old versions cannot see JUnit 5 tests at all. They fail without any error, and just report Tests run: 0.

4.2 The program

The first program asks the running JVM to describe itself. Every line has a comment saying why it is there:

// Every Java file declares which package it belongs to. A package is a named
// folder for classes; Maven REQUIRES the folder path on disk to match this line.
package com.corejava.jvm;

// The front door of jvm-explorer. For Lesson 00 its only job is to prove the
// toolchain works end to end by asking the running JVM to describe itself.
// "final" because nothing should ever extend this entry point.
public final class JvmExplorer {

    // The method the JVM looks for, by this exact signature, when told to run this
    // class. No object is created first, which is why it must be static; it must be
    // public so the JVM (outside our package) is allowed to call it.
    public static void main(String[] args) {

        // A banner, so our output is easy to spot among Maven's own lines.
        System.out.println("=== jvm-explorer: hello from inside the JVM ===");

        // "java.version": the exact version of the Java running RIGHT NOW - which
        // can differ from what is installed elsewhere, so we ask the JVM, not the OS.
        System.out.println("Java version : " + System.getProperty("java.version"));

        // "java.vm.name": which JVM implementation this is (expected: HotSpot).
        System.out.println("JVM name     : " + System.getProperty("java.vm.name"));

        // "java.vm.vendor": who built this JVM (Eclipse Adoptium, Oracle, ...).
        System.out.println("JVM vendor   : " + System.getProperty("java.vm.vendor"));

        // Runtime is the JVM's description of itself. maxMemory() answers "how big
        // may the heap grow?" in bytes. A long, because byte counts overflow an int
        // past about 2 GB.
        long maxHeapBytes = Runtime.getRuntime().maxMemory();

        // Bytes to megabytes, purely so the number is readable.
        System.out.println("Max heap     : " + (maxHeapBytes / (1024 * 1024)) + " MB");

        // How many CPU cores the JVM believes it may use; it sizes its own
        // clean-up threads from this number (Lessons 04 and 05).
        System.out.println("CPU cores    : " + Runtime.getRuntime().availableProcessors());
    }
}

Two ideas in there need a proper introduction.

First, the JVM keeps a table of facts about itself and the machine. Each fact is a pair of text values: a name and a value, like "java.version" → "21.0.7". Each entry is called a system property. System.getProperty reads one.

Second, the JVM sets aside one big pool of memory. Every object your program makes with new is stored there. That pool is called the heap. The number we print is the largest size the heap is allowed to grow to. By default, the JVM picks it based on your machine's memory. It is often about a quarter of it. But that default changes with version and setup, so check it rather than trusting a rule. The heap is the main stage of Lessons 03–05. Today we only read its size.

Why does maxHeapBytes have to be a long, not an int?
An int can only go up to about 2.1 billion. Counted in bytes, that is about 2 GB. Heaps are often bigger than that (4 GB is about 4.29 billion bytes). An int would overflow and give a wrong number, often a negative one. A long can safely hold much larger numbers.

4.3 The tests

This lesson's tests are unusual. They check the machine, not our code. The first one guards against the trap from Section 3.7.

// Fails loudly if the JVM running the build is not Java 21.
@Test
void runsOnPinnedJavaVersion() {
    // Runtime.version().feature() is the major number: 21 for any 21.x.y build.
    // Major only, because patch releases (21.0.1, 21.0.2...) are all "Java 21".
    assertEquals(21, Runtime.version().feature(),
            // The failure message says what to FIX, not just what broke.
            "Expected Java 21 (the pinned course version). "
                    + "Run 'java -version' and check troubleshooting.md.");
}

// A working JVM must report a heap limit above zero.
@Test
void jvmReportsAPositiveMaxHeap() {
    assertTrue(Runtime.getRuntime().maxMemory() > 0, /* … */);
}

// And at least one CPU core - never legally fewer.
@Test
void jvmSeesAtLeastOneCpuCore() {
    assertTrue(Runtime.getRuntime().availableProcessors() >= 1, /* … */);
}

Notice what the first test checks. It checks the JVM that is actually running the tests. It does not check what java -version says in your terminal. Section 3.7 showed those can be two different Javas. This test measures the one that matters.

4.4 What happens when you run mvn test

  1. Maven starts on the Java that JAVA_HOME names. It reads pom.xml. It learns the Java 21 pin, the JUnit 5.13.4 dependency, and the three pinned plugins.
  2. For each item it needs, it looks in the local cache (C:\Users\<you>\.m2\repository). It downloads anything missing from Maven Central. On the first run, you see a minute or more of Downloading… lines. That is normal, and it only happens once.
  3. The compiler plugin calls javac on JvmExplorer.java for Java 21. The compiled file lands in target/classes/.
  4. It compiles the test file into target/test-classes/. JUnit is now available for this step.
  5. Surefire finds JvmExplorerTest and runs each @Test method.
  6. runsOnPinnedJavaVersion asks the running JVM for its major version and checks that it is 21. The other two tests check for a heap limit above zero and at least one core.
  7. Surefire prints the count. Maven prints BUILD SUCCESS. Or it prints BUILD FAILURE and names exactly which check broke and why.

4.5 What happens when you run the program

  1. mvn compile exec:java compiles anything out of date into target/classes/.
  2. The exec plugin reads the main class named in the POM: com.corejava.jvm.JvmExplorer.
  3. JvmExplorer.main runs inside the Java that Maven itself is running on.
  4. The banner prints. Then five questions go to the running JVM. Three go to its system properties (version, name, vendor). Two go to Runtime (heap limit, core count).
  5. Each answer prints as one labelled line. main ends. Maven reports success.

Predicted output of mvn compile exec:java (Maven's [INFO] lines trimmed). Your numbers will be different. Patch version, heap size and core count are facts about your machine. That is exactly the point:

=== jvm-explorer: hello from inside the JVM ===
Java version : 21.0.7
JVM name     : OpenJDK 64-Bit Server VM
JVM vendor   : Eclipse Adoptium
Max heap     : 4096 MB
CPU cores    : 8
[INFO] BUILD SUCCESS

From inside jvm-explorer/, run mvn clean test. Then run mvn compile exec:java. Compare both with the predictions above. Two lines matter most. Java version should start with 21. JVM vendor should name the vendor you actually installed. Project state: compiles, 3 tests green (predicted). If what you see is different, the machine is right. troubleshooting.md covers the likely failures, and the difference is itself the lesson.

5 In the wild

Real software uses the same calls we used to learn about the machine it runs on. Then it adjusts itself to fit. The clearest example is our last line, Runtime.getRuntime().availableProcessors(). The JDK has a shared pool of worker threads, ForkJoinPool.commonPool(). It does the work behind parallel streams like list.parallelStream(). It calls availableProcessors() to decide how many workers to create. That is why the same program uses 4 workers on your laptop and 32 on a big server, with no setup anywhere. The JVM does the same thing when it decides how many clean-up threads to run. We will see those threads in its logs in Lesson 05. Also look at the top of your own mvn -version output. It shows the Java version, vendor and operating system. Maven is doing exactly what JvmExplorer.main does, for the same reason.

On a real team, when something goes wrong in production, the first question is not “what's the bug?”. It is “what machine, what engine, what version?” Deploy pipelines, container images and incident checklists all start by printing what JvmExplorer prints. In interviews, if you can explain why java -version and mvn -version can disagree, it shows you have really shipped Java.

6 Gotchas and common mistakes

  • Checking in an old terminal. Installers change PATH and JAVA_HOME. But a terminal that was already open keeps the old values. So java -version looks broken, or looks fine when it is not. Avoid it: always open a fresh terminal after installing anything. If in doubt, restart the IDE too.
  • java -version right, Maven wrong. The terminal finds java through PATH. Maven picks its Java through JAVA_HOME. So the two can disagree. Avoid it: read the Java version: line inside mvn -version. It must say 21. (The simulation in Section 3.7 shows this.)
  • Running mvn from the wrong folder. Maven needs pom.xml in the current folder. From the repo's top folder, you get there is no POM in this directory. Avoid it: run every mvn command in this course from inside jvm-explorer/.
  • Following old tutorials. Much Java setup advice online is from before modern Java. It talks about separate JRE downloads, CLASSPATH variables, and old POM snippets that do not work with JUnit 5. The classic sign is Tests run: 0. The tests are quietly skipped instead of failing. Avoid it: trust the pinned setup here, and treat Tests run: 0 as a failure.
  • Trusting the IDE's green tick over Maven's. IntelliJ may run tests with its own JDK and its own runner. So it can show green while mvn test shows red, or the other way round. Avoid it: the command line has the final say. If they disagree, believe mvn test and fix the IDE's SDK setting.

7 Key takeaways

  • The JVM is a program that pretends to be an imaginary standard machine, so compiled Java runs unchanged on any computer with a JVM. The JDK is that engine plus the developer tools, and it is what you install.
  • This series pins Java 21 (LTS), Maven 3.9.x and JUnit 5.13.4 in committed files. Versions that are not pinned change quietly between machines and over time, and that ruins every observation a JVM course makes.
  • Maven reads one committed file, pom.xml, and makes the same build on any machine. It downloads libraries by their three coordinates, uses pinned plugins, and puts everything it makes in the target/ folder, which is never committed.
  • mvn test runs the project's JUnit tests and answers “did I break anything?” in one command. jvm-explorer's first tests check the machine itself, and fail loudly if the Java running the build is not 21.
  • .gitignore must exist before the first git add ., because Git only ignores files that are not already in history. After that, each lesson ends with one commit pushed to GitHub.

8 Challenge

Your friend clones the repo and runs mvn test inside jvm-explorer/. They get BUILD FAILURE. The failing test is runsOnPinnedJavaVersion, with the message Expected Java 21 ... but was: 17. Yet java -version in their terminal prints openjdk version "21.0.7".

  1. Explain how both outputs can be true at the same time.
  2. Name the one command from this lesson that shows which Java Maven is really using.
  3. Say what to fix.

Bonus: why is it good that this failure happened on day one?

Tip: try it in the simulation. Set PATH to “JDK 21 first” and JAVA_HOME to “JDK 17”.

Click to reveal the answer

(1) How both can be true. Two different lookups choose the Java in the two cases. The terminal finds java by going down the PATH list. On this machine, it reaches Java 21 first. Maven does not use that list. It starts the Java named by JAVA_HOME, which here points at an installed JDK 17. So the terminal's Java really is 21, and the Java running the tests really is 17. They are two different JVMs on the same computer. The test checked the Java actually running it (Runtime.version().feature()). That is why it caught what java -version could not.

(2) The command that shows it. mvn -version. Its output has a Java version: line that names the Java Maven runs on. It also has a runtime: line that shows where that Java is installed.

(3) The fix. Point JAVA_HOME at the JDK 21 folder. On Windows: Edit environment variables for your account → set JAVA_HOME to e.g. C:\Program Files\Eclipse Adoptium\jdk-21…. Open a fresh terminal, because an old one keeps the old value. Check that mvn -version now says Java version: 21. Then run mvn test again.

# PREDICTED output after the fix (trimmed):
[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS

Bonus. The mismatch showed up on day one, as one loud failure with a clear message. Without the test, it would show up weeks later. The JVM would quietly behave differently from the lesson text, with no error at all. Turning a hidden problem into an instant, labelled failure is the whole reason runsOnPinnedJavaVersion exists. It is also the whole point of pinning.
