Core Java · Course 01 · JVM Internals & Memory

Lesson 00 — Full Setup

Decide every version once, write it into committed files, and make the machine prove its identity before anything else runs.

Position: Lesson 00 of 07 (the setup lesson)  ·  Prerequisites: none  ·  Project files: pom.xml, JvmExplorer.java, JvmExplorerTest.java

1 The pain

Picture two people working on the same small Java program. On Priya's laptop it compiles cleanly and every test passes. She sends the exact same code to Sam. On Sam's laptop the compiler rejects one of her lines, a test fails with a strange message, and the build quietly downloads a different version of a library. Nothing about the code changed. What changed is the machines: Sam has an older Java, a different build tool, and no written record of which library versions the project expects. This failure is so common it has a sarcastic name: “works on my machine.” The hours it burns are pure waste — nobody is fixing a real bug, they are fixing a disagreement between two computers.

Now shrink that story to one person: you, three weeks from now. In the meantime you installed some other tool, and it quietly put a different Java at the front of your system. Lesson code that worked before now behaves slightly differently. That matters more here than almost anywhere, because this course is about observing the JVM's exact behavior. A garbage-collection log line looks different; a default has changed. You can no longer tell whether you are learning a fact about Java or a fact about your accidental upgrade.

The cure is boring and absolute: decide every version once, write the decision into files that live with the code, and make the machine prove its identity before anything else runs. That is all this lesson is. It looks like installation chores, but it is really the first JVM lesson: the first thing we build is a program that asks the JVM about itself — its version, its maker, its memory limit — and a test that fails loudly if the machine drifts away from what we agreed.

3 The concept explained

We meet each tool in the order they depend on each other: first the thing that runs Java at all, then the thing that builds projects, then testing, then history-keeping. Take it slowly; everything later in the course stands on these.

3.1 What actually runs your Java code

Start with a puzzle. A program compiled on Windows normally cannot run on Linux. A compiled program is a list of instructions for one specific kind of machine, and different machines and operating systems follow different rules. Yet compiled Java runs on both, unchanged. How?

The trick is that Java is not compiled for any real machine. It is compiled for an imaginary machine — one that is described precisely on paper but has never been built as hardware. Then, on every real computer, you install a program whose whole job is to pretend to be that imaginary machine: it reads the imaginary machine's instructions and carries them out using the real computer underneath. Your compiled program only ever talks to the pretender, so it never notices which real computer it is on. A program that plays the part of a machine like this is called a virtual machine, and the one that plays Java's imaginary machine is the Java Virtual Machine — the JVM. The JVM is the main character of this whole course: it is where your objects live, where memory is managed, where unused objects are cleaned up, and where code gets faster as it runs. (How your source code becomes instructions for that imaginary machine is exactly Lesson 01.)

Three names get confused constantly, so let us pin them down, smallest first:

  • The JVM can run code that is already compiled, but it cannot compile anything itself.
  • The JVM together with the standard library — the huge collection of ready-made classes like String and ArrayList that every program uses — is the minimum needed to run Java programs. This run-only bundle is called the JRE — Java Runtime Environment. Modern Java no longer offers it as a separate download, but the name survives in error messages and old articles, so you need to recognise it.
  • Everything in the JRE plus developer tools — most importantly javac, the compiler that turns your .java source files into instructions the JVM understands — is called the JDK — Java Development Kit. As a developer you always install a JDK.

One more wrinkle: “the JDK” is not one product from one company. Java's source code is open — it lives in a public project called OpenJDK — and several organisations compile that shared source into installable packages: Eclipse Adoptium (whose builds are named Temurin), Oracle, Amazon, Microsoft and others. Same engine, different wrapper, like the same novel printed by different publishers. This course uses Eclipse Temurin because it is free for any use and the community's usual default. The engine inside all of them is called HotSpot — remember that name. When this course says “the JVM does X,” it means HotSpot, and our first program will print that name so you can see it is really there.

Why does compiled Java run unchanged on Windows and Linux?
Because javac does not compile for any real machine; it compiles for an imaginary one. Each real computer runs a JVM whose job is to pretend to be that imaginary machine on top of the real hardware. Your program only ever talks to the JVM, so it never notices the real operating system or chip underneath.

3.2 Why version 21, and what “pinned” means

Java releases a new version every six months, and most of them receive fixes for only six months — fine for experiments, bad for a 19-course journey. Every couple of years, one release is chosen to receive fixes and security patches for years. A release with that long promise is called an LTS — Long-Term Support release. Java 21 is an LTS release, it is what a large share of the industry runs, and it has every feature this series needs. So the whole series uses Java 21.

Pinning means three things together: the version is written into committed files (pom.xml says 21, and the almanac records it), the build checks it automatically, and nobody changes it casually. The payoff: when code behaves oddly, “wrong version somewhere” is ruled out in seconds — you run one test and know. In a course about observing precise JVM behavior, that certainty is essential, because garbage-collection defaults, log formats and speed-up behavior all change between versions.

Pinning is a promise to manage versions, not to freeze them forever. New patch releases (21.0.1, 21.0.2, …) carry security fixes, so staying on one exact build for years quietly means staying vulnerable. Real teams upgrade on purpose, on a schedule, and re-check everything when they do. That is why our test pins the major version (21) and accepts any patch release of it.

3.3 Maven — the build tool

Imagine there were no build tool. To build even our small project you would personally: download the JUnit testing library from the internet, plus every other library JUnit itself needs, finding each one by hand; run javac with a correctly spelled list of every source file and every library's location; keep compiled test code out of the finished program; run the tests; and package the result. Every step retyped, in the right order, every time — and your teammate must copy your exact downloads to get the same result. People really worked this way, and it was miserable.

A program that does all of that from one written description is called a build tool. The standard one in the Java world is Maven (the popular alternative is called Gradle). You write down what the project is — its name, its Java version, which libraries it uses — in one file, and Maven works out how to build it. That file is pom.xml (POM stands for Project Object Model — the project described as structured data), and it always sits at the project's top folder.

Words inside the POM you will meet constantly:

  • A dependency is a library your code relies on — someone else's code you use instead of writing it yourself. You name it in the POM; Maven fetches it, and everything it in turn relies on, automatically. Our only dependency is JUnit.
  • Every library (and your own project) is identified by three coordinates, like a postal address: groupId (who made it, written like a reversed web address, e.g. org.junit.jupiter), artifactId (which product, e.g. junit-jupiter) and version (which edition, e.g. 5.13.4). Three parts, because names collide — dozens of libraries are called “core”.
  • Maven fetches libraries from a public online warehouse called Maven Central, and keeps a copy of each download in a folder on your machine (C:\Users\<you>\.m2\repository on Windows) so each library downloads only once. The first build is slow and prints many Downloading… lines; later builds are quick and quiet.
  • Maven itself is only a coordinator; the real work is done by plugins — add-on pieces, one per job (one calls the compiler, one runs tests, one runs your main class). Plugins have versions too, and our POM pins each one.
  • Our own version is 1.0-SNAPSHOT. The suffix SNAPSHOT is Maven's way of saying “still changing, not a finished release” — right for a project that grows every lesson.

What goes wrong without pinning. Here is a POM that looks fine and builds fine today — and is broken in a way you will not notice for weeks:

<!-- WRONG: builds today, drifts tomorrow -->
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>RELEASE</version>   <!-- "whatever is newest when you build" -->
</dependency>
<!-- ...and no <maven.compiler.release> at all, and no plugin versions. -->

Three separate drifts hide in there. RELEASE means two builds of the same code, a month apart, can use different JUnit versions and disagree. With no maven.compiler.release, which Java level the code is compiled for is decided by each machine — Priya's says 21, Sam's says 17, and Java-21-only code builds for her but not for him. And with no plugin versions, each Maven installation chooses its own compiler plugin and test runner. The cure is simply to write every one of those numbers down, which is exactly what our POM does (Section 4).

Maven also settles “where do files go?” by convention — a fixed layout every Maven project shares:

jvm-explorer/
    pom.xml                                   <- the recipe card (committed)
    src/main/java/com/corejava/jvm/           <- the real program code (committed)
    src/test/java/com/corejava/jvm/           <- the test code (committed)
    target/                                   <- Maven's generated output (NEVER committed)

target/ is where Maven writes everything it generates. It is disposable: you never edit it and never commit it, and deleting it costs nothing — that is literally what mvn clean does. You drive Maven from a terminal, from the folder that contains pom.xml:

CommandWhat it does
mvn compileCompile the main source code into target/
mvn testCompile everything, then run all tests and report pass or fail
mvn cleanDelete target/, so the next build starts completely fresh
mvn exec:javaRun the project's main class (our POM says which one)

Honest limit: for a 30-line throwaway program, Maven plus tests plus Git is a sledgehammer for a thumbtack. java One.java (Java 11 and later) compiles and runs a single file in one step and is the right tool there. Inside this course, such throwaways go into a clearly labelled experiments/ package in the project instead of getting projects of their own.

3.4 JUnit — tests that check themselves

Without tests, “does the project still work?” means running the program and reading the output by eye. As the project grows, you would have to re-read everything after every change — or, more realistically, you stop checking and break things without noticing. A unit test is a small piece of code whose job is to check a piece of real code automatically: it calls the real code, states what must be true about the result, and a framework runs all such checks and prints a verdict. The standard framework for this in Java is JUnit; we pin version 5.13.4 of the JUnit 5 line.

Inside a test, each “this must be true” statement is called an assertion. For example, assertEquals(21, actualVersion) passes silently if the value is 21 and fails the test loudly if it is anything else. The habit this course builds: every capability jvm-explorer gains comes with a test, so mvn test is a one-command answer to “did I break anything?” Run it any time, and always before committing.

3.5 Git and GitHub — the project's memory

Without version control, a project's history is a folder of copies called project-final-v2-REALLY-FINAL/, and one bad edit with no surviving copy loses work for good. A version control system is a program that records snapshots of your files over time, so you can see what changed, when and why, and go back to any earlier state. The standard one is Git. Its vocabulary, each piece in plain words first:

  • A repository (“repo”) is a folder whose history Git is tracking: your visible files plus a hidden .git folder that holds every recorded snapshot. This course folder is a repo, which is why it contains .git/.
  • A commit is one saved snapshot with a message saying what changed. It takes two steps: git add <files> chooses which changes to include (git add . means “everything that changed in this folder”), then git commit -m "message" seals them into history.
  • History on one disk can still be lost with that disk. GitHub is a website that keeps copies of Git repositories online — a backup you can also share. The online copy linked to your local repo is called the remote, and git push uploads your new commits to it.
  • A .gitignore file lists names Git must pretend not to see, so git add . can never accidentally include them. Ours lists two kinds of thing: generated output (target/, *.class, IDE settings folders), because committing it bloats history and causes pointless conflicts; and this course's three private control files (CLAUDE.md, curriculum.md, progress-tracker.md).

The ordering rule that cannot be undone: .gitignore must exist before the first git add .. Git only ignores files that are not already in history. Commit first, and thousands of files from target/ — plus private files — are recorded permanently; adding .gitignore afterwards does not remove them. Your repo was set up in the right order.

For a brand-new project, the one-time setup is below. Your repo has already done this — it is shown so you know what created it:

git init                                    # turn this folder into a repository
# ...write .gitignore FIRST...
git add .
git commit -m "chore: initial course setup"
git branch -M main                          # name the main line of history "main"
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main                     # first upload; -u remembers where to push

The rhythm for the rest of the course: one lesson → one commit → one push, with messages shaped like lesson: 01/lesson-XX - <title>. Every lesson ends by giving you the exact commands.

3.6 The IDE

You could write Java in Notepad, but you would be typing blind: no red underline under a typo, no auto-complete, no one-key rename, no clickable test results. A program that bundles an editor, live error-checking, navigation and test running into one workbench is called an IDE — Integrated Development Environment. Recommended here: IntelliJ IDEA Community Edition, which is free and has the strongest Java support (VS Code with the “Extension Pack for Java” is a fine lighter choice). One honest warning: IntelliJ keeps its own list of JDKs and its own test runner, so it can disagree with the pinned setup. In this course the command line (mvn test) is the referee; the IDE is a comfortable place to read and write code.

3.7 How your computer chooses a Java — and the classic trap

Two terms first. When you type a bare command like java, the operating system searches a list of folders, in order, and runs the first match it finds. That list is called the PATH. Installers that offer to “add to PATH” are offering to put their folder on that list — and when several Javas are installed, which one wins is decided purely by list order.

Separately, many Java tools read a setting you create, conventionally named JAVA_HOME, that holds your JDK's install folder. (A named setting like this, kept by the operating system for programs to read, is called an environment variable; PATH is one too.) Maven uses JAVA_HOME to choose which Java to run with — so if JAVA_HOME is missing or points at an old JDK, Maven misbehaves even though java -version looks perfect.

This is the most common day-one trap, and it is worth seeing before you read the fix. Pick which JDK comes first on PATH and where JAVA_HOME points, then read what each command reports. Watch java -version (which follows PATH) and mvn test (which follows JAVA_HOME) disagree — that disagreement is the whole bug.

3.8 The installation checklist

Do these in order. Each step ends with a check. If a tool is already installed from before, just run its check — there is no need to reinstall. Fixes for every likely failure are in troubleshooting.md.

  1. JDK 21 (Temurin). From adoptium.net, download Temurin 21 (LTS) for Windows x64 (the .msi file). In the installer, enable both “Add to PATH” and “Set JAVA_HOME”. Check in a fresh terminal: java -version must say 21.x and name Temurin, and javac -version must say javac 21.x (this proves you have the full JDK, not just a runtime).
  2. Maven. From maven.apache.org, download the binary zip of the current 3.9.x release. Unzip it somewhere permanent (e.g. C:\tools\apache-maven-3.9.x), add its bin folder to PATH, open a fresh terminal, and check: mvn -version must print the Maven version and Java version: 21.
  3. Git. From git-scm.com, install with the default options. Check: git --version. Then introduce yourself once: git config --global user.name "Your Name" and git config --global user.email "you@example.com".
  4. GitHub. Create an account at github.com and an empty repository (no auto-generated README). Already done for this repo — the remote is connected.
  5. IDE. Install IntelliJ IDEA Community Edition from jetbrains.com/idea. Open the jvm-explorer folder, and in File → Project Structure → SDK check that the SDK is the Temurin 21 you installed.

4 Applied to jvm-explorer

This lesson creates the project. Three files, all saved to disk:

  • jvm-explorer/pom.xml — the pinned build recipe.
  • jvm-explorer/src/main/java/com/corejava/jvm/JvmExplorer.java — the program's entry point.
  • jvm-explorer/src/test/java/com/corejava/jvm/JvmExplorerTest.java — the environment tests.

4.1 The pins, in pom.xml

Every line of the POM carries a comment in the file itself. These are the lines that cure the three drifts from Section 3.3:

<!-- Compile for Java 21 and ONLY Java 21, on every machine. -->
<maven.compiler.release>21</maven.compiler.release>

<!-- One exact JUnit version, named once and reused below. -->
<junit.version>5.13.4</junit.version>

<!-- Every plugin pinned, so the compiler and test runner never differ. -->
<artifactId>maven-compiler-plugin</artifactId>   <version>3.13.0</version>
<artifactId>maven-surefire-plugin</artifactId>   <version>3.5.2</version>
<artifactId>exec-maven-plugin</artifactId>       <version>3.5.0</version>

The Surefire plugin is the piece of Maven that finds and runs your tests. Its version matters more than it looks: old versions cannot see JUnit 5 tests at all, and fail silently by reporting Tests run: 0.

4.2 The program

The first program asks the running JVM to describe itself. Every line carries its reason:

// Every Java file declares which package it belongs to. A package is a named
// folder for classes; Maven REQUIRES the folder path on disk to match this line.
package com.corejava.jvm;

// The front door of jvm-explorer. For Lesson 00 its only job is to prove the
// toolchain works end to end by asking the running JVM to describe itself.
// "final" because nothing should ever extend this entry point.
public final class JvmExplorer {

    // The method the JVM looks for, by this exact signature, when told to run this
    // class. No object is created first, which is why it must be static; it must be
    // public so the JVM (outside our package) is allowed to call it.
    public static void main(String[] args) {

        // A banner, so our output is easy to spot among Maven's own lines.
        System.out.println("=== jvm-explorer: hello from inside the JVM ===");

        // "java.version": the exact version of the Java running RIGHT NOW - which
        // can differ from what is installed elsewhere, so we ask the JVM, not the OS.
        System.out.println("Java version : " + System.getProperty("java.version"));

        // "java.vm.name": which JVM implementation this is (expected: HotSpot).
        System.out.println("JVM name     : " + System.getProperty("java.vm.name"));

        // "java.vm.vendor": who built this JVM (Eclipse Adoptium, Oracle, ...).
        System.out.println("JVM vendor   : " + System.getProperty("java.vm.vendor"));

        // Runtime is the JVM's description of itself. maxMemory() answers "how big
        // may the heap grow?" in bytes. A long, because byte counts overflow an int
        // past about 2 GB.
        long maxHeapBytes = Runtime.getRuntime().maxMemory();

        // Bytes to megabytes, purely so the number is readable.
        System.out.println("Max heap     : " + (maxHeapBytes / (1024 * 1024)) + " MB");

        // How many CPU cores the JVM believes it may use; it sizes its own
        // clean-up threads from this number (Lessons 04 and 05).
        System.out.println("CPU cores    : " + Runtime.getRuntime().availableProcessors());
    }
}

Two ideas in there need a proper introduction. First, the JVM keeps a table of facts about itself and the machine, stored as name/value pairs of text — "java.version" → "21.0.7", and so on. Each entry is called a system property, and System.getProperty reads one. Second, the JVM sets aside one big pool of memory where every object your program creates with new is stored. That pool is called the heap. The number we print is the most the heap is allowed to grow to. By default the JVM chooses it from your machine's memory — commonly about a quarter of it, but that default varies by version and setup, so treat it as something to check, not a rule. The heap is the main stage of Lessons 03–05; today we only read its size.

Why does maxHeapBytes have to be a long, not an int?
An int tops out near 2.1 billion — about 2 GB counted in bytes. Heap sizes routinely exceed that (4 GB is about 4.29 billion bytes), so an int would overflow into a wrong, often negative, number. A long holds far larger counts safely.

4.3 The tests

This lesson's tests are unusual: they check the machine, not our code. The first one is the guard against the trap from Section 3.7.

// Fails loudly if the JVM running the build is not Java 21.
@Test
void runsOnPinnedJavaVersion() {
    // Runtime.version().feature() is the major number: 21 for any 21.x.y build.
    // Major only, because patch releases (21.0.1, 21.0.2...) are all "Java 21".
    assertEquals(21, Runtime.version().feature(),
            // The failure message says what to FIX, not just what broke.
            "Expected Java 21 (the pinned course version). "
                    + "Run 'java -version' and check troubleshooting.md.");
}

// A working JVM must report a heap limit above zero.
@Test
void jvmReportsAPositiveMaxHeap() {
    assertTrue(Runtime.getRuntime().maxMemory() > 0, /* … */);
}

// And at least one CPU core - never legally fewer.
@Test
void jvmSeesAtLeastOneCpuCore() {
    assertTrue(Runtime.getRuntime().availableProcessors() >= 1, /* … */);
}

Notice what the first test checks: the version of the JVM that is actually running the tests, not what java -version says in your terminal. Section 3.7 showed those can be two different Javas. This test measures the one that matters.

4.4 What happens when you run mvn test

  1. Maven starts on the Java that JAVA_HOME names, reads pom.xml, and learns the Java 21 pin, the JUnit 5.13.4 dependency and the three pinned plugins.
  2. It looks in the local cache (C:\Users\<you>\.m2\repository) for each item it needs, and downloads anything missing from Maven Central. On the first run that means a minute or more of Downloading… lines — normal, and only once.
  3. The compiler plugin calls javac on JvmExplorer.java for Java 21; the compiled file lands in target/classes/.
  4. It compiles the test file, with JUnit now available, into target/test-classes/.
  5. Surefire finds JvmExplorerTest and runs each @Test method.
  6. runsOnPinnedJavaVersion asks the running JVM for its major version and checks it is 21; the other two check for a positive heap limit and at least one core.
  7. Surefire prints the count, and Maven prints BUILD SUCCESS — or BUILD FAILURE naming exactly which check broke and why.

4.5 What happens when you run the program

  1. mvn compile exec:java compiles anything out of date into target/classes/.
  2. The exec plugin reads the main class named in the POM: com.corejava.jvm.JvmExplorer.
  3. JvmExplorer.main runs inside the Java that Maven itself is running on.
  4. The banner prints, then five questions go to the running JVM — three to its system properties (version, name, vendor) and two to Runtime (heap limit, core count).
  5. Each answer prints as one labelled line; main ends; Maven reports success.

Predicted output of mvn compile exec:java (Maven's [INFO] lines trimmed). Your numbers will differ — patch version, heap size and core count are facts about your machine, which is exactly the point:

=== jvm-explorer: hello from inside the JVM ===
Java version : 21.0.7
JVM name     : OpenJDK 64-Bit Server VM
JVM vendor   : Eclipse Adoptium
Max heap     : 4096 MB
CPU cores    : 8
[INFO] BUILD SUCCESS

From inside jvm-explorer/, run mvn clean test and then mvn compile exec:java, and compare with the predictions above. The two lines most worth checking: Java version starts with 21, and JVM vendor names the vendor you actually installed. Project state: compiles, 3 tests green (predicted). If what you see differs, the machine is right — troubleshooting.md covers the likely failures, and the difference is itself the lesson.

5 In the wild

The self-inspection calls we used are exactly what real software uses to adapt to the machine it lands on. The clearest example is our last line, Runtime.getRuntime().availableProcessors(). The JDK's own ForkJoinPool.commonPool() — the shared pool of worker threads behind parallel streams like list.parallelStream() — calls it to decide how many workers to create. That is why the same program uses 4 workers on your laptop and 32 on a big server, with no configuration anywhere. The JVM does the same thing when it decides how many clean-up threads to run; we will see those threads in its logs in Lesson 05. And look at the top of your own mvn -version output: Java version, vendor, operating system — Maven doing exactly what JvmExplorer.main does, for exactly the same reason.

On a real team, the first question when something misbehaves in production is not “what's the bug?” — it is “what machine, what engine, what version?” Deploy pipelines, container images and incident checklists all start by printing what JvmExplorer prints. In interviews, explaining why java -version and mvn -version can disagree marks you as someone who has actually shipped Java.

6 Gotchas and common mistakes

  • Checking in a stale terminal. Installers change PATH and JAVA_HOME, but a terminal that was already open keeps its old copies, so java -version looks broken — or looks fine when it is not. Avoid it: always open a fresh terminal after installing anything; if in doubt, restart the IDE too.
  • java -version right, Maven wrong. java is found through PATH, but Maven picks its Java through JAVA_HOME, so the two can disagree. Avoid it: read the Java version: line inside mvn -version — it must say 21. (This is what the simulation in Section 3.7 shows.)
  • Running mvn from the wrong folder. Maven needs pom.xml in the current folder; from the repo's top folder you get there is no POM in this directory. Avoid it: every mvn command in this course runs from inside jvm-explorer/.
  • Following old tutorials. Much of the internet's Java setup advice is from before modern Java — separate JRE downloads, CLASSPATH variables, old POM snippets that do not work with JUnit 5. The classic symptom is Tests run: 0: the tests are silently skipped rather than failing. Avoid it: trust the pinned setup here, and treat Tests run: 0 as a failure.
  • Trusting the IDE's green tick over Maven's. IntelliJ may run tests with its own JDK and its own runner, so it can say green while mvn test says red, or the reverse. Avoid it: the command line is the referee; if they disagree, believe mvn test and fix the IDE's SDK setting.

7 Key takeaways

  • The JVM is a program that plays the part of an imaginary standard machine, which is why compiled Java runs unchanged on any computer that has a JVM; the JDK is that engine plus the developer tools, and it is what you install.
  • This series pins Java 21 (LTS), Maven 3.9.x and JUnit 5.13.4 in committed files, because unpinned versions drift silently between machines and over time, and drifting versions spoil every observation a JVM course makes.
  • Maven turns one committed description, pom.xml, into the same build on any machine: it fetches libraries by their three coordinates, uses pinned plugins, and keeps all generated output in the never-committed target/ folder.
  • mvn test runs the project's JUnit tests and is the standing one-command answer to “did I break anything?”; jvm-explorer's first tests guard the machine itself, failing loudly if the Java actually running the build is not 21.
  • .gitignore must exist before the first git add ., because Git only ignores files that are not already in history; after that, each lesson ends with one commit pushed to GitHub.

8 Challenge

Your friend clones the repo, runs mvn test inside jvm-explorer/, and gets BUILD FAILURE. The failing test is runsOnPinnedJavaVersion, with Expected Java 21 ... but was: 17. Yet java -version in their terminal prints openjdk version "21.0.7". (1) Explain how both outputs can be true at once. (2) Name the one command from this lesson that shows which Java Maven is really using. (3) Say what to fix. Bonus: why is it good that this failure happened on day one?

Tip: replay it in the simulation — set PATH to “JDK 21 first” and JAVA_HOME to “JDK 17”.

Click to reveal the answer

(1) How both can be true. Two different lookups choose the Java in the two cases. The terminal finds java by walking the PATH list, and on this machine that walk reaches Java 21 first. Maven ignores that walk and starts the Java named by JAVA_HOME, which here points at an installed JDK 17. So the terminal's Java really is 21 and the Java running the tests really is 17 — two different JVMs on the same computer. The test checked the Java actually running it (Runtime.version().feature()), which is why it caught what java -version could not.

(2) The revealing command. mvn -version. Its output includes a Java version: line naming the Java Maven itself runs on, and a runtime: line showing where that Java is installed.

(3) The fix. Point JAVA_HOME at the JDK 21 folder (Windows: Edit environment variables for your account → set JAVA_HOME to e.g. C:\Program Files\Eclipse Adoptium\jdk-21…). Open a fresh terminal (an old one keeps the old value), check that mvn -version now says Java version: 21, then run mvn test again.

# PREDICTED output after the fix (trimmed):
[INFO] Tests run: 3, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS

Bonus. Because the mismatch showed up as one loud, named failure with a message on day one — instead of weeks later, as JVM behavior that quietly contradicts the lesson text with no error at all. Swapping invisible drift for an immediate, labelled failure is the whole reason runsOnPinnedJavaVersion exists, and the whole point of pinning.
