Lesson 02 — Class Loading

Who finds your .class files, in what order, and at exactly what moment your static code runs. This is the machinery behind NoClassDefFoundError, old values that will not update, and “Config cannot be cast to Config.”

Position: Lesson 02 of 07  ·  Prerequisites: Lesson 01 — How Java Actually Runs  ·  Project files: loading/ClassLoaderReporter.java, loading/InitializationLog.java, four demonstration subjects, experiments/ClassLoadingExperiment.java, JvmExplorer.java (modified), and three test classes

1 The pain

In Lesson 01 we wrote a line and walked straight past the interesting part of it:

ClassFileInspector.class.getResourceAsStream("/com/corejava/jvm/BytecodeSubject.class");

Something found that file. Something decided where to look, in what order, and at what moment. That something is the part of the JVM this lesson is about. Until you know how it works, three of Java's most common failures make no sense at all.

The first pain is two errors that look the same but mean opposite things. One program crashes with ClassNotFoundException. A colleague's program crashes with NoClassDefFoundError. Both say a class is missing. Both point at the same jar. But the fixes are different. It gets worse. There is a third form: NoClassDefFoundError: Could not initialize class com.acme.Config. It is thrown for a class that is sitting right there on the class path. The file is present and readable. The real cause happened earlier, in a different thread, with a different exception. That message has already scrolled off the screen. People restart the server and hope.

The second pain is old values that will not update, with no cache anywhere. A team ships a shared library with public static final String API_VERSION = "1.0";. Six months later they change it to "2.0". They rebuild the library, drop in the new jar, and restart everything. The application still logs 1.0. Not sometimes. Every time. There is no cache and no old build folder. The old value is actually stored inside the application's own bytecode. Only the rules of class loading explain why, and what to do about it.

The third pain is the one that makes people doubt their eyesight. A plugin-based application throws:

java.lang.ClassCastException: class com.acme.Config cannot be cast to
        class com.acme.Config (com.acme.Config is in unnamed module of loader
        'app'; com.acme.Config is in unnamed module of loader
        org.acme.PluginLoader @4f3f5b24)

The same name is on both sides. It is not a typo. It is not a packaging problem or a generics mistake. To understand that message, you need one fact that is almost never taught early enough: while a program runs, a class is known by its name plus the loader that defined it. Two loaders and one name give you two truly different types. You cannot assign one to the other.

Under all three pains is a timing question you have probably never asked out loud. When does a static block run? When the JVM starts? When the class is first mentioned? When the first object is created? The answer is exact, written down in the rules, and surprising. It decides whether your settings load before or after the code that needs them. By the end of this lesson, your project will print the chain of loaders for any class. A log will also show you, line by line, which classes have been set up and which have not been touched yet.

2 Real-world analogy

Picture a library with three librarians, each above the next. A junior works at the front desk. A senior works in the back office. The head librarian is the only one with the key to the rare-books vault.

You ask the junior for Hamlet. She does not go looking. She turns around and asks the senior. He does not go looking either. He asks the head librarian. The head librarian checks the vault, finds the real Hamlet, and passes it back down the chain to you. The senior checks his own shelves only if the head librarian says “not in the vault”. The junior checks hers only if the senior also finds nothing. If all three fail, you get a clear answer: we do not have that book.

Now the reason for the rule, which is the whole point. Suppose someone slipped a fake Hamlet onto the junior's front-desk shelf. It is a copy with the ending rewritten. With this system, nobody ever reaches it. The real copy is found first, in the vault, every single time. Nobody has to watch for the fake, spot it, or block it. The way the system works means nobody can ever reach it.

The libraryThe JVM
A librarian: the person you ask for a book by titleA class loader: the object you ask for a class by name
The head librarian and the rare-books vaultThe bootstrap loader and java.base (String, Object…)
The senior librarian's office shelvesThe platform loader and the rest of the JDK
The junior librarian's front deskThe application loader and your class path
“Ask upward before you search”Parent delegation
The forged Hamlet nobody can reachA fake java.lang.String in your own jar — harmless

Cutting the pages of a new book before first readingInitialization — the static code, run once

Two more details of the analogy match exactly. Both matter later.

Nothing is fetched early. The library does not carry every book to your table when you walk in. A book is fetched when a reader asks for it, and not a moment sooner. The JVM is the same. Your program does not “load” at startup. Classes arrive one at a time, the first time they are used, for as long as the program runs.

Two libraries can hold two different books with the same title. Say your city has a second library, run separately. You borrow Hamlet from each. Now you hold two physical books. They share a title, but you cannot swap them. Returning one to the wrong library is a mistake. That is exactly the ClassCastException from Section 1: two loaders, one name, two different types.

3 The concept explained

We build this in the order the ideas depend on each other:

  1. what “loading a class” has to achieve,
  2. who does it,
  3. the rule they follow,
  4. why a class is not known by its name alone,
  5. the five steps every class goes through, and
  6. the exact moment your static code runs.

Then we watch all of it happen, using the JVM's own logging.

3.1 What “loading a class” actually has to achieve

Lesson 01 left us with a file: a class file. It is full of bytes, starts with 0xCAFEBABE, and holds the bytecode for some methods. But a file is not a type. Before your program can write new Config(), the JVM needs a live thing in memory that knows:

  • what this class is called,
  • what its fields are, and how big one object of it must be,
  • what its methods are, and where their bytecode lives,
  • what its parent class (its superclass) is, and
  • most important: that all of the above has been checked and is safe to run.

Turning bytes on disk into that live thing is what we mean by loading a class. This raises a question the file itself cannot answer. Given the name com.acme.Config, where do the bytes come from? A folder? A jar? The network? A program that makes them up on the spot? Java chose not to fix any one answer. It gave the job to a normal Java object instead.

3.2 The class loader: an object with one job

A class loader is a Java object with one job: you give it a class's name as text, and it gives you back a loaded class. That is all it promises. It is not a keyword, a JVM flag, or a step of the build. It is an object of a class that extends java.lang.ClassLoader. It sits in memory next to your own objects. You can hold a reference to it and ask it questions.

Why build it that way? Because “where do class bytes come from?” has many good answers. Fixing just one would have frozen Java as it was in 1995. Because the loader is a normal object, the answer can be any of these:

  • “from this folder”,
  • “from inside this jar”,
  • “from this web server”,
  • “from these bytes I just made”, or
  • “from a fresh copy, so I can reload the class without restarting.”

Every one of those is used in real systems. In Lesson 01 we saw Mockito make classes that were never compiled. That is this exact mechanism at work.

Every class knows which loader defined it, and you can ask:

ClassLoader mine   = JvmExplorer.class.getClassLoader();   // an object
ClassLoader theirs = String.class.getClassLoader();       // null !

That null is not a bug. It is not a missing value, and you do not need to guard against it. It is the JVM's way of saying “the bootstrap loader”. That loader is written in C++ inside the JVM itself. So it has no Java object to hand back. Many beginners write x.getClassLoader().getResource(...) on a JDK class and get a NullPointerException that seems to make no sense. It makes perfect sense: there is no object there to call a method on.

3.3 The three loaders every JVM has

A standard JVM starts with three loaders already in place. Each one has a parent: the loader it asks first. They are not equals. They form a chain.

LoadergetName()What it can findIts parent
Bootstrapno Java object at all — shows up as nulljava.base: Object, String, Integer, System — the classes the JVM cannot start without— (it is the top)
Platform"platform"the rest of the JDK's modules, e.g. java.sql, java.xmlbootstrap
Application"app"your classes and your libraries — everything on the class pathplatform

Two naming traps that will never go away. First, the application loader is what ClassLoader.getSystemClassLoader() returns. It is called “system” for old reasons. It has nothing to do with the operating system, and it confuses everyone. Second, before Java 9 the top two were called the bootstrap and extension loaders. Java 9 added modules, removed the extension loader, and put the platform loader in its place. Old tutorials still say “ext”. Old code still mentions a lib/ext folder that no longer exists.

You do not need to memorise which loader owns which JDK class. You can just ask. Our new module prints the answer for any class you name. Section 4 shows it running.

3.4 Parent delegation: ask upward, search downward

Here is the rule behind every class request in Java. It is the opposite of what you might expect, on purpose: when a loader is asked for a class, it does not look. It asks its parent first. The parent asks its own parent, all the way to the top. A loader searches its own places only if every loader above it has failed. This is called parent delegation.

Why go to this trouble? There are three reasons, most important first.

Safety, built into the design. Suppose you put a file named java/lang/String.class in your own jar. It holds a fake String whose equals always returns true. With delegation, the application loader never gets the chance to define it. The request goes up. The bootstrap loader finds the real String in java.base. That is the one everybody gets. Your fake sits on disk forever, and nothing ever reaches it. Nothing had to spot it or block it. (Modern JVMs also flatly refuse to let any loader except bootstrap define classes in java.* packages. That is a second layer of safety. But delegation alone already solves the problem.)

Only one copy of each core class. Without delegation, three loaders might each define their own java.lang.Object. Section 3.6 explains why those would be three types that do not fit together. Nothing in Java would work. Delegation makes sure that a class found higher in the chain is shared by every loader below it.

A clear answer. The search order is fixed, and it covers every place. So “not found” really means “nowhere”. It does not mean “not in the one place I happened to look”.

Delegation is a habit written in code, not a law the JVM forces. It lives in ClassLoader.loadClass, and any subclass may override that method. Application servers and plugin systems break the rule on purpose (see Section 5). That is exactly where the strangest class-loading bugs live.

You add a jar containing your own java/lang/String.class to the class path. What happens?
Nothing. Every request for java.lang.String goes up to the bootstrap loader. It finds the real one in java.base and returns it. Your file is never read. Nobody spots it or rejects it. It is just never reached, because the loader that could find it never gets to search.

3.6 A class is known by its name plus its loader

This one fact explains the third pain from Section 1. It is also the fact most people are missing in their picture of how Java works.

Inside the JVM, a loaded class is known by a pair of things. The first is its full name, including the package. The second is the loader that defined it. Together, this pair is the class's runtime identity. (The package name plus the loader is called its runtime package.) The result is simple and harsh. If two different loaders each define a class called com.acme.Config, the JVM holds two different types. Not two copies of one type. Two types, as unrelated as String and Integer. You cannot put an object of one into a variable of the other. The cast fails, with a message that names the same class twice.

Notice how well this fits with delegation. Everybody asks upward first. So java.lang.String is defined exactly once, by the bootstrap loader, and shared by every loader below it. That means there is only ever one String type. Delegation stops duplicate types from happening by accident. Breaking delegation on purpose is what makes them happen.

3.7 The five steps, from bytes to usable class

Loading is not one action. The JVM Specification defines a series of steps. Knowing their names is what makes error messages readable. People often sum up the series as loading → linking → initialization. Linking has three smaller steps of its own.

1 · Loading

A loader is asked for a name. Delegation runs. Some loader finds the bytes. The JVM reads them into its own internal form. It also makes the Class object that you can hold in a variable. The magic number and version check from Lesson 01 happen here. If a file does not start with 0xCAFEBABE, or is too new, it is rejected at this step. A too-new file gives UnsupportedClassVersionError.

2a · Verification

Verification is the JVM proving to itself that the bytecode cannot misbehave. It does this before running a single instruction. Remember, the JVM has no idea where a class file came from. Someone may have edited it by hand. It may have been damaged on the way. A compiler for a different language may have made it. So the JVM checks things like these:

  • Does every instruction leave the operand stack in a sensible state, no matter which path led there?
  • Does any jump land in the middle of an instruction, or outside the method?
  • Does any code treat an int as an object reference? Does any code read a local slot that was never written?
  • Are the access rules kept? For example, no code may call a private method from outside its class.

This is why a damaged class file gives you a clear VerifyError, not a crashed program. It is a big part of what “Java is memory-safe” really means. The safety is checked at the door, once per class, not on every instruction. There used to be a flag to switch verification off for faster startup. It has been deprecated, and on modern JDKs it no longer does anything useful. Treat it as gone. If you see it in an old script, check your JDK's release notes.

2b · Preparation

Preparation makes room for the class's static fields and sets them to default values: 0 for numbers, false for booleans, null for references. These are not your values. If you wrote static int count = 5;, then after preparation count is 0. The 5 is set later, in step 3, because setting it means running code.

There is exactly one exception, and it matters for this lesson. Some fields are static final and set to a constant expression (a fixed value known at compile time). These are filled in during preparation. The value comes straight from the ConstantValue attribute stored in the class file. No code is needed, so the field does not wait for initialization.

2c · Resolution

Lesson 01 showed bytecode full of # numbers that point into the constant pool. Each one is a reference by name, like “the method named println with descriptor (Ljava/lang/String;)V in the class java/io/PrintStream”. Resolution turns each of those names into a direct pointer to the real thing. That may mean loading yet another class.

The rules allow resolution to happen early, during linking, or late, on first use. HotSpot chooses late. That one choice explains a whole family of production problems. A class you never call can be missing from the class path for months, and nobody notices. Then one rare piece of code finally runs, and the JVM tries to resolve it. The failure arrives at 3 a.m., not at startup.

3 · Initialization

Finally, the JVM runs the class's own setup code: static field assignments and static { } blocks. This is the step with rules. The next two subsections are all about it.

Immediately after preparation, what is the value of static int count = 5;?
Zero. Preparation only sets default values. Setting the 5 is code, and code belongs to initialization. The exception is a static final field set to a constant expression. That one is filled in during preparation, from the class file's ConstantValue attribute, without running anything.

3.8 <clinit>: the method you never wrote

Where does “the class's setup code” live? Lesson 01 showed that a constructor is stored in the class file as a normal method with the special name <init>. Initialization works the same way. javac collects every static field assignment and every static { } block. It keeps them in the order they appear in your source file. Then it joins them into one hidden method named <clinit>, short for “class initializer”. You never wrote it. You cannot call it. The JVM runs it exactly once.

Our new ConstantHolder is built to make this visible. It has two compile-time constants, one field whose value is worked out by a method, and one static block:

public static final int PINNED_MAJOR_VERSION = 65;                 // constant
public static final String COURSE_NAME = "JVM Internals & Memory";  // constant
public static final String DESCRIPTION = buildDescription();        // NOT constant

static {
    InitializationLog.record("ConstantHolder");
}
// PREDICTED javap -c -p output for ConstantHolder (the # numbers will differ)
  static {};
    Code:
       0: invokestatic  #7    // Method buildDescription:()Ljava/lang/String;
       3: putstatic     #13   // Field DESCRIPTION:Ljava/lang/String;
       6: ldc           #19   // String ConstantHolder
       8: invokestatic  #21   // Method …/InitializationLog.record:(Ljava/lang/String;)V
      11: return

Look at what is there and what is missing. The two things that ran are in source order. First the DESCRIPTION assignment (declared first), then the static block. PINNED_MAJOR_VERSION and COURSE_NAME appear nowhere at all. No instruction sets them, because preparation already filled them in from their ConstantValue attributes. javap -v shows those attributes inside the field declarations.

Three facts about <clinit> are worth remembering for good:

  • It runs exactly once, per class, per loader. There is no “re-initialize”. Once it is done, it is done, for as long as that loader lives.
  • It is thread-safe, and the JVM does the locking for you. Say two threads touch a class that has not been set up yet, at the same moment. One runs <clinit>. The other waits until it finishes. You never write a lock for this. It is the only built-in way in Java to run setup code exactly once, safely, and only when first needed. Section 5 shows a common pattern built on it.
  • If it throws, the class is broken forever. The first failure shows up as ExceptionInInitializerError. It wraps whatever your code actually threw. Every later try to use that class gets NoClassDefFoundError: Could not initialize class …. That is a different error, and the real cause is nowhere in sight. This is what causes the confusing failure from Section 1.

What goes wrong when you forget those three facts. Here is a very common piece of code. It is a settings class that loads its file in a static block:

// WRONG: runs at a moment you do not control, and its failure reaches the wrong person
public final class Settings {
    public static final Properties VALUES = new Properties();
    static {
        try (InputStream in = new FileInputStream("/etc/app/settings.properties")) {
            VALUES.load(in);                    // file reading inside <clinit>
        } catch (IOException e) {
            throw new RuntimeException(e);      // ...and it can throw
        }
    }
}
// PREDICTED symptom on a machine where the file is missing — the first caller sees:
java.lang.ExceptionInInitializerError
Caused by: java.lang.RuntimeException: java.io.FileNotFoundException: /etc/app/settings.properties

// ...and every caller after that sees only:
java.lang.NoClassDefFoundError: Could not initialize class com.acme.Settings

Three things go wrong here:

  • The file is read whenever something first touches Settings. That could be at startup, ten minutes in, or never. You do not control it.
  • Only the first thread sees the useful error.
  • No test can make it read a different file, or reset it, because a class initializes only once per loader.

The cure: keep static initializers to simple assignments that cannot fail. Put anything that can fail (files, network, settings) in a method that the caller calls on purpose. That is why every static block in our project does exactly one thing: add a name to a list in memory.

3.9 Exactly when a class initializes

Now the rules. The Java Language Specification lists exactly what makes a class initialize. The list is shorter than people expect. A class initializes the first time any of these happens:

This does initializeWhy
new Foo()you are creating an instance, so the class must be ready
calling a static method declared by Foorunning the class's code requires the class's code to be set up
reading or writing a static field declared by Foo that is not a compile-time constantthe value only exists once the initializer has produced it
Class.forName("Foo") (one-argument form)documented to initialize — that is the point of the method
initializing a subclass of Fooa superclass is always ready before its subclass
Foo is the class named on the java command linethe JVM initializes it before calling main
This does not initializeWhy
import com.acme.Foo;imports are a compile-time convenience; nothing remains of them at run time
Foo.classasks for the class object — needs loading, not initializing
new Foo[10]every slot is null; not one Foo is created
reading a static final compile-time constantthe value was copied into your class file at compile time
Class.forName("Foo", false, loader)the false explicitly says “load, do not initialize”
loader.loadClass("Foo")documented to load without initializing
declaring a variable, a parameter, or a return type of type Fooa type mention is not a use
reading a static field declared in the superclass through the subclass's nameonly the class that declares the field initializes
initializing a superclassparents do not wake their children

The last two rows catch out even experienced developers, so let us spell them out. Say we have class Child extends Parent, and Parent declares static String NAME = compute();:

System.out.println(Child.NAME);   // initializes Parent ONLY. Child stays cold.

The source says Child. But the field is declared in Parent. Initialization follows where the field is declared, not the name you typed. Child does get loaded, because the JVM has to look at it to find out the field is inherited. But its <clinit> does not run. Our project tests exactly this. The language specification even gives an example of it, because everyone gets it wrong.

Two smaller rules, to be complete. First, interfaces initialize under the same conditions, with one twist. Initializing a class also initializes its superclasses. It also initializes any interfaces above it that declare default methods. It does not initialize plain interfaces that only hold constants. Second, an assert statement inside a class also makes that class initialize. That is a rare corner you will probably never meet.

What goes wrong when you confuse mentioning a class with using it. For years, programs that connected to a database did this. It failed with “no suitable driver found”:

import com.mysql.cj.jdbc.Driver;                       // compile-time only - does nothing at run time
Connection c = DriverManager.getConnection(url);    // the driver never registered itself

The driver registers itself with DriverManager from inside its own static block. So it only works once the driver class has initialized. An import never initializes anything. Every old tutorial has a line that looks like a superstition: Class.forName("com.mysql.cj.jdbc.Driver");. That line was the fix. It forces the class to initialize, by name. (Modern drivers are found automatically, as Section 5 shows. But now you know why that line ever existed.)

Does List<Config> list = new ArrayList<>(); initialize Config?
No. Config appears only as a type argument. The compiler removes type arguments (this is called erasure). They leave nothing in the bytecode that mentions the class at run time. Even without erasure, mentioning a type is not using it. Config initializes the first time you actually create one, call one of its static methods, or read one of its static fields that is not a constant.

3.10 Why a compile-time constant is different from everything else

This gets its own subsection. It is the cause of the “old value” pain, and it surprises people every time.

A field is a compile-time constant when all of these are true:

  • it is static and final,
  • its type is a primitive (like int) or String, and
  • it is set to a constant expression: a fixed value like 65 or "hi", or arithmetic on fixed values and other constants.

(The specification calls it a constant variable.) When javac compiles code that reads such a field, it does not write a field read at all. It copies the value straight into the reading class's own bytecode.

So our JvmExplorer contains this line:

System.out.println("Constant read      : " + ConstantHolder.PINNED_MAJOR_VERSION);

Both sides of that + are constants. So javac joins them into one fixed string at compile time. The compiled JvmExplorer does not mention ConstantHolder anywhere. Not in its instructions, and not in its constant pool. You can prove it with one command:

# from jvm-explorer/, after mvn compile — expect NO output at all
javap -v target/classes/com/corejava/jvm/JvmExplorer.class | findstr ConstantHolder

# on macOS / Linux:
javap -v target/classes/com/corejava/jvm/JvmExplorer.class | grep ConstantHolder

Now the real-world result. Ship a library with public static final String API_VERSION = "1.0";. Every application that compiles against it copies "1.0" into its own class files. Now release version 2 of the library with "2.0". Drop in the new jar and restart. Every application that was not recompiled still prints 1.0. The string is in their bytecode, not in the library's. The library is never asked. There is no cache to clear.

This leads to a rule worth writing on the wall: in a library's public API, use a compile-time constant only for a value that will truly never change. If a value might change between releases, offer it through a method (public static String apiVersion()). Or use a field that is not a constant (public static final String API_VERSION = computeVersion();). Then callers really read it while the program runs. And when constants do change, rebuild everything that reads them. Do a full clean build, not a partial one.

3.11 Watching it happen on your own machine

You can see all of the above for yourself. It is not just theory. The JVM will describe its own class loading if you ask:

# one line per class, as it loads — the classic flag
java -verbose:class -cp target/classes com.corejava.jvm.JvmExplorer

# the modern equivalent, part of "unified logging" (Java 9 and later)
java -Xlog:class+load=info -cp target/classes com.corejava.jvm.JvmExplorer

# send it to a file instead, so it does not drown your program's own output
java -Xlog:class+load=info:file=classes.txt -cp target/classes com.corejava.jvm.JvmExplorer

Each line names a class and where it came from. That answers the loader question from the outside:

// PREDICTED shape (there will be hundreds of lines before ours)
[0.004s][info][class,load] java.lang.Object source: shared objects file
[0.021s][info][class,load] java.sql.Date source: jrt:/java.sql
[0.089s][info][class,load] com.corejava.jvm.JvmExplorer source: file:/D:/.../target/classes/
[0.093s][info][class,load] com.corejava.jvm.loading.ClassLoaderReporter source: file:/D:/.../target/classes/

Two details in that output are worth naming.

  • jrt:/java.sql is where the JDK stores its own modules. It replaced the old rt.jar file. Its addresses start with jrt:.
  • shared objects file means the class came from a ready-made archive that ships with the JDK. This is called class-data sharing, and it makes startup faster. The JVM does not read java.lang.Object from scratch every time it starts. It keeps a ready-made memory image and just loads that. You will see this on most core JDK classes.

Why not mvn exec:java for this? Because exec:java runs your main inside Maven's own JVM. So -verbose:class would list Maven's thousands of classes next to yours. You would also have to give the JVM flags to Maven, not to your program. Running java directly on target/classes gives a clean JVM. It holds nothing but the JDK and your code. That is exactly what you want to watch.

3.12 The three errors, finally readable

What you seeWhat actually happenedWhere to look
ClassNotFoundException
(a checked Exception)		 Some code asked for a class by name, as text. For example Class.forName, loadClass, or a framework reading a config file. The whole delegation chain found nothing. The name in the message. Look for a typo, a wrong package, or a jar that really is missing from the class path.
NoClassDefFoundError
(an Error)		 The JVM was resolving a reference inside your compiled code. So the class existed when you compiled, but it is not there now. A dependency that was there at build time but is missing at run time. For example: a jar that was not packaged, a “provided” scope, or a container image built from the wrong layer.
NoClassDefFoundError: Could not initialize class X A completely different problem. X is present. Its <clinit> ran earlier and threw. So the class can never be used again, and every later use reports this. Scroll back in the log to the first ExceptionInInitializerError. That one holds the real cause. This one does not.
ExceptionInInitializerError The first time a static initializer threw. Its getCause() is your real exception. Whatever your static block does. For example: reading a missing file, a null setting, or a regex that fails.
ClassCastException: X cannot be cast to X Two loaders each defined a class named X. These are two different types. The loader names in brackets in the message. Usually the same jar is in two places at once.
UnsupportedClassVersionError Rejected during loading: the file's major version is newer than this JVM. (Lesson 01.) Subtract 44 from both numbers in the message.
Your app dies with NoClassDefFoundError: Could not initialize class com.acme.Settings, and the jar containing Settings is definitely on the class path. What do you do?
Stop looking at the class path. It is not a packaging problem. Search earlier in the log for the first ExceptionInInitializerError that mentions com.acme.Settings. That stack trace holds the real cause. Something in the class's static initializer threw. It was probably a missing settings file or a null value. Once a class's initializer fails, that loader can never use the class again. Every later use reports this misleading second error instead.

4.1 What happens, step by step, when the new code in JvmExplorer runs

  1. JvmExplorer.main asks for the report on String.class. getClassLoader() returns null. The loop body never runs. The chain has one entry: “bootstrap”.
  2. It asks about java.sql.Date. That class lives in a JDK module outside java.base. So we expect it to come from the platform loader. The chain is platform, then bootstrap. This is printed, not tested. Check what your JDK reports.
  3. It asks about JvmExplorer itself. Our class came from the class path, so the application loader defined it. The chain is app → platform → bootstrap.
  4. It prints the built-in chain on its own, without naming any class. That is ClassLoader.getSystemClassLoader() and its parents.
  5. It prints the initialization log. The log is empty. Importing classes at the top of the file changed nothing.
  6. It reads ConstantHolder.PINNED_MAJOR_VERSION, a compile-time constant. Then it prints the log again. It is still empty. The number 65 came out of JvmExplorer's own bytecode.

4.3 The reporting module

Saved at jvm-explorer/src/main/java/com/corejava/jvm/loading/ClassLoaderReporter.java. A new sub-package, loading, keeps this lesson's classes together. (In the same way, experiments keeps throwaway programs apart.) Here is the core of it:

// What we print where the JVM hands us null. Named, not repeated as a literal,
// because tests assert on it and a typo in one of two copies is invisible.
public static final String BOOTSTRAP_DESCRIPTION = "bootstrap (built into the JVM, no Java object)";

public static String describe(ClassLoader loader) {
    // null is the bootstrap loader, not a mistake. Handling it FIRST means every
    // line below can assume a real object exists.
    if (loader == null) {
        return BOOTSTRAP_DESCRIPTION;
    }

    // Since Java 9 the built-in loaders carry names: "app" and "platform". Loaders
    // created by other code may have no name at all, so getName() can return null.
    String name = loader.getName();
    if (name == null) {
        name = "(unnamed)";
    }

    // The class name is the giveaway that something custom is in play.
    return name + " — " + loader.getClass().getName();
}

4.4 The witness

Saved at .../loading/InitializationLog.java. Class initialization leaves no trace of its own, so we make one. Every sample class calls record from its static initializer. The tests read the log afterwards.

// One log for the whole JVM - the right shape, since a class also initializes
// once per JVM (strictly: once per class loader).
private static final List<String> EVENTS = Collections.synchronizedList(new ArrayList<>());

public static void record(String simpleClassName) {
    // No validation, no formatting, no I/O. A static initializer is the worst
    // possible place for something that might throw or block.
    EVENTS.add(simpleClassName);
}

public static List<String> events() {
    // synchronizedList makes each add safe, but COPYING means iterating, and
    // iteration must be guarded by hand - the documented rule for these wrappers.
    synchronized (EVENTS) {
        return List.copyOf(EVENTS);   // immutable: nobody can rewrite history
    }
}

5 In the wild

The initialization-on-demand holder idiom. (An idiom is a common, well-known code pattern.) This is the neatest use of everything in Section 3.9. You will find it all over the JDK and in well-written libraries:

public final class ExpensiveThing {

    // A private nested class that exists ONLY to hold the instance.
    private static class Holder {
        static final ExpensiveThing INSTANCE = new ExpensiveThing();
    }

    public static ExpensiveThing get() {
        return Holder.INSTANCE;   // Holder initializes HERE, on the first call, once
    }
}

There is no synchronized, no double-checked locking, no volatile, and no atomics. Yet it is completely thread-safe, and the object is only made when first needed. Here is why:

  • A nested class is a separate class. So Holder is not initialized when ExpensiveThing is.
  • Holder initializes the first time someone reads Holder.INSTANCE.
  • The JVM's own <clinit> lock makes sure that happens exactly once, even if a hundred threads arrive at the same moment.

The idiom is nothing more than the class-initialization rules, used on purpose.

Application servers and Spring Boot turn delegation around on purpose. A servlet container like Tomcat runs several web applications in one JVM. Each one has its own libraries. Application A wants version 1 of a library. Application B wants version 3. With strict parent delegation, both would get whichever copy the shared parent held. So a web application's loader checks itself first for application classes. It only asks upward for JDK classes. This is a careful, documented reversal of the rule in Section 3.4. It is why “it works in my IDE but not in the container” is a whole family of bugs, not just one. Spring Boot's runnable jar also uses its own loader, to read jars stored inside the jar. A plain JVM cannot do that, because the class path does not support jars inside jars. (The exact class name of Boot's loader has changed between major versions. Check your version's source instead of trusting a blog post.)

ServiceLoader and the context class loader. Delegation causes one built-in problem: a parent can never see its children's classes. The JDK's java.sql.DriverManager is loaded by the platform loader. But it must somehow create your MySQL driver, which lives on the application class path, below it. It cannot reach down. Java's answer is the thread context class loader. Each thread carries a reference to a loader, and framework code can ask for it. This gets around the chain on purpose. ServiceLoader uses it to find implementations. It is why modern JDBC no longer needs Class.forName. It also causes many hard-to-find bugs. A thread's context loader is whatever the last framework to touch the thread set it to.

Every hot-reload you have used is a new class loader. A loader can never load or initialize the same class a second time. That rule has no exceptions. So every tool that seems to reload code works by throwing away a whole class loader and building a fresh one. Examples are JRebel, Spring Boot devtools, an application server redeploy, and an IDE's hot swap for bigger changes. That one fact explains why reloading works. It also explains why reloading leaks memory when something still holds a reference to the old loader.

Interview questions about class loading almost always come down to one question: do you understand that the JVM only does things when it must, and that this has consequences? Strong answers link the mechanism to something real:

  • why a missing jar can crash a service at 3 a.m. instead of at startup (late resolution),
  • why the holder idiom needs no locks (the <clinit> promise),
  • why a redeploy leaks exactly one application's worth of memory (loader leaks), and
  • why a version string will not change (constants copied into the caller).

Any one of those, explained with the mechanism behind it, is worth more than reciting three loader names.

6 Gotchas and common mistakes

  • Calling a method on the result of getClassLoader(). For any core JDK class it returns null. So String.class.getClassLoader().getResource(…) always throws a NullPointerException. People make this mistake because every other “get” method in Java returns an object. Avoid it: remember that null means bootstrap. Prefer SomeClassOfYours.class.getResourceAsStream(…). That is the Class method, not the ClassLoader one, and it handles this for you. Its path is relative to the class's package, unless you start it with /.
  • Mixing up ClassNotFoundException and NoClassDefFoundError. They come from different places and mean different things. The first is a failed lookup by name (reflection, a config file, a framework). The second is a failed resolution of something your compiled code already points to. Avoid it: ask “did anyone type this class's name as a string?” If yes, it is a name problem. If no, it is a packaging problem: something on the compile class path is missing from the runtime class path.
  • Expecting a changed public static final constant to reach callers. It was copied into their class files when they were compiled. Avoid it: in a library API, offer values that may change through a method or a field that is not a constant. When a constant must change, rebuild everything that uses it from clean, not partially.
  • Thinking Class.forName and loader.loadClass do the same thing. The first initializes. The second does not. If you swap one for the other, things can quietly stop happening: a driver does not register, a plugin does not install itself, a static cache does not fill. There is no error at all. Avoid it: choose on purpose. To look at a class without initializing it, use the three-argument Class.forName(name, false, loader).
  • Putting the same class on the class path twice and expecting a predictable winner. The class path is searched in order, so the first copy does win. But which copy comes first depends on the order your build tool happened to produce. That order can change when you add an unrelated dependency. Avoid it: treat a duplicate class as a bug to remove, not an order to tweak. Maven's dependency tree shows where each copy comes from.
  • Writing a custom class loader for a problem that is not a class-loading problem. Custom loaders are right for exactly two jobs: keeping things apart (plugins that must not see each other) and reloading. “Two libraries want different versions of a third” is a dependency problem, and you fix it in the build file. Also, every custom loader risks a class loader leak. One leftover reference, like a ThreadLocal or a static registry entry, keeps the loader alive. It also keeps alive every class that loader defined. So each redeploy leaks a whole copy of the application. Avoid it: do not write one unless the problem really is keeping things apart or reloading. Lesson 07 shows what a leak looks like in a heap dump.

7 Key takeaways

  • A class loader is a normal Java object that turns a class's name into a loaded class. Every JVM starts with three loaders in a parent chain: bootstrap (which has no Java object and shows up as null), platform, and application.
  • Parent delegation means a loader asks its parent before searching itself. That is why a fake java.lang.String on your class path can never be reached, and why every JDK class exists exactly once.
  • A class is known by its name plus the loader that defined it. So two loaders that define the same name make two truly different types, which causes ClassCastException: Config cannot be cast to Config.
  • Every class goes through loading, then linking (verification, preparation, resolution), then initialization. Only initialization runs your own code, in a hidden <clinit> method that runs exactly once per loader, is locked by the JVM, and breaks the class forever if it throws.
  • A class initializes on new, a static method call, reading or writing a static field that is not a constant, or Class.forName(name). It does not initialize on an import, a class literal, an array of the type, or reading a compile-time constant. Constants are copied into the reader's own bytecode, which is why changed constants do not reach callers that were not recompiled.

Line by line:

  • 1: 10 — nothing initializes. PINNED is a compile-time constant. So its value was copied into Puzzle's bytecode. It does not matter at all that the source names Beta. Alpha is never touched either.
  • 2: 3 — nothing initializes. Making an array of a type does not make any object of that type. All three slots are null.
  • 3: Beta — nothing initializes. A class literal needs Beta to be loaded, so that the Class object exists. Asking for its name only reads information about the class. It runs none of the class's code.
  • Alpha init, then 4: 20. COMPUTED is not a constant expression. So reading it forces initialization. But it initializes the class that declares the field. That is Alpha, not Beta. This is the rule people get wrong. Beta is still not initialized here, which is why Beta init has not printed. Notice the order too. Alpha init appears before 4: 20. The initializer must run before the field can be read. And the whole "4: " + Beta.COMPUTED is worked out before println is called.
  • Beta init, then 5: …. new Beta() finally initializes Beta. Its superclass Alpha would go first, but Alpha is already done. So only Beta init prints. Then the object's default toString prints the class name, an @, and a hex number (its identity hash). That number changes on every run.

The bonus lesson: three of the five lines printed without initializing anything at all. If you predicted Alpha init and Beta init at the top, you assumed classes initialize as soon as the program starts. That is the most common wrong picture, and this lesson exists to replace it.

Part B (1) — how it is possible. A class is known by its full name together with the loader that defined it. So two loaders that each define com.acme.Config make two different types, as unrelated as String and Integer. The message prints the same name twice because the name really is the same. The JVM adds the two loaders in brackets. That is the only part that is different, so it is the only part worth reading.

Part B (2) — the likely cause. The jar that holds com.acme.Config is in two places at once: on the application class path and inside the plugin. Plugin loaders usually search themselves before asking upward. So the plugin's loader defines its own copy. Then the host passes the plugin an object of the app-loader type, or gets one of the plugin-loader type back. The cast fails.

Part B (3) — the fix. Decide which loader owns the shared type, and make sure only that loader can define it. In practice:

  • Put the shared API classes in a separate “api” jar that lives only on the parent's class path.
  • Plugins compile against it, but do not pack a copy of it inside themselves.
  • Set up the plugin loader to ask upward for that package.

Packing a copy of a shared API inside a plugin is the mistake. Removing the duplicate is the fix.

Part C — what you should see. When you use only a compile-time constant, java -verbose:class … | findstr YourClass prints nothing, and your static block never runs.
