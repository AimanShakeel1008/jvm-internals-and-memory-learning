Lesson 02 — Class Loading

Who finds your .class files, in what order, and at exactly which instant your static code finally runs — the machinery behind NoClassDefFoundError, stale constants, and “Config cannot be cast to Config.”

Position: Lesson 02 of 07  ·  Prerequisites: Lesson 01 — How Java Actually Runs  ·  Project files: loading/ClassLoaderReporter.java, loading/InitializationLog.java, four demonstration subjects, experiments/ClassLoadingExperiment.java, JvmExplorer.java (modified), and three test classes

1 The pain

In Lesson 01 we wrote a line and walked straight past the interesting part of it:

ClassFileInspector.class.getResourceAsStream("/com/corejava/jvm/BytecodeSubject.class");

Something found that file. Something decided where to look, in what order, and at what moment. That something is the part of the JVM this lesson is about, and until you know how it works, three of Java's most common failures are unreadable noise.

The first pain is a pair of errors that look identical and mean opposite things. A program dies with ClassNotFoundException. A colleague's dies with NoClassDefFoundError. Both say a class is missing; both point at the same jar; the fixes are different. Worse, there is a third form — NoClassDefFoundError: Could not initialize class com.acme.Config — which is thrown for a class that is sitting right there on the class path, perfectly present, perfectly readable. The real cause happened earlier, in a different thread, with a different exception, and has already scrolled off the screen. People restart the server and hope.

The second pain is stale values with no cache in sight. A team ships a shared library with public static final String API_VERSION = "1.0";. Six months later they change it to "2.0", rebuild the library, drop the new jar in, restart everything — and the application logs 1.0. Not sometimes. Every time. There is no cache, no stale build folder, no CDN. The old value is physically inside the application's own bytecode, and only the rules of class loading explain why, or what to do about it.

The third pain is the one that makes people doubt their eyesight. A plugin-based application throws:

java.lang.ClassCastException: class com.acme.Config cannot be cast to
        class com.acme.Config (com.acme.Config is in unnamed module of loader
        'app'; com.acme.Config is in unnamed module of loader
        org.acme.PluginLoader @4f3f5b24)

The same name on both sides. Not a typo, not a shading problem, not a generics mistake. To understand that message at all you need one fact that is never taught early enough: a class's runtime identity is its name plus the loader that defined it. Two loaders, one name, two genuinely different types that cannot be assigned to one another.

And underneath all three is a timing question you have probably never asked out loud. A static block runs — when? When the JVM starts? When the class is first mentioned? When the first object is created? The answer is precise, specified, and surprising, and it decides whether your configuration loads before or after the thing that needs it. By the end of this lesson your project will print the loader chain for any class, and a witness log will show you, line by line, which classes have woken up and which are still cold.

2 Real-world analogy

Picture a library with three librarians in a strict hierarchy: a junior at the front desk, a senior in the back office, and the head librarian, who alone holds the key to the rare-books vault.

You ask the junior for Hamlet. She does not go looking. She turns around and asks the senior. He does not go looking either — he asks the head librarian. The head librarian checks the vault, finds the authentic Hamlet, and passes it back down the chain to you. Only if the head librarian says “not in the vault” does the senior check his own office shelves; only if he also comes up empty does the junior finally check hers. And if all three fail, you get a definite answer: we do not have that book.

Now the reason for the rule, which is the whole point. Suppose someone slipped a forged Hamlet onto the junior's front-desk shelf — a copy with the ending rewritten. Under this system nobody ever reaches it. The authentic copy is found first, in the vault, every single time. The forgery is not policed, not detected, not blocked: it is simply unreachable by construction.

The libraryThe JVM
A librarian: the person you ask for a book by titleA class loader: the object you ask for a class by name
The head librarian and the rare-books vaultThe bootstrap loader and java.base (String, Object…)

The junior librarian's front deskThe application loader and your class path

Two more details of the analogy map exactly, and both matter later.

Nothing is fetched in advance. The library does not carry every book to your table when you walk in. A book is fetched when a reader asks for it, and not a moment sooner. The JVM is the same: your program does not “load” at startup. Classes arrive one at a time, on first use, for the entire life of the process.

Two libraries can hold two different books with the same title. If your city has a second, independent library and you borrow Hamlet from each, you now hold two physical objects. They share a title; they are not interchangeable; returning one to the wrong library is an error. That is precisely the ClassCastException from Section 1 — two loaders, one name, two distinct types.

3 The concept explained

We build this in dependency order: what “loading a class” has to accomplish, who does it, the rule they follow, why a class's identity is not just its name, the five steps every class goes through, and the exact instant your static code runs. Then we watch all of it happen with the JVM's own logging.

3.1 What “loading a class” actually has to accomplish

Lesson 01 left us with a file: a class file full of bytes, starting with 0xCAFEBABE, holding bytecode for some methods. A file is not a type. Before your program can write new Config(), the JVM needs a live thing in memory that knows: what this class is called, what its fields are and how big an instance must be, what its methods are and where their bytecode lives, who its superclass is, and — crucially — that all of the above has been checked and is safe to run.

Turning bytes on disk into that live thing is what we mean by loading a class. And it raises a question the file itself cannot answer: given the name com.acme.Config, where do the bytes come from? A folder? A jar? A network stream? A generator that invents them on the spot? Java's answer was to refuse to hard-code any of it, and hand the job to an ordinary Java object instead.

3.2 The class loader: an object with one job

A class loader is a Java object whose job is: given a class's name as text, produce a loaded class. That is the entire contract. It is not a keyword, not a JVM flag, not a phase of the build — it is an object of a class extending java.lang.ClassLoader, sitting in memory alongside your own objects, that you can hold a reference to and ask questions of.

Why build it that way? Because “where do class bytes come from” has many legitimate answers, and hard-coding one would have frozen Java in 1995. Because the loader is an ordinary object, the answer can be “from this folder”, “from inside this jar”, “from this web server”, “from these bytes I just generated”, or “from a fresh copy so I can reload the class without restarting.” Every one of those exists in real systems, and Lesson 01's sighting of Mockito generating classes that were never compiled is exactly this mechanism in use.

Every class knows which loader defined it, and you can ask:

ClassLoader mine   = JvmExplorer.class.getClassLoader();   // an object
ClassLoader theirs = String.class.getClassLoader();       // null !

That null is not a bug, not a missing value, and not something to guard against. It is the JVM's way of spelling “the bootstrap loader” — which is written in C++ inside the JVM itself and therefore has no Java object to hand back. A great many beginner crashes come from writing x.getClassLoader().getResource(...) on a JDK class and getting a NullPointerException that seems to make no sense. It makes perfect sense: there is no object there to call a method on.

3.3 The three loaders every JVM has

A standard JVM starts with three loaders already in place, arranged so that each one has a parent — the loader it defers to. They are not equals; they form a chain.

LoadergetName()What it can findIts parent
Bootstrapno Java object at all — shows up as nulljava.base: Object, String, Integer, System — the classes the JVM cannot start without— (it is the top)
Platform"platform"the rest of the JDK's modules, e.g. java.sql, java.xmlbootstrap
Application"app"your classes and your libraries — everything on the class pathplatform

Two naming traps, both permanent. First, the application loader is what ClassLoader.getSystemClassLoader() returns — it is called “system” for historical reasons, has nothing to do with the operating system, and confuses everyone forever. Second, before Java 9 the top two were called the bootstrap and extension loaders; the extension loader was removed in Java 9 and replaced by the platform loader when modules arrived. Old tutorials still say “ext”, and old code still refers to a lib/ext folder that no longer exists.

Which loader owns which JDK class is not something to memorise — it is something to ask. Our new module prints the answer for any class you name, and Section 4 shows it running.

3.4 Parent delegation: ask upward, search downward

Here is the rule that governs every class request in Java, and it is deliberately counter-intuitive: when a loader is asked for a class, it does not look. It asks its parent first. Only when the parent (and the parent's parent, all the way to the top) reports failure does a loader search its own sources. This is called parent delegation.

Why go to this trouble? Three reasons, in order of importance.

Security, by construction rather than by policing. Suppose you put a file named java/lang/String.class in your own jar, containing a String whose equals always returns true. Under delegation, the application loader never gets to define it: the request goes up, the bootstrap loader finds the real String in java.base, and that is the one everybody gets. Your forgery sits on disk, unreachable, forever. Nothing had to detect it or block it. (Modern JVMs additionally refuse outright to let anyone but the bootstrap loader define classes in java.* packages — belt and braces — but delegation alone already solves it.)

Uniqueness. Without delegation, three loaders might each define their own java.lang.Object, and — for the reason in Section 3.6 — those would be three incompatible types. Nothing in Java would work. Delegation guarantees that a class found higher in the chain is shared by everyone below it.

A definite answer. Because the search order is fixed and exhaustive, “not found” means genuinely nowhere, not “not in the place I happened to look.”

Delegation is a convention implemented in code, not a law the JVM enforces. It lives in ClassLoader.loadClass, which any subclass may override. Application servers and plugin systems deliberately break it — see Section 5 — and that is exactly where the strangest class-loading bugs live.

You add a jar containing your own java/lang/String.class to the class path. What happens?
Nothing. Every request for java.lang.String is delegated up to the bootstrap loader, which finds the real one in java.base and returns it. Your file is never read. It is not detected or rejected — it is simply never reached, because the loader that could have found it never gets to search.

3.6 A class's identity is its name plus its loader

This single sentence explains the third pain from Section 1, and it is the fact most often missing from people's mental model.

Inside the JVM, a loaded class is identified by the pair: its fully-qualified name, and the loader that defined it. Formally that pair is called the class's runtime package and, at the type level, its runtime identity. The consequence is blunt: if two different loaders each define a class called com.acme.Config, the JVM holds two different types. Not two copies of one type — two types, as unrelated as String and Integer. An object of one cannot be assigned to a variable of the other, and the cast fails with a message that names the same class twice.

Notice how neatly this dovetails with delegation. Because everybody delegates upward, java.lang.String is defined exactly once, by the bootstrap loader, and shared by every loader beneath it — so there is only ever one String type. Delegation is what keeps duplicate types from happening by accident; deliberately breaking delegation is what makes them happen on purpose.

3.7 The five steps, from bytes to usable class

Loading is not one action. The JVM Specification defines a sequence, and knowing its names is what makes error messages readable. The whole sequence is often summarised as loading → linking → initialization, where linking has three sub-steps of its own.

1 · Loading

A loader is asked for a name, delegation runs, somebody finds the bytes, and the JVM parses them into an internal representation — plus the Class object you can hold in a variable. The magic number and version check from Lesson 01 happen here: a file that is not 0xCAFEBABE, or is too new, is rejected at this step with UnsupportedClassVersionError.

2a · Verification

Verification is the JVM proving to itself that the bytecode cannot misbehave, before running a single instruction of it. Remember that the JVM has no idea where a class file came from; it may have been hand-edited, corrupted in transit, or produced by a compiler for another language entirely. So it checks things like: does every instruction leave the operand stack in a consistent state, whatever path was taken to reach it? Does any jump land in the middle of an instruction, or outside the method? Does any code treat an int as an object reference, or read a local slot that was never written? Are the access rules obeyed — no calling a private method from outside its class?

This is why a corrupted class file gives you a clear VerifyError instead of a crashed process, and it is a large part of what “Java is memory-safe” actually buys you: the safety is enforced at the door, once per class, rather than on every instruction. There used to be a flag to switch verification off for faster startup; it has been deprecated and no longer has a useful effect on modern JDKs — treat it as gone, and verify against your JDK's release notes if you meet it in an old script.

2b · Preparation

Preparation allocates the class's static fields and sets them to default values: 0 for numbers, false for booleans, null for references. Not your values. If you wrote static int count = 5;, then after preparation count is 0. The 5 is assigned later, in step 3, because assigning it means running code.

There is exactly one exception, and it matters for this lesson: a field that is static final and assigned a constant expression is filled in during preparation, straight from the ConstantValue attribute stored in the class file. It needs no code, so it does not wait for initialization.

2c · Resolution

Lesson 01 showed bytecode full of # numbers pointing into the constant pool — symbolic references like “the method named println with descriptor (Ljava/lang/String;)V in the class java/io/PrintStream”. Resolution is turning each of those names into a direct pointer to the real thing, which may require loading yet another class.

The specification permits resolution to happen eagerly at link time or lazily on first use, and HotSpot chooses lazy. That single choice explains a whole family of production incidents: a class you never call can be missing from the class path for months without anyone noticing, until one rare code path finally executes and the JVM tries to resolve it. The failure arrives at 3 a.m., not at startup.

3 · Initialization

Finally, the JVM runs the class's own setup code: static field assignments and static { } blocks. This is the step with rules, and the next two subsections are entirely about it.

Immediately after preparation, what is the value of static int count = 5;?
Zero. Preparation only assigns default values; the assignment of 5 is code, and code belongs to initialization. The exception is a static final field assigned a constant expression — that one is filled in during preparation, from the class file's ConstantValue attribute, without running anything.

3.8 <clinit>: the method you never wrote

Where does “the class's setup code” live? Lesson 01 showed that a constructor is stored in the class file as an ordinary method with the reserved name <init>. Initialization works the same way: javac collects every static field assignment and every static { } block, in the order they appear in your source file, and welds them into a single synthetic method named <clinit> — short for “class initializer”. You never wrote it, you cannot call it, and the JVM runs it exactly once.

Our new ConstantHolder is built to make this visible. It has two compile-time constants, one computed field, and one static block:

public static final int PINNED_MAJOR_VERSION = 65;                 // constant
public static final String COURSE_NAME = "JVM Internals & Memory";  // constant
public static final String DESCRIPTION = buildDescription();        // NOT constant

static {
    InitializationLog.record("ConstantHolder");
}
// PREDICTED javap -c -p output for ConstantHolder (the # numbers will differ)
  static {};
    Code:
       0: invokestatic  #7    // Method buildDescription:()Ljava/lang/String;
       3: putstatic     #13   // Field DESCRIPTION:Ljava/lang/String;
       6: ldc           #19   // String ConstantHolder
       8: invokestatic  #21   // Method …/InitializationLog.record:(Ljava/lang/String;)V
      11: return

Read what is there and what is missing. The two things that ran are in source order: the DESCRIPTION assignment (declared first), then the static block. And PINNED_MAJOR_VERSION and COURSE_NAME appear nowhere at all — no instruction assigns them, because they were already filled in during preparation from their ConstantValue attributes. javap -v shows those attributes sitting in the field declarations.

Three properties of <clinit> are worth carrying around permanently:

  • It runs exactly once, per class, per loader. There is no “re-initialize”. Once done, done — for the life of that loader.
  • It is thread-safe, and the JVM does the locking for you. If two threads touch a cold class simultaneously, one runs <clinit> while the other blocks until it finishes. You never write a lock for this. It is the only piece of guaranteed-once, guaranteed-safe lazy initialization Java gives you for free — and Section 5 shows the idiom built on it.
  • If it throws, the class is poisoned forever. The first failure surfaces as ExceptionInInitializerError, wrapping whatever your code actually threw. Every later attempt to use that class gets NoClassDefFoundError: Could not initialize class … — a different error, with the real cause nowhere in sight. This is the mechanism behind the confusing failure from Section 1.

What goes wrong when you forget those three facts. Here is a very common piece of code — a settings class that loads its file in a static block:

// WRONG: runs at a moment you do not control, and its failure reaches the wrong person
public final class Settings {
    public static final Properties VALUES = new Properties();
    static {
        try (InputStream in = new FileInputStream("/etc/app/settings.properties")) {
            VALUES.load(in);                    // file reading inside <clinit>
        } catch (IOException e) {
            throw new RuntimeException(e);      // ...and it can throw
        }
    }
}
// PREDICTED symptom on a machine where the file is missing — the first caller sees:
java.lang.ExceptionInInitializerError
Caused by: java.lang.RuntimeException: java.io.FileNotFoundException: /etc/app/settings.properties

// ...and every caller after that sees only:
java.lang.NoClassDefFoundError: Could not initialize class com.acme.Settings

The file is read whenever something first touches Settings — at startup, ten minutes in, or never. Only the first thread sees the useful error. And no test can make it read a different file, or reset it, because a class initializes once per loader. The cure: keep static initializers to simple assignments that cannot fail, and put anything that can fail — files, network, configuration — in a method the caller invokes on purpose. That is why every static block in our project does exactly one thing: add a name to an in-memory list.

3.9 Exactly when a class initializes

Now the rules. The Java Language Specification lists precisely what triggers initialization, and the list is shorter than people expect. A class initializes on the first occurrence of any of these:

This does initializeWhy
new Foo()you are creating an instance, so the class must be ready
calling a static method declared by Foorunning the class's code requires the class's code to be set up
reading or writing a static field declared by Foo that is not a compile-time constantthe value only exists once the initializer has produced it
Class.forName("Foo") (one-argument form)documented to initialize — that is the point of the method
initializing a subclass of Fooa superclass is always ready before its subclass
Foo is the class named on the java command linethe JVM initializes it before calling main
This does not initializeWhy
import com.acme.Foo;imports are a compile-time convenience; nothing remains of them at run time
Foo.classasks for the class object — needs loading, not initializing
new Foo[10]every slot is null; not one Foo is created
reading a static final compile-time constantthe value was copied into your class file at compile time
Class.forName("Foo", false, loader)the false explicitly says “load, do not initialize”

declaring a variable, a parameter, or a return type of type Fooa type mention is not a use
reading a static field declared in the superclass through the subclass's nameonly the class that declares the field initializes
initializing a superclassparents do not wake their children

The last two rows are the ones that catch experienced developers, so let us be explicit. Given class Child extends Parent, where Parent declares static String NAME = compute();:

System.out.println(Child.NAME);   // initializes Parent ONLY. Child stays cold.

The source says Child. The field is declared in Parent. Initialization follows the declaration, not the name you typed. Child does get loaded — the JVM has to look at it to discover the field is inherited — but its <clinit> does not run. Our project asserts exactly this, and it is one of the few places the language specification bothers to spell out an example, precisely because everyone gets it wrong.

Two smaller rules, for completeness. Interfaces initialize under the same conditions, but with a twist: initializing a class initializes its superclasses and any superinterfaces that declare default methods — not plain constant-only interfaces. And an assert statement inside a class counts as a trigger for that class, which is an obscure corner you will likely never meet.

What goes wrong when you mistake a mention for a use. For years, programs connecting to a database did this, and it failed with “no suitable driver found”:

import com.mysql.cj.jdbc.Driver;                       // compile-time only - does nothing at run time
Connection c = DriverManager.getConnection(url);    // the driver never registered itself

The driver registers itself with DriverManager from inside its own static block, so it only works once the driver class has initialized — and an import never initializes anything. The historical cure is the line that looks like superstition in every old tutorial: Class.forName("com.mysql.cj.jdbc.Driver");, which forces initialization by name. (Modern drivers are found automatically — see Section 5 — but now you know why that line ever existed.)

Does List<Config> list = new ArrayList<>(); initialize Config?
No. Config appears only as a type argument, and type arguments are erased at compile time — they leave nothing in the bytecode that mentions the class at run time. Even without erasure, a type mention is not a use. Config initializes the first time you actually create one, call one of its static methods, or read a non-constant static field of it.

3.10 Why a compile-time constant is different from everything else

This deserves its own subsection, because it is the mechanism behind the “stale value” pain and it surprises people every time.

A field is a compile-time constant — the specification calls it a constant variable — when it is static, final, of a primitive type or String, and initialized with a constant expression: a literal, or arithmetic on literals and other constants. When javac compiles code that reads such a field, it does not emit a field access at all. It copies the value directly into the reading class's own bytecode.

So our JvmExplorer contains this line:

System.out.println("Constant read      : " + ConstantHolder.PINNED_MAJOR_VERSION);

and both halves of that concatenation are constants, so javac folds the whole thing into one string literal. The compiled JvmExplorer does not mention ConstantHolder anywhere — not in its instructions, not in its constant pool. You can prove it in one command:

# from jvm-explorer/, after mvn compile — expect NO output at all
javap -v target/classes/com/corejava/jvm/JvmExplorer.class | findstr ConstantHolder

# on macOS / Linux:
javap -v target/classes/com/corejava/jvm/JvmExplorer.class | grep ConstantHolder

Now the real-world consequence. Ship a library with public static final String API_VERSION = "1.0";. Every application that compiles against it bakes "1.0" into its own class files. Release version 2 of the library with "2.0", drop the new jar in, restart — and every application that was not recompiled still prints 1.0, because the string is in their bytecode, not in the library's. The library is not consulted. There is nothing to invalidate.

The rule that follows is worth writing on the wall: in a library's public API, use a compile-time constant only for a value that is genuinely eternal. If a value may ever change between releases, expose it through a method (public static String apiVersion()) or a non-constant field (public static final String API_VERSION = computeVersion();) so that callers actually read it at run time. And when constants do change, everything that reads them must be rebuilt — a full clean build, not an incremental one.

3.11 Watching it happen on your own machine

All of the above is observable, not theoretical. The JVM will narrate its own class loading if you ask:

# one line per class, as it loads — the classic flag
java -verbose:class -cp target/classes com.corejava.jvm.JvmExplorer

# the modern equivalent, part of "unified logging" (Java 9 and later)
java -Xlog:class+load=info -cp target/classes com.corejava.jvm.JvmExplorer

# send it to a file instead, so it does not drown your program's own output
java -Xlog:class+load=info:file=classes.txt -cp target/classes com.corejava.jvm.JvmExplorer

Each line names a class and where it came from — which is the loader question answered from the outside:

// PREDICTED shape (there will be hundreds of lines before ours)
[0.004s][info][class,load] java.lang.Object source: shared objects file
[0.021s][info][class,load] java.sql.Date source: jrt:/java.sql
[0.089s][info][class,load] com.corejava.jvm.JvmExplorer source: file:/D:/.../target/classes/
[0.093s][info][class,load] com.corejava.jvm.loading.ClassLoaderReporter source: file:/D:/.../target/classes/

Two details in that output are worth naming. jrt:/java.sql is the JDK's own module storage — the modern replacement for the old rt.jar, addressed by a scheme called jrt:. And shared objects file means the class came from a pre-parsed archive the JDK ships (class-data sharing), which is a startup optimisation: rather than parsing java.lang.Object from scratch every time any JVM starts, the JDK keeps a ready-made memory image and maps it in. You will see it on most core JDK classes.

Why not mvn exec:java for this? Because exec:java runs your main inside Maven's own JVM, so -verbose:class would report Maven's thousands of classes alongside yours, and the JVM flags would have to be given to Maven rather than to your program. Running java directly against target/classes gives a clean JVM containing nothing but the JDK and your code — which is exactly what you want to observe.

3.12 The three errors, finally readable

What you seeWhat actually happenedWhere to look
ClassNotFoundException
(a checked Exception)		 Someone asked for a class by name, as text — Class.forName, loadClass, a framework reading a config file — and the whole delegation chain came up empty. The name in the message: a typo, a wrong package, or a jar genuinely absent from the class path.
NoClassDefFoundError
(an Error)		 The JVM was resolving a reference that your compiled code contains — so the class existed when you compiled, and does not now. A dependency present at build time but missing at run time: a jar not packaged, a “provided” scope, a container image built from the wrong layer.
NoClassDefFoundError: Could not initialize class X Different beast entirely. X is present. Its <clinit> ran earlier and threw, so the class is permanently unusable and every later touch reports this. Scroll back in the log for the first ExceptionInInitializerError. That one carries the real cause; this one does not.
ExceptionInInitializerError The first time a static initializer threw. Its getCause() is your actual exception. Whatever your static block does: reading a missing file, a null config, a failing regex.
ClassCastException: X cannot be cast to X Two loaders each defined a class named X. Two distinct types. The loader names in brackets in the message. Usually a jar present in two places at once.
UnsupportedClassVersionError Rejected during loading: the file's major version is newer than this JVM. (Lesson 01.) Subtract 44 from both numbers in the message.
Your app dies with NoClassDefFoundError: Could not initialize class com.acme.Settings, and the jar containing Settings is definitely on the class path. What do you do?
Stop looking at the class path — it is not a packaging problem. Search earlier in the log for the first ExceptionInInitializerError mentioning com.acme.Settings. That stack trace holds the real cause: something in the class's static initializer threw, probably a missing configuration file or a null value. Once a class's initializer fails, that class is permanently unusable for that loader, and every subsequent use reports this misleading second error instead.

4 Applied to jvm-explorer

Eight new source files, one modified, three new test classes. The project gains its second real capability — it can now report who loaded any class — plus a set of demonstration subjects whose only job is to prove, in assertions, exactly when a class wakes up.

4.1 What happens, step by step, when the new code in JvmExplorer runs

  1. JvmExplorer.main asks for the report on String.class. getClassLoader() returns null, the loop body never runs, and the chain is the single entry “bootstrap”.
  2. It asks about java.sql.Date. That class lives in a JDK module outside java.base, so it is expected to come from the platform loader; the chain is platform, then bootstrap. Printed, not asserted — confirm what your JDK reports.
  3. It asks about JvmExplorer itself. Our class came off the class path, so the application loader defined it, and the chain is app → platform → bootstrap.
  4. It prints the built-in chain on its own, asked for without naming any class: ClassLoader.getSystemClassLoader() and its parents.
  5. It prints the initialization log, which is empty — importing classes at the top of the file changed nothing.
  6. It reads ConstantHolder.PINNED_MAJOR_VERSION, a compile-time constant, and prints the log again: still empty. The number 65 came out of JvmExplorer's own bytecode.
  7. It calls LazyHolder.stamp(). A static method call cannot happen before the class is initialized, so <clinit> runs, the witness records LazyHolder, and the third print of the log finally shows one entry.

4.3 The reporting module

Saved at jvm-explorer/src/main/java/com/corejava/jvm/loading/ClassLoaderReporter.java. A new sub-package, loading, keeps this lesson's classes together the same way experiments keeps throwaway programs apart. The heart of it:

// What we print where the JVM hands us null. Named, not repeated as a literal,
// because tests assert on it and a typo in one of two copies is invisible.
public static final String BOOTSTRAP_DESCRIPTION = "bootstrap (built into the JVM, no Java object)";

public static String describe(ClassLoader loader) {
    // null is the bootstrap loader, not a mistake. Handling it FIRST means every
    // line below can assume a real object exists.
    if (loader == null) {
        return BOOTSTRAP_DESCRIPTION;
    }

    // Since Java 9 the built-in loaders carry names: "app" and "platform". Loaders
    // created by other code may have no name at all, so getName() can return null.
    String name = loader.getName();
    if (name == null) {
        name = "(unnamed)";
    }

    // The class name is the giveaway that something custom is in play.
    return name + " — " + loader.getClass().getName();
}

4.4 The witness

Saved at .../loading/InitializationLog.java. Class initialization leaves no trace of its own, so we make one. Every demonstration class calls record from its static initializer, and the tests read the log afterwards.

// One log for the whole JVM - the right shape, since a class also initializes
// once per JVM (strictly: once per class loader).
private static final List<String> EVENTS = Collections.synchronizedList(new ArrayList<>());

public static void record(String simpleClassName) {
    // No validation, no formatting, no I/O. A static initializer is the worst
    // possible place for something that might throw or block.
    EVENTS.add(simpleClassName);
}

public static List<String> events() {
    // synchronizedList makes each add safe, but COPYING means iterating, and
    // iteration must be guarded by hand - the documented rule for these wrappers.
    synchronized (EVENTS) {
        return List.copyOf(EVENTS);   // immutable: nobody can rewrite history
    }
}

4.6 The tests that make the rules real

Thirteen new tests. The three that carry the most weight:

@Test

    assertFalse(InitializationLog.wasInitialized("ConstantHolder"), /* … */);

    // Both values were baked into THIS class's constant pool by javac.
    assertEquals(65, ConstantHolder.PINNED_MAJOR_VERSION, /* … */);

    // rebuilt the library, and the caller still prints the old value".

    assertEquals("Course 01 pins Java 21", ConstantHolder.DESCRIPTION, /* … */);

@Test

    String name = "com.corejava.jvm.loading.ForNameSubject";

    assertEquals(loadedOnly, Class.forName(name), /* … */);

@Test
void aSuperclassInitializesFirstAndOnlyTheDeclaringClassWakesUp() {

And note what the class-loader tests deliberately do not assert: which loader loaded the test classes themselves. What they assert instead are the guarantees the specification actually makes — String comes from bootstrap, every chain ends at bootstrap, and app's parent is platform whose parent is null.

5 In the wild

The initialization-on-demand holder idiom. This is the most elegant use of everything in Section 3.9, and it appears throughout the JDK and well-written libraries:

public final class ExpensiveThing {

    // A private nested class that exists ONLY to hold the instance.
    private static class Holder {
        static final ExpensiveThing INSTANCE = new ExpensiveThing();
    }

    public static ExpensiveThing get() {
        return Holder.INSTANCE;   // Holder initializes HERE, on the first call, once
    }
}

No synchronized, no double-checked locking, no volatile, no atomics — and it is completely thread-safe and completely lazy. Holder is not initialized when ExpensiveThing is, because a nested class is an independent class; it initializes at the first read of Holder.INSTANCE, and the JVM's own <clinit> lock guarantees that happens exactly once even under a hundred simultaneous threads. The idiom is nothing but the class-initialization rules, used deliberately.

Application servers and Spring Boot deliberately invert delegation. A servlet container like Tomcat runs several web applications in one JVM, each with its own libraries — application A wants version 1 of a library, application B wants version 3. Under strict parent delegation both would get whichever copy the shared parent held. So a web application's loader checks itself first for application classes, and only delegates upward for JDK classes. That is a controlled, documented inversion of the rule in Section 3.4, and it is the reason “it works in my IDE but not in the container” is a genre of bug rather than a single one. Spring Boot's executable jar uses a loader of its own to read nested jars — a shape a plain JVM cannot handle, since the class path does not support jars inside jars. (The exact class name of Boot's loader has changed between major versions; check your version's source rather than trusting a blog post.)

ServiceLoader and the context class loader. Delegation creates one structural problem: a parent can never see its children's classes. The JDK's java.sql.DriverManager, loaded by the platform loader, must somehow instantiate your MySQL driver, which lives on the application class path — below it. It cannot reach down. Java's answer is the thread context class loader: a loader reference carried on each thread that framework code can ask for, deliberately side-stepping the hierarchy. It is what ServiceLoader uses to discover implementations, and it is why modern JDBC no longer needs Class.forName. It is also a persistent source of subtle bugs, because a thread's context loader is whatever the last framework to touch it set it to.

Every hot-reload you have used is a new class loader. A class cannot be re-loaded or re-initialized in the loader that already defined it — that is absolute. So every tool that appears to reload code (JRebel, Spring Boot devtools, an application server redeploy, an IDE's hot swap for structural changes) works by throwing away a whole class loader and building a fresh one. Understanding that single sentence explains both why reloading works and why it leaks memory when something holds a reference to the old loader.

“Class loading” questions in interviews are almost always really one question: do you understand that the JVM is lazy, and that laziness has consequences? The strong answers connect the mechanism to something observed: why a missing jar can crash a service at 3 a.m. rather than at startup (lazy resolution); why the holder idiom needs no locks (the <clinit> guarantee); why a redeploy leaks exactly one application's worth of memory (loader leaks); why a version string will not change (constant inlining). Any one of those, explained with the mechanism behind it, is worth more than reciting three loader names.

6 Gotchas and common mistakes

  • Calling a method on the result of getClassLoader(). For any core JDK class it returns null, so String.class.getClassLoader().getResource(…) is a guaranteed NullPointerException. People make this mistake because every other “get” method in Java returns an object. Avoid it: remember that null means bootstrap, and prefer SomeClassOfYours.class.getResourceAsStream(…) — the Class method, not the ClassLoader one — which handles this for you and takes a path relative to the class's package unless you start it with /.
  • Confusing ClassNotFoundException with NoClassDefFoundError. They come from different places and mean different things: the first is a failed lookup by name (reflection, configuration, a framework), the second is a failed resolution of something your compiled code already refers to. Avoid it: ask “did anyone type this class's name as a string?” If yes, it is a name problem. If no, it is a packaging problem — something on the compile class path is missing from the runtime class path.
  • Expecting a changed public static final constant to reach callers. It was inlined into their class files at their compile time. Avoid it: in a library API, expose changeable values through a method or a non-constant field; when a constant must change, rebuild every consumer from clean rather than incrementally.
  • Assuming Class.forName and loader.loadClass are interchangeable. The first initializes; the second does not. Swapping one for the other silently stops a driver registering, a plugin self-installing, or a static cache filling — with no error at all, just behaviour that quietly does not happen. Avoid it: choose deliberately, and remember the three-argument Class.forName(name, false, loader) when you want to inspect a class without waking it.
  • Putting the same class on the class path twice and expecting a predictable winner. The class path is searched in order, so the first copy does win — but which copy is first depends on the order your build tool happened to produce, which can change when you add an unrelated dependency. Avoid it: treat a duplicated class as a bug to remove (Maven's dependency tree shows where each copy comes from), not an ordering to tune.
  • Writing a custom class loader for a problem that is not a class-loading problem. Custom loaders are right for exactly two jobs: isolation (plugins that must not see each other) and reloading. “Two libraries want different versions of a third” is a dependency problem with a build-file fix. And every custom loader risks a class loader leak: one lingering reference — a ThreadLocal, a static registry entry — keeps the loader and every class it defined alive, so each redeploy leaks a whole copy of the application. Avoid it: do not write one unless the problem is genuinely isolation or reloading. Lesson 07 shows what a leak looks like in a heap dump.

7 Key takeaways

  • A class loader is an ordinary Java object that turns a class's name into a loaded class, and every JVM starts with three in a parent chain — bootstrap (which has no Java object and shows up as null), platform, and application.
  • Parent delegation means a loader asks its parent before searching itself, which is why a forged java.lang.String on your class path is unreachable rather than merely forbidden, and why every JDK class exists exactly once.
  • A class's runtime identity is its name plus its defining loader, so two loaders defining the same name produce two genuinely different types — the cause of ClassCastException: Config cannot be cast to Config.
  • Every class goes through loading, then linking (verification, preparation, resolution), then initialization — and only initialization runs your own code, in a synthetic <clinit> method that runs exactly once per loader, is locked by the JVM, and poisons the class permanently if it throws.
  • Initialization is triggered by new, a static method call, a non-constant static field access, or Class.forName(name) — and specifically not by an import, a class literal, an array of the type, or a compile-time constant, which was copied into the reader's own bytecode and is why changed constants do not reach un-recompiled callers.

Part A — predict the output. Without compiling anything, write down exactly what this program prints, and in what order:

Line by line:

  • 1: 10 — nothing initializes. PINNED is a compile-time constant, so its value was copied into Puzzle's bytecode. It does not matter at all that the source names Beta; Alpha is never touched either.
  • 2: 3 — nothing initializes. Creating an array of a type does not create any instance of it. All three slots are null.
  • 3: Beta — nothing initializes. A class literal requires Beta to be loaded so the Class object exists, and asking it for its name is metadata, not code.
  • Alpha init, then 4: 20. COMPUTED is not a constant expression, so reading it forces initialization — but of the class that declares it, which is Alpha, not Beta. This is the rule people get wrong: Beta is still cold at this point, which is why Beta init has not printed. Note the ordering too: Alpha init appears before 4: 20, because the initializer runs before the field can be read, and the whole right-hand side of the concatenation is evaluated before println is called.
  • Beta init, then 5: …. new Beta() finally initializes Beta — and its superclass Alpha would have gone first, except Alpha is already done, so only Beta init prints. Then the object's default toString prints the class name, an @, and a hexadecimal identity hash that will differ on every run.

The bonus insight: three of the five lines produced output without initializing anything at all. If you predicted Alpha init and Beta init at the top, you were assuming eager initialization — the single most common wrong model, and the one this lesson exists to replace.

Part B (1) — how it is possible. A class's runtime identity is its fully-qualified name together with the loader that defined it, so two loaders that each define com.acme.Config produce two distinct types, as unrelated as String and Integer. The message prints the same name twice because the name really is the same — and the JVM helpfully appends the two loaders in brackets, which is the only part that differs and therefore the only part worth reading.

Part B (2) — the likely cause. The jar containing com.acme.Config is present in two places at once: on the application class path and inside the plugin, so the plugin's loader — which searches itself before delegating, as plugin loaders usually do — defines its own copy. The host then hands the plugin an object of the app-loader type, or receives one of the plugin-loader type back, and the cast fails.

Part B (3) — the fix. Decide which loader owns the shared type and make sure only that one can define it. In practice: the shared API classes go in a separate “api” jar that lives only on the parent's class path, plugins compile against it but do not bundle it, and the plugin loader is configured to delegate for that package. Bundling a copy of a shared API inside a plugin is the mistake; removing the duplicate is the fix.

Part C — what you should see. With the reference being a compile-time constant, java -verbose:class … | findstr YourClass prints nothing and your static block never runs. Change the reference to a static method call, recompile, and exactly one [class,load] line appears, followed by your static block's output — at the point in the program where the call is, not at startup. If your machine shows something different, it wins: tell me what you saw.
