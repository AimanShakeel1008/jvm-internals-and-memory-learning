Lesson 01 — How Java Actually Runs

Open the black box between the code you type and the behaviour you observe: the class file, the instruction set inside it, and the two ways the JVM runs those instructions.

Position: Lesson 01 of 07  ·  Prerequisites: Lesson 00 — Full Setup  ·  Project files: BytecodeSubject.java, ClassFileHeader.java, ClassFileInspector.java, experiments/WarmupExperiment.java, JvmExplorer.java (modified), and three test classes

1 The pain

Priya finishes a small tool, builds it, and emails the finished file to Sam so he can try it. Sam double-clicks. Nothing happens. He runs it from a terminal instead, and gets this:

Exception in thread "main" java.lang.UnsupportedClassVersionError:
        com/example/Tool has been compiled by a more recent version of the Java
        Runtime (class file version 65.0), this runtime only recognizes class
        file version 61.0

Read that message as a beginner and almost every word raises a question. Compiled by a more recent version — but Java was supposed to be “write once, run anywhere,” so why does the compiler's version matter after compiling is finished? Class file version 65.0 — what is a class file, and why does it have a version number of its own, one that matches no Java release Sam has ever heard of? And this runtime only recognizes 61.0 — where is that number stored, who checks it, and at what moment? Without knowing what the compiler actually produced, Sam cannot even search for the answer usefully; he can only paste the error into a forum and hope.

Here is a second, quieter pain, and it is the one that lasts a career. Someone asks you: “is total += i in a loop expensive?” Or: “why is joining strings with + inside a loop such a famous mistake?” Or, from a code review: “this method creates an object every call — does that matter?” If the space between your source code and the machine's behaviour is a black box, every one of those questions can only be answered by folklore — something you half-remember from a blog post. You cannot reason, you can only recite. And this course is entirely about that space, so leaving it closed now means guessing at everything that follows: where objects live, when they are collected, why the tenth run is faster than the first.

Which is the third pain, and the strangest one. Run the same loop ten times in a row on the same data, and time each run. The first takes maybe forty milliseconds. The tenth takes two. Nothing changed — not the code, not the input, not the machine. If you do not know that the JVM has two different ways of running your instructions and quietly switches between them, that measurement looks like a broken stopwatch. People genuinely dismiss it as noise, or worse, publish it as a benchmark.

The cure for all three is the same, and it is unglamorous: look at what the compiler actually produced. The .class file is not magic and it is not encrypted. It is a documented binary format with a fixed shape, holding instructions written in a small, learnable language. By the end of this lesson you will have read the file's first eight bytes with your own code, disassembled four methods and understood every instruction in them, and watched the JVM's second execution mode kick in on your own machine.

2 Real-world analogy

A composer writes a piece of music. It gets performed in Tokyo, Lagos and Oslo, by orchestras that have never met the composer and do not speak the composer's language. How?

Not by shipping recordings, and not by re-writing the piece for each country. By sheet music: a standardised written notation that every trained musician on Earth can read. The composer's ideas are written once, into notation; each orchestra reads that same notation and produces sound using its own local instruments, in its own hall, with its own acoustics.

The concert worldThe Java world
The composer's ideas, written out in a personal shorthandYour .java source file — written for humans
The engraver who turns that shorthand into clean standard notationjavac, the compiler
The printed score in standard notationThe .class file — bytecode
“Notation edition 2024” printed on the score's first pageThe class file's version number (65 = Java 21)
The orchestra that reads the score and performs itThe JVM
The actual violins, drums and air in the roomThe real CPU and its own instruction set
Sight-reading the first pass — correct, but slow and note-by-noteThe interpreter
A passage rehearsed so often it is played fluently from memoryJIT-compiled machine code
A 2024 score handed to players who only read the 2019 editionUnsupportedClassVersionError

Three details of the analogy are worth pressing on, because each maps onto something exact.

The score is not the sound. Nobody confuses a page of notation with music. Yet people routinely say Java is “compiled to machine code,” which is the same confusion. The .class file is notation: precise, complete, and totally silent until an orchestra performs it.

The edition number is on the page for a reason. Notation evolves; new symbols get added. Players who trained on an older edition will hit a symbol they cannot read — so responsible publishers print the edition on the front, and a conductor checks it before rehearsal rather than discovering the problem mid-concert. That printed edition number is exactly what Sam's error message was about, and the JVM checks it in the first eight bytes of the file before executing a single instruction.

Rehearsal changes the performance without changing the score. The tenth playthrough of a passage is faster and smoother than the first, and the page did not change. That is the whole of the interpreter-versus-JIT story, and it is why the same loop takes forty milliseconds and then two.

3 The concept explained

We will build this up in dependency order: what a CPU actually eats, what Java produces instead, how those instructions are shaped, how the file that holds them is laid out, how to read it with a tool, and finally how the JVM executes it in two modes at once. Nothing here is skipped as “it just works.”

3.1 What a computer can actually run

Underneath everything sits a physical chip: the CPU (central processing unit), the part of the machine that carries out instructions. A CPU understands exactly one language, and it is nothing like Java. It is a list of very small numbered commands — copy this number into that slot; add these two slots; if the result is zero, continue from that position instead. Each command is stored as a number, because numbers are all a chip can hold. This numeric command language is called machine code, and the specific set of commands a family of chips understands is called its instruction set.

Here is the catch that shapes everything else: different chip families have different, incompatible instruction sets. The Intel and AMD chips in most laptops use one (called x86-64, often just “x64”); Apple Silicon Macs and most phones use another (ARM). The number that means “add” on one is not the number that means “add” on the other. On top of that, operating systems disagree about how a program starts, how it asks for memory, and how it opens a file.

So a language like C, which compiles straight to machine code, produces a file that runs on one chip family and one operating system. Want it on another? Compile it again, there, with a compiler that targets that combination. The word for “machine code for the actual chip you are on” is native code — you will meet the word constantly, and that is all it means: not translated, not simulated, the real thing the chip runs directly.

Why can a compiled C program not simply be copied from a Windows laptop to a Mac?
Because it is machine code for one specific instruction set and one operating system's conventions. The Mac's chip may not even use the same numbers for the same operations, and the operating system starts programs and hands out memory differently. The file is a set of instructions addressed to a machine that is not there.

3.2 What Java produces instead: bytecode

Java's designers took a deliberate detour. javac does not produce machine code for your chip. It produces instructions for an imaginary machine — one carefully specified on paper, that no manufacturer has ever built. That imaginary machine has its own small instruction set, and because each of its instruction codes fits in a single byte, the instructions are called bytecode.

Let us be precise about the pieces, since these words get used loosely everywhere.

  • An opcode (short for “operation code”) is the one-byte number that says which operation to perform. One byte holds 0 to 255, so the format allows at most 256 different operations; the specification defines a little over two hundred of them, and the rest are unused. That upper limit is why they are called bytecodes.
  • Some opcodes are followed by operands: extra bytes giving details, such as which local variable to read or where to jump to. So an instruction is one opcode byte plus zero or more operand bytes.
  • Each opcode has a short human name — iadd, iload_0, goto — called its mnemonic. The file stores the number; tools show you the mnemonic. When people say “reading bytecode,” they mean reading these names.

Now the payoff. Since bytecode targets an imaginary machine, it is identical no matter where it was produced. To run it on a real machine, that machine needs one program installed whose job is to act out the imaginary machine — read its instructions and carry them out using whatever real chip is underneath. That program is the JVM. This is what the slogan “write once, run anywhere” (often abbreviated WORA) actually describes: not that Java source is portable — most languages' source is portable if you have a compiler — but that the compiled output is portable. The compiling happens once, on one machine, and the resulting file is shipped everywhere.

3.3 The imaginary machine is a stack machine

What kind of machine did Java's designers imagine? A deliberately simple one. To follow any bytecode at all you need exactly two of its parts.

Part one: the local variable table. Every method call gets a small private array of numbered slots to keep its variables in. Slot 0, slot 1, slot 2, and so on. Your variable names (a, total, i) do not exist at this level — they became slot numbers during compilation. For a static method, slot 0 holds the first parameter. For an instance method, slot 0 always holds this, and the parameters start at slot 1; that is the whole reason the numbering seems to shift by one between the two kinds of method.

Part two: the operand stack. This is the part that surprises people, so here is the idea before the name. Imagine a spike on a desk that you can push paper slips onto, and from which you may only ever take the topmost slip. To add two numbers you write each on a slip, push both onto the spike, then run an “add” step which takes the top two slips off, adds them, and pushes one new slip with the answer. Nothing is addressed or named; everything happens at the top of the pile. A pile you can only add to and take from at one end is called a stack, pushing on and taking off are called push and pop, and the one the JVM uses for calculations is the operand stack. A machine that computes this way — rather than by naming registers, as real CPUs do — is called a stack machine.

Why choose a stack machine for the imaginary machine? Because it makes the instructions tiny and universal. iadd needs no operands at all — no “add register 3 to register 7” — because both inputs are, by definition, on top of the stack. That keeps bytecode compact, keeps the instruction set small, and means the format assumes nothing about how many registers the real chip happens to have. The real machine underneath has registers, of course, and mapping stack operations onto them is the JVM's job, not yours.

Two rules follow from that picture and they hold for all bytecode. First, instructions carry their type in their name: the leading i in iload, iadd, ireturn means int. There are parallel families for long (l), float (f), double (d) and references — that is, anything that is an object rather than a plain number (a, for “address”). So areturn returns an object reference and ireturn returns an int; there is no single generic “return a value” instruction. Second, very common operations get their own single-byte shorthand: reading local slot 0 could be written as the two-byte instruction iload 0, but because it happens so often the format also defines a dedicated one-byte iload_0. That is why disassembly is full of names with underscores and small numbers glued on.

In a static method, which local slot holds the first parameter — and why is it different in an instance method?
Slot 0. An instance method is always called on an object, and that object (this) is passed invisibly as an extra first argument, so it occupies slot 0 and the declared parameters begin at slot 1. This is why an instance method's disassembly usually starts with aload_0 — that is the machine picking up this.

3.4 The .class file: a documented binary format

The bytecode has to live somewhere, and that somewhere is the .class file — one file per class, named after the class, produced by javac and placed by Maven in target/classes/ mirroring the package folders. It is a binary file: it stores raw numbers rather than readable text, so opening it in a text editor shows nonsense. That is not obfuscation and it is not compression. The layout is published in the Java Virtual Machine Specification, and anything that follows the specification can read it — including code you write yourself, which is exactly what we build in Section 5.

Every class file begins with the same eight bytes, in the same order, always:

Bytes 0–3: the magic number. A magic number is a fixed value at the very start of a file that announces what kind of file it is. Renaming photo.png to photo.txt does not change what is inside it, so programs identify file types by their first few bytes rather than by name. Java's is 0xCAFEBABE — four bytes that spell a word in hexadecimal, chosen by James Gosling's team as a joke that stuck. (Hexadecimal is base 16, using the digits 0–9 then A–F for ten to fifteen; it is convenient here because each byte is exactly two hex digits, so CA FE BA BE is precisely four bytes.) If those four bytes are anything else, the JVM stops immediately — it has been handed something that is not a class file.

Bytes 4–5: the minor version. Bytes 6–7: the major version. Together they say which edition of the class file format these bytes follow. The major version is the one that matters. The numbering began at 45 for Java 1.1 and has added one per release ever since, which gives a rule you can do in your head:

Java release = major version − 44. So major 65 means Java 21 (65 − 44), major 61 means Java 17, major 52 means Java 8. Going the other way: Java 21 writes 65. The offset looks arbitrary because it is — it is a historical accident from 1996 that we are all stuck with.

Major versionJava releaseNote
45Java 1.1where the numbering started
52Java 8still extremely common in old systems
55Java 11the previous long-term-support release
61Java 17the number in Sam's error message
65Java 21what this course pins and what our build writes

The minor version is almost always 0. It has exactly one use worth knowing: when a class is compiled with preview features enabled (experimental language features shipped for feedback, switched on with --enable-preview), the compiler writes 65535 — the largest value two bytes can hold — into the minor version as an unmistakable flag. The JVM then refuses to run that file unless it is exactly the same release and was started with preview features enabled too. This course never uses preview features, so every file we produce has minor version 0, and one of our tests asserts precisely that.

Now Sam's error decodes completely. His file's bytes 6–7 held 65; his JVM was a Java 17 JVM, which understands up to 61; the JVM read those two bytes before executing anything, saw a number from the future, and refused. The rule is one-directional and worth memorising: a newer JVM happily runs older class files; an older JVM always refuses newer ones. It must — the newer file may contain instructions or structures that did not exist when that JVM was built, and there is no safe way to guess at them.

The remaining sections of the file are named in the diagram above. Two deserve a sentence each now, because they show up in disassembly. The constant pool is a numbered table of everything the class refers to by name or value: string literals, the names of methods it calls, the names of classes it mentions. Rather than repeating "java/lang/Object" everywhere, the bytecode says “entry #11” — which is why disassembly is peppered with # numbers. The methods section holds, for each method, its name, its type signature and its actual bytecode. Everything else — access flags, this/super class, interfaces, fields, attributes — we will meet as later lessons need it, and Lesson 02 picks up exactly here, at the moment the JVM decides to load a class file at all.

3.5 How types are written: descriptors

One more piece of notation, because it appears in every line of disassembly and is pure gibberish until explained. The class file cannot store a method's type as friendly Java text like int add(int, int); it needs something compact and unambiguous. So it uses a small code called a descriptor: each type becomes a letter, the parameter types go in brackets, and the return type follows.

DescriptorJava typeMemory hook

So add(int, int) returning int is written (II)I. greet(String) returning String is (Ljava/lang/String;)Ljava/lang/String;. And main(String[]) returning nothing is ([Ljava/lang/String;)V — which you have now, finally, fully read. Note the dots in package names become slashes: inside a class file the separator is always /.

What Java method signature does (IJ)Ljava/lang/String; describe?
A method taking an int and a long, in that order, and returning a String. In Java source: String something(int a, long b). The method's name is not part of the descriptor — it is stored separately.

3.6 Reading bytecode with javap

You do not have to decode bytes by hand to read bytecode. The JDK ships a tool for it, already installed on your machine since Lesson 00: javap, the Java class file disassembler. A disassembler is a program that reads compiled instructions and prints them back in their human-readable mnemonic form. It is the exact reverse of the compiler's last step — and note that it recovers instructions, not your source code: comments, blank lines, and your formatting are simply gone, because they were never in the file.

The flags worth knowing, all of which we use:

CommandWhat it shows
javap Foo.classthe public signatures only — the class's outward shape
javap -p Foo.classthe same, plus private members (p for private)
javap -c Foo.classthe bytecode of every method (c for code) — the main event
javap -v Foo.classverbose: the version header, the whole constant pool, flags, everything
javap -l Foo.classline numbers and local variable names, when the compiler recorded them

Reading the output takes ten seconds of orientation. Each method prints its signature, then a Code: block of lines shaped like this:

   6: if_icmpgt     19
   ^      ^           ^
   |      |           |
   |      |           +--- operand: where to jump to (a byte offset)
   |      +--------------- mnemonic: which operation
   +---------------------- the byte offset of this instruction inside the method

That left-hand number is the single most misread thing in disassembly. It is not a line number and not a step count — it is the position of that instruction measured in bytes from the start of the method's code. That is why the numbers jump unevenly: 0, 1, 2, 3 means four one-byte instructions in a row, while a jump from 6 to 9 means the instruction at 6 occupied three bytes (one opcode plus a two-byte operand). It also explains how jumps work: goto 4 means “continue from byte offset 4,” and offsets are stable regardless of how the code is printed.

3.7 Four methods, disassembled

Our project now contains BytecodeSubject, a class whose only purpose is to be taken apart. Here are its four methods with their predicted disassembly, each teaching one thing. (Section 6 lists the file in full; the exact commands to reproduce all of this are in Section 5.)

(a) add — arguments, arithmetic, return

public static int add(int a, int b) {
    return a + b;
}
// PREDICTED javap -c output
  public static int add(int, int);
    Code:
       0: iload_0        // push slot 0 (a) onto the operand stack
       1: iload_1        // push slot 1 (b)
       2: iadd           // pop both, push their sum
       3: ireturn        // pop the top value and return it as an int

Four instructions, four bytes, no surprises — this is the picture from Section 3.3 in text form. Notice what is absent: no mention of the names a and b in the instructions themselves, and no mention of the class or the method being called from. A method's bytecode is a self-contained little program over slots and a stack.

(b) sumTo — where the for loop went

public static int sumTo(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}
// PREDICTED javap -c output
  public static int sumTo(int);
    Code:
       0: iconst_0       // push the constant 0
       1: istore_1       // pop it into slot 1  -> total = 0
       2: iconst_1       // push the constant 1
       3: istore_2       // pop it into slot 2  -> i = 1
       4: iload_2        // push i          <-- top of the loop
       5: iload_0        // push n
       6: if_icmpgt  19  // pop both; if i > n, continue from offset 19
       9: iload_1        // push total
      10: iload_2        // push i
      11: iadd           // pop both, push total + i
      12: istore_1       // pop into slot 1 -> total updated
      13: iinc       2, 1 // add 1 to slot 2 IN PLACE -> i++ (stack untouched)
      16: goto       4   // jump back to the top of the loop
      19: iload_1        // push total
      20: ireturn        // return it

There is no for instruction, because the JVM has no concept of a loop. A loop is a conditional jump forward (escape when the test fails) plus an unconditional jump backward (repeat). Every while, for, do-while and enhanced-for in Java compiles into some arrangement of exactly those two moves. Three details reward a second look:

  • The test is inverted. You wrote “keep going while i <= n”; the bytecode says “jump out if i > n.” A jump needs a condition under which it fires, and the useful one is the exit condition, so the compiler flips your test.
  • iinc is special. Incrementing a local variable is so common that the format gives it a dedicated instruction that modifies a slot in place — no push, no pop. It takes two operands: which slot, and by how much. This is why i++ as a statement costs one instruction while total += i costs four.
  • The offsets prove the widths. 6 to 9 and 13 to 16 are gaps of three: if_icmpgt and iinc and goto each carry two operand bytes. Everything else here is a single byte. You can literally count the size of a method by reading its last offset.

(c) greet — when bytecode looks nothing like the source

public static String greet(String name) {
    return "Hello, " + name;
}
// PREDICTED javap -c output (the # numbers will differ on your machine)
  public static java.lang.String greet(java.lang.String);
    Code:
       0: aload_0            // push slot 0 (name) - 'a' because it is a reference
       1: invokedynamic #7,  0  // InvokeDynamic #0:makeConcatWithConstants:
                                 //   (Ljava/lang/String;)Ljava/lang/String;
       6: areturn            // return the reference on top of the stack

One + in your source became one instruction you have never heard of, and the words “Hello, ” are nowhere in sight. Here is what happened, plainly. Since Java 9, the compiler does not decide how to join strings. Instead it emits a single instruction meaning: the first time this line runs, call a helper in the JDK, hand it a description of this exact concatenation, and let the helper build a fast routine on the spot; then use that routine here forever after. The instruction that does this — “work out what to call the first time, then remember the answer” — is invokedynamic, and the helper here is named makeConcatWithConstants. The literal "Hello, " is part of the description handed to the helper (that is the “WithConstants” part), which is why only name has to be pushed at run time.

Why go to that trouble? Because it lets the JDK change its string-joining strategy — and get faster — without recompiling a single line of anyone's code. The decision moved out of the compiler and into the runtime. Keep the name invokedynamic in mind: it is also how lambda expressions are compiled, which we will meet again in Section 7.

This is the single best cure for guessing about performance from source alone. Your one-character + is a call into a machine-generated routine; a for loop is a pair of jumps; a field access may be free or may not exist at all by the time the JIT is finished. Source lines and work done are different things. Measure, or read the bytecode — do not intuit.

(d) newObject — the shape of every new in Java

public static Object newObject() {
    return new Object();
}
// PREDICTED javap -c output (the # numbers will differ on your machine)
  public static java.lang.Object newObject();
    Code:
       0: new           #11   // class java/lang/Object - allocate blank memory, push a reference
       3: dup                 // duplicate that reference, so there are now two on the stack
       4: invokespecial #1    // Method java/lang/Object."<init>":()V - run the constructor,
                              //   which consumes one of the two references
       7: areturn             // return the surviving reference

This tiny sequence answers a question most Java developers never think to ask: what is new? It is two separate things that your source fuses into one word. First, new reserves the memory for a blank object of that class in the heap and pushes a reference to it (a reference is just a value identifying where the object lives — Lesson 03 is entirely about this). Second, invokespecial runs the constructor on that blank object, to fill in its fields. The constructor call consumes the reference from the stack, which is why dup is needed in between: without a duplicate, the reference would be swallowed by the constructor and there would be nothing left to return or assign.

Two more facts fall out of this. A constructor is stored in the class file as an ordinary method with the reserved name <init> and return type V (void) — which is why the disassembly mentions "<init>":()V, and why javap -p on our class shows a Code: block for the private constructor too. And the four call instructions are worth naming now, since you will see them constantly: invokestatic (a static method), invokevirtual (an ordinary method, where the actual implementation depends on the object's real class), invokespecial (constructors, super. calls, and private methods — cases where no such lookup is wanted), and invokeinterface (a call through an interface type).

3.9 Two ways to run the same instructions

We now know what the JVM is handed. How does it actually execute it? The obvious answer is a loop: fetch the next instruction, look at its opcode, do the corresponding thing, move on. Carrying out instructions one at a time like this, without translating them first, is called interpreting, and the part of the JVM that does it is the interpreter.

Interpreting has one enormous advantage: it starts instantly. There is no preparation, no translation step, no waiting — the first instruction runs immediately. Its disadvantage is equally clear: for every one of your instructions the JVM does a pile of its own work — read the opcode, decide what it means, jump to the right handler, adjust the stack pointer. A single iadd costs far more than the CPU's own add. Roughly speaking, interpreted code runs on the order of ten to a hundred times slower than native code — the exact factor depends on everything, so treat that as a shape, not a measurement.

The other option is to translate a method's bytecode into real machine code for the chip you are on, once, and then run the translated version at full native speed. This costs time up front — the translation itself is work, and good translation is expensive work — but it pays that cost back on every subsequent call.

So which does the JVM choose? Both, at the same time. It starts by interpreting, so your program is running within milliseconds. Meanwhile it counts things: how many times each method has been called, how many times each loop has gone around. When a method's counters cross a threshold — when it looks, on the evidence, worth the investment — the JVM hands that method to a compiler running on a background thread, which produces native code while your program keeps going. Once the native version is ready, subsequent calls quietly use it instead. Compiling during execution like this, rather than ahead of time, is called just-in-time compilation, universally shortened to JIT. A method that has been called often enough to earn compilation is called hot — and now the name HotSpot, the JVM you are running, finally makes sense: it finds the hot spots in your program and compiles those.

The two compilers in that picture are real and both ship inside HotSpot. C1 compiles quickly and optimises lightly, so warm code gets faster soon. C2 compiles slowly and optimises aggressively, so the hottest code eventually gets very fast indeed. HotSpot uses both — interpreter first, then C1, then C2 for the true hot spots — and the arrangement is called tiered compilation. The period at the start of a program during which this is still settling out is called warm-up, and it is why the first run of a loop can be twenty times slower than the tenth. Lesson 06 takes all of this apart properly (including how the JIT can undo a compilation when an assumption it made turns out to be wrong); for now the shape is enough, and our experiment in Section 6 makes it visible on your machine.

This is why Java has a reputation for being “slow to start but fast once running,” and why that reputation causes real architectural decisions. A long-lived server process warms up in the first seconds and then runs at native speed for weeks — Java's ideal case. A command-line tool that runs for 200 milliseconds and exits never gets past the interpreter, which is why some Java CLI tools feel sluggish next to equivalents written in Go or Rust. It is also why benchmark numbers posted without a warm-up phase are worthless, and why interviewers like asking why the first iteration of a loop is slow.

Why does the JVM interpret at all, instead of just compiling everything to native code up front?
Because compiling costs time, and most code is not worth it. A typical program spends nearly all its time in a small fraction of its methods; compiling every method eagerly would delay startup for code that may run once or never. Interpreting starts instantly and costs nothing up front, and counting lets the JVM spend its compilation budget only where it pays back. The bonus is that by the time it compiles, it has watched the code run and can optimise using facts about this particular execution — something an ahead-of-time compiler never knows.

3.10 Where “run anywhere” leaks

Depth means honesty about limits, so: portability is real but not absolute. The bytecode is identical everywhere and the JVM guarantees the semantics — the same arithmetic, the same object model, the same threading rules. What leaks is everything around the edges. Code that shells out to native libraries specific to one operating system is not portable. Neither is code that hard-codes C:\ or assumes / as a path separator, or assumes a particular default character encoding, or relies on file names being case-insensitive. Thread scheduling and timing differ between operating systems, so a program with a latent race condition can pass on one machine for years and fail on another. And a class file compiled for Java 21 cannot run on Java 17 — portability across machines was never portability across versions. “Write once, run anywhere” is a statement about the compiled artifact, not a promise that you cannot write machine-specific bugs.

4 The wrong way

WRONG APPROACH — three ways people try to look inside a class file and end up with a wrong belief. Each of these is a real mistake with a real symptom.

Mistake 1: opening a class file as text

The file has an ordinary-looking name, so the obvious move is to print it:

D:\...\jvm-explorer> type target\classes\com\corejava\jvm\BytecodeSubject.class

// PREDICTED: something like this, varying wildly by terminal and code page
Ê¾..A...Z..
..java/lang/Object..<init>...()V...add...(II)I...sumTo...Code
LineNumberTable...BytecodeSubject.java...

The conclusion people draw is “it is compiled, so it is unreadable.” Both halves are wrong. Readable fragments are visible in that mess — java/lang/Object, <init>, (II)I, method names — because the constant pool stores names as text. What is unreadable is everything else, and only because a text viewer is the wrong instrument: it takes each byte, guesses it is a character, and prints the guess. The bytes are fine; the interpretation is nonsense. Worse, type and cat can also mangle your terminal (some byte values are control codes), which cements the impression that the file is hostile.

Mistake 2: decoding the header without masking the sign bit

The more serious mistake is made by people who do know the format. You read the first four bytes and compare them to 0xCAFEBABE:

// WRONG: looks right, is wrong, and the failure accuses the innocent file
byte[] header = in.readNBytes(8);

// The bug is on this line: no masking.
int magic = (header[0] << 24)
          | (header[1] << 16)
          | (header[2] << 8)
          |  header[3];

System.out.println(String.format("0x%08X", magic));
// PREDICTED output of the wrong version:
0xFFFFFFBE
// ...against an expected 0xCAFEBABE. Conclusion drawn: "my file is corrupt."

The file is perfect. The bug is that a Java byte is signed: it holds −128 to 127, not 0 to 255. The byte 0xCA therefore arrives as the number −54. When Java uses a byte in arithmetic it first widens it to an int, and widening a negative number fills the new high bits with ones — so −54 becomes 0xFFFFFFCA, not 0x000000CA. Those stray ones then flood every position of the OR, and the four values collapse into 0xFFFFFFBE.

The fix is one operation per byte: & 0xFF, which keeps the same eight bits but re-reads them as 0 to 255. There is a second, quieter trap hiding behind the first: even correctly assembled, 0xCAFEBABE does not fit in a positive int (an int stops at about 2.1 billion; that value is about 3.4 billion), so storing it in an int makes it appear negative and every comparison misbehaves. The magic number has to be held in a long. Section 5 does both.

Mistake 3: reasoning about cost from the shape of the source

The most common wrong approach needs no code at all — it is the habit of predicting work from how source code looks:

  • “i++ and total += i are both one line, so they cost the same.” In bytecode, i++ as a statement is a single iinc; total += i is four instructions.
  • “"Hello, " + name is one +, so it is trivial.” It is an invokedynamic into a JDK helper that builds and caches a routine on first use.
  • “This loop looks tight, so it must be fast.” Until it has run enough times to be compiled, every instruction in it is being interpreted — and after C2 gets hold of it, the loop you are reading may not exist in the native code at all.

Predicted symptoms of all three mistakes: confident statements that cannot be checked; a “corrupt file” bug report against a file that is fine; performance work aimed at the wrong line; and — the expensive one — an UnsupportedClassVersionError in production that nobody can decode, because nobody knows the version is sitting in bytes 6 and 7 of every file being shipped.

5 The right way

CORRECT APPROACH: read the header with code that respects the format, and read the instructions with the tool built for it. Two habits, both cheap.

5.1 Decode the header yourself

The project gains a small module — ClassFileInspector — that finds a class's own .class file and decodes its first eight bytes. The heart of it is this pair of helpers; the full file with every line commented is in Section 6.

// CORRECT: mask every byte, and hold the four-byte value in a long.
private static long readUnsignedInt(byte[] bytes, int offset) {
    return ((long) (bytes[offset]     & 0xFF) << 24)   // re-read the bits as 0..255,
         | ((long) (bytes[offset + 1] & 0xFF) << 16)   // then slide each byte into
         | ((long) (bytes[offset + 2] & 0xFF) <<  8)   // its place, most significant
         |  (long) (bytes[offset + 3] & 0xFF);          // byte first (big-endian).
}

private static int readUnsignedShort(byte[] bytes, int offset) {
    return ((bytes[offset] & 0xFF) << 8)                 // two bytes, same rule;
         |  (bytes[offset + 1] & 0xFF);                  // 0..65535 fits in an int.
}

One design decision in that module is worth pausing on, because it is the difference between code that works and code that keeps working. To find the bytes, we do not open target/classes/com/corejava/jvm/BytecodeSubject.class as a file path. We ask the JVM for them:

// Rebuild the class's location the way the class path stores it:
// com.corejava.jvm.BytecodeSubject  ->  /com/corejava/jvm/BytecodeSubject.class
String resourcePath = "/" + type.getName().replace('.', '/') + ".class";

// Ask the same machinery that LOADED this class for its raw bytes.
try (InputStream in = ClassFileInspector.class.getResourceAsStream(resourcePath)) { /* … */ }

A hard-coded path assumes the class lives in a folder on this machine right now. The resource lookup asks whichever loader supplied the class to supply its bytes as well, so the same code works when the project is a folder, when it is packaged into a jar, and inside the test run — where the working directory is not what you would guess. It also quietly foreshadows the whole of Lesson 02: something located and loaded that file, and that something is a class loader.

5.2 What happens, step by step, when the inspector runs

  1. A caller passes a Class object, for example BytecodeSubject.class. A null is rejected immediately with a message naming the mistake.
  2. The fully-qualified name com.corejava.jvm.BytecodeSubject has its dots replaced by slashes and gains a leading slash and a .class suffix, producing the class path location /com/corejava/jvm/BytecodeSubject.class.
  3. getResourceAsStream hands back an open stream of that file's bytes — or null, which we turn into a clear IllegalStateException rather than a mystery NullPointerException two lines later.
  4. readNBytes(8) pulls exactly the eight header bytes. If fewer arrive, the file cannot be a class file and we say so with the actual length in the message.
  5. Bytes 0–3 are assembled into a long with masking: 0xCAFEBABE. Bytes 4–5 become the minor version: 0. Bytes 6–7 become the major version: 65.
  6. The four values are packaged into an immutable ClassFileHeader, which knows how to say 0xCAFEBABE in hex, how to turn 65 into “Java 21” (subtract 44), and whether the minor version is the preview flag 65535.
  7. The stream is closed automatically by try-with-resources, whether we returned normally or threw.

6.1 The disassembly subject

Saved at jvm-explorer/src/main/java/com/corejava/jvm/BytecodeSubject.java. The class is deliberately useless: every method was chosen for what its compiled form teaches.

public final class BytecodeSubject {

    // Private + empty: nobody should instantiate a bag of teaching samples.
    // It is also the shortest possible proof that a constructor is just a method:
    // javap -c -p prints a Code: block for it, calling Object's constructor.
    private BytecodeSubject() {
    }

    // SAMPLE 1 - arguments arrive as numbered slots; arithmetic happens on a stack.
    public static int add(int a, int b) {
        return a + b;                 // iload_0, iload_1, iadd, ireturn
    }

    // SAMPLE 2 - the smallest thing that produces a jump: a loop is two jumps.
    public static int sumTo(int n) {
        int total = 0;                // slot 1 (slot 0 holds the parameter n)
        for (int i = 1; i <= n; i++) { // slot 2; iinc does the ++ in place
            total += i;               // four instructions, not one
        }
        return total;
    }

    // SAMPLE 3 - one '+' becomes one invokedynamic; the literal is in the recipe.
    public static String greet(String name) {
        return "Hello, " + name;
    }

    // SAMPLE 4 - every 'new' in Java is new / dup / invokespecial.
    public static Object newObject() {
        return new Object();
    }
}

6.2 The header, as a value

Saved at jvm-explorer/src/main/java/com/corejava/jvm/ClassFileHeader.java. This file introduces one piece of Java syntax the course has not used yet, so here it is properly.

Writing a small class whose only job is to hold a few values means typing the same boilerplate every time: private fields, a constructor that assigns them, a reader method for each, plus equals, hashCode and toString if you want the object to behave sensibly. It is twenty lines of ceremony to carry four values. So Java added a shorthand: you declare the values in the header and the compiler generates all of that for you. For example, record Point(int x, int y) { } gives you a finished immutable class with new Point(3, 4), p.x(), p.y(), and sensible equality — and the fields can never be changed afterwards. This shorthand is called a record. Our header is exactly that kind of thing: four facts read from bytes already on disk, which should never change.

public record ClassFileHeader(
        String className,   // whose file this is
        long magic,         // bytes 0-3; long because 0xCAFEBABE overflows an int
        int minorVersion,   // bytes 4-5; 65535 means "compiled with preview features"
        int majorVersion) { // bytes 6-7; 65 means Java 21

    public static final long JAVA_MAGIC = 0xCAFEBABEL;
    public static final int PREVIEW_MINOR_VERSION = 65535;
    private static final int MAJOR_VERSION_OFFSET = 44;

    // The check the JVM itself performs before reading one more byte.
    public boolean hasJavaMagic() {
        return magic == JAVA_MAGIC;
    }

    // %08X = hexadecimal, uppercase, zero-padded to 8 digits -> "0xCAFEBABE".
    public String magicAsHex() {
        return String.format("0x%08X", magic);
    }

    // 65 helps nobody; "Java 21" is the fact you actually want.
    public String javaVersionName() {
        if (majorVersion >= 49) {                              // Java 5 and later
            return "Java " + (majorVersion - MAJOR_VERSION_OFFSET);
        }
        return "Java 1." + (majorVersion - MAJOR_VERSION_OFFSET); // 45 -> 1.1 … 48 -> 1.4
    }

    // javac --enable-preview writes 65535 here; the JVM reads it to refuse the file
    // on any other release. This course never uses preview features.
    public boolean usesPreviewFeatures() {
        return minorVersion == PREVIEW_MINOR_VERSION;
    }

    // One printable line, used by JvmExplorer's report.
    public String describe() { /* className + magic + major (+ name) + minor */ }
}

6.3 The inspector

Saved at jvm-explorer/src/main/java/com/corejava/jvm/ClassFileInspector.java. Its core was shown in Section 5.1; here is the whole method it hangs on, with the error handling that makes it usable rather than merely correct.

public static ClassFileHeader inspect(Class<?> type) {
    // Fail at the door, naming the mistake, instead of a NullPointerException later.
    if (type == null) {
        throw new IllegalArgumentException("Cannot inspect a null class.");
    }

    // com.corejava.jvm.Foo -> /com/corejava/jvm/Foo.class (leading / = class path root)
    String resourcePath = "/" + type.getName().replace('.', '/') + ".class";

    // try-with-resources: the stream closes itself, even if we throw.
    try (InputStream in = ClassFileInspector.class.getResourceAsStream(resourcePath)) {

        if (in == null) {   // should be impossible for a loaded class - so say so loudly
            throw new IllegalStateException(
                "No class file found on the class path at " + resourcePath);
        }

        // readNBytes asks for exactly this many and reports what it really got.
        byte[] header = in.readNBytes(HEADER_BYTES);
        if (header.length < HEADER_BYTES) {
            throw new IllegalStateException(/* names the actual length */);
        }

        long magic        = readUnsignedInt(header, 0);   // bytes 0-3
        int minorVersion  = readUnsignedShort(header, 4); // bytes 4-5
        int majorVersion  = readUnsignedShort(header, 6); // bytes 6-7

        return new ClassFileHeader(type.getName(), magic, minorVersion, majorVersion);

    } catch (IOException e) {
        // Reading bytes the JVM already read should not fail; if it does, rethrow
        // unchecked but keep the original as the cause so nothing is lost.
        throw new UncheckedIOException(
            "Failed to read the class file for " + type.getName(), e);
    }
}

6.4 The warm-up experiment

Saved at jvm-explorer/src/main/java/com/corejava/jvm/experiments/WarmupExperiment.java — in the experiments package, kept apart from the project's real capabilities on purpose.

// Results are added into a field that outlives the method, so the JVM cannot
// decide the whole loop is pointless and delete it. (Crude, but readable.)
public static long sink;

public static long[] timeBatches(int batches, int callsPerBatch, int n) {
    if (batches < 1 || callsPerBatch < 1 || n < 0) {
        throw new IllegalArgumentException(/* names the offending values */);
    }

    long[] elapsedNanos = new long[batches];

    for (int batch = 0; batch < batches; batch++) {
        // nanoTime is a stopwatch, not a clock: only DIFFERENCES are meaningful,
        // and it is immune to the system clock being adjusted mid-measurement.
        long start = System.nanoTime();

        long batchTotal = 0;
        for (int call = 0; call < callsPerBatch; call++) {
            batchTotal += BytecodeSubject.sumTo(n);  // the method under test
        }

        sink += batchTotal;                            // publish, so it cannot vanish
        elapsedNanos[batch] = System.nanoTime() - start;
    }
    return elapsedNanos;
}

This is not how to benchmark Java, and using it as a template would be a genuine mistake. A real measurement must control for warm-up, dead-code elimination, constant folding, the effect of running the loop's own compilation on the timings, garbage collection pauses, CPU frequency scaling and more. The standard tool is JMH (the Java Microbenchmark Harness, part of OpenJDK), which handles all of that. This twenty-line stopwatch exists because it is readable in one sitting and makes the effect visible; Lesson 06 measures properly.

7 In the wild

Reading and writing class files is not an academic exercise — it is load-bearing infrastructure under tools you already use, usually invisibly.

Mockito creates classes that were never compiled. When a test calls mock(PaymentService.class), no source file for that mock exists anywhere. Mockito generates a class file's worth of bytes in memory — magic number, version, constant pool, methods, the lot — and hands them to the JVM to load. It does this through a library called Byte Buddy, whose entire job is assembling class files programmatically. The same trick, with different libraries, is how Hibernate makes lazy-loading proxies and how Spring wraps a bean so that a method call can be intercepted before it reaches your code.

Lambdas are invokedynamic, exactly like our greet method. Write list.forEach(x -> System.out.println(x)) and disassemble it: there is no anonymous class in the bytecode. There is one invokedynamic instruction naming a JDK helper called LambdaMetafactory, which builds the implementation the first time that line runs, then reuses it. Our string concatenation used the same mechanism with a different helper (makeConcatWithConstants). Once you recognise the instruction, a whole family of modern Java features stops being mysterious: the compiler deferred the decision to the runtime.

Every code-coverage report is bytecode manipulation. JaCoCo, the standard coverage tool, works by inserting extra instructions into your methods as they are loaded, so each branch records that it was reached. Your source is untouched; the class files the JVM actually runs are not the ones on disk.

And javap is a normal working tool, not a curiosity. The realistic use is settling arguments: does this switch compile to a jump table? Did the compiler really inline that constant? Is this library's class file version too new for our runtime? For that last question there is a fast professional move — javap -v SomeClass.class | findstr "major" on Windows (or | grep major elsewhere) answers “what Java version was this jar built for?” without running anything at all.

The class file version check is one of the most common production incidents in Java shops, and it has a distinctive shape: the code is fine, the tests passed, and the deploy fails at startup with UnsupportedClassVersionError because the build server's JDK is newer than the runtime image. Teams that have been burned once pin both — the compiler's --release and the base container image's JDK — and often add a build step that checks the produced class files, which is precisely what classFilesAreCompiledToThePinnedJavaVersion now does in this project.

One item to verify rather than trust: recent JDKs added a built-in API for reading and writing class files (java.lang.classfile), which went through preview and was finalised in a release after 21. It is not available on our pinned Java 21 — check the release notes of your JDK before reaching for it. Everything in this lesson uses only InputStream and plain arithmetic, which work everywhere.

8 Gotchas and common mistakes

  • Forgetting that byte is signed. Every hand-written binary parser in Java hits this, usually once. Reading 0xCA gives you −54, and combining raw bytes silently produces a wrong number rather than an error — the worst kind of bug, because it accuses the data. Avoid it: mask every byte with & 0xFF the moment you take it out of the array, and hold four-byte unsigned values in a long, never an int.
  • Reading UnsupportedClassVersionError backwards. The message names two numbers and it is easy to mix up whose is whose. The phrase “has been compiled by a more recent version” refers to the file; “this runtime only recognizes” refers to the JVM you are running. Subtract 44 from each to get Java releases. Avoid it: the fix is almost always to run a newer JVM, not to downgrade the build — and never to “just rebuild” without changing anything, which changes nothing.
  • Using -source/-target instead of --release. The old flags set the language level and the class file version but still compile against the current JDK's libraries. So a build on JDK 21 with -target 17 happily produces a class file marked 61 that calls a method which only exists in Java 21 — it compiles, ships, and then fails at runtime with NoSuchMethodError on the actual Java 17 machine. Avoid it: use --release (our POM's maven.compiler.release), which also swaps in that release's API definitions, so the compiler rejects the call up front.
  • Expecting javap to show your source. It shows instructions, not code: comments, formatting and blank lines were never in the file. Local variable names and line numbers are optional extras that only appear if the compiler was told to record them (javac -g; Maven's compiler plugin enables debug information by default, which is why javap -l usually has something to show). Avoid it: use -c to read logic, -v for the header and constant pool, and remember that a stripped build may show nothing but slot numbers.
  • Forgetting -p, then concluding a method does not exist. Plain javap prints only public members. A private method, a private constructor, or a package-private helper is simply absent from the output, which reads exactly like “the compiler removed it.” Avoid it: make javap -c -p your default muscle memory.
  • Being surprised by extra .class files. One source file can produce several class files: a nested class becomes Outer$Inner.class, an anonymous class becomes Outer$1.class, and enums and records generate members you never typed. Avoid it: remember that the unit of compilation output is the class, not the file — and that $ in a class file name means “generated relationship,” not a naming convention someone chose.

9 Tradeoffs and when not to use this

The bytecode-plus-JVM design buys portability and safety, and it is paid for in two currencies. The first is startup time: before your first line runs, a JVM process must start, find and verify class files, and begin interpreting — which is why a Java command-line tool that finishes in 200 milliseconds feels heavier than a native equivalent, and why short-lived serverless functions are an awkward fit. The second is warm-up: peak speed arrives seconds or minutes into the run, so a process that exits early never collects the benefit it paid for. There are answers to both — ahead-of-time compilation to a native binary (GraalVM native-image), class-data sharing, and ongoing work in the JDK itself — but they trade away flexibility, and they are firmly outside this course; name them, do not reach for them yet.

As for reading bytecode: be honest that it is a diagnostic and learning tool, not a daily practice. Ninety-nine times in a hundred, the right way to answer “why is this slow?” is a profiler (which tells you where time goes, which bytecode never can) or a proper benchmark with JMH (which measures the compiled reality rather than the shipped instructions). Bytecode is what you ship; native code produced by C2 is what actually runs, and the two can differ dramatically — a loop may be unrolled, a method inlined out of existence, an object never allocated at all. Optimising your source because the disassembly looks long is a classic way to waste a day and make code worse. Read bytecode to understand a mechanism, to settle a factual argument about what the compiler emits, or to inspect a jar you cannot rebuild. For everything else, measure.

And the tiny module we built has a deliberate boundary: it reads eight bytes, not the whole format. Parsing the constant pool by hand is genuinely intricate, and it is solved work — javap does it, Byte Buddy and ASM do it. Writing our own would teach less per hour than the rest of this course. Knowing that the format is readable, and having read part of it yourself, is the lasting value.

10 Key takeaways

  • javac does not produce machine code for your chip; it produces bytecode — instructions for an imaginary stack machine — and it is that single compiled file, not the source, which is what “write once, run anywhere” actually makes portable.
  • A .class file is a documented binary format that always begins with the same eight bytes: the magic number 0xCAFEBABE, then the minor version, then the major version — where the Java release is the major version minus 44, so Java 21 writes 65.
  • The JVM checks those version bytes before executing anything, and the rule is one-directional: a newer JVM runs older class files, an older JVM always refuses newer ones, which is exactly what UnsupportedClassVersionError reports.
  • Bytecode computes on an operand stack using numbered local variable slots, so instructions are small and typed by name (iload, iadd, areturn); loops are a conditional forward jump plus an unconditional backward one, and new is always the trio new, dup, invokespecial.
  • The JVM interprets your bytecode immediately and, in the background, compiles the methods that prove themselves hot into native code — which is why the same loop is slow on its first run and fast on its tenth, and why any Java measurement taken without warm-up is worthless.

11 Challenge

Part A — decode an incident. A colleague's deploy fails at startup:

java.lang.UnsupportedClassVersionError: com/acme/Report has been compiled by a
more recent version of the Java Runtime (class file version 65.0), this runtime
only recognizes class file version 55.0

(1) Translate both numbers into Java releases. (2) Say in one sentence which machine has the problem — the build machine or the runtime machine. (3) Give two possible fixes and say which is usually correct. (4) Name one command that would have revealed this from the jar before deploying, without running any of the code.

Part B — predict a disassembly. Without compiling anything, write down the bytecode you expect for this method, including the byte offsets:

public static int twice(int x) {
    return x + x;
}

Then check yourself: add the method to BytecodeSubject, run mvn compile, and disassemble. Bonus: before you look, predict whether x + x and x * 2 produce the same instructions — and then find out.

Click to reveal the answer

Part A (1) — the numbers. Subtract 44 from each. The class file's 65 means it was compiled for Java 21. The runtime's 55 means the JVM trying to run it is Java 11.

Part A (2) — whose problem. Neither machine is broken; they disagree. But the mismatch is a property of the pair, and the practical statement is: the runtime machine is too old for the artifact it was given. The build machine did nothing illegal — it did exactly what it was configured to do.

Part A (3) — two fixes. Either (a) upgrade the runtime to Java 21 or newer, or (b) build for Java 11 by setting maven.compiler.release to 11 (never -target alone — see Gotcha 3, which is how you turn this loud startup failure into a quiet NoSuchMethodError later). Usually (a) is correct: the code was written and tested against Java 21's language and libraries, and downgrading the target may not even compile — and if it does, it silently gives up whatever Java 21 features the code uses. Fix (b) is right only when the runtime genuinely cannot be moved, in which case the whole project should be pinned to 11 and tested there, not just re-targeted at the last minute.

Part A (4) — the pre-flight command. Unpack or list the jar and run javap -v on any class inside it, reading the major version: line:

javap -v -cp report.jar com.acme.Report | findstr "major"
# on macOS/Linux:  javap -v -cp report.jar com.acme.Report | grep major
  major version: 65

This reads the file's bytes 6–7 and never executes a line of the code. (Our own ClassFileInspector answers the same question in the same way, from inside a running program.)

Part B — the predicted disassembly. The parameter x is in slot 0 because the method is static; it must be pushed twice, because iadd consumes two stack values and there is no instruction meaning “double the top of the stack”:

// PREDICTED javap -c output for twice(int)
  public static int twice(int);
    Code:
       0: iload_0        // push x
       1: iload_0        // push x again - the same slot, read twice
       2: iadd           // pop both, push the sum
       3: ireturn        // return it

All four instructions are one byte, so the offsets are 0, 1, 2, 3 — exactly the shape of add, with one slot doing the work of two.

Bonus — x + x versus x * 2. They produce different bytecode. x * 2 is predicted to be:

       0: iload_0        // push x
       1: iconst_2       // push the constant 2
       2: imul           // pop both, push the product
       3: ireturn

Same length, same speed in practice, different instructions — because javac does very little optimising. It translates faithfully and leaves the clever work to the JIT, which will turn both into the same native code (probably a single shift or add) once the method is hot. That is the deeper point of the whole lesson in miniature: bytecode reflects your source closely; native code does not have to.
