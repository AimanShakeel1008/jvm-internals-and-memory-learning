Lesson 01 — How Java Actually Runs

See what happens between the code you type and the result you see. Meet the class file, the instruction language inside it, and the two ways the JVM runs those instructions.

Position: Lesson 01 of 07  ·  Prerequisites: Lesson 00 — Full Setup  ·  Project files: BytecodeSubject.java, ClassFileHeader.java, ClassFileInspector.java, experiments/WarmupExperiment.java, JvmExplorer.java (modified), and three test classes

1 The pain

Priya finishes a small tool and emails the compiled file to Sam. He runs it and gets this:

Exception in thread "main" java.lang.UnsupportedClassVersionError:
        com/example/Tool has been compiled by a more recent version of the Java
        Runtime (class file version 65.0), this runtime only recognizes class
        file version 61.0

Almost every word raises a question. Java was meant to be “write once, run anywhere”. So why does the compiler's version matter after compiling is done? What is a class file? Why does it have its own version number, 65, which matches no Java release Sam has heard of? Where is that number stored, and who checks it? Sam does not know what the compiler actually made. So he cannot even search for the answer well.

A second, quieter pain lasts a whole career. Someone asks: “is total += i in a loop expensive?” Or: “does creating an object on every call matter?” If you cannot see what happens between your source code and the machine, you can only guess from half-remembered blog posts. This whole course lives in that hidden space.

The third pain is the strangest. Time the same loop ten times in a row on the same data. The first run takes about 40 milliseconds. The tenth takes 2. Nothing changed: not the code, not the input, not the machine. The JVM has two different ways of running your code, and it switches between them without telling you. If you do not know that, it looks like a broken stopwatch.

The cure for all three is the same: look at what the compiler actually made. The .class file is not magic and not secret. Its layout is written down in public. It holds instructions in a small language that you can learn. By the end of this lesson, you will have:

  • read its first eight bytes with your own code,
  • read every instruction in four compiled methods, and
  • watched the JVM's second way of running code switch on, on your own machine.

2 Real-world analogy

A composer writes a piece of music. Orchestras in Tokyo, Lagos and Oslo play it, even though they have never met the composer. How? Not by sending recordings. Not by rewriting the piece for each country. They use sheet music: a standard way of writing music that every trained musician can read. The composer writes it once. Each orchestra plays it on its own instruments.

The concert worldThe Java world
The composer's ideas, in personal shorthandYour .java source file — written for humans
The engraver who turns shorthand into standard notationjavac, the compiler
The printed scoreThe .class file — bytecode
“Notation edition 2024” printed on page oneThe class file's version number (65 = Java 21)
The orchestra that reads the score and performs itThe JVM
The violins, drums and air in the roomThe real chip and its own instruction language
Sight-reading on the first pass — correct, but slowThe interpreter
A passage rehearsed until it is played fluently from memoryJIT-compiled code
A 2024 score handed to players who only read the 2019 editionUnsupportedClassVersionError

Two details match exactly. The edition number is on the page for a reason. Music writing gains new symbols over time. So a conductor checks the edition before rehearsal, instead of finding a problem in the middle of the concert. That printed edition is exactly what Sam's error was about. And rehearsal changes the performance without changing the score. The tenth play-through is faster than the first, but the page is the same. That is the whole “interpreter versus JIT” story in one picture.

3 The concept explained

We build this in the order the ideas depend on each other:

  1. what a chip actually runs,
  2. what Java makes instead,
  3. how those instructions work,
  4. how the file that holds them is laid out,
  5. how to read it, and
  6. how the JVM runs it in two ways at once.

3.1 What a computer can actually run

Under everything is a physical chip: the CPU (central processing unit). It is the part of the computer that carries out instructions. A CPU understands exactly one language, and it is nothing like Java. It is a list of tiny numbered commands, like: copy this number into that slot; add these two slots; if the result is zero, jump somewhere else. Each command is stored as a number, because numbers are all a chip can hold. This number-based command language is called machine code. The set of commands that one family of chips understands is called its instruction set.

Here is the problem. Different chip families have different instruction sets, and they do not mix. Most laptops with Intel or AMD chips use one (called x86-64, or “x64”). Apple Silicon Macs and most phones use another (ARM). The number that means “add” on one does not mean “add” on the other. A language like C compiles straight to machine code. So its output runs on one chip family and one operating system only. Machine code for the chip you are actually running on is called native code. You will see that word a lot, and that is all it means.

Why can a compiled C program not simply be copied from a Windows laptop to a Mac?
Because it is machine code for one instruction set and one operating system's habits. The Mac's chip may not even use the same numbers for the same operations. Its operating system also starts programs and hands out memory in a different way.

3.2 What Java produces instead: bytecode

Java takes a different route on purpose. javac does not make machine code for your chip. It makes instructions for an imaginary machine. This machine is described exactly on paper, but nobody has ever built it. The imaginary machine has its own small instruction set. Each of its instruction codes fits in a single byte. So these instructions are called bytecode. Here are three words for its parts:

  • An opcode (“operation code”) is the one-byte number that says which operation to do. One byte holds 0 to 255, so there can be at most 256 operations. The JVM defines a little over two hundred.
  • Some opcodes are followed by operands. These are extra bytes that give details, such as which variable to read or where to jump. So an instruction is one opcode byte plus zero or more operand bytes.
  • Each opcode has a short name for humans, like iadd, iload_0 or goto. This name is called its mnemonic. The file stores the number. Tools show you the name.

Bytecode is made for an imaginary machine. So it is exactly the same, no matter which computer compiled it. To run it, a real computer needs one program that acts out the imaginary machine on the real chip underneath. That program is the JVM. This is what “write once, run anywhere” (WORA) really means. It does not mean Java source is portable. It means the compiled output is. You compile once, and send the same file everywhere.

Honest limit: portability covers the compiled file, not everything around it. Some code can still behave differently on different machines. Examples: code that hard-codes C:\ paths, code that calls native libraries made for one operating system, and code that depends on thread timing. Also, a file compiled for Java 21 does not run on Java 17. Working on any machine never meant working on any version.

3.3 The imaginary machine is a stack machine

To follow any bytecode, you need exactly two parts of the imaginary machine.

Part one: the local variable table. Every method call gets a small private array of numbered slots for its variables: slot 0, slot 1, slot 2, and so on. Your variable names (a, total, i) do not exist at this level. They became slot numbers during compiling. In a static method, slot 0 holds the first parameter. In an instance method, slot 0 always holds this, and the parameters start at slot 1.

Part two: the operand stack. Picture a spike on a desk. You can push paper slips onto it. You may only ever take the top slip off. To add two numbers, you write each one on a slip and push both. Then you do an “add” step. It takes the top two slips off, adds them, and pushes one slip with the answer. Nothing has a name. Everything happens at the top. A pile you only add to and take from at one end is called a stack. Adding is a push. Removing is a pop. The stack the JVM does its sums on is the operand stack. A machine that works this way is a stack machine.

Why a stack machine? Because it keeps instructions tiny. iadd needs no operands at all. It never needs to say “add slot 3 to slot 7”, because both inputs are always on top of the stack. Here is add(7, 5) running, one instruction at a time:

Two rules follow, and they hold for all bytecode.

First, instructions carry their type in their name. The first letter i in iload, iadd and ireturn means int. There are matching families for long (l), float (f), double (d) and references to objects (a, for “address”). So areturn returns an object, and ireturn returns an int.

Second, very common operations get their own one-byte shortcut. Reading slot 0 could be written as the two-byte iload 0. But it is so common that there is also a one-byte iload_0. That is why bytecode listings are full of names with underscores and small numbers.

In a static method, which slot holds the first parameter — and why is it different in an instance method?
Slot 0. An instance method is always called on an object. That object (this) is passed in secretly as an extra first argument. So it takes slot 0, and the normal parameters start at slot 1. That is why an instance method's bytecode usually begins with aload_0.

3.4 The .class file and its eight-byte header

The bytecode lives in the .class file. There is one file per class. javac makes it, and Maven puts it in target/classes/. It is a binary file. That means it stores raw numbers, not readable text, so a text editor shows nonsense. That is not secrecy. The layout is published in the Java Virtual Machine Specification. Any program that follows it can read it, including one you write. Every class file begins with the same eight bytes, in the same order:

Bytes 0–3: the magic number. A file's type depends on what is inside it, not on its name. Renaming photo.png to photo.txt changes nothing inside it. So many file formats start with a fixed value that says what they are. This value is called a magic number. Java's is 0xCAFEBABE.

That number is written in hexadecimal, which is base 16. It uses the digits 0–9, then A–F for ten to fifteen. It suits bytes well, because every byte is exactly two hex digits. So CA FE BA BE is exactly four bytes. If a file does not start with these four bytes, the JVM refuses it at once.

Bytes 4–5: the minor version. Bytes 6–7: the major version. Together they say which edition of the class file format the file uses. The numbers started at 45 for Java 1.1. They have gone up by one with each release since. That gives a rule you can do in your head:

Java release = major version − 44. Major 65 is Java 21. 61 is Java 17. 52 is Java 8. The gap of 44 is an accident of history from 1996, and everyone is stuck with it.

Major versionJava releaseNote
45Java 1.1where the numbering started
52Java 8still very common in old systems
55Java 11an earlier long-term-support release
61Java 17the number in Sam's error
65Java 21what this course pins and what our build writes

The minor version is almost always 0. There is one use worth knowing. Preview features are new language features that are still experimental. You switch them on with --enable-preview. Code compiled with them gets 65535 as its minor version. That is the largest two-byte value, used as a flag nobody can miss. The JVM then runs that file only on the exact same release, and only if preview is switched on there too. This course never uses preview features.

Now Sam's error makes complete sense. His file said 65 in bytes 6–7. His JVM was Java 17, which understands up to 61. It read those two bytes before running anything. It saw a number from the future, and refused. The rule only works one way: a newer JVM runs older class files, but an older JVM always refuses newer ones. The newer file may use things that did not exist when that JVM was built.

What goes wrong when you read the header yourself. Reading those bytes in Java looks simple. But the obvious version is wrong:

// WRONG: looks right, and the failure blames an innocent file
int magic = (header[0] << 24) | (header[1] << 16)
          | (header[2] << 8)  |  header[3];
// PREDICTED result: 0xFFFFFFBE instead of 0xCAFEBABE -> "the file is corrupt!"

The file is fine. The bug is that a Java byte is signed. It holds −128 to 127, not 0 to 255. So the byte 0xCA arrives as −54. When Java uses a byte in arithmetic, it first turns it into an int. An int has more bits than a byte. When a negative number gets those extra bits, Java fills them all with ones. This is called sign extension. Those extra ones spill into the result and spoil it.

The cure is one small step per byte: & 0xFF. It keeps the same eight bits but reads them as 0 to 255. There is a second trap behind the first. 0xCAFEBABE is about 3.4 billion. An int stops at about 2.1 billion. So the value must be held in a long. Our ClassFileInspector (Section 4) does both.

The diagram names the rest of the file. Two parts appear in every bytecode listing, so meet them now. The constant pool is a numbered table of every name and fixed value the class uses. That includes text values, the names of methods it calls, and the names of classes it mentions. The bytecode does not repeat "java/lang/Object" everywhere. It just says “entry #11”. That is why listings are full of # numbers. The methods section holds each method's name, type and bytecode.

3.5 How types are written: descriptors

The class file cannot store a method's type as friendly text like int add(int, int). It needs something short with only one possible meaning. So it uses a small code called a descriptor. Each type becomes a letter. The parameter types go in brackets. The return type comes after.

DescriptorJava typeMemory hook
IintI for int
JlongL was taken, so long got J
D / Fdouble / floatfirst letters
ZbooleanB was taken by byte; Z as in “zero or one”
B / S / Cbyte / short / charfirst letters
Vvoidonly allowed as a return type
Ljava/lang/String;StringL + class name with slashes + semicolon
[Iint[]one [ per array dimension

So add(int, int) returning int is (II)I. And main(String[]) returning nothing is ([Ljava/lang/String;)V. Inside class files, the dots in package names always become slashes.

What Java method signature does (IJ)Ljava/lang/String; describe?
A method that takes an int, then a long, and returns a String: String something(int a, long b). The method's name is not part of the descriptor. It is stored separately.

3.6 Reading bytecode with javap

What goes wrong without the right tool. The obvious first move is to print the file: type target\classes\com\corejava\jvm\BytecodeSubject.class. You get a mess of strange characters with a few readable bits, like java/lang/Object, <init> and (II)I. It may even scramble your terminal. People decide that “compiled means unreadable.” That is wrong. A text viewer treats every byte as a letter, and that is the wrong way to read numbers. The bytes are fine. The tool is wrong.

The right tool comes with the JDK you installed in Lesson 00. It is javap. It is a disassembler: a program that reads compiled instructions and prints them back as readable mnemonics. It gets back the instructions, not your source. Comments and formatting were never in the file.

CommandWhat it shows
javap Foo.classthe public signatures only
javap -p Foo.classthe same, plus private members (p for private)
javap -c Foo.classthe bytecode of every method (c for code) — the main event
javap -v Foo.classverbose: version header, the whole constant pool, everything
javap -l Foo.classline numbers and local variable names, when the compiler recorded them

Each line of -c output looks like this:

   6: if_icmpgt     19
   ^      ^           ^
   |      |           +--- operand: where to jump to (a byte offset)
   |      +--------------- mnemonic: which operation
   +---------------------- the byte offset of this instruction inside the method

That left-hand number is the most misread thing in a bytecode listing. It is not a line number. It is the instruction's position, counted in bytes from the start of the method. This is called its byte offset. That is why the numbers jump unevenly. 0, 1, 2, 3 means four one-byte instructions. A jump from 6 to 9 means the instruction at 6 took three bytes: one opcode plus a two-byte operand.

3.7 Four methods, disassembled

Our project's BytecodeSubject exists only to be taken apart. Here are its four methods with their predicted bytecode. Section 4 gives the commands to check them on your machine.

(a) add — arguments, arithmetic, return

public static int add(int a, int b) {
    return a + b;
}
// PREDICTED javap -c output
  public static int add(int, int);
    Code:
       0: iload_0        // push slot 0 (a) onto the operand stack
       1: iload_1        // push slot 1 (b)
       2: iadd           // pop both, push their sum
       3: ireturn        // pop the top value and return it as an int

Four one-byte instructions. This is the stack picture from 3.3, written as text. Notice that the names a and b appear nowhere. A method's bytecode is a small program that only knows about slots and a stack.

(b) sumTo — where the for loop went

public static int sumTo(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}
// PREDICTED javap -c output
  public static int sumTo(int);
    Code:
       0: iconst_0       // push the constant 0
       1: istore_1       // pop it into slot 1  -> total = 0
       2: iconst_1       // push the constant 1
       3: istore_2       // pop it into slot 2  -> i = 1
       4: iload_2        // push i          <-- top of the loop
       5: iload_0        // push n
       6: if_icmpgt  19  // pop both; if i > n, continue from offset 19
       9: iload_1        // push total
      10: iload_2        // push i
      11: iadd           // pop both, push total + i
      12: istore_1       // pop into slot 1 -> total updated
      13: iinc       2, 1 // add 1 to slot 2 IN PLACE -> i++ (stack untouched)
      16: goto       4   // jump back to the top of the loop
      19: iload_1        // push total
      20: ireturn        // return it

There is no for instruction. The JVM has no idea what a loop is. A loop is just two jumps. One is a jump forward that only happens if a test is true: it leaves the loop. The other is a jump backward that always happens: it repeats the loop. Every while, for and do-while compiles to some mix of those two moves. Three details:

  • The test is flipped. You wrote “keep going while i <= n”. The bytecode says “jump out if i > n”. A jump needs to know when it should happen, so the test is turned around.
  • iinc is special. Adding to a local variable is so common that one instruction does it in place, with no push or pop. That is why i++ costs one instruction and total += i costs four.
  • The offsets prove the sizes. 6→9 and 13→16 are gaps of three. That is because if_icmpgt, iinc and goto each carry two operand bytes.

(c) greet — when bytecode looks nothing like the source

public static String greet(String name) {
    return "Hello, " + name;
}
// PREDICTED javap -c output (the # numbers will differ on your machine)
  public static java.lang.String greet(java.lang.String);
    Code:
       0: aload_0            // push slot 0 (name) - 'a' because it is a reference
       1: invokedynamic #7,  0  // InvokeDynamic #0:makeConcatWithConstants:
                                 //   (Ljava/lang/String;)Ljava/lang/String;
       6: areturn            // return the reference on top of the stack

One + became an instruction you have never heard of. And “Hello, ” is nowhere in sight. Since Java 9, the compiler does not decide how to join strings. Instead, it writes one instruction that means: the first time this line runs, ask a helper in the JDK to build a fast routine for this exact joining. Then reuse that routine forever. An instruction that works out what to call the first time, and then remembers the answer, is called invokedynamic. The helper here is makeConcatWithConstants. The text “Hello, ” is part of the recipe given to the helper. So only name is pushed when the code runs. The benefit: the JDK can make string-joining better without anyone recompiling. Remember invokedynamic. Lambdas use it too.

Short source code does not mean little work. A one-character + is a call into a generated routine. A for loop is two jumps. i++ is one instruction, and total += i is four. Never guess the cost of code from how it looks. Read the bytecode, or better, measure.

(d) newObject — the shape of every new in Java

public static Object newObject() {
    return new Object();
}
// PREDICTED javap -c output (the # numbers will differ on your machine)
  public static java.lang.Object newObject();
    Code:
       0: new           #11   // class java/lang/Object - reserve blank memory, push a reference
       3: dup                 // copy that reference, so there are two on the stack
       4: invokespecial #1    // Method java/lang/Object."<init>":()V - run the constructor,
                              //   which uses up one of the two references
       7: areturn             // return the surviving reference

This answers a question most developers never ask: what is new? It is two separate things joined into one word.

  1. The new instruction reserves memory for a blank object in the heap. It pushes a reference to it: a value that says where the object lives. (Lesson 03 is all about this.)
  2. Then invokespecial runs the constructor to fill in the fields.

The constructor call uses up one reference from the stack. That is why dup copies it first. Without the copy, there would be nothing left to return.

Two more facts come out of this. First, a constructor is stored as a normal method with the special name <init> and return type V. Second, the four normal call instructions are worth knowing by sight:

  • invokestatic: calls a static method.
  • invokevirtual: calls a normal method. The real object's class picks which version of the method runs.
  • invokespecial: calls constructors, super. methods and private methods. Here we do not want the object's class to pick a version.
  • invokeinterface: calls a method through an interface type.

Honest limit: reading bytecode helps you understand how things work and settle arguments about facts. It is not a tool for everyday speed tuning. The native code the JVM finally runs can look very different. Loops may be unrolled, and methods may be merged away. To find out why something is slow, use a profiler or a proper benchmark. Never change source code to “make it faster” just because its bytecode looks long.

3.9 Two ways to run the same instructions

How does the JVM actually carry out bytecode? The obvious way is a loop: get the next instruction, see what it is, do it, move on. Carrying out instructions one at a time like this, without translating them first, is called interpreting. The part of the JVM that does it is the interpreter. It starts instantly. But for each of your instructions, the JVM does a lot of its own work. It reads the opcode, decides what it means, and jumps to the right piece of code to handle it. So interpreted code runs very roughly 10 to 100 times slower than native code. (That is a rough idea, not a measurement.)

The other choice is to translate a method's bytecode into real machine code for your chip, once. Then the JVM runs that translation at full speed. Translating costs time at the start, but it pays back on every later call.

The JVM does both, at the same time. It starts by interpreting, so your program runs within milliseconds. Meanwhile, it counts how often each method is called and how often each loop goes round. When a method's count passes a set limit, the JVM hands it to a compiler. The compiler runs on a background thread, so your program keeps going while it makes native code. Later calls use the native version. Compiling while the program runs is called just-in-time compilation, or JIT. A method called often enough to be compiled is called hot. That is where the name HotSpot comes from: it finds the hot spots and compiles them.

HotSpot has two JIT compilers. C1 compiles quickly but does only light speed-ups, so warm code gets faster soon. C2 compiles slowly but does heavy speed-ups, so the hottest code ends up very fast. Using the interpreter, then C1, then C2 is called tiered compilation. The settling-in time at the start of a run is called warm-up. Warm-up is why the first run of a loop can be twenty times slower than the tenth. Lesson 06 explains this fully. The experiment in Section 4 lets you see it now.

This is why Java is “slow to start but fast once running.” A server that runs for weeks warms up in seconds. Then it runs at native speed. That is Java's best case. A command-line tool that runs for 200 milliseconds and exits never leaves the interpreter. That is why some Java tools feel slow next to Go or Rust tools. It is also why a speed test number published without warm-up is worthless.

Why does the JVM interpret at all, instead of compiling everything to native code up front?
Because compiling costs time, and most code is not worth it. Programs spend nearly all their time in a small part of their methods. Compiling everything first would slow down startup for code that may run once, or never. Interpreting starts instantly. Counting lets the JVM spend compile time only where it pays off. There is a bonus too. By the time it compiles, the JVM has watched the code run. So it can tune the code using facts about this exact run.

4 Applied to jvm-explorer

The project gets its first real skill: it can read the raw files the JVM runs. There are four new source files, one changed file, and three new test classes.

4.1 What happens, step by step, when the new code runs

  1. JvmExplorer.main prints the Lesson 00 report as before. Then it asks ClassFileInspector to inspect BytecodeSubject.class.
  2. The inspector turns the class name com.corejava.jvm.BytecodeSubject into the file's location on the class path. Dots become slashes. It adds a / at the front and .class at the end: /com/corejava/jvm/BytecodeSubject.class.
  3. getResourceAsStream asks the JVM for that file's bytes. It asks the same machinery that loaded the class. It does not use a fixed folder path. So it also works from a packaged jar and inside tests. (Lesson 02 explains what that machinery is.) If the file is missing, you get a clear error message instead of a confusing NullPointerException.
  4. readNBytes(8) reads exactly the eight header bytes. A shorter file is reported as “not a class file”.
  5. Bytes 0–3 are joined into a long, with & 0xFF on each one. The result is 0xCAFEBABE. Bytes 4–5 give minor version 0. Bytes 6–7 give major version 65.
  6. The values are packed into a ClassFileHeader record. The record can print the magic number in hex, turn 65 into “Java 21”, and spot the preview flag. The stream closes itself automatically.
  7. The same happens for JvmExplorer.class. The last two lines print the compiled version next to the running JVM's version. These are the two numbers that disagreed in Sam's error.

4.3 The header, as a value

ClassFileHeader uses one piece of Java syntax the course has not used yet. A small class that only holds a few values normally needs a lot of boilerplate: private fields, a constructor, a getter for each field, and equals, hashCode and toString. That is about twenty lines. Java has a shortcut. You list the values in the class header, and the compiler writes the rest. record Point(int x, int y) { } gives you new Point(3, 4), p.x(), p.y() and sensible equality. The values can never change afterwards. This shortcut is called a record. It is a perfect fit for four facts read from bytes already on disk.

public record ClassFileHeader(
        String className,   // whose file this is
        long magic,         // bytes 0-3; long because 0xCAFEBABE overflows an int
        int minorVersion,   // bytes 4-5; 65535 means "compiled with preview features"
        int majorVersion) { // bytes 6-7; 65 means Java 21

    public static final long JAVA_MAGIC = 0xCAFEBABEL;
    private static final int MAJOR_VERSION_OFFSET = 44;

    // 65 helps nobody; "Java 21" is the fact you actually want.
    public String javaVersionName() {
        if (majorVersion >= 49) {                              // Java 5 and later
            return "Java " + (majorVersion - MAJOR_VERSION_OFFSET);
        }
        return "Java 1." + (majorVersion - MAJOR_VERSION_OFFSET); // 45 -> 1.1 … 48 -> 1.4
    }
    // ...plus hasJavaMagic(), magicAsHex(), usesPreviewFeatures() and describe().
}

4.4 The inspector's core

// CORRECT: mask every byte, and hold the four-byte value in a long.
private static long readUnsignedInt(byte[] bytes, int offset) {
    return ((long) (bytes[offset]     & 0xFF) << 24)   // re-read the bits as 0..255,
         | ((long) (bytes[offset + 1] & 0xFF) << 16)   // then slide each byte into
         | ((long) (bytes[offset + 2] & 0xFF) <<  8)   // its place, most significant
         |  (long) (bytes[offset + 3] & 0xFF);          // byte first.
}

public static ClassFileHeader inspect(Class<?> type) {
    if (type == null) {
        throw new IllegalArgumentException("Cannot inspect a null class.");
    }
    // com.corejava.jvm.Foo -> /com/corejava/jvm/Foo.class (leading / = class path root)
    String resourcePath = "/" + type.getName().replace('.', '/') + ".class";

    // try-with-resources: the stream closes itself, even if we throw.
    try (InputStream in = ClassFileInspector.class.getResourceAsStream(resourcePath)) {
        /* null check, readNBytes(8), length check ... */
        return new ClassFileHeader(type.getName(),
                readUnsignedInt(header, 0),     // bytes 0-3
                readUnsignedShort(header, 4),   // bytes 4-5
                readUnsignedShort(header, 6));  // bytes 6-7
    } catch (IOException e) {
        throw new UncheckedIOException("Failed to read the class file for " + type.getName(), e);
    }
}

There is one new piece of syntax in there. try (InputStream in = …) { } is a try that closes what it opened, automatically. It does this whether the block ends normally or by throwing an exception. It is called try-with-resources. It is why nothing here can leave a file open by mistake.

4.5 The warm-up experiment

experiments/WarmupExperiment.java calls sumTo(1000) 200,000 times per batch, for ten batches. It times each batch with System.nanoTime(). This is a stopwatch, and the only useful thing about it is the difference between two readings. The results are added into a static field called sink. That stops the JVM from deciding the work is pointless and deleting it.

This is not how to benchmark Java. A real measurement must deal with warm-up, the JVM deleting unused work, garbage-collection pauses, CPU speed changes and more. The standard tool is JMH (the Java Microbenchmark Harness, part of OpenJDK). This twenty-line stopwatch exists only because it lets you see the effect quickly. Lesson 06 measures properly.

There are fourteen new tests, seventeen in total. The key ones turn the file format's rules into checks:

            "Class files should be Java 21 (major 65). Check <maven.compiler.release> in pom.xml.");

@Test

    // The two numbers whose disagreement causes UnsupportedClassVersionError.
    assertEquals("Java " + Runtime.version().feature(),
            ClassFileInspector.inspect(JvmExplorer.class).javaVersionName(), /* … */);

Lesson 00's test proved we run on Java 21. These tests prove we compile for Java 21, and that the two agree. Compiling for a version is a separate setting, and it can change on its own. Now the build guards both halves of Sam's error.

The warm-up tests are special because of what they do not check. No test claims that later batches are faster. That effect is real, but it depends on the machine and on luck. A timing check would fail on a busy laptop and pass on a quiet one. A test that sometimes fails for reasons that have nothing to do with the code is called a flaky test. One flaky test teaches a team to ignore red builds. So the tests check only what is always true: the right number of timings, each one above zero, and the work really reaching the sink.

5 In the wild

Mockito creates classes that were never compiled. When a test calls mock(PaymentService.class), there is no source file for that mock. Mockito uses a library called Byte Buddy to build the bytes of a class file in memory: magic number, version, constant pool, methods. Then it hands those bytes to the JVM. Hibernate and Spring build their proxy classes the same way. Making or rewriting class files from code like this is called bytecode manipulation. Code-coverage tools such as JaCoCo use it too. They add counting instructions to your methods as the methods load.

Lambdas are invokedynamic, just like greet. Disassemble list.forEach(x -> System.out.println(x)). There is no hidden class in the bytecode. There is just one invokedynamic that names a JDK helper called LambdaMetafactory. The helper builds the code for the lambda the first time it is used.

The class-version check causes many real production problems in Java companies. The code is fine and the tests passed. But the deploy fails at startup with UnsupportedClassVersionError. Why? The build server's JDK is newer than the JDK in the runtime image. You can find the cause without running any code: javap -v -cp app.jar com.acme.Main | findstr major (or | grep major on macOS/Linux) tells you which Java a jar was built for. Teams that have been hurt by this pin two things: the compiler's --release, and the runtime image's JDK. That is exactly what our classFilesAreCompiledToThePinnedJavaVersion test now guards.

Check this yourself, do not just trust it: newer JDKs added a built-in API for reading and writing class files (java.lang.classfile). It was finished in a release after 21. It is not available on our pinned Java 21. Everything in this lesson uses only InputStream and plain arithmetic.

6 Gotchas and common mistakes

  • Forgetting that byte is signed. Almost everyone who writes a binary file reader in Java hits this once. 0xCA arrives as −54. Joining raw bytes gives a wrong number, not an error. So the bug makes the data look broken. Avoid it: mask each byte with & 0xFF as you take it from the array. Hold four-byte values that cannot be negative in a long.
  • Reading UnsupportedClassVersionError backwards. “Has been compiled by a more recent version” describes the file. “This runtime only recognizes” describes the JVM you are running. Subtract 44 from each. Avoid it: the fix is usually a newer runtime, not an older build. And “just rebuilding” without changing anything changes nothing.
  • Using -source/-target instead of --release. The old flags set the class file version. But they still compile against the current JDK's library. So building on JDK 21 with -target 17 can make a “Java 17” file that calls a method only Java 21 has. It compiles and ships. Then it crashes with NoSuchMethodError on the real Java 17 machine. Avoid it: use --release (our POM's maven.compiler.release). It also uses that release's library, so the compiler catches the bad call.
  • Forgetting -p, then deciding a method does not exist. Plain javap prints only public members. So private methods and constructors are just missing. That looks exactly as if the compiler removed them. Avoid it: make javap -c -p your habit.
  • Being surprised by extra .class files. One source file can make several class files. A nested class becomes Outer$Inner.class. An anonymous class becomes Outer$1.class. Avoid it: remember that the compiler makes one file per class, not per source file. A $ in a class file name means “made from a nested class”.

7 Key takeaways

  • javac does not make machine code for your chip. It makes bytecode for an imaginary stack machine, and that compiled file (not the source) is what “write once, run anywhere” makes portable.
  • Every .class file starts with the same eight bytes: the magic number 0xCAFEBABE, the minor version, then the major version. The Java release is the major version minus 44, so Java 21 writes 65.
  • The JVM checks those version bytes before running anything, and the rule only works one way. A newer JVM runs older class files, but an older JVM always refuses newer ones, and that is what UnsupportedClassVersionError reports.
  • Bytecode does its sums on an operand stack and keeps variables in numbered local slots, with the type in each instruction's name. A loop is a forward jump plus a backward jump, and every new is the three instructions new, dup, invokespecial.
  • The JVM interprets bytecode at once, and compiles hot methods to native code in the background (C1, then C2). That is why the same loop is slow on its first run and fast on its tenth, and why any Java timing taken without warm-up is meaningless.

8 Challenge

Part A — explain a failed deploy. A colleague's deploy fails at startup:

java.lang.UnsupportedClassVersionError: com/acme/Report has been compiled by a
more recent version of the Java Runtime (class file version 65.0), this runtime
only recognizes class file version 55.0
  1. Turn both numbers into Java releases.
  2. Say in one sentence which machine has the problem.
  3. Give two possible fixes, and say which one is usually right.
  4. Name one command that would have shown this from the jar before deploying, without running any code.

Part B — predict the bytecode. Without compiling, write down the bytecode you expect for this method, with byte offsets:

public static int twice(int x) {
    return x + x;
}

Then check it. Add the method to BytecodeSubject, run mvn compile, and disassemble. Bonus: predict whether x + x and x * 2 give the same instructions. Then find out.

Click to reveal the answer

Part A (1). Subtract 44 from each. The file's 65 means Java 21. The runtime's 55 means Java 11.

Part A (2). Neither machine is broken. They just disagree: the runtime machine is too old for the file it was given.

Part A (3). There are two fixes:

  • (a) Upgrade the runtime to Java 21 or newer.
  • (b) Build for Java 11 by setting maven.compiler.release to 11. (Never use -target alone. See the Gotchas.)

Usually (a) is right. The code was written and tested on Java 21, and building for 11 may not even compile. Choose (b) only when the runtime really cannot be upgraded. Then test properly on Java 11.

Part A (4). Read the header with javap. It never runs the code:

javap -v -cp report.jar com.acme.Report | findstr "major"
# on macOS/Linux:  javap -v -cp report.jar com.acme.Report | grep major
  major version: 65

Part B. x is in slot 0, because the method is static. It must be pushed twice, because iadd takes two values from the stack:

// PREDICTED javap -c output for twice(int)
  public static int twice(int);
    Code:
       0: iload_0        // push x
       1: iload_0        // push x again - the same slot, read twice
       2: iadd           // pop both, push the sum
       3: ireturn        // return it

Bonus. They are different. x * 2 is predicted to be iload_0, iconst_2, imul, ireturn. Same length, same speed in practice, but different instructions. That is because javac hardly tries to make code faster. It translates your code as written, and leaves the clever work to the JIT. Once the method is hot, the JIT turns both into the same native code. That is the whole lesson in a nutshell: bytecode closely follows your source, but native code does not have to.
