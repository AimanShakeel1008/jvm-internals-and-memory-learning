Lesson 01 — How Java Actually Runs

Open the black box between the code you type and the behaviour you see: the class file, the instruction language inside it, and the two ways the JVM runs those instructions.

Position: Lesson 01 of 07  ·  Prerequisites: Lesson 00 — Full Setup  ·  Project files: BytecodeSubject.java, ClassFileHeader.java, ClassFileInspector.java, experiments/WarmupExperiment.java, JvmExplorer.java (modified), and three test classes

1 The pain

Priya finishes a small tool and emails the compiled file to Sam. He runs it and gets this:

Exception in thread "main" java.lang.UnsupportedClassVersionError:
        com/example/Tool has been compiled by a more recent version of the Java
        Runtime (class file version 65.0), this runtime only recognizes class
        file version 61.0

Almost every word raises a question. Java was supposed to be “write once, run anywhere” — so why does the compiler's version matter once compiling is finished? What is a class file, and why does it have a version of its own — 65, a number that matches no Java release Sam has heard of? Where is that number stored, and who checks it? Without knowing what the compiler actually produced, Sam cannot even search for the answer usefully.

A second, quieter pain lasts a whole career. Someone asks: “is total += i in a loop expensive?” or “does creating an object every call matter?” If the space between your source code and the machine is a black box, you can only answer from half-remembered blog posts. And this whole course lives in that space.

The third pain is the strangest. Time the same loop ten times in a row on the same data. The first run takes about 40 milliseconds; the tenth takes 2. Nothing changed — not the code, not the input, not the machine. If you do not know that the JVM has two different ways of running your code and quietly switches between them, that looks like a broken stopwatch.

The cure for all three is the same: look at what the compiler actually produced. The .class file is not magic and not encrypted. It is a documented format holding instructions in a small, learnable language. By the end of this lesson you will have read its first eight bytes with your own code, read every instruction in four compiled methods, and watched the JVM's second way of running code kick in on your machine.

2 Real-world analogy

A composer writes a piece of music, and it is performed in Tokyo, Lagos and Oslo by orchestras that have never met the composer. How? Not by shipping recordings, and not by rewriting the piece for each country — by sheet music: a standard written notation every trained musician can read. The composer writes it once; each orchestra plays it on its own local instruments.

The concert worldThe Java world
The composer's ideas, in personal shorthandYour .java source file — written for humans
The engraver who turns shorthand into standard notationjavac, the compiler
The printed scoreThe .class file — bytecode
“Notation edition 2024” printed on page oneThe class file's version number (65 = Java 21)
The orchestra that reads the score and performs itThe JVM
The violins, drums and air in the roomThe real chip and its own instruction language
Sight-reading on the first pass — correct, but slowThe interpreter
A passage rehearsed until it is played fluently from memoryJIT-compiled code
A 2024 score handed to players who only read the 2019 editionUnsupportedClassVersionError

Two details map exactly. The edition number is on the page for a reason: notation gains new symbols over time, so a conductor checks the edition before rehearsal rather than discovering a problem mid-concert. That printed edition is exactly what Sam's error was about. And rehearsal changes the performance without changing the score: the tenth play-through is faster than the first, yet the page is the same. That is the whole interpreter-versus-JIT story in one sentence.

3 The concept explained

We build this in the order the ideas depend on each other: what a chip actually runs, what Java produces instead, how those instructions work, how the file holding them is laid out, how to read it, and finally how the JVM runs it in two ways at once.

3.1 What a computer can actually run

Underneath everything is a physical chip: the CPU (central processing unit), the part of the computer that carries out instructions. A CPU understands exactly one language, and it is nothing like Java: a list of tiny numbered commands — copy this number into that slot; add these two slots; if the result is zero, jump somewhere else. Each command is stored as a number, because numbers are all a chip can hold. This numeric command language is called machine code, and the set of commands one family of chips understands is called its instruction set.

The catch: different chip families have different, incompatible instruction sets. Most laptops with Intel or AMD chips use one (called x86-64, or “x64”); Apple Silicon Macs and most phones use another (ARM). The number that means “add” on one does not mean “add” on the other. So a language like C, which compiles straight to machine code, produces a file that runs on one chip family and one operating system only. Machine code for the actual chip you are running on is called native code — you will meet that word constantly, and that is all it means.

Why can a compiled C program not simply be copied from a Windows laptop to a Mac?
Because it is machine code for one specific instruction set and one operating system's conventions. The Mac's chip may not even use the same numbers for the same operations, and its operating system starts programs and hands out memory differently.

3.2 What Java produces instead: bytecode

Java takes a deliberate detour. javac does not produce machine code for your chip. It produces instructions for an imaginary machine — one described precisely on paper, that nobody has ever built. That imaginary machine has its own small instruction set, and because each of its instruction codes fits in a single byte, the instructions are called bytecode. Three words for its parts:

  • An opcode (“operation code”) is the one-byte number saying which operation to perform. One byte holds 0 to 255, so there can be at most 256 operations; the JVM defines a little over two hundred.
  • Some opcodes are followed by operands: extra bytes giving details, such as which variable to read or where to jump. So an instruction is one opcode byte plus zero or more operand bytes.
  • Each opcode has a short human name — iadd, iload_0, goto — called its mnemonic. The file stores the number; tools show you the name.

Because bytecode targets an imaginary machine, it is identical wherever it was produced. To run it, a real computer needs one program that acts out the imaginary machine using the real chip underneath — the JVM. That is what “write once, run anywhere” (WORA) actually means: not that Java source is portable, but that the compiled output is. You compile once, and ship the same file everywhere.

Honest limit: portability covers the compiled file, not everything around it. Code that hard-codes C:\ paths, calls operating-system-specific native libraries, or depends on thread timing can still behave differently on different machines. And a file compiled for Java 21 does not run on Java 17 — portability across machines was never portability across versions.

3.3 The imaginary machine is a stack machine

To follow any bytecode you need exactly two parts of the imaginary machine.

Part one: the local variable table. Every method call gets a small private array of numbered slots for its variables: slot 0, slot 1, slot 2, and so on. Your variable names (a, total, i) do not exist at this level — they became slot numbers during compilation. In a static method, slot 0 holds the first parameter. In an instance method, slot 0 always holds this, and the parameters start at slot 1.

Part two: the operand stack. Picture a spike on a desk. You can push paper slips onto it, and you may only ever take the topmost slip off. To add two numbers, you write each on a slip, push both, then do an “add” step that takes the top two off, adds them, and pushes one slip with the answer. Nothing has a name; everything happens at the top. A pile you only add to and take from at one end is called a stack (adding is a push, removing is a pop), and the one the JVM computes on is the operand stack. A machine that works this way is a stack machine.

Why a stack machine? Because it keeps instructions tiny. iadd needs no operands at all — no “add slot 3 to slot 7” — because both inputs are, by definition, on top of the stack. Here is add(7, 5) running, one instruction at a time:

Two rules follow, and they hold for all bytecode. First, instructions carry their type in their name: the leading i in iload, iadd, ireturn means int. There are parallel families for long (l), float (f), double (d) and references to objects (a, for “address”). So areturn returns an object and ireturn returns an int. Second, very common operations get their own one-byte shortcut: reading slot 0 could be the two-byte iload 0, but because it is so common there is also a one-byte iload_0. That is why disassembly is full of names with underscores and small numbers.

In a static method, which slot holds the first parameter — and why is it different in an instance method?
Slot 0. An instance method is always called on an object, and that object (this) is passed invisibly as an extra first argument, so it takes slot 0 and the declared parameters start at slot 1. That is why an instance method's bytecode usually begins with aload_0.

3.4 The .class file and its eight-byte header

The bytecode lives in the .class file — one file per class, produced by javac and placed by Maven in target/classes/. It is a binary file: it stores raw numbers rather than readable text, so a text editor shows nonsense. That is not secrecy. The layout is published in the Java Virtual Machine Specification, and any program that follows it — including one you write — can read it. Every class file begins with the same eight bytes, in the same order:

Bytes 0–3: the magic number. A file's type is decided by its contents, not its name — renaming photo.png to photo.txt changes nothing inside it. So many formats start with a fixed value that announces what they are, called a magic number. Java's is 0xCAFEBABE. (That is written in hexadecimal, base 16, which uses the digits 0–9 then A–F for ten to fifteen. It suits bytes well because every byte is exactly two hex digits, so CA FE BA BE is precisely four bytes.) If a file does not start with these four bytes, the JVM refuses it immediately.

Bytes 4–5: the minor version. Bytes 6–7: the major version. Together they say which edition of the class file format the file follows. The numbering started at 45 for Java 1.1 and has gone up by one per release since, which gives a rule you can do in your head:

Java release = major version − 44. Major 65 is Java 21; 61 is Java 17; 52 is Java 8. The offset is a historical accident from 1996 that everyone is stuck with.

Major versionJava releaseNote
45Java 1.1where the numbering started
52Java 8still very common in old systems
55Java 11an earlier long-term-support release
61Java 17the number in Sam's error
65Java 21what this course pins and what our build writes

The minor version is almost always 0. Its one use worth knowing: code compiled with preview features switched on (experimental language features, enabled with --enable-preview) gets 65535 there — the largest two-byte value, used as an unmistakable flag. The JVM then only runs that file on exactly the same release, started with preview enabled too. This course never uses preview features.

Now Sam's error decodes completely. His file said 65 in bytes 6–7. His JVM was Java 17, which understands up to 61. It read those two bytes before running anything, saw a number from the future, and refused. The rule is one-directional: a newer JVM runs older class files; an older JVM always refuses newer ones — the newer file may contain things that did not exist when that JVM was built.

What goes wrong when you read the header yourself. Reading those bytes in Java looks simple, and the obvious version is wrong:

// WRONG: looks right, and the failure blames an innocent file
int magic = (header[0] << 24) | (header[1] << 16)
          | (header[2] << 8)  |  header[3];
// PREDICTED result: 0xFFFFFFBE instead of 0xCAFEBABE -> "the file is corrupt!"

The file is fine. The bug is that a Java byte is signed: it holds −128 to 127, not 0 to 255, so the byte 0xCA arrives as −54. When Java uses a byte in arithmetic it first widens it to an int, and widening a negative number fills the new high bits with ones (this is called sign extension). Those extra ones flood the result. The cure is one small operation per byte: & 0xFF, which keeps the same eight bits but reads them as 0 to 255. There is a second trap behind the first: 0xCAFEBABE is about 3.4 billion, and an int stops at about 2.1 billion, so the value must be held in a long. Our ClassFileInspector (Section 4) does both.

The rest of the file is named in the diagram. Two parts appear in every disassembly, so meet them now. The constant pool is a numbered table of every name and fixed value the class refers to — text literals, the names of methods it calls, the names of classes it mentions. Instead of repeating "java/lang/Object" everywhere, the bytecode says “entry #11”, which is why disassembly is full of # numbers. The methods section holds, for each method, its name, its type, and its bytecode.

3.5 How types are written: descriptors

The class file cannot store a method's type as friendly text like int add(int, int); it needs something short and unambiguous. So it uses a small code called a descriptor: each type becomes a letter, the parameter types go in brackets, and the return type follows.

DescriptorJava typeMemory hook
IintI for int
JlongL was taken, so long got J
D / Fdouble / floatfirst letters
ZbooleanB was taken by byte; Z as in “zero or one”
B / S / Cbyte / short / charfirst letters
Vvoidonly allowed as a return type
Ljava/lang/String;StringL + class name with slashes + semicolon
[Iint[]one [ per array dimension

So add(int, int) returning int is (II)I, and main(String[]) returning nothing is ([Ljava/lang/String;)V. Inside class files, dots in package names always become slashes.

What Java method signature does (IJ)Ljava/lang/String; describe?
A method taking an int and then a long, and returning a String: String something(int a, long b). The method's name is not part of the descriptor — it is stored separately.

3.6 Reading bytecode with javap

What goes wrong without the right tool. The obvious first move is to print the file: type target\classes\com\corejava\jvm\BytecodeSubject.class. You get a mess of strange characters with a few readable fragments — java/lang/Object, <init>, (II)I — and it may even scramble your terminal. People conclude “compiled means unreadable.” Wrong: a text viewer guesses that every byte is a letter, which is the wrong way to read numbers. The bytes are fine; the instrument is wrong.

The right instrument ships with the JDK you installed in Lesson 00: javap. It is a disassembler — a program that reads compiled instructions and prints them back as readable mnemonics. It recovers instructions, not your source: comments and formatting were never in the file.

CommandWhat it shows
javap Foo.classthe public signatures only
javap -p Foo.classthe same, plus private members (p for private)
javap -c Foo.classthe bytecode of every method (c for code) — the main event
javap -v Foo.classverbose: version header, the whole constant pool, everything
javap -l Foo.classline numbers and local variable names, when the compiler recorded them

Each line of -c output looks like this:

   6: if_icmpgt     19
   ^      ^           ^
   |      |           +--- operand: where to jump to (a byte offset)
   |      +--------------- mnemonic: which operation
   +---------------------- the byte offset of this instruction inside the method

That left-hand number is the most misread thing in disassembly. It is not a line number — it is the instruction's position in bytes from the start of the method, called its byte offset. That is why the numbers jump unevenly: 0, 1, 2, 3 means four one-byte instructions, while a jump from 6 to 9 means the instruction at 6 took three bytes (one opcode plus a two-byte operand).

3.7 Four methods, disassembled

Our project's BytecodeSubject exists only to be taken apart. Here are its four methods with their predicted disassembly; Section 4 gives the commands to check them on your machine.

(a) add — arguments, arithmetic, return

public static int add(int a, int b) {
    return a + b;
}
// PREDICTED javap -c output
  public static int add(int, int);
    Code:
       0: iload_0        // push slot 0 (a) onto the operand stack
       1: iload_1        // push slot 1 (b)
       2: iadd           // pop both, push their sum
       3: ireturn        // pop the top value and return it as an int

Four one-byte instructions — the stack picture from 3.3 in text form. Notice the names a and b appear nowhere: a method's bytecode is a self-contained little program over slots and a stack.

(b) sumTo — where the for loop went

public static int sumTo(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}
// PREDICTED javap -c output
  public static int sumTo(int);
    Code:
       0: iconst_0       // push the constant 0
       1: istore_1       // pop it into slot 1  -> total = 0
       2: iconst_1       // push the constant 1
       3: istore_2       // pop it into slot 2  -> i = 1
       4: iload_2        // push i          <-- top of the loop
       5: iload_0        // push n
       6: if_icmpgt  19  // pop both; if i > n, continue from offset 19
       9: iload_1        // push total
      10: iload_2        // push i
      11: iadd           // pop both, push total + i
      12: istore_1       // pop into slot 1 -> total updated
      13: iinc       2, 1 // add 1 to slot 2 IN PLACE -> i++ (stack untouched)
      16: goto       4   // jump back to the top of the loop
      19: iload_1        // push total
      20: ireturn        // return it

There is no for instruction; the JVM has no idea what a loop is. A loop is a conditional jump forward (escape when the test fails) plus an unconditional jump backward (repeat). Every while, for and do-while compiles to some arrangement of those two moves. Three details:

  • The test is flipped. You wrote “keep going while i <= n”; the bytecode says “jump out if i > n”, because a jump needs the condition under which it fires.
  • iinc is special. Adding to a local variable is so common that one instruction does it in place, with no push or pop. That is why i++ costs one instruction and total += i costs four.
  • The offsets prove the widths. 6→9 and 13→16 are gaps of three, because if_icmpgt, iinc and goto each carry two operand bytes.

(c) greet — when bytecode looks nothing like the source

public static String greet(String name) {
    return "Hello, " + name;
}
// PREDICTED javap -c output (the # numbers will differ on your machine)
  public static java.lang.String greet(java.lang.String);
    Code:
       0: aload_0            // push slot 0 (name) - 'a' because it is a reference
       1: invokedynamic #7,  0  // InvokeDynamic #0:makeConcatWithConstants:
                                 //   (Ljava/lang/String;)Ljava/lang/String;
       6: areturn            // return the reference on top of the stack

One + became an instruction you have never heard of, and “Hello, ” is nowhere in sight. Since Java 9, the compiler does not decide how to join strings. It emits one instruction meaning: the first time this line runs, ask a helper in the JDK to build a fast routine for this exact joining, then reuse that routine forever. An instruction that works out what to call on first use and then remembers the answer is called invokedynamic, and the helper here is makeConcatWithConstants. The literal “Hello, ” is part of the recipe handed to the helper, so only name is pushed at run time. The benefit: the JDK can improve its string-joining without anyone recompiling. Remember invokedynamic — lambdas use it too.

Source lines and work done are different things. A one-character + is a call into a generated routine; a for loop is two jumps; i++ is one instruction and total += i is four. Never estimate cost from how source code looks. Read the bytecode, or better, measure.

(d) newObject — the shape of every new in Java

public static Object newObject() {
    return new Object();
}
// PREDICTED javap -c output (the # numbers will differ on your machine)
  public static java.lang.Object newObject();
    Code:
       0: new           #11   // class java/lang/Object - reserve blank memory, push a reference
       3: dup                 // copy that reference, so there are two on the stack
       4: invokespecial #1    // Method java/lang/Object."<init>":()V - run the constructor,
                              //   which uses up one of the two references
       7: areturn             // return the surviving reference

This answers a question most developers never ask: what is new? It is two separate things fused into one word. The new instruction reserves memory for a blank object in the heap and pushes a reference to it — a value saying where the object lives (Lesson 03 is all about this). Then invokespecial runs the constructor to fill in the fields. The constructor call uses up a reference from the stack, which is why dup copies it first; without the copy there would be nothing left to return.

Two more facts fall out. A constructor is stored as an ordinary method with the reserved name <init> and return type V. And the four ordinary call instructions are worth knowing by sight: invokestatic (a static method), invokevirtual (an ordinary method, where the real object's class picks the implementation), invokespecial (constructors, super. calls and private methods, where no such choice is wanted), and invokeinterface (a call through an interface type).

Honest limit: reading bytecode is a tool for understanding a mechanism and settling factual arguments, not for daily performance tuning. The native code the JVM finally runs can look very different — loops unrolled, methods merged away. To find out why something is slow, use a profiler or a proper benchmark; never “optimise” source just because its bytecode looks long.

3.9 Two ways to run the same instructions

How does the JVM actually carry out bytecode? The obvious way is a loop: fetch the next instruction, see what it is, do it, move on. Carrying out instructions one at a time like this, without translating them first, is called interpreting, and the part of the JVM that does it is the interpreter. It starts instantly. But for each of your instructions the JVM does a pile of its own work — read the opcode, decide what it means, jump to the right handler — so interpreted code runs very roughly 10 to 100 times slower than native code (a rough shape, not a measurement).

The other option is to translate a method's bytecode into real machine code for your chip once, then run that translation at full speed. Translating costs time up front, but it pays back on every later call.

The JVM does both, at the same time. It starts by interpreting, so your program runs within milliseconds. Meanwhile it counts how often each method is called and each loop goes round. When a method crosses a threshold, the JVM hands it to a compiler running on a background thread, which produces native code while your program keeps going; later calls quietly use the native version. Compiling while the program runs is called just-in-time compilation — JIT. A method called often enough to earn this is called hot, which is where the name HotSpot comes from: it finds the hot spots and compiles those.

HotSpot has two JIT compilers. C1 compiles quickly with light optimisation, so warm code gets faster soon. C2 compiles slowly with heavy optimisation, so the hottest code eventually gets very fast. Using the interpreter, then C1, then C2 is called tiered compilation, and the settling-in period at the start of a run is called warm-up — the reason the first run of a loop can be twenty times slower than the tenth. Lesson 06 takes this apart properly; the experiment in Section 4 makes it visible now.

This is why Java is “slow to start but fast once running.” A server that runs for weeks warms up in seconds and then runs at native speed — Java's ideal case. A command-line tool that runs for 200 milliseconds and exits never leaves the interpreter, which is why some Java tools feel sluggish next to Go or Rust ones. And it is why a benchmark number published without warm-up is worthless.

Why does the JVM interpret at all, instead of compiling everything to native code up front?
Because compiling costs time, and most code is not worth it. Programs spend nearly all their time in a small fraction of their methods, so compiling everything first would delay startup for code that may run once or never. Interpreting starts instantly, and counting lets the JVM spend compilation effort only where it pays off. As a bonus, by the time it compiles it has watched the code run, so it can optimise using facts about this particular run.

4 Applied to jvm-explorer

The project gains its first real capability: it can read the raw material the JVM eats. Four new source files, one modified, three new test classes.

4.1 What happens, step by step, when the new code runs

  1. JvmExplorer.main prints the Lesson 00 report as before, then asks ClassFileInspector to inspect BytecodeSubject.class.
  2. The inspector turns the class name com.corejava.jvm.BytecodeSubject into its location on the class path — dots become slashes, with a leading / and a .class ending: /com/corejava/jvm/BytecodeSubject.class.
  3. getResourceAsStream asks the JVM for that file's bytes. (It asks the same machinery that loaded the class, rather than using a hard-coded folder path — so it also works from a packaged jar and inside tests. Who that machinery is, is Lesson 02.) A missing file becomes a clear error message instead of a mystery NullPointerException.
  4. readNBytes(8) reads exactly the eight header bytes; a shorter file is reported as not a class file.
  5. Bytes 0–3 are combined, with & 0xFF on each, into a long: 0xCAFEBABE. Bytes 4–5 give minor version 0; bytes 6–7 give major version 65.
  6. The values are packed into a ClassFileHeader record, which can print the magic in hex, turn 65 into “Java 21”, and spot the preview flag. The stream closes itself automatically.
  7. The same happens for JvmExplorer.class, and the last two lines print the compiled version beside the running JVM's version — the two numbers whose disagreement caused Sam's error.

4.3 The header, as a value

ClassFileHeader uses one piece of Java syntax the course has not used yet. A small class that only holds a few values normally needs private fields, a constructor, a reader method per field, and equals/hashCode/toString — twenty lines of ceremony. Java offers a shorthand: declare the values in the header and the compiler writes the rest. record Point(int x, int y) { } gives you new Point(3, 4), p.x(), p.y() and sensible equality, and the values can never change afterwards. This shorthand is called a record — a perfect fit for four facts read from bytes already on disk.

public record ClassFileHeader(
        String className,   // whose file this is
        long magic,         // bytes 0-3; long because 0xCAFEBABE overflows an int
        int minorVersion,   // bytes 4-5; 65535 means "compiled with preview features"
        int majorVersion) { // bytes 6-7; 65 means Java 21

    public static final long JAVA_MAGIC = 0xCAFEBABEL;
    private static final int MAJOR_VERSION_OFFSET = 44;

    // 65 helps nobody; "Java 21" is the fact you actually want.
    public String javaVersionName() {
        if (majorVersion >= 49) {                              // Java 5 and later
            return "Java " + (majorVersion - MAJOR_VERSION_OFFSET);
        }
        return "Java 1." + (majorVersion - MAJOR_VERSION_OFFSET); // 45 -> 1.1 … 48 -> 1.4
    }
    // ...plus hasJavaMagic(), magicAsHex(), usesPreviewFeatures() and describe().
}

4.4 The inspector's core

// CORRECT: mask every byte, and hold the four-byte value in a long.
private static long readUnsignedInt(byte[] bytes, int offset) {
    return ((long) (bytes[offset]     & 0xFF) << 24)   // re-read the bits as 0..255,
         | ((long) (bytes[offset + 1] & 0xFF) << 16)   // then slide each byte into
         | ((long) (bytes[offset + 2] & 0xFF) <<  8)   // its place, most significant
         |  (long) (bytes[offset + 3] & 0xFF);          // byte first.
}

public static ClassFileHeader inspect(Class<?> type) {
    if (type == null) {
        throw new IllegalArgumentException("Cannot inspect a null class.");
    }
    // com.corejava.jvm.Foo -> /com/corejava/jvm/Foo.class (leading / = class path root)
    String resourcePath = "/" + type.getName().replace('.', '/') + ".class";

    // try-with-resources: the stream closes itself, even if we throw.
    try (InputStream in = ClassFileInspector.class.getResourceAsStream(resourcePath)) {
        /* null check, readNBytes(8), length check ... */
        return new ClassFileHeader(type.getName(),
                readUnsignedInt(header, 0),     // bytes 0-3
                readUnsignedShort(header, 4),   // bytes 4-5
                readUnsignedShort(header, 6));  // bytes 6-7
    } catch (IOException e) {
        throw new UncheckedIOException("Failed to read the class file for " + type.getName(), e);
    }
}

One new piece of syntax is in there: try (InputStream in = …) { } is a try that automatically closes what it opened, whether the block ends normally or by throwing an exception. It is called try-with-resources, and it is why nothing here can leak an open file.

4.5 The warm-up experiment

experiments/WarmupExperiment.java calls sumTo(1000) 200,000 times per batch, for ten batches, timing each batch with System.nanoTime() — a stopwatch whose only meaningful use is the difference between two readings. The results are added into a static field called sink, so the JVM cannot decide the work is pointless and delete it.

This is not how to benchmark Java. A real measurement must control for warm-up, the JVM deleting unused work, garbage-collection pauses, CPU speed changes and more. The standard tool is JMH (the Java Microbenchmark Harness, part of OpenJDK). This twenty-line stopwatch exists only because it makes the effect visible in one sitting; Lesson 06 measures properly.

            "Class files should be Java 21 (major 65). Check <maven.compiler.release> in pom.xml.");

@Test

    // The two numbers whose disagreement causes UnsupportedClassVersionError.
    assertEquals("Java " + Runtime.version().feature(),

Lesson 00's test proved we run on Java 21. These prove we compile for Java 21 — a separate setting that can drift on its own — and that the two agree. Both halves of Sam's error are now guarded by the build.

And the warm-up tests are defined by what they deliberately do not check: no test claims later batches are faster. That effect is real, but it depends on the machine and on luck. A timing assertion would fail on a busy laptop and pass on an idle one. A test that sometimes fails for reasons that have nothing to do with the code is called a flaky test, and one flaky test teaches a team to ignore red builds. So the tests check only what is always true: the right number of timings, each above zero, and the work really reaching the sink.

5 In the wild

Mockito creates classes that were never compiled. When a test calls mock(PaymentService.class), no source file for that mock exists. Mockito builds a class file's worth of bytes in memory — magic number, version, constant pool, methods — and hands them to the JVM, using a library called Byte Buddy. Hibernate and Spring build their proxy classes the same way. Generating or rewriting class files from code like this is called bytecode manipulation, and code-coverage tools such as JaCoCo use it too, adding counting instructions to your methods as they load.

Lambdas are invokedynamic, just like greet. Disassemble list.forEach(x -> System.out.println(x)) and there is no hidden class in the bytecode — just one invokedynamic naming a JDK helper called LambdaMetafactory, which builds the implementation on first use.

The class-version check is one of the most common production incidents in Java shops: the code is fine, the tests passed, and the deploy fails at startup with UnsupportedClassVersionError because the build server's JDK is newer than the runtime image. The fast diagnosis needs no running code: javap -v -cp app.jar com.acme.Main | findstr major (or | grep major on macOS/Linux) tells you which Java a jar was built for. Teams that have been burned pin both the compiler's --release and the runtime image's JDK — which is exactly what our classFilesAreCompiledToThePinnedJavaVersion test now guards.

To verify, not trust: recent JDKs added a built-in API for reading and writing class files (java.lang.classfile), finalised in a release after 21. It is not available on our pinned Java 21. Everything in this lesson uses only InputStream and plain arithmetic.

6 Gotchas and common mistakes

  • Forgetting that byte is signed. Almost every hand-written binary reader in Java hits this once: 0xCA arrives as −54, and combining raw bytes gives a wrong number rather than an error — a bug that blames the data. Avoid it: mask each byte with & 0xFF as it leaves the array, and hold four-byte unsigned values in a long.
  • Reading UnsupportedClassVersionError backwards. “Has been compiled by a more recent version” describes the file; “this runtime only recognizes” describes the JVM you are running. Subtract 44 from each. Avoid it: the fix is usually a newer runtime, not a downgraded build — and “just rebuilding” without changing anything changes nothing.
  • Using -source/-target instead of --release. The old flags set the class file version but still compile against the current JDK's library. So building on JDK 21 with -target 17 can produce a “Java 17” file that calls a Java-21-only method — it compiles, ships, then dies with NoSuchMethodError on the real Java 17 machine. Avoid it: use --release (our POM's maven.compiler.release), which also swaps in that release's library definitions so the compiler catches the call.
  • Forgetting -p, then deciding a method does not exist. Plain javap prints only public members, so private methods and constructors are simply missing — which looks exactly like the compiler removed them. Avoid it: make javap -c -p your habit.
  • Being surprised by extra .class files. One source file can produce several: a nested class becomes Outer$Inner.class, an anonymous class Outer$1.class. Avoid it: remember the unit of compiler output is the class, not the file, and $ in a class file name means “generated from a nested class”.

7 Key takeaways

  • javac does not produce machine code for your chip; it produces bytecode for an imaginary stack machine, and it is that compiled file — not the source — that “write once, run anywhere” makes portable.
  • Every .class file starts with the same eight bytes — the magic number 0xCAFEBABE, the minor version, then the major version — and the Java release is the major version minus 44, so Java 21 writes 65.
  • The JVM checks those version bytes before running anything, and the rule only goes one way: a newer JVM runs older class files, but an older JVM always refuses newer ones, which is exactly what UnsupportedClassVersionError reports.
  • Bytecode computes on an operand stack using numbered local slots, with the type in each instruction's name; a loop is a forward jump plus a backward jump, and every new is the trio new, dup, invokespecial.
  • The JVM interprets bytecode immediately and, in the background, compiles hot methods to native code (C1, then C2), which is why the same loop is slow on its first run and fast on its tenth — and why any Java timing taken without warm-up is meaningless.

8 Challenge

Part A — decode an incident. A colleague's deploy fails at startup:

java.lang.UnsupportedClassVersionError: com/acme/Report has been compiled by a
more recent version of the Java Runtime (class file version 65.0), this runtime
only recognizes class file version 55.0

(1) Turn both numbers into Java releases. (2) Say in one sentence which machine has the problem. (3) Give two possible fixes and say which is usually right. (4) Name one command that would have revealed this from the jar before deploying, without running any code.

Part B — predict a disassembly. Without compiling, write down the bytecode you expect for this method, with byte offsets:

public static int twice(int x) {
    return x + x;
}

Then check: add it to BytecodeSubject, run mvn compile, and disassemble. Bonus: predict whether x + x and x * 2 give the same instructions — then find out.

Click to reveal the answer

Part A (1). Subtract 44 from each: the file's 65 means Java 21; the runtime's 55 means Java 11.

Part A (2). Neither machine is broken — they disagree: the runtime machine is too old for the file it was given.

Part A (3). Either (a) upgrade the runtime to Java 21 or newer, or (b) build for Java 11 by setting maven.compiler.release to 11 (never -target alone — see the Gotchas). Usually (a) is right: the code was written and tested against Java 21, and building for 11 may not even compile. Choose (b) only when the runtime genuinely cannot move — and then test on Java 11 properly.

Part A (4). Read the header with javap, which never runs the code:

javap -v -cp report.jar com.acme.Report | findstr "major"
# on macOS/Linux:  javap -v -cp report.jar com.acme.Report | grep major
  major version: 65

Part B. x is in slot 0 because the method is static. It must be pushed twice, because iadd takes two values from the stack:

// PREDICTED javap -c output for twice(int)
  public static int twice(int);
    Code:
       0: iload_0        // push x
       1: iload_0        // push x again - the same slot, read twice
       2: iadd           // pop both, push the sum
       3: ireturn        // return it

Bonus. They are different. x * 2 is predicted to be iload_0, iconst_2, imul, ireturn. Same length, same speed in practice, different instructions — because javac barely optimises. It translates faithfully and leaves the clever work to the JIT, which turns both into the same native code once the method is hot. That is the whole lesson in miniature: bytecode closely follows your source; native code does not have to.
