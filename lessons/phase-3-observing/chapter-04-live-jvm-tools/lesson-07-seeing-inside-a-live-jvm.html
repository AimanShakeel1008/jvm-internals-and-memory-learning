Lesson 07 — Seeing Inside a Live JVM

Look into a running JVM from the outside, without stopping it. Find it, read its threads, count its objects, and take a snapshot of its whole heap. Use all of it to catch a memory leak planted on purpose. Then join up the whole course.

Position: Lesson 07 of 07 — the final lesson  ·  Prerequisites: Lesson 03, Lesson 04  ·  Project files: live/LeakyRegistry.java, live/FixedRegistry.java, live/HistogramRow.java, live/ClassGrowth.java, live/ClassHistogram.java, live/HistogramDiffTool.java, live/HeapDumper.java, experiments/LeakHunt.java, JvmExplorer.java and .gitignore (modified), and four test classes

1 The pain

Three earlier lessons ended an explanation with the same words: take a heap dump (Lesson 07).

  • Lesson 03 said OutOfMemoryError: Java heap space means something is still holding objects. What is?
  • Lesson 04 said a leak is an object that is reachable but not wanted. Reachable from where?
  • Lesson 05 said live data that rises after full GCs means a leak. Made of which objects?

So far, every module in this course answered questions by having the program report on itself. Real production problems do not let you do that. Say a production service has been running for four days and its memory is climbing. Or it has frozen, with the CPU idle and requests piling up. You cannot add a println and redeploy, because the problem may take days to come back. You cannot attach a debugger to production and pause it for an hour. And the most tempting move, restarting it, destroys the one thing you need: the running process, with the evidence inside it.

So the last skill in this course is looking inside a running JVM from the outside, without stopping it. By the end of this lesson you will:

  • find a JVM by its process number,
  • read what each of its threads is doing,
  • count its objects by class twice, and see which class keeps growing,
  • take a full snapshot of its heap, and
  • use all of that to catch a memory leak planted in jvm-explorer on purpose.

Then we join the whole course up into one story.

2 Real-world analogy

A doctor has to find out what is wrong with a patient without operating. The patient carries on with their life. The doctor uses instruments that look inside from the outside, starting with the cheapest and gentlest ones.

The doctorThe JVM
Finding the right patient on the ward by bed numberjps / jcmd: list running JVMs by process id
A stethoscope that can do many quick checksjcmd: one tool, dozens of diagnostic commands
A snapshot of what every organ is doing right nowA thread dump (jstack)
A blood count: how many of each kind of cellA class histogram: instances and bytes per class

Notice the order a good doctor works in. Cheap, quick, harmless checks come first. The expensive full scan comes only when the quick checks point somewhere. The same order applies here. A histogram costs a second. A heap dump pauses the patient.

3 The concept explained

We go from the gentlest tool to the most disruptive one: finding and attaching to a JVM, the thread dump, the class histogram, the heap dump and how to read one, and the visual tools. Then comes the course recap.

3.1 Finding a JVM and attaching to it

The operating system gives every running program a number, so it can tell them apart. That number is called its process id, or PID. Every JDK diagnostic tool finds a JVM by its PID. Here are two ways to list the JVMs running under your user:

jps -l          # each running JVM: PID and main class (-l = full class name)
jcmd            # the same list, from the tool you will use for everything else

The JDK tools then connect to that running JVM through a local channel built into HotSpot. They ask it to do something, such as print its threads, count its objects, or write a dump. Then they show the answer. Connecting a tool to a JVM that is already running is called attaching. It only works on the same machine. It also only works as the same operating-system user that started the JVM. That is a security rule, and it causes most “cannot attach” errors (Section 6).

jcmd is the one tool worth learning first. It puts dozens of diagnostic commands behind one name. jcmd <pid> help lists everything your JVM supports. Here are the ones this course has already pointed to:

CommandWhat it doesCost
jcmd <pid> VM.version · VM.flags · VM.command_linewhich JVM, which flags — Lesson 00's “which machine?” asked from outsidenone
jcmd <pid> GC.heap_infogeneration sizes right now (Lesson 04)none

Command names and options belong to HotSpot, and they sometimes change. jcmd <pid> help <command> gives the true answer for your JDK. The older single-job tools still exist. jstack is for threads. jmap is for histograms (jmap -histo:live <pid>) and dumps (jmap -dump:live,format=b,file=heap.hprof <pid>). jcmd covers them both, and the JDK's own documentation recommends it.

3.2 The thread dump: what every thread is doing right now

What goes wrong without it. A service stops answering. The CPU is idle, memory is flat, the GC log is quiet, and there are no errors. Nothing is happening, so nothing logs anything. Without a way to ask “what is each thread waiting for?”, you can only guess and restart. A restart fixes it for a week, until it happens again.

A thread dump is a snapshot of every thread in the JVM. For each thread, it shows its name, its state, and its stack of frames. These are Lesson 03's frames, live. You read them from the top (the method running now) down to where the thread started:

// PREDICTED SHAPE of one thread in jstack / jcmd Thread.print output (Java 21)
"main" #1 [14820] prio=5 os_prio=0 cpu=812.50ms elapsed=95.32s tid=0x... nid=14820 waiting on condition  [0x...]
   java.lang.Thread.State: TIMED_WAITING (sleeping)
	at java.lang.Thread.sleep0(java.base@21.0.4/Native Method)
	at java.lang.Thread.sleep(java.base@21.0.4/Thread.java:509)
	at com.corejava.jvm.experiments.LeakHunt.main(LeakHunt.java:131)

The most useful line is the state:

  • RUNNABLE means running, or ready to run.
  • BLOCKED means waiting to enter a synchronized block that another thread holds.
  • WAITING means waiting, with no time limit, for another thread to send a signal.
  • TIMED_WAITING means waiting with a time limit, as in Thread.sleep.

The frozen service above usually shows two or more threads BLOCKED. Each one holds a lock the other needs, so neither can ever carry on. That is called a deadlock. HotSpot finds simple Java-level deadlocks for you. The dump ends with Found one Java-level deadlock: and names the threads and locks involved.

One dump is a single snapshot, and it can mislead. A thread that just happened to be waiting at that moment looks stuck. The standard practice is to take three dumps a few seconds apart. A thread that is in the same place in all three really is stuck.

3.3 The class histogram — and why you need two

A class histogram lists every class that has objects on the heap. For each one, it shows how many objects exist and how many bytes they take. The largest come first:

 num     #instances         #bytes  class name (module)
-------------------------------------------------------
   1:          4300       41000000  [B (java.base@21.0.4)
   2:          4600         110400  java.lang.String (java.base@21.0.4)
   ...
   5:           620           9920  com.corejava.jvm.live.LeakyRegistry$LeakedSession
Total         11520       41241920

Two details need careful reading.

  • Array names are the type descriptors from Lesson 01. [B is byte[]. [Ljava.lang.Object; is Object[].
  • The byte counts are shallow sizes. That is the size of the object itself (its header and fields), not what its fields point at. A LeakedSession is only a few bytes shallow: two references. The 32 KB array it points at is counted under [B. That is why the leaked bytes in a histogram usually show up under byte[] or Object[], not under the class that is really leaking.

What goes wrong with one histogram. byte[], String and HashMap$Node sit near the top of every Java program's histogram, leak or no leak. A single histogram mostly tells you what all programs look like. The technique that works is comparing two histograms of the same process, taken a few minutes apart, under similar load. Classes that stay steady are the objects the program normally uses. Look for a class whose count only ever goes up, when nothing in the workload explains it. That is the suspect. The project's new HistogramDiffTool does exactly this comparison.

3.4 The heap dump, and the two ideas that make it readable

A histogram says what is piling up. It cannot say why it is still alive. For that, you need every object and every reference between them, written to a file. That file is a heap dump (a .hprof file). There are three ways to get one:

  • When you ask, from outside: jcmd <pid> GC.heap_dump C:\dumps\service.hprof. Give a full path. A relative path is taken from the target JVM's working folder, not yours.
  • Automatically, at the moment of death: start the JVM with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<folder>. When an OutOfMemoryError happens, the dump is written before the JVM dies. This is the most valuable flag for any production service. (Lesson 03 recommended it.)
  • From inside the program: HotSpot's HotSpotDiagnosticMXBean.dumpHeap. The project's new HeapDumper uses it.

A heap dump holds millions of objects, so you read it with a tool (Section 3.5). The tools rest on two ideas.

Retained size. Shallow size counts far too little. The HashMap at the heart of our leak is only a few dozen bytes shallow. Yet it holds the whole leak. The useful question is: if this object were collected, how much memory would be freed along with it? That is the object itself, plus everything that can be reached only through it. That amount is called the object's retained size. Say every path to some object B must pass through object A. Then A is said to dominate B. Analysis tools build a dominator tree, so the objects with the biggest retained sizes rise to the top. A leak usually shows up as one object with a retained size of hundreds of megabytes.

Path to GC roots. This is Lesson 04's reachability rule, turned into a question you can ask the tool. Pick a suspicious object. Ask for the chain of references from a GC root down to it. The chain answers “why is this still alive?”. Its first link usually names the bug.

A heap dump is a copy of everything in memory. That includes passwords, access tokens, session cookies, customers' personal data, and keys. Treat it like a database backup. Store it safely. Never attach it to a public bug report. Delete it when the investigation ends. Never commit one (this project's .gitignore now ignores *.hprof). Taking a dump also pauses the JVM. The bigger the live heap, the longer the pause. It also needs about as much disk space as the live heap.

3.5 The visual tools

Command-line tools give snapshots. To watch a JVM over time, people use three standard graphical tools. All of them attach the same way:

  • JConsole comes with the JDK. Run jconsole and pick the process. It shows live graphs of heap, threads, classes and CPU. It reads them from the same MX beans the project has used since Lesson 03.
  • VisualVM is a separate free download. (It has not come with the JDK since Java 9.) It does live monitoring, thread views and sampling, and it can open .hprof heap dumps.
  • Eclipse MAT (Memory Analyzer) is a free tool built just for heap dumps. Its Leak Suspects report and dominator tree are the classic way to read a big dump.

Beyond these is JDK Flight Recorder (JFR). It is an event recorder built into HotSpot. It is cheap enough to leave running in production. You start it with jcmd <pid> JFR.start and view the results in JDK Mission Control. It needs a course of its own. It is named here so you know where to go next. The download places and versions of the outside tools change, so check each tool's own website.

3.6 The whole course: the life of one object

Every lesson in this course described one stage in the life of something the JVM handles. Let us follow one object through all of them. It is an Order, made while handling one web request: Order order = new Order(id, items);

Here is the same journey in words.

  • javac turns new Order(...) into three bytecode instructions: new, dup, invokespecial <init>. It writes them into a class file stamped with version 65 (Lesson 01).
  • The first time that code runs, the application class loader finds Order.class, after asking its parents first. It verifies and prepares the class, and runs its <clinit> exactly once (Lesson 02). The class's description now lives in Metaspace (Lesson 03).
  • new bumps a pointer in this thread's slice of Eden. A slot in the method's frame gets an arrow to the object, not the object itself (Lesson 03, Lesson 04).
  • If this code is hot and the order never escapes the method, C2 may not make it at all (Lesson 06).

Then comes one of three endings.

  • Most likely: the request finishes and the frame is popped. Nothing reaches the order any more. The next minor GC (a short Pause Young in the log) frees it without ever looking at it (Lessons 04 and 05).
  • Kept on purpose: the program keeps it, for example in a session or a cache. It survives collection after collection, ages, and gets promoted to the old generation. When the program finally lets it go, a mixed or full collection frees it there (Lessons 04 and 05).
  • Kept by mistake: the program keeps it in a static map that never forgets. That is a leak. The old generation climbs, and the live data after full GCs rises. This lesson's tools find the class that grows and the path that holds it.

4 Applied to jvm-explorer

The project gets a live package. It holds a leak planted on purpose and its fix, a tool that reads and compares class histograms, and a heap dumper that runs inside the program. The LeakHunt experiment keeps running long enough for you to point real JDK tools at it.

4.1 What happens, step by step

  1. You start LeakHunt. It prints its own PID (ProcessHandle.current().pid()) and the exact jcmd commands to run against it. Then it handles ten fake requests per second.
  2. Each request calls LeakyRegistry.handleRequest. That puts a new LeakedSession (holding a 32 KB array) into a static HashMap, and never removes anything. About 320 KB a second becomes reachable forever. Every two seconds, a status line shows the session count and the heap's used number climbing.
  3. In a second terminal, you run jcmd <pid> GC.class_histogram > histo-before.log. It attaches, runs a full GC so only live objects are counted, and writes the histogram. A minute later, the same command writes histo-after.log.
  4. HistogramDiffTool reads both files, UTF-16 or not, using Lesson 06's reader. It parses every row, matches classes by name, and lists the ones whose bytes grew, largest first. byte[] tops the list, because it holds the data. LeakyRegistry$LeakedSession grows by exactly ten objects per second. That is the suspect.
  5. jcmd <pid> Thread.print shows the main thread TIMED_WAITING in Thread.sleep, called from LeakHunt.main. So the service is idle between requests, not stuck.
  6. You press Enter. With --dump, HeapDumper asks HotSpot's diagnostic bean to write a heap dump of live objects to leak-<pid>.hprof. Open it in VisualVM or Eclipse MAT. The HashMap held by LeakyRegistry.SESSIONS has by far the largest retained size. Its path to GC roots ends at that static field.
  7. Run it again with --fixed. FixedRegistry removes its oldest session once it holds 20. Removed sessions become unreachable and are collected. The heap stays flat, and the two histograms show nothing growing.

4.3 The leak and its fix, side by side

// THE LEAK - a static field (a GC root) holding a map that only grows.
private static final Map<String, LeakedSession> SESSIONS = new HashMap<>();

public static synchronized int handleRequest(int requestNumber) {
    String id = "session-" + requestNumber;
    SESSIONS.put(id, new LeakedSession(id, new byte[PAYLOAD_BYTES]));   // never removed
    return SESSIONS.size();
}

// THE FIX - the same map, bounded: after every put, drop the eldest past CAPACITY.
private static final Map<String, byte[]> SESSIONS = new LinkedHashMap<>() {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, byte[]> eldest) {
        return size() > CAPACITY;   // the eldest loses its only reference: garbage
    }
};

The bug is one line, and it looks harmless. The fix is one method. A real cache should usually come from a caching library with size and time limits. But the idea is exactly this: every collection that lives as long as the program needs a rule that removes things from it.

The tool also turns array names into Java, using Lesson 01's descriptors. There is one [ per dimension. Then comes a letter for a primitive, or L…; for a class. So [B prints as byte[], and [[Ljava.lang.String; prints as java.lang.String[][].

4.5 The tests

The registries are tested exactly. The leaky one keeps every request. The bounded one never goes over its limit and always removes the oldest first. Both are static, so every test empties them afterwards. The histogram tests use two samples worked out by hand, with every expected difference written in a comment. LiveToolsTest takes one real heap dump of the test JVM. It writes it into JUnit's temporary folder, which is deleted afterwards. No test runs the long-running LeakHunt service itself. The tests only check how it reads its arguments.

@Test
void theFixedRegistryEvictsTheOldestFirst() {
    int total = FixedRegistry.CAPACITY + 5;
    for (int request = 1; request <= total; request++) {
        FixedRegistry.handleRequest(request);
    }
    assertFalse(FixedRegistry.holds(1), "The very first session was evicted - and is now collectable.");
    assertTrue(FixedRegistry.holds(total), "The newest session is always held.");
}

5 In the wild

The flag pair -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=... is on the standard checklist for running Java in production. A service that dies of a leak at 3 a.m. leaves behind the exact state that killed it, not just one line in a log. On container platforms, the dump path must point at storage that survives a container restart. Otherwise the evidence disappears with the container. Teams that have been hurt by this once add a storage volume for exactly that reason.

A real leak investigation follows this lesson's order:

  1. The GC log or a dashboard shows the lowest point of the old generation rising (Lesson 05).
  2. Two class histograms are taken ten minutes apart. They name a suspect class in seconds. They pause nothing except a quick GC.
  3. Only then is one heap dump taken. It is taken during a quiet period, because it pauses the service. It is copied somewhere safe and opened in MAT.
  4. The path to GC roots names the field. The field names the code. The fix is a rule that removes entries.

In an interview, describe that order: cheapest evidence first, the dump last, and the dump treated as sensitive data. It shows you have really done it, not just read about it.

6 Gotchas and common mistakes

  • Treating a heap dump as harmless. It holds every value in memory: passwords, tokens, customer data. People attach dumps to tickets and leave them in shared folders. Avoid it: handle dumps like a production database backup. Keep them in locked-down storage, delete them when done, and never put them in version control.
  • Taking a heap dump of a busy production JVM without thinking. It pauses the JVM, for seconds on a large heap. It needs about as much disk space as the live heap. So it can fill the disk and bring the service down by itself. Avoid it: start with histograms. Take the dump when traffic is low, or from an instance already removed from the load balancer.
  • “Unable to attach” / “AttachNotSupportedException”. To attach, you must be the same operating-system user as the target JVM, on the same machine. Inside a container, that means the same container. Avoid it: run jcmd as the user that started the JVM, and inside the container (docker exec, kubectl exec). Also check that the JVM was not started with attaching turned off.
  • Hunting a leak with a single histogram. The top of every histogram is byte[], String and similar classes, leak or no leak. Avoid it: always compare two, taken minutes apart under similar load. Look for your classes growing in step with requests.
  • Forgetting that GC.class_histogram and live heap dumps run a full GC. On a service with a large heap, that is a noticeable pause by itself. It also changes the very thing you are measuring. Avoid it: know the cost before you press Enter. The live-only view is still usually what you want, because it hides garbage that is about to disappear anyway.

7 Key takeaways

  • JDK tools attach to a running JVM by its process id, as the same user on the same machine. jcmd puts almost everything behind one command: version and flags, thread dumps, class histograms, heap dumps, and logging.
  • A thread dump shows every thread's name, state and stack. Several threads BLOCKED on each other is a deadlock, which HotSpot reports for you. Three dumps a few seconds apart tell a stuck thread from a busy one.
  • One class histogram only shows what every program looks like. Two histograms taken minutes apart show the class that keeps growing, and that class is the leak suspect.
  • A heap dump captures every object and reference. Retained size points at the object holding the leak, and the path to GC roots shows exactly which field keeps it alive. The dump itself is sensitive data, and taking it pauses the JVM.
  • Every lesson in this course is one stage in an object's life: compiled, its class loaded, made in Eden or optimised away, then dying young, being promoted and collected, or leaking. This lesson's tools let you see each stage in a real, running JVM.

Part C — check yourself on the machine. Run LeakHunt with -Xmx64m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=oom.hprof. Before you start, predict roughly when it will die, from 320 KB per second and a 64 MB heap. Then compare your prediction with what happens.

Part A (1). com.acme.web.UserContext. byte[] grows the most in bytes. But almost every Java program makes byte arrays, so on its own it proves nothing. Its bytes are probably the data held by something else. UserContext is one of the application's own classes. It grows by about 48,000 in ten minutes under steady traffic, in step with a map node count. A context object made for each request should die with its request (Lesson 04's fate 1). This one is being kept. Order, on the other hand, barely moves. That is the normal set of objects in use.

Part A (2). A ConcurrentHashMap that gains one entry per request. Its node count grows in exact step with UserContext. Most likely, it is a static map of contexts, keyed by request or session id, with nothing ever removed. It is this lesson's LeakyRegistry with a different name. The byte[] growth is probably data that each context holds (about 2 KB each).

Part A (3). In the dump, find UserContext objects and ask for the path to GC roots of one. Expect a chain that ends at a static field holding a ConcurrentHashMap. The dominator tree should show that map with a retained size of about 100 MB. The field's name and class point at the code. The fix is a rule that removes entries: remove the context when the request ends, or use a cache with a size limit and expiry times.

Part B. A deadlock. worker-1 is moving money between two accounts. It holds account b2's lock and wants a1's. worker-2 is moving money the other way. It holds a1 and wants b2. Each waits for the other forever. So the CPU is idle and nothing moves forward. The standard fix is a fixed lock order. Always lock the two accounts in the same order, for example by account id, lowest first, whichever way the money moves. Then two threads can never each hold one lock of the pair. (The other common answer is higher-level concurrency tools with timeouts. A later course in this series covers them.)

Part C. 64 MB ÷ 0.32 MB per second ≈ 200 seconds. But the leak never gets the whole heap. The JVM's own objects, the young generation's working space, and the collector's need for spare room all take a share. So a prediction of about two to three minutes is reasonable. You should then see java.lang.OutOfMemoryError: Java heap space, a line saying a heap dump was written to oom.hprof, and the JVM exit. Opening that file shows LeakyRegistry.SESSIONS holding nearly the whole heap. If your timing is very different, look at the last status lines before the crash. The machine wins.
