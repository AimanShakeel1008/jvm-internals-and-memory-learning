Lesson 07 — Seeing Inside a Live JVM

Look into a running JVM from the outside without stopping it: list it, read its threads, count its objects, photograph its whole heap — and use all of it to catch a memory leak planted on purpose. Then the whole course, joined up.

Position: Lesson 07 of 07 — the final lesson  ·  Prerequisites: Lesson 03, Lesson 04  ·  Project files: live/LeakyRegistry.java, live/FixedRegistry.java, live/HistogramRow.java, live/ClassGrowth.java, live/ClassHistogram.java, live/HistogramDiffTool.java, live/HeapDumper.java, experiments/LeakHunt.java, JvmExplorer.java and .gitignore (modified), and four test classes

1 The pain

Three earlier lessons ended an explanation with the same words: take a heap dump (Lesson 07). Lesson 03 said OutOfMemoryError: Java heap space means something is still holding objects — what? Lesson 04 said a leak is an object that is reachable but unwanted — reachable from where? Lesson 05 said rising live data after full GCs means a leak — made of which objects?

Every module in this course so far answered questions by having the program report on itself. Real incidents do not let you do that. A production service has been running for four days and its memory is climbing; or it has frozen, with the CPU idle and requests piling up. You cannot add a println and redeploy — the problem may take days to come back. You cannot attach a debugger to production and pause it for an hour. And the most tempting move, restarting it, destroys the one thing you need: the running process, with the evidence inside it.

So the last skill in this course is looking inside a running JVM from the outside, without stopping it. By the end of this lesson you will find a JVM by its process number, read what each of its threads is doing, count its objects by class twice and see which class keeps growing, take a full photograph of its heap, and use all of that to catch a memory leak planted in jvm-explorer on purpose. Then we join the whole course up into one story.

2 Real-world analogy

A doctor has to find out what is wrong with a patient without operating. The patient keeps living their life; the doctor uses instruments that look inside from the outside, cheapest and least intrusive first.

Note the order a good doctor works in: cheap, quick, harmless checks first; the expensive full scan only when the quick checks point somewhere. The same order applies here — a histogram costs a second, a heap dump pauses the patient.

3 The concept explained

We go from least to most intrusive: finding and attaching to a JVM, the thread dump, the class histogram, the heap dump and how to read one, and the visual tools. Then the course recap.

3.1 Finding a JVM and attaching to it

Every running program is given a number by the operating system so it can be told apart from all the others. That number is called its process id, or PID. Every JDK diagnostic tool finds a JVM by its PID. Two ways to list the JVMs running as you:

jps -l          # each running JVM: PID and main class (-l = full class name)
jcmd            # the same list, from the tool you will use for everything else

The JDK tools then connect to that running JVM through a local channel built into HotSpot, ask it to do something — print its threads, count its objects, write a dump — and show the answer. Connecting a tool to an already-running JVM like this is called attaching. It works only on the same machine, and only as the same operating-system user that started the JVM — a security rule, and the cause of most “cannot attach” errors (Section 6).

jcmd is the one tool worth learning first: it bundles dozens of diagnostic commands behind one name. jcmd <pid> help lists everything your JVM supports. The ones this course has already pointed at:

CommandWhat it doesCost

Command names and options are HotSpot's and occasionally change; jcmd <pid> help <command> is the authority on your JDK. The older single-purpose tools still exist: jstack for threads, and jmap for histograms (jmap -histo:live <pid>) and dumps (jmap -dump:live,format=b,file=heap.hprof <pid>). jcmd covers them both, and is the tool the JDK's own documentation recommends.

3.2 The thread dump: what every thread is doing right now

What goes wrong without it. A service stops answering. The CPU is idle, memory is flat, the GC log is quiet, there are no errors. Nothing is happening — so nothing logs anything. Without a way to ask “what is each thread waiting for?”, the only options are guessing and restarting, and a restart fixes it for a week until it happens again.

A thread dump is a snapshot, for every thread in the JVM, of its name, its state, and its stack of frames — Lesson 03's frames, live, read from the top (the method running now) down to where the thread started:

// PREDICTED SHAPE of one thread in jstack / jcmd Thread.print output (Java 21)
"main" #1 [14820] prio=5 os_prio=0 cpu=812.50ms elapsed=95.32s tid=0x... nid=14820 waiting on condition  [0x...]
   java.lang.Thread.State: TIMED_WAITING (sleeping)
	at java.lang.Thread.sleep0(java.base@21.0.4/Native Method)
	at java.lang.Thread.sleep(java.base@21.0.4/Thread.java:509)
	at com.corejava.jvm.experiments.LeakHunt.main(LeakHunt.java:131)

The most useful line is the state. RUNNABLE means running, or ready to run. BLOCKED means waiting to enter a synchronized block another thread holds. WAITING means waiting indefinitely for another thread to signal. TIMED_WAITING means waiting with a timeout, as in Thread.sleep. The frozen service above usually shows two or more threads BLOCKED, each holding a lock the other needs, so neither can ever continue. That is called a deadlock, and HotSpot detects simple Java-level ones for you: the dump ends with Found one Java-level deadlock: and names the threads and locks involved.

One dump is a single photograph and can mislead — a thread that happened to be waiting at that instant looks stuck. The standard practice is to take three dumps a few seconds apart: a thread in the same place in all three really is stuck.

3.3 The class histogram — and why you need two

A class histogram lists, for every class with objects on the heap, how many instances exist and how many bytes they take, largest first:

 num     #instances         #bytes  class name (module)
-------------------------------------------------------
   1:          4300       41000000  [B (java.base@21.0.4)
   2:          4600         110400  java.lang.String (java.base@21.0.4)
   ...
   5:           620           9920  com.corejava.jvm.live.LeakyRegistry$LeakedSession
Total         11520       41241920

Two details to read correctly. The names of arrays are type descriptors from Lesson 01: [B is byte[], [Ljava.lang.Object; is Object[]. And the byte counts are shallow sizes: the object itself (its header and fields), not what its fields point at. A LeakedSession is only a few bytes shallow — two references — while the 32 KB array it points at is counted under [B. That is why the leaked bytes in a histogram usually show up under byte[] or Object[], not under the class that is actually leaking.

What goes wrong with one histogram. byte[], String and HashMap$Node sit near the top of every Java program's histogram, leak or no leak. A single histogram mostly tells you what all programs look like. The technique that works is comparing two histograms of the same process, taken a few minutes apart under similar load. Classes that stay steady are the program's normal working set. A class whose count only ever goes up, with nothing in the workload that explains it, is the suspect. That comparison is exactly what the project's new HistogramDiffTool does.

3.4 The heap dump, and the two ideas that make it readable

A histogram says what is piling up. It cannot say why it is still alive. For that you need every object and every reference between them, written to a file: a heap dump (a .hprof file). Three ways to get one:

  • On demand, from outside: jcmd <pid> GC.heap_dump C:\dumps\service.hprof. Give a full path — a relative one is resolved against the target JVM's working folder, not yours.
  • Automatically, at the moment of death: start the JVM with -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<folder>. When an OutOfMemoryError happens, the dump is written before the JVM dies — the single most valuable flag for any production service (Lesson 03 recommended it).
  • From inside the program: HotSpot's HotSpotDiagnosticMXBean.dumpHeap — the project's new HeapDumper uses it.

A heap dump holds millions of objects, so it is read with a tool (Section 3.5). The tools rest on two ideas.

Retained size. Shallow size undercounts badly: the HashMap at the heart of our leak is a few dozen bytes shallow, yet it holds the whole leak. The useful question is: if this object were collected, how much memory would be freed along with it? That means the object itself, plus everything that is reachable only through it. That amount is called the object's retained size. An object that every path to some other object must pass through is said to dominate it, and analysis tools build a dominator tree so the objects with the biggest retained sizes float to the top. A leak typically appears as one object with a retained size of hundreds of megabytes.

Path to GC roots. This is Lesson 04's reachability rule, turned into a query: pick a suspicious object and ask the tool for the chain of references from a GC root down to it. The chain is the answer to “why is this still alive?”, and its first link usually names the bug.

A heap dump is a copy of everything in memory: passwords, access tokens, session cookies, customers' personal data, keys. Treat it like a database backup. Store it securely, never attach it to a public bug report, delete it when the investigation ends — and never commit one (this project's .gitignore now ignores *.hprof). Taking one also pauses the JVM, for longer the bigger the live heap, and needs disk space roughly the size of the live heap.

3.5 The visual tools

Command-line tools give snapshots. For watching a JVM over time, three graphical tools are standard, and all of them attach the same way:

  • JConsole — ships with the JDK; run jconsole, pick the process. Live graphs of heap, threads, classes and CPU, read from the same MX beans the project has used since Lesson 03.
  • VisualVM — a separate free download (no longer bundled with the JDK since Java 9). Live monitoring, thread views, sampling, and it opens .hprof heap dumps.
  • Eclipse MAT (Memory Analyzer) — a free, dedicated heap-dump analyser. Its Leak Suspects report and dominator tree are the classic way to read a big dump.

Beyond these sits JDK Flight Recorder (JFR): an event recorder built into HotSpot, cheap enough to leave running in production, started with jcmd <pid> JFR.start and viewed in JDK Mission Control. It deserves a course of its own; it is named here so you know where to go next. Download locations and versions of the external tools change — check each tool's own site.

3.6 The whole course: the life of one object

Every lesson in this course described one stage in the life of something the JVM handles. Follow a single object through all of them — an Order created while handling one web request: Order order = new Order(id, items);

In words, the same journey. javac turns new Order(...) into three bytecode instructions — new, dup, invokespecial <init> — in a class file stamped with version 65 (Lesson 01). The first time that code runs, the application class loader finds Order.class after asking its parents first, verifies and prepares it, and runs its <clinit> exactly once (Lesson 02); its description now lives in Metaspace (Lesson 03). new bumps a pointer in this thread's slice of Eden, and a slot in the method's frame receives an arrow to the object, not the object (Lesson 03, Lesson 04). If this code is hot and the order never escapes the method, C2 may skip creating it at all (Lesson 06).

Then one of three endings. Most likely, the request finishes, the frame is popped, nothing reaches the order any more, and the next minor GC — a short Pause Young in the log — reclaims it without ever looking at it (Lessons 04 and 05). If the program keeps it on purpose — in a session, a cache — it survives collection after collection, ages, gets promoted to the old generation, and is eventually reclaimed there by a mixed or full collection once it is finally let go (Lessons 04 and 05). And if the program keeps it by mistake, in a static map that never forgets, it is a leak: the old generation climbs, the live data after full GCs rises, and the tools of this lesson find the class that grows and the path that holds it.

4 Applied to jvm-explorer

The project gains a live package: a deliberately planted leak and its fix, a class-histogram parser and comparison tool, and an in-process heap dumper. The LeakHunt experiment keeps running long enough for you to aim real JDK tools at it.

4.1 What happens, step by step

  1. You start LeakHunt. It prints its own PID (ProcessHandle.current().pid()) and the exact jcmd commands to run against it, then handles ten fake requests per second.
  2. Each request calls LeakyRegistry.handleRequest, which puts a new LeakedSession (holding a 32 KB array) into a static HashMap and never removes anything. About 320 KB a second becomes permanently reachable. Every two seconds a status line shows the session count and the heap's used figure climbing.
  3. In a second terminal, jcmd <pid> GC.class_histogram > histo-before.log attaches, runs a full GC so only live objects are counted, and writes the histogram. A minute later, the same command writes histo-after.log.
  4. HistogramDiffTool reads both files — UTF-16 or not, using Lesson 06's reader — parses every row, matches classes by name, and lists those whose bytes grew, largest first. byte[] tops the list, holding the payloads, with LeakyRegistry$LeakedSession growing by exactly ten instances per second: the suspect.
  5. jcmd <pid> Thread.print shows the main thread TIMED_WAITING in Thread.sleep, called from LeakHunt.main: the service is idle between requests, not stuck.
  6. You press Enter. With --dump, HeapDumper asks HotSpot's diagnostic bean to write a live-objects heap dump to leak-<pid>.hprof. Opened in VisualVM or Eclipse MAT, the HashMap held by LeakyRegistry.SESSIONS has by far the largest retained size, and its path to GC roots ends at that static field.
  7. Run again with --fixed: FixedRegistry evicts its oldest session once it holds 20. Evicted sessions become unreachable and are collected, the heap stays flat, and the two histograms show nothing growing.

4.3 The leak and its fix, side by side

// THE LEAK - a static field (a GC root) holding a map that only grows.
private static final Map<String, LeakedSession> SESSIONS = new HashMap<>();

public static synchronized int handleRequest(int requestNumber) {
    String id = "session-" + requestNumber;
    SESSIONS.put(id, new LeakedSession(id, new byte[PAYLOAD_BYTES]));   // never removed
    return SESSIONS.size();
}

// THE FIX - the same map, bounded: after every put, drop the eldest past CAPACITY.
private static final Map<String, byte[]> SESSIONS = new LinkedHashMap<>() {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, byte[]> eldest) {
        return size() > CAPACITY;   // the eldest loses its only reference: garbage
    }
};

The bug is one line, and it looks innocent. The fix is one method. A real cache should usually come from a caching library with size and time limits, but the principle is exactly this: every collection that lives as long as the program needs a rule that removes things from it.

for (HistogramRow row : after) {

And the array names, read with Lesson 01's descriptors: one [ per dimension, then a letter for a primitive or L…; for a class. So [B prints as byte[] and [[Ljava.lang.String; as java.lang.String[][].

4.5 The tests

The registries are tested exactly: every request is kept by the leaky one, and the bounded one never exceeds its capacity and always evicts the oldest. Because both are static, every test empties them afterwards. The histogram tests use two hand-worked samples with every expected difference written in a comment. LiveToolsTest takes one real heap dump of the test JVM into JUnit's temporary folder, which is deleted afterwards. The long-running LeakHunt service itself is never run by a test; only its argument handling is.

@Test
void theFixedRegistryEvictsTheOldestFirst() {
    int total = FixedRegistry.CAPACITY + 5;
    for (int request = 1; request <= total; request++) {
        FixedRegistry.handleRequest(request);
    }
    assertFalse(FixedRegistry.holds(1), "The very first session was evicted - and is now collectable.");
    assertTrue(FixedRegistry.holds(total), "The newest session is always held.");
}

5 In the wild

The flag pair -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=... is on the standard checklist for running Java in production. A service that dies of a leak at 3 a.m. leaves behind the exact state that killed it, instead of a single line in a log. In container platforms the dump path must point at storage that survives the container's restart, or the evidence vanishes with it. Teams that have been burned once add a volume for exactly that.

A realistic leak investigation follows this lesson's order. First, the GC log or a dashboard shows the old generation's floor rising (Lesson 05). Next come two class histograms ten minutes apart, which name a suspect class in seconds and pause nothing but a quick GC. Only then is one heap dump taken, during a quiet period because it pauses the service, then copied somewhere safe and opened in MAT. The path to GC roots names the field, the field names the code, and the fix is a removal rule. In an interview, describing that sequence — cheapest evidence first, the dump last, and the dump treated as sensitive data — is what distinguishes someone who has done it from someone who has read about it.

6 Gotchas and common mistakes

  • Treating a heap dump as harmless. It contains every value in memory: passwords, tokens, customer data. People attach them to tickets and leave them in shared folders. Avoid it: handle dumps like a production database backup — restricted storage, deleted when done, never in version control.
  • Taking a heap dump of a busy production JVM without thinking. It pauses the JVM, for seconds on a large heap, and needs disk space roughly equal to the live heap, so it can fill the disk and take the service down itself. Avoid it: start with histograms; take the dump when traffic is low, or from an instance already removed from the load balancer.
  • “Unable to attach” / “AttachNotSupportedException”. Attaching requires the same operating-system user as the target JVM, on the same machine (inside a container, the same container). Avoid it: run jcmd as the user that started the JVM, and inside the container (docker exec, kubectl exec); check that the JVM was not started with attaching disabled.
  • Hunting a leak with a single histogram. The top of every histogram is byte[], String and friends, leak or no leak. Avoid it: always compare two, minutes apart under similar load, and look for your classes growing in step with requests.
  • Forgetting that GC.class_histogram and live heap dumps run a full GC. On a service with a large heap that is a noticeable pause in its own right, and it changes the very thing you are measuring. Avoid it: know the cost before you press Enter. The live-only view is still usually what you want, because it hides garbage that is about to vanish anyway.

7 Key takeaways

  • JDK tools attach to a running JVM by its process id, as the same user on the same machine, and jcmd bundles almost everything — version and flags, thread dumps, class histograms, heap dumps, logging — behind one command.
  • A thread dump shows every thread's name, state and stack; several threads BLOCKED on each other is a deadlock, which HotSpot reports for you, and three dumps a few seconds apart separate a stuck thread from a busy one.
  • One class histogram shows what every program looks like; two histograms taken minutes apart show the class that keeps growing, which is the leak suspect.
  • A heap dump captures every object and reference; retained size points at the object holding the leak, the path to GC roots shows exactly which field keeps it alive, and the dump itself is sensitive data that pauses the JVM to take.
  • Every lesson in this course is one stage in an object's life — compiled, its class loaded, allocated in Eden or optimised away, then dying young, being promoted and collected, or leaking — and the tools in this lesson let you see each stage in a real, running JVM.

Part A (1). com.acme.web.UserContext. byte[] grows the most in bytes, but almost every Java program allocates byte arrays, so on its own it proves nothing — and its shallow bytes are probably the payloads held by something else. UserContext is one of the application's own classes, growing by about 48,000 in ten minutes under steady traffic, in step with a map node count. A per-request context object should die with its request (Lesson 04's fate 1); this one is being kept. Order, by contrast, barely moves: normal working set.

Part A (2). A ConcurrentHashMap gaining one entry per request — the node count grows in exact step with UserContext. Most likely a static map of contexts keyed by request or session id, with no removal — this lesson's LeakyRegistry with a different name. The byte[] growth is plausibly data each context holds (about 2 KB each).

Part A (3). In the dump: find UserContext instances, ask for the path to GC roots of one, and expect a chain ending at a static field holding a ConcurrentHashMap. The dominator tree should show that map with a retained size of about 100 MB. The field's name and class point at the code; the fix is a removal rule — remove the context when the request ends, or use a bounded, expiring cache.

Part B. A deadlock. worker-1 is transferring between two accounts: it holds account b2's lock and wants a1's. worker-2 is transferring in the opposite direction: it holds a1 and wants b2. Each waits for the other forever, so the CPU is idle and nothing progresses. The standard fix is a consistent lock order: always lock the two accounts in the same order (for example by account id, lowest first), whatever the direction of the transfer, so two threads can never each hold one lock of the pair. (Higher-level concurrency utilities with timeouts are the other common answer — a later course in this series.)

Part C. 64 MB ÷ 0.32 MB per second ≈ 200 seconds, but the heap is never fully available to the leak: the JVM's own objects, the young generation's working space, and the collector's need for headroom all take a share. A prediction of roughly two to three minutes is reasonable. You should then see java.lang.OutOfMemoryError: Java heap space, a line saying a heap dump was written to oom.hprof, and the JVM exit — and opening that file shows LeakyRegistry.SESSIONS holding nearly the whole heap. If your timing is very different, look at the last status lines before the crash; the machine wins — tell me what you saw.
